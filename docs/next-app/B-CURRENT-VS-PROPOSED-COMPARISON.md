# B — Current XQAP vs. Proposed Structure: A Side-by-Side Comparison

**Date:** 2026-09-07
**Subject:** XQAP v132.1.0 (shipped, in production) vs. `docs/next-app/0-PROPOSED-STRUCTURE-SOURCE.md` (72-section study, dated 2026-09-06)
**What this document is:** a neutral, evidence-anchored comparison of the two architectures across six dimensions. It does not recommend a plan (that is `A-ENHANCED-STRUCTURE-AND-PLAN.md`) and does not rule on viability or cost-benefit (that is `C-VIABILITY-AND-MISTAKES-FIXED.md`). It answers one question only: **where does each system actually win, and by how much.**

**Bottom line up front.** These are not two designs for the same problem — they are two designs for two different problems that happen to share a runtime. The proposal is a generic *department collaboration app* (tasks, chat, 10 people editing one record) built on a shared folder; XQAP is a *monthly batch quality-assurance pipeline* (import → process → sample → distribute → answer → report) that also happens to run on a shared folder. Roughly half of the proposal's platform recommendations describe things XQAP already shipped after production incidents — per-writer immutable segments, a rebuildable derived cache, columnar+gzip encoding, worker-side Excel parsing, idempotent event IDs, admin-triggered maintenance — and the study does not know this. Where the proposal genuinely leads is narrow but real: causal ordering instead of wall-clock ordering, writer-head change beacons, a durable local cache, backup cut vectors with a verifiable-at-rest manifest, segment quarantine, property/fuzz and N-client simulation testing, a shared report scene model, editable PowerPoint export, and moving sync and report work into workers. Where XQAP leads is broader and harder-won: a write layer whose failure taxonomy cost 36 error codes and two named production incidents to learn, a measured file-operation cost model for UNC, an already-shipped 132× compression result, Arabic RTL discipline accumulated over 23 fix rounds, a self-contained offline report artifact, an e2e harness that can actually drive a picker-gated app, and a governance apparatus (edit-log ladder, release gates, bundle budget, security acceptance register) the proposal does not mention at all. The proposal is strongest as a *specification of missing capabilities*; it is weakest as a *description of this domain*.

Disk layout is numbered roots (`1-population/` … `6-templates/`) with permanent legacy-unnumbered fallbacks, all resolved through `workspacePaths.ts`. ### 2.2 What the proposal actually specifies

A 1,512-line, 72-section study dated 2026-09-06, targeting the same runtime (managed Windows, Chromium, UNC share, exactly one HTML file, no installer). Its architecture:

| Layer | Specification |
|---|---|
| Shared data model | Immutable domain events (§6) in per-writer streams; `writerId = employeeId + deviceId + instanceId` (§9); micro-batched segments of 20/100/250 events or 64–256 KB (§11); a tiny mutable `head.bin` per writer as a change beacon (§12) |

| Sync | A 13-component `SyncEngine` (§16) with send/receive flows; adaptive polling 1–2 s (chat) → 30–60 s (hidden tab) (§17); `FileSystemObserver` as optional accelerator; `BroadcastChannel` + Web Locks for same-PC leader election (§17.2) |
| Formats | MessagePack for events and heads, ZSTD preferred / GZIP fallback, Parquet as a benchmark candidate for Excel-derived data; a mandatory 6-way format benchmark (§20–24) |
| Workers | Five mandatory: Data, Sync, Import, Report, Backup (§26) |
| UI | Lit + Web Awesome Core + Tabulator 6.5 + Apache ECharts + Lucide + Zod (§27–34) |

The study's worked examples throughout are tasks and chat: §7 is "how 10 employees update the same task", §11.1 is a chat flush exception, §17's fastest polling tiers are chat, and §71's validation prototype is one task assigned to ten users plus a department chat room. It contains no calendar, no effort estimate, and no reference to any XQAP subsystem.

## 3. Dimension 1 — Concurrency, shared data model, conflict handling

| Aspect | Current XQAP | Proposed | Assessment |
|---|---|---|---|
| Write primitive for high-frequency state | Per-writer-session NDJSON segments (`appendOnlyEventLog.ts`), 128 KiB in-place rotation, post-close size verify, three-tier degrading durability | §5/§9/§11: per-writer immutable micro-segments closed after each 1–3 s flush | Same principle. The flush cadence differs materially: XQAP rewrites one open segment and rotates by byte cap; the proposal closes a file per flush. At XQAP's click cadence (one event per Manual Review action) that is ≈one file per click — the shape v61.0 replaced |
| Low-frequency shared config (permissions, template index, month lock) | `casLoop.ts`: UUID token CAS, 10 retries, jittered backoff, optional 80–180 ms delayed re-verify | §8 "strict version check + audit"; §49 permission changes as events | CAS is adequate for admin-cadence edits. Event-sourcing permissions is a genuine improvement: it removes the whole-object-replace collision in `userSync.ts` |
| Ordering | `eventAt` ISO string compare with eventId tiebreak; `findLateEvent` forces a refold | §13: per-writer sequence + `baseVersion`; clocks display-only | **Proposal wins.** Two machines with skewed clocks can currently order a completion before the reassignment that preceded it; the legality table then drops one — a silent ownership decision made by clock drift |
| Conflict surfacing | `droppedEventIds` / `absentRowEventIds` logged via `logError`; the actor is never told | §7.2/§61: both events persist, conflict record, `Conflict requires review` | **Proposal wins in principle.** But it never names the resolution owner, the queue, or the allowed actions per entity |
| Conflict rule coverage | Fold legality table for the 7-member distribution event union, ~218 test cases, terminal-state enforcement | §8 table: chat, comments, assignees, counters, due dates, rich documents | **Current wins on fit.** None of §8's rows is an XQAP entity. `xrayImageId` ownership, four-eyes sample approval, competing month imports, and month close/reopen have no rule |
| Change detection | Per-family stamps and bounded signatures; ~29 round trips/tick; `UNPROBED` sentinel; empty change set broadcasts nothing; one in-flight guard | §12 head beacons; §17 adaptive 1–4 s tiers; §17.2 per-PC sync leader | Head beacons are the cleaner probe *if* flat. §10 nests them three levels deep, so a scan of 40 users × 2 instances is ~80 directory + 80 file opens per tick — **must be benchmarked**, against a Chromium measurement of 142 s per 1,000 small file ops over a Windows UNC share |
| Idempotency | `knownEventIds` checkpoint, `sourceRequestId` command key, commutative `eventSetDigest` | §16.2/§61: unique event IDs, ignore duplicates, idempotent replay | Equivalent — except the proposal has no command-level idempotency key, only event-level |
| Optimistic UI | None. Write → verify → local echo → refresh | §16.1: IndexedDB outbox, optimistic apply, `Local`/`Syncing`/`Synced` states | Solves a real latency complaint (≈7 share ops per Manual Review click). Collides head-on with the app's most-repeated bug class — see §5.1 |
| Corrupt-segment isolation | One unparseable segment throws and fails the whole month's fold (`appendOnlyEventLog.ts:416`) | §10/§47: quarantine directory; the rest of the stream still folds | **Proposal wins**, subject to distinguishing "invalid" from "newer than I understand" |

**Where the current app is actually better.** Everything below the event model. `safeWrite.ts` distinguishes *absent* from *unreadable* from *corrupt* at the type level, because conflating them "recurred at least eight separate times across nine days" and once rewrote an employee's twenty answers as one. It compares staged bytes byte-for-byte rather than checking that they parse, because on a shared folder a competing writer's valid envelope also parses. It classifies errors strictly by DOMException `name`, never message text, because Chromium's wording is unstable. v97.1 split "I could not read the file back" from "I read it and it is wrong" after the single-outcome version orphaned real assignments. The proposal's §16.1 compresses all of that into "close() → verify persisted bytes/hash" — the correct goal, stated without any of the machinery that makes it true on SMB. Its `RetryPolicy` has no error taxonomy at all.

**Where the proposal is clearly better.** Three things. (1) **Ordering.** XQAP's fold decides ownership using a wall-clock string; the proposal's per-writer sequence plus per-entity `baseVersion` makes conflict decisions causal, and a `baseVersion` mismatch becomes an explicit, reportable outcome instead of a clock-dependent drop. (2) **Quarantine.** One corrupt segment currently denies a whole month to every client. (3) **Auditability of permission changes.** Making the permission event *be* the state change removes both the whole-object-replace collision and the possibility of the audit trail drifting from the state it describes — a real drift, since a 2026-08-22 audit found four declared action types, `backup-restored` among them, that no call site ever emitted.

## 4. Dimension 2 — Data volume, serialization, compression, UNC/SMB performance

| Aspect | Current XQAP | Proposed | Assessment |
|---|---|---|---|
| Large tabular format | Columnar + dictionary encoding (`columnarCodec.ts`) + gzip (`compressedEnvelope.ts`), opt-in per file name, 2,000-row gate. Measured: 139.07 MB → 1.05 MB | §19–21 describe the same technique as new; §20/§24 add Parquet+ZSTD as a candidate; §24.2 mandates a 6-way benchmark on "the known ~20 MB Excel case" | The proposal's option D *is* the shipped format. | On-disk inspectability | Small files plain JSON; compressed files self-describing with a greppable head; NDJSON segments open in any editor | §10: custom extensions "because users are discouraged from manually editing"; `head.bin`, `.evtz` | **Current wins.** Every XQ-IO incident in this repo was diagnosed by opening files |

**Where the current app is actually better.** It has already run this experiment. The 2026-08-04 optimization audit rated gzip **2/10** ("solves bandwidth, not round-trip latency — the actual bottleneck"), and eleven days later real customer data forced columnar+gzip into production anyway, at 132× on the population file and 168× on the BI raw import. That history produced three durable pieces of knowledge the proposal lacks: the bottleneck is per-file round trips, not bytes; a size gate plus a per-file policy table lets a format change ship without touching 250 test fixtures; and a plain uncompressed head line keeps CAS and change-probing O(1) on a multi-hundred-megabyte file. The proposal proposes six formats and two codecs and defers the decision to a benchmark whose fixture is roughly half the size of the real data.

**Where the proposal is clearly better.** The structural moves, not the format moves. A durable local cache with a principled invalidation key (snapshot id + per-writer head sequence) would fix cold-start cost on a share measured at ~40× slower than local for small file operations, and would close the still-open finding that a *hidden* Browse view re-parses up to a 400k-row file on every distribution action. Moving head scans, segment reads and report aggregation into dedicated workers is a placement change with no architectural cost. And §57's "remove unused columns early" is a step XQAP does not take — its row type carries ~47 fields including a raw-row passthrough.

## 9. Head-to-head on the things that matter most

### 9.1 Optimistic local writes vs. the ownership-on-stale-snapshot bug class

**Failure scenario today.** A supervisor opens Manual Review. The tab holds a folded distribution state read minutes ago. Meanwhile another supervisor reassigns a row on a different PC. The first supervisor clicks Assign. Historically this shape produced silent ownership theft — v90.0 transferred another employee's already-assigned row with no event trail and no notification, described in the lessons-learned document as the most serious instance. The class was independently rediscovered at least five times (v43.6/43.7, v59.9/57.9, v88.0/89.1, v90.0, v98.4/98.5) and fixed the same way every time: **re-read the authoritative state immediately before an ownership-dependent write.**

**What the proposal changes.** It helps and hurts. `baseVersion` (§13) means a stale assignment is *detectable* after the fact rather than resolved by a clock comparison — a real gain. But §14 and §16.1 make the local store the working memory and apply commands optimistically before the share is consulted, and nothing in §8 or §16 requires an ownership-changing command to scan peer heads and re-fold first. The user sees "Saved locally", the event sits in a per-browser-profile outbox, and the next command in the same tab builds on it. On a shared or roaming Windows PC, an employee who signs out strands those events in a profile nobody reopens. **Net: the detection improves, the prevention regresses.** The fix is a command classification — append-only personal events may be optimistic; ownership-changing commands (assign, reassign, replace, approve, close month, draw sample) must be synchronous.

### 9.2 Micro-batched segments vs. the measured file-operation cost model

**Failure scenario today — already fixed.** The original distribution storage wrote one file per event. For 8,000 events that was 192,063 filesystem operations and 3–6 hours on the target UNC share. v61.0 replaced it with per-writer-session NDJSON segments and 78 operations — a 2,462× reduction. The lesson is stated flatly in the lessons-learned document: on a shared multi-writer folder the fix for contention is architectural, and a retry ladder tuned for local-disk timing is not a safety margin on a network share.

**What the proposal changes.** §11 closes a segment after every 1–3 s flush (100–500 ms for chat). XQAP's event cadence is one event per Manual Review click, seconds apart — so micro-batching degenerates to roughly one file per user action, and every reader pays a `getFile()` per segment on every fold, forever, until a compaction step §11 defers to "later" and §59 reduces to an admin button with no protocol. Layer on §17's 1–4 s polling over §10's three-level `writers/` tree — a scan of 40 users × 2 instances requires opening ~80 directories and ~80 head files — against a Chromium-measured 142 s per 1,000 small file operations over a Windows UNC share, and the tick budget **must be benchmarked before anything is built on it**. The proposal names file-operation count as a first-class optimization dimension in §18 and then never budgets it.

### 9.3 The V8 read ceiling — the one hard failure neither side solves

**Failure scenario today.** `safeReadJson` ends in `JSON.parse`, which requires the whole file as one JavaScript string. V8 caps strings at 536,870,888 UTF-16 code units. A real customer's `bi.raw.json` measured 573,236,797 bytes decoding to 455,755,299 code units — **84.9% of a hard ceiling, on data that exists today.** Past it, the file cannot be read at all; this is an unparseable month, not a slow one. v86.0 fixed the *write* path with 4 MB windowed streaming; v87.0's columnar+gzip reduces bytes stored but the decompressed body still has to become one string before parsing. The only real fixes are Phase C (port-partitioned parts + a bounded LRU, estimated 10–18 engineering days, blocked on backup coordination) and Phase D (streaming consumers, 12–22 days) — both unapproved.

**What the proposal changes.** Nothing, because it never mentions the ceiling. MessagePack decode still builds one object graph; ZSTD still decompresses to one buffer. Only Parquet's typed column projection, or an explicit partition index, moves it — and Parquet is a §24 "benchmark candidate", not a commitment. **This is the highest-stakes item in the whole comparison and it is absent from the proposal's non-negotiables (§2).** Whichever architecture ships, this needs a partitioned snapshot layout, not a codec.

### 9.4 Backup during a live save — the clearest proposal win

**Failure scenario today.** A backup walks the live workspace copying files while distribution events append. A last-write-wins JSON file that vanishes between the listing and the read is skipped as expected churn. A derived cache copied early can be newer than the segments copied later — which is why `distribution.current.json` and `distribution.checkpoint.json` are classified "derived, never restored." Separately, v41.4 recorded a `NotFoundError` race between the backup's directory walk and `safeWriteJson`'s own tmp-file create/remove, and a review round found the backup's private segment comparator would declare two different answer events sharing an eventId identical and silently drop one. The manifest carries no per-file hash, so a backup that rots later still passes its completeness check.

**What the proposal changes.** §45 captures a per-writer sequence cut vector at backup start and copies exactly the segments up to each captured sequence plus the latest verified snapshot. The archive is a consistent logical state regardless of ongoing writes; nobody has to stop working; and because §47 routes everything through one verified read pipeline, backup never needs to interpret event contents, so there is no consumer-specific comparator to be wrong. §46's hashed manifest makes the result verifiable a week later rather than only at copy time. This is the proposal's cleanest, least-contested win, and it is only available because segments are immutable — which XQAP already made them.

### 9.5 Editable PowerPoint vs. Arabic fidelity

**Failure scenario today.** A manager wants the executive deck as slides they can edit. XQAP's answer is a toast telling them to use the browser's print command to save a PDF. The deck editions imitate PowerPoint down to the keyboard conventions and fullscreen presenter mode, but there is no `.pptx` code or dependency anywhere in `src/` or `package.json`.

**What the proposal changes.** §35–43 and §68 specify the only architecture that actually gets there: render both HTML and OOXML from one layout model rather than converting finished HTML. That is correct, and §41's fidelity table is a sensible mapping. What the proposal does not confront is Arabic. `rtlMode` is a per-paragraph flag; mixed RTL/LTR run rendering is a documented open defect in the library; fonts cannot be embedded in a PPTX, so the brand font will substitute on any recipient PC that lacks it — changing metrics, wrapping and therefore whether text overflows a fixed-size box; and the presentation theme sets only the Latin typeface slot while Arabic glyphs come from the complex-script slot. This app formats every number with Latin digits inside Arabic sentences, so **every KPI string is the known-bad mixed-run case.** The capability is real and worth having; the fidelity claim is one sentence and **must be spiked on the department's actual Office build before anything is built on it.**

### 9.6 A rewrite's blast radius vs. the recorded bug history

**The asymmetry.** 348 of 961 edit-log entries are fixes. Clustering by root cause, roughly 40–45% trace to architectural properties (persistence model, effect/mount timing, permission hydration, schema boundaries, browser memory limits) and the remainder to feature-level work — of which RTL/bidi/visual polish is roughly 15–16%. A rewrite inherits none of that. Concretely: the fold's terminal-state legality table absorbed four shipped bugs before it was right; the boot-progress checklist regressed five consecutive times in one evening (v59.190–v59.197), every round caught by review rather than by the implementer's own tests, including after real-browser confirmation; the unsaved-draft destruction shipped twice in one day in two views; `typecheck` was silently checking zero files for days.

**What the proposal changes.** It proves its architecture (§62 Phase 4, §71) on a task-and-chat prototype and compresses the entire XQAP domain — population pipeline, Hamilton apportionment with a seeded Mulberry32 RNG, the seven-event distribution fold, answers, approvals, referrals, templates, three deck editions, workbook, Report Designer, ad-hoc import, KPI, notifications — into one paragraph at Phase 9. There is no calendar, no effort figure, and no migration path for workspaces holding 573 MB imports, seeded sample draws stamped with `samplingAlgorithmVersion`, per-actor audit hash chains, and thousands of distribution events. Nor is there a rule for what happens when a stale copy of the current HTML — still sitting on desktops, a documented reality — is opened against a migrated workspace, which is precisely the condition under which `workspacePaths.ts` once made every legacy month permanently invisible.

The fold's terminal-state table is the answer, and it is deterministic, snapshot-tested and already correct | Replacing it with §8's generic per-field rules would discard the domain's actual conflict semantics. The right move is to keep the table and add `baseVersion` as a second guard |
| **Reports are on-screen views** (§38: "HTML Renderer → Browser UI") | Reports are artifacts: one self-contained HTML file with base64-inlined fonts, opened offline from a share or a USB stick, printed to PDF, and used as audit evidence | Rendering reports as live in-app views with an ECharts runtime either drops the artifact or inlines roughly a megabyte of library into every exported file |
| **The platform can be proven before the domain exists** (§62 Phase 4 on tasks + chat; Phase 9 for business modules) | The domain *is* the hard part. The platform half is real but bounded; the fold, the sampling determinism contract, the approval chains and the report grain rules are where 349 recorded fixes actually live | A prototype can pass §71's acceptance criteria ("event loss = 0, silent overwrites = 0" on a chat benchmark) and still fail on the first real month |

To be fair to the study: it is explicitly a general architecture for a shared-folder department application, and it never claims to have analysed XQAP. Its runtime constraints (§2, §3), its concurrency rule (§5.1), its rejection list (§64) and its reliability guarantee list (§61) are all correct and would apply to any app in this environment. The mismatch is one of *fit*, not of *competence*.

| Factor | Incremental adoption inside XQAP | Full rebuild per §62 |

| Test corpus | 461 files carry forward | 176 jsdom component tests do not survive a Web Components move; ~160 storage tests survive only if `memoryDirectory.ts` is ported |

### 12.3 What must be measured before any of this is costed

These are the open numbers. None of them exists today and none should be guessed:

1. **Head-scan cost on the real share** — time to enumerate and open N writer heads at the department's actual user count, with antivirus scanning active (§60.4).
2. **Segment-open cost** — per-`getFile()` latency on the real UNC share, which determines rotation size and flush cadence.
3. **Format benchmark on real fixtures** — the §24.2 matrix run against the 117,336-row month and a larger projection, with the shipped columnar+gzip format as the baseline column, measuring peak RAM and time-to-first-page, not just stored size.
4. **`file://` capability verification** — IndexedDB persistence, Web Locks, `BroadcastChannel` and `CompressionStream` codec support on the managed browser build, opened as a local file.
5. **Arabic PPTX fidelity** — mixed Arabic/Latin-digit runs, RTL table column order, native chart categories, font substitution behaviour, and repair prompts on the department's actual Office build.
6. **Bundle delta per proposed library** — measured raw and gzip growth against the current 4,507,893-byte artifact, with time-to-interactive when opened from the share.

## 13. Summary judgement

The proposal is a good study of the wrong application. Its platform reasoning is sound and, where it advances beyond XQAP, it advances on exactly the axes XQAP's own history says matter: causality over wall clocks, verified backups over hopeful copies, isolation over all-or-nothing folds, measurement before implementation. Its domain reasoning is absent, its cost model is unstated, and several of its concrete recommendations — micro-batched segments, sub-4-second polling over a deep directory tree, binary opaque on-disk formats, optimistic writes for every command, and a framework swap justified in two sentences — would trade measured, hard-won behaviour for unmeasured convenience.

XQAP is not a better architecture than the proposal. It is a *worse architecture that has been debugged against reality* — and on a shared folder with no server, that distinction is worth more than it looks. The interesting question is not which design wins; it is which of the proposal's nine genuine advances can be brought inside a system that already knows what breaks. That question belongs to `A-ENHANCED-STRUCTURE-AND-PLAN.md`; whether the answer is worth the money belongs to `C-VIABILITY-AND-MISTAKES-FIXED.md`.
