<a id="1-system-context"></a>
## 1. System context — why this architecture exists

XQAP is an Arabic/RTL React 19 + TypeScript + Vite SPA with **no backend of any kind**. All business data — population imports, samples, distribution assignments, inspection answers, reports — is stored as plain JSON files in a **user-selected folder on disk**, accessed through the browser's **File System Access API**. That folder is frequently a **Windows SMB/network share**, opened by several machines and browser tabs at once, with no server to coordinate them. The whole app ships as **one self-contained `index.html` file** (`vite-plugin-singlefile`), often opened directly via `file://` rather than served over HTTP.

Every architectural decision below is a direct consequence of that combination:

- **No backend → no database, no transactions, no server-side locking.** Every "ACID" property the app needs (atomicity, isolation, durability) had to be reconstructed by hand on top of a directory of JSON files.
- **SMB/UNC share → high, variable-latency, sometimes-flaky file I/O.** Retry ladders, error classification, and file-count minimization are first-class engineering concerns, not edge cases.
- **`file://` deployment → no HTTP caching/compression negotiation.** Bundle *raw* size matters, not gzip size (a real, hard-won correction to an earlier wrong assumption — see §7).
- **Browser-only compute → Web Workers are the only way to avoid blocking the UI** on Excel parsing, large-population queries, and report generation.
- **Multiple machines, same folder, no lock server → every shared file needs an explicit conflict-resolution protocol** (see §3.3), and the safest fix for contention is usually architectural (give every writer its own file) rather than a longer retry loop.

## 2. Technology stack

| Concern | Technology | Why |
|---|---|---|
| Durable business data | **File System Access API** (`showDirectoryPicker`, directory/file handles) | The only way a browser app can treat a real folder on disk as its database. Chromium-only — other browsers get an explicit `unsupported_browser` state. |
| Same-tab write serialization | **Web Locks API** (`navigator.locks.request`), with a hand-rolled promise-chain fallback | Guarantees one writer at a time per logical file path within a tab/origin, even where the API is unsupported. |
| Cross-tab/cross-machine write safety | Home-grown **CAS (compare-and-swap) loop** (`casLoop.ts`) | No distributed lock server exists; CAS with a UUID write-token and jittered retry is the substitute. |
| Ordering-sensitive shared state | **Append-only immutable event log** (distribution events) | Avoids last-write-wins races entirely by never having two writers target the same file. |
| Password hashing | **hash-wasm** (WebAssembly Argon2id), with legacy PBKDF2-SHA256 (`crypto.subtle`) kept verifiable | Web Crypto has no native Argon2; hash-wasm brings OWASP-baseline hashing to a pure client. |
| UUIDs / hashing / randomness | **Web Crypto** (`crypto.randomUUID`, `crypto.getRandomValues`, `crypto.subtle`) | Native, no dependency. |
| Large-payload compression | **CompressionStream/DecompressionStream** (native gzip) | Browser-native, self-describing, avoids inventing a binary format. |
| Handle persistence (not business data) | **IndexedDB** | Only used to remember the last-picked workspace directory handle across reloads. |
| Excel/XLSX read & write | **xlsx (SheetJS)**, **vendored** as a local tarball (`vendor/xlsx-0.20.3.tgz`), not the npm registry package | Avoids depending on network reachability to the SheetJS CDN in CI; `check:vendor` verifies the tarball's SHA-256 against a committed hash. |
| Off-main-thread parsing/querying | **Web Workers** (`workbookWorker.ts`, `populationQueryWorker.ts`) | The only way to keep a multi-hundred-thousand-row Excel parse or table query from freezing the UI, given there's no server to offload to. |
| Single-file bundling | **vite-plugin-singlefile** (`assetsInlineLimit` maxed, `cssCodeSplit: false`) | Produces one portable `dist/index.html` with everything inlined — required because the app is copied onto a network share and opened directly. |
| UI virtualization | **@tanstack/react-virtual** | Chosen over `react-window` specifically because `react-window`'s RTL support is broken/removed — a real, RTL-first-app-specific decision. |
| Charting primitives | **d3-scale / d3-shape** (native SVG, no chart framework) | Recharts deliberately not used; a hand-built responsive SVG + semantic table serves accessibility better for this app's KPI p-charts. |
| Data-fetch/cache layer | **@tanstack/react-query** | Introduced later (v62.0) specifically to add one invalidation authority over derived-data reads, replacing ad hoc caching. |
| Main-thread scheduling | **`scheduler.postTask` (Prioritized Task Scheduling API)**, falling back to `setTimeout(fn, 0)` | A single `yieldToMain()` helper used pervasively to chunk long synchronous loops (report generation, exports, population processing) without freezing the UI. |

<a id="3-core-persistence-layer"></a>
## 3. Core persistence layer

This is the single most reusable part of the whole codebase for a new project: a hand-built "safe file storage" layer that gives JSON-file storage most of the guarantees a real database gives for free.

### 3.1 The write/read algorithm (`safeWrite.ts`)

Every write goes through **stage → verify → commit → re-verify → rollback-or-promote**, always under a per-file lock:

1. **Read current state** (tolerant of missing/oversized/compressed) to get the previous envelope revision and decide whether a `.bak` snapshot is worth taking.
2. **Snapshot to `.bak`** — only if the current file is *provably recoverable* (fully parses/inflates), never blindly copied. A framing-only check here was a real, fixed bug: it once let a torn gzip member overwrite the last good `.bak` (§9, v89.0).
3. **Stage to `{file}.tmp`.**
4. **Verify staged** — read `.tmp` back and compare **byte-exact** against what was meant to be written (not just "does it parse," which would accept a concurrent peer's valid file as if it were your own write).
5. **Commit** — copy the verified `.tmp` bytes onto the live file (byte copy, never re-serialize).
6. **Verify committed** — read the live file back and byte-compare again.
7. **On failure:** roll back to `.bak` if recoverable; otherwise **promote** the still-verified `.tmp` onto live rather than losing the write; if that also fails, leave `.tmp` on disk as a last-resort recoverable artifact instead of deleting it.
8. **Cleanup** `.tmp` on success.

**Error classification is by DOMException `.name`, never by message text** (non-portable across browsers/locales), with two deliberately different retry postures:

- **Ordinary reads** treat `NotFoundError` as immediate absence (correct for a first write, an optional file, a `.bak`/`.tmp` probe).
- **Post-write verification reads only** retry `NotFoundError` for a short ladder (~630ms), because the file provably exists (this call just wrote and closed it) — a "not found" there can only mean an SMB directory listing hasn't caught up yet. Applying this retry to *every* read would add dead latency to every optional-file probe.
- A separate, small retry ladder handles `NotReadableError`/`InvalidStateError` (a `File` object's captured `(size, mtime)` going stale mid-read) — but only if the handle/File is **re-acquired** on retry, not reused, since a stale interface object fails identically forever.
- `NoModificationAllowedError` (another writer holds the file open — real on SMB) is deliberately **not** treated as permission loss; conflating the two once caused users to be told to re-pick their folder for a problem that was actually just contention (§9, v99.5).

**Large-file handling:** V8 has a hard ~536.8M-UTF-16-code-unit string length limit. Real customer files (`bi.raw.json`) were measured at up to 85% of that ceiling. The module has a fully **streamed** path — chunked serialization, chunked incremental hashing, chunked read-back verification via `Blob.slice()` windows — that activates automatically when a plain `JSON.stringify` would overflow, so a payload too big to hold as one JS string can still be written and byte-exactly verified.

**Compressed files:** large files can opt into a gzip envelope (plain UTF-8 head line + gzip body) once they cross a row-count threshold. Reading is **format-agnostic and permanent** — a file's own first bytes classify it as plain or compressed on every read, so both formats coexist forever with no migration step required.

**`readOptionalJson`'s core contract:** "could not read it" is never the same as "does not exist." An optional-file reader across multiple candidate locations returns "absent" only if every location was genuinely, successfully examined and found empty; any inconclusive failure (permission, transient I/O) **throws** instead of degrading to an empty default — because an empty default fed into a read-modify-write becomes the entire file. This exact failure mode is credited with real historical data loss (zeroed employee answers, truncated logs) before the rule was enforced.

### 3.2 JsonEnvelope — schema versioning wrapper

Every persisted file is `{ metadata: { schemaVersion, revision, contentHash, writtenAt }, data }`. `wrap()`/`unwrap()`/`isEnvelope()` handle building, extracting, and detecting it — `unwrap` returns a bare value unchanged for back-compat with pre-envelope files, so schema evolution never requires a migration pass.

`contentHash` is a **non-cryptographic** hash (corruption detection, explicitly **not** tamper-proofing — anyone editing the file by hand can recompute a matching hash). Full-payload hash verification is gated by size (≤512KB) since re-hashing a 500k-row file costs ~5× more than the `JSON.parse` it's checking; above that size, integrity relies instead on the write path's byte-exact verification, which is strictly stronger anyway.

### 3.3 Concurrency control — three mechanisms, chosen by contention shape

1. **Web Locks (same-tab)** — the baseline for every write, cheap, but does nothing across machines/tabs sharing a disk folder.
2. **CAS loop (`casLoop.ts`, cross-tab/cross-machine)** — for shared single files with real multi-writer risk (notifications, permissions, action/error logs, per-employee answers, template/design indexes). Algorithm: mint a fresh UUID write-token, read current state, compute next state (`revision+1`, new token), write, read back and verify **both** revision and token match. Up to 10 retries with jittered exponential backoff. An optional `verify` callback adds a **delayed re-read** (80–180ms jittered sleep, then re-check) to catch the interleaving where two readers both start from the same state, both write, and both same-instant read-backs look fine — a bug that was live in production for weeks before being caught (§9, v43.15).
3. **Append-only immutable event log** — for state where **ordering**, not last-write-wins, matters (the distribution assignment history). Each event is its own uniquely-named entry, so independent writers never target the same filename at all, sidestepping CAS entirely for the event itself. Current state is always a **derived, rebuildable projection** of the log, never itself the source of truth.

**The single biggest structural lesson in this codebase:** when a shared file becomes a contention hotspot, **the fix is almost never a longer retry ladder — it's giving every writer their own file.** This pattern repeats verbatim across notifications (→ per-employee ack files), the audit log (→ per-actor files), the error log (→ per-user files), and feedback (→ per-conversation files) — each time citing the same underlying cause: a CAS retry ladder tuned for local-disk timing is not a safety margin on a contended SMB share; it can be shorter than the round trip of the very write it's racing against.

### 3.4 Workspace folder layout & path resolution

Numbered top-level roots (`1-population/` … `6-templates/`) represent ordered pipeline stages; every root resolver tries the numbered name first and **falls back to a legacy unnumbered name** only on genuine absence. Layout detection (`current`/`legacy`/`mixed`/`empty`) is explicitly **detection-only, never a migration engine** — the File System Access API has no atomic whole-tree move/rename primitive, so a partial migration could destroy data; permanent dual-path reading was judged safer than a lossy migration. This "detect and permanently support both, never migrate" doctrine recurs throughout the codebase (legacy feedback messages, legacy notification acks, legacy audit log).

Directory handles are cached per logical path to avoid re-walking the directory chain (3+ round trips per file) on every read on a slow share; a per-file **lock-key collision bug** (keying locks on bare `dir.name` instead of the full logical path) once made every same-named file in *different* folders — e.g. every month's `sample.master.json` — contend on one global lock (§9, v81.0).

### 3.5 Auth & password security model

Dual-algorithm hashing: **Argon2id** (via hash-wasm, OWASP 2026 baseline params) is the default; **legacy PBKDF2-SHA256** hashes remain verifiable and are **transparently upgraded to Argon2id on next successful login**. Session state moved from `sessionStorage` to `localStorage` (deliberate, owner-accepted relaxation) so a session survives a browser restart, guarded by a 7-day TTL re-checked on read.

**The trust boundary is explicitly "advisory only"** — documented at length in `SECURITY_MODEL.md`: with no backend, every permission check is client-side and all business data is plain unencrypted JSON; a user with local/devtools access can self-elevate or edit files directly. The bootstrap admin's hash ships inside the client bundle, making it offline-crackable — mitigated only by Argon2id's cost, not by any rate limiting. **A new app with the same no-backend constraint should adopt this same posture explicitly and early**, rather than accidentally implying a security guarantee the architecture cannot deliver.

<a id="4-data-pipeline"></a>
## 4. Data pipeline: population → sampling → distribution

### 4.1 Population processing

Excel workbooks (risk data required, BI data optional) are parsed **off the main thread** in a Web Worker via SheetJS, which posts `progress`/`result` messages back so a 100k+ row workbook never blocks the UI. Rows carry a `rawRow` reference to the original Excel row attached as a **lazy, non-enumerable accessor** rather than an eagerly-merged copy — an OOM fix, since eagerly spreading merge deltas across 300k+ rows doubled resident memory and crashed the tab.

Saving a processed month writes five files under a per-month lock: raw JSON + original binary workbook copies, the final processed dataset, a processing summary, and a status-tracking manifest (written **last**, since it records totals that depend on every prior write having committed). Re-importing a month **archives** the previous raw file (`{base}.raw.{timestamp}.superseded.json`) rather than overwriting it — an immutable-raw-data guarantee that recurs as a deliberate design principle across the whole system.

### 4.2 Sampling algorithm

A fully deterministic, reproducible stratified draw:

1. **Group by port**, then **Hamilton apportionment** (largest-remainder method) distributes the total sample size across ports proportional to population.
2. Within each port, a **second Hamilton apportionment** splits the port's quota between CertScan/NonCertScan strata (and, in the newer "stage" model, further across four audit-level strata mapped from raw `stage` text via configurable aliases).
3. **Fisher-Yates shuffle**, driven by a **seeded Mulberry32 PRNG**, draws without replacement from each stratum.
4. **Spillover redistribution** — if a stratum can't meet its quota, the shortfall is redistributed to strata with spare capacity, again via Hamilton apportionment.

**Determinism is a first-class contract, not an accident.** `Math.random()` is never used — every draw is seeded (`hashSeedString` turns an arbitrary seed string into the Mulberry32 seed) so a historical sample can, in principle, be exactly reproduced from `(population rows, seed, algorithm version)`. Hamilton's tie-breaking is deliberately a raw UTF-16 code-unit comparison, **not** `localeCompare` — Arabic collation behavior varies by host locale/runtime, and a naive `localeCompare` tie-break once made sample-draw output non-reproducible across machines (§9, v41.37).

**`SAMPLING_ALGORITHM_VERSION` is stamped onto every draw** specifically so a historical sample can be recognized as *non-replayable* under newer code — bumped only for a deliberate, approved semantic change, never for a pure refactor. This version stamp caught two real algorithmic bugs after release (a phantom-shortfall miscalculation, and a rounding-order bug that turned a configured 50% CertScan target into a 100% draw — see §9, v101–v103).

**A deliberate design choice worth reusing:** when a stratum can't be filled, the system **reports the shortfall rather than silently backfilling from a different stratum** — misrepresenting the composition of an audit sample is judged worse than an honest, visible gap.

### 4.3 Distribution — the append-only event log

Assignment/completion/replacement/reassignment/reopen state changes are modeled as **immutable events**, never as edits to a shared "current state" file — because there is no cross-machine transaction primitive, and two writers targeting the same file on a shared folder is exactly the race this design avoids by construction. Current state (`distribution.current.json`) is always a **rebuildable derived cache**, validated by a revision + a commutative digest over folded event IDs (order-independent, so two clients that discovered events in different orders still agree) before being trusted.

**Storage format evolved under real load**: one-file-per-event → per-writer-session NDJSON segments (rotated at a fixed size, since the target UNC share's dominant cost is per-file-open latency, not per-byte). Filenames were shortened from 80-character UUIDs to 22-character hashes specifically because deep UNC paths plus Chromium's write-through temp-file naming were hitting Windows' 260-character path limit (§9, v99.4) — a concrete "works on your machine, fails on the target deployment" lesson.

**The fold** maps each event to a state transition via a lookup table, explicitly rejecting illegal transitions (once `replaced`, only another `replaced` event may touch an entry; once `completed`, assignment events are dropped without an explicit `reopened` event). This fold's edge cases were the single most bug-prone piece of the whole system — see the distribution-fold entries throughout §9 — because every new event type or new caller pattern (bulk assignment, ad-hoc import, cross-supervisor approval) had to be re-verified against the same terminal-state guard, and several rounds of bugs shipped from *not* re-verifying it.

<a id="5-answers-templates-reporting"></a>
## 5. Answers, templates, sample mirrors, reporting

**Answers**: one file per employee per month, holding both their answers and their own referral/replacement/reopen requests — "sole owner, no shared-file conflicts" by construction. The real actor is tracked separately from the nominal assignee (`answeredOnBehalfBy`) so a supervisor answering on someone's behalf never corrupts the identity used for cross-referencing against the distribution log. Two independent audit trails exist: an oversight-action history and a separate, capped value-history snapshotting every prior answer on overwrite.

**Templates**: a small, deliberately non-general conditional-visibility engine — one condition per field (`equals`/`notEquals`/`truthy`/`falsy` against another field), walked recursively with cycle protection. This is a good example of *not* reaching for a general rules/expression library when a handful of operators covers the real requirement.

**Sample mirrors**: per-employee, rewritten-whole projections of the workspace-wide distribution state, so an employee's own UI never has to load and filter the entire month. Consumers always fall back to a full derivation if the mirror or its accelerator index looks stale — the mirror is never treated as sole-source authoritative. This "cheap scoped read-replica, authoritative source still available as fallback" pattern generalizes well to any per-user "my stuff" view over a larger shared dataset.

**Reporting**: every report/export is a single self-contained HTML string (inline CSS, inline JS, inline data — no external references, since a generated report may be opened from anywhere). The most reusable technique here is **`yieldToMain()`** — a tiny helper that yields the main thread every N units of work in a long synchronous loop, preferring the browser's real task scheduler (`scheduler.postTask`) over a bare `setTimeout`. It's used pervasively across every report/export builder and is the single biggest lever against freezing the UI during large-dataset operations in a backend-less app. Converting a builder from synchronous to chunked-async surfaced a real correctness class worth flagging: **any shared mutable module-level state a builder touches becomes a reentrancy bug once yields are possible mid-build**, requiring an explicit promise-chain mutex around the builder (the same pattern used for Web Locks).

## 6. Cross-cutting support domains

| Domain | Storage shape | Concurrency pattern | Notable lesson |
|---|---|---|---|
| Notifications | One shared broadcast file + **per-employee** ack files | CAS on the shared file; CAS on ack files too (only same-user multi-tab risk remains) | Started as one shared file for both broadcasts *and* acks — every employee's "accept" click rewrote it. Split fixed the real contention. |
| Audit log | **Per-actor** files, keyed by a collision-resistant hash of the username | CAS-under-lock per actor | Archival before trim, plus a tamper-*evident* (not tamper-proof) hash chain — deliberately applied here (governance evidence about people) but not to notifications/error logs (software diagnostics). |
| Error log | **Per-user** files, same stem convention as audit | Identical CAS-under-lock pattern, explicitly "copied verbatim, do not re-derive" | The clearest documented case study of SMB contention: a 4×50ms retry ladder tuned for local-disk timing was "not a ladder at all" on a network share. |
| Referential integrity | Read-only on-demand scan (`orphanScan.ts`) walking population → sample → distribution → {answers, approvals} | None — pure, side-effect-free set-difference over IDs gathered from each layer's existing loader | The reusable recipe for "foreign keys" in a schemaless JSON store: define the FK chain once, diff ID sets hop-by-hop, run on demand not reactively, **report, never auto-repair** (a mismatch gives no safe way to know which side is wrong). |
| Ad-hoc import | Own field catalog/mapping/storage, fully independent of the regular Population pipeline; one bridge module touches distribution/answers | CAS on its own index, reuses distribution's event-log machinery unchanged | An earlier version *did* depend on Population's live config, so an admin editing column aliases silently changed how ad-hoc imports parsed — fixed by snapshotting the mapping used at import time instead of reading live config. |
| Feedback | **Per-conversation** thread files + a rebuildable summary index | CAS per thread; index write-back made **opt-in and rate-limited**, never on the read/poll path | The textbook "read-repair is fine unconditionally; write-repair on a shared file must never ride a polling loop" case study (§9, v123.0/v117.x) — an index self-heal that ran on every 60s poll from every signed-in user became a self-sustaining write storm. |
| Approvals | **Per-supervisor** decision files, append-only | CAS-under-lock per supervisor | "First-decision-wins" (earliest timestamp), not last-write-wins — because two supervisors' files can't be serialized against each other, and last-write-wins would make the outcome depend on clock skew. |
| Labels / preferences / month selection | `localStorage` / `sessionStorage`, not workspace disk | None needed | Correctly scoped as per-browser UI preference, not shared business data — no CAS machinery imported where it isn't needed. |
| Backup | Manifest-tracked copy + verify-by-read-back, sentinel files marking "restore in progress" / "backup complete" | Coarse-grained, sentinel-sequenced rather than CAS'd (single-admin-initiated operations) | Derived/rebuildable files (distribution's current-state cache, fold checkpoint) are **explicitly never restored** — restoring a stale checkpoint after a later segment merge would cause silent event loss on the next read. |

<a id="7-performance-optimization"></a>
## 7. Performance & optimization

**Why this app's performance problem is unusual:** `file://` deployment means no HTTP caching/compression negotiation — every raw byte is read off a (often slow) network share on every open. Single-bundle deployment forecloses code-splitting/lazy asset loading. No backend means every optimization has to be re-derived using only what a browser offers.

**Bundle-size discipline:** `vite-plugin-singlefile` inlines everything into one `dist/index.html`. A hard ceiling (currently 30MB raw / 10MB gzip) is enforced in CI, but **the ceiling itself is documented as "permission, not a target"** — every prior raise names the specific feature that justified it and the measured overage, never a blind bump. The team held a **wrong assumption for months** ("gzip size is what matters") until an explicit correction: for a `file://`-opened app with no content-encoding negotiation, **raw bytes are what the user actually waits on**. A large ceiling with headroom to spare cannot catch a small regression, so the real day-to-day guard is a **per-PR bundle-size delta report**, not the ceiling. A separate lesson: "unused in the UI" is not the same claim as "absent from the bundle" — a tree-shaking bundler already drops genuinely dead code for free, so never bank a deletion as headroom without an actual build-delete-rebuild-diff.

**Web Workers, done right:** simply moving parsing into a worker (`workbookWorker.ts`) did **not** by itself fix an out-of-memory crash on large imports — the fix was **streaming rows out in bounded chunks** and never posting one giant array back across `postMessage` (structured clone requires the whole payload as one contiguous allocation). The lesson: *bounding the message payload*, not just relocating computation, is what actually bounds memory.

**Population-scale query performance** was tackled in two shipped phases (a third and fourth remain deliberately unimplemented, gated on owner approval and backup-tooling readiness): Phase A gated data loading by which tab/capability actually needs it (an employee with no processing rights used to eagerly pay the cost of loading the entire month regardless); Phase B moved parsing and querying of the legacy monolithic population file into a dedicated worker with paged results. The **explicit, stated lesson from the proposal doc**: UI page size, on-disk storage partition size, and in-memory cache budget are **three separate decisions** — conflating them (letting "how many rows render" dictate "how many rows live together on disk") was called out as the mistake to avoid.

**Virtualization** (`@tanstack/react-virtual`) renders only the visible row window in large tables — chosen over the more common `react-window` specifically because of a documented RTL-support gap in that library, a directly relevant call for an RTL-first app.

**Deterministic-computation discipline**: sampling, distribution folding, and report/export builders are all documented as deterministic by contract, and every performance refactor of them is required to **snapshot output before changing code, then diff after** — because a performance refactor is exactly the kind of change most likely to silently perturb ordering or floating-point-adjacent logic without anyone noticing until much later.

<a id="8-concurrency-cheat-sheet"></a>
## 8. Concurrency patterns — decision cheat sheet

Use this table when deciding how to protect a new file in a similar backend-less architecture:

| Situation | Pattern | Why |
|---|---|---|
| File is written by only one logical owner (a specific user's own file) | `withResourceLock` alone (same-tab serialization) | No real cross-writer risk; a plain lock avoids CAS overhead for nothing. |
| File is shared and multiple machines/tabs might write it, but writes are rare | CAS loop (revision + write-token, verified read-back, jittered retry) | Cheap correctness for low-frequency contention. |
| File is shared, writes are *frequent*, and per-writer identity is known | **Split into one file per writer** (per-user, per-actor, per-thread, per-supervisor) | Removes contention structurally instead of retrying around it — the single most repeated fix in this codebase's history. |
| Order of events matters more than "latest wins" | Append-only immutable event log + a rebuildable derived/current-state cache | Two writers can never collide on the same filename; state is always reconstructable, and a fold bug can be fixed retroactively by re-running it. |
| A CAS write might race a slightly-later competing write that both same-instant read-backs miss | Add a **delayed re-read** (tens-to-low-hundreds of ms, jittered) after the immediate verify | Immediate read-backs alone cannot see a peer's write that lands microseconds later; only a short deliberate delay does. |
| Deciding "is this contention or corruption" | Classify by DOMException `.name`, never by message text; treat `NoModificationAllowedError` as contention, not permission loss | Message text is non-portable across browsers/locales; conflating "someone else has it open" with "you lost access" sends users on a pointless folder-repick. |
| Data lives on a network share | Size every retry ladder for real network latency (this codebase settled on ~6×100ms as its standard for CAS, ~11s for post-write existence verification), not local-disk timing | A "short" ladder tuned for local disk can be shorter than the round trip of the very write it's supposed to be racing against. |

## 9. Full chronological issue/bug history (Jun 23 – Aug 25, 2026)

This section is the exhaustive extraction from all 47 daily edit-log files, read in full, filtered to data-layer-relevant entries (storage, sync, sampling, distribution, workers, concurrency, performance, workspace layout). Every entry follows **Problem → Fix**, with version and date. It is intentionally long and complete rather than curated to highlights — a future team wants the full failure history, not a sampler.

### 9.1 — 2026-06-23 → 2026-07-13

#### Storage / CAS / locking / concurrency

- **[v2, 06-23] Safe-write staging + hash mismatch.** *Problem:* `safeWriteJson` wrote in place with no staging; the write-time hash and read-time hash were computed over different byte representations, so optimistic-concurrency comparisons never matched; lock was keyed by bare filename. *Fix:* stage→verify→commit→rollback-on-failure; hash the exact written bytes; lock key becomes `${dir.name}/${fileName}`.
- **[v5.13–5.14, 06-24] JsonEnvelope guard too narrow.** *Problem:* `isEnvelope()` only recognized a numeric `schemaVersion`, missing legacy string versions. *Fix:* broadened to check only for the field's presence.
- **[v5.6, 06-24] Duplicated legacy-path fallback logic.** *Fix:* extracted one `resolveSampleDir` helper used by all three call sites; added a regression test.
- **[v6.0–6.1, 06-28] "Invalid string length" on very large population files.** *Problem:* unconditional pretty-printed `JSON.stringify` could exceed V8's ~512MB string ceiling on a ~300k-row payload; the read path also recomputed a full hash on every read. *Fix (staged over three releases):* compact-first serialization; a genuinely streamed write path (generator-based serializer + incremental hasher) for payloads too big even compact; incremental hashing extended to the read path.
- **[v26.1, 06-29] casLoop retried on all errors, including real bugs.** *Fix:* unexpected exceptions fail immediately now; only genuine conflict/verify mismatches retry.
- **[v26.1, 06-29] Distribution quota miscount after reassignment.** *Problem:* quota counted raw `assigned` events instead of the folded entry map, so a reassigned row was still charged to the original employee. *Fix:* count from the post-fold entry map, excluding replaced rows.
- **[v37.9, 07-01] NUL byte corruption in the edit log itself.** *Fix:* stripped the byte; added `.gitattributes` declaring source files as text so future corruption shows as a real diff.
- **[v41.4/41.35, 07-05] Auto-backup aborted on `NotFoundError` during concurrent saves.** *Problem:* a recursive backup directory walk running concurrently with normal saves hit a directory mutated mid-enumeration (each save creates/removes a `.tmp`), aborting the *entire* backup; also, the legacy `.system` layout wasn't excluded from recursion, so backup recursed into its own output. *Fix:* materialize directory entries up front tolerating mid-scan `NotFoundError`; both numbered and legacy backup-folder names excluded.
- **[v41.36, 07-05] Browse-preset save self-deadlock via lock-key collision.** *Problem:* an outer read-modify-write lock reused the exact same key `safeWriteJson` used internally; since locks aren't reentrant, the outer lock held while awaiting the identically-keyed inner lock — permanent hang. *Fix:* distinct `:rmw`-suffixed outer key. **Lesson: never let an outer RMW lock share a key with a lock the called function takes internally.**
- **[v41.37, 07-05] Hamilton apportionment tie-break was locale-dependent.** *Problem:* `localeCompare` with no locale argument made Arabic tie-breaks vary by host locale, breaking cross-machine reproducibility of sample draws. *Fix:* stable UTF-16 code-unit comparison.
- **[v41.39, 07-05] Distribution derive-cache staleness after a fold-semantics change.** *Problem:* the cache was keyed only by `logRevision`; a fold-algorithm change left old caches at the same revision indistinguishable from fresh ones. *Fix:* added `DERIVE_VERSION`, required to match on every cache hit.
- **[v41.40–41.41, 07-05] Fold's quota pass and error logging ignored dropped events.** *Fix:* quota pass now skips dropped event IDs; per-event error logging collapsed to one summary entry per derivation.
- **[v41.42, 07-05] safeWrite discarded the only good copy on a first-write failure.** *Problem:* if post-write verify failed with no usable `.bak` (e.g. first-ever write), the verified `.tmp` was deleted and the write reported failed — losing the only intact copy. *Fix:* promote the verified `.tmp` to live instead; if that fails too, keep `.tmp` on disk as a recoverable survivor; `safeReadJson` gained a third fallback tier recovering a leftover `.tmp`.
- **[v41.13, v42.53/54/56/76–80, v43.3, S1–S6, 07-05→07-13] Systematic sweep: shared multi-writer files needed CAS, not just same-tab locks.** *Problem, recurring:* many shared files (feedback log, browse presets, permissions, template/design indexes, config, month manifest, per-supervisor decisions, auth activity log) were guarded only by a same-tab lock — two admins on two machines could each read the same pre-mutation state and the second write silently clobbered the first (lost decisions, dropped messages, overwritten password hashes, un-closed months). *Fix pattern, applied uniformly:* lock-wrapped CAS loop (fresh read, mutate, bump revision, fresh write-token, write, verify both fields on read-back, retry with jitter). New concurrent-writer regression tests added at every site.
- **[v43.15/43.14, 07-13] casLoop's own verification window was too narrow.** *Problem:* only the *immediate* read-back after write was checked; a competing write landing slightly later was invisible — both writers' own read-backs could look fine while the second silently clobbered the first. *Fix:* optional `verify` callback sleeps a jittered 80–180ms then re-reads, retrying the whole attempt on a later-arriving conflict. Threaded through all existing casLoop call sites. Terminal-error classification added so permission loss surfaces immediately instead of being retried and misreported.
- **[v43.4, 07-13] Workspace bootstrap files had no `.bak` recovery.** *Problem:* the workspace manifest and permissions file had no fallback or hash verification unlike everything else — a torn write (no atomic rename in the File System Access API) could brick workspace entry. *Fix:* added the same `.bak` fallback used everywhere else.
- **[v43.9, 07-13] Sample-mirror writes had no ordering guard.** *Fix:* monotonic `sourceLogRevision` guard skips a write whose incoming revision is not newer than what's already persisted.
- **[v43.8, 07-13] `saveMonthRun` had no lock/CAS; "sample already drawn" check was TOCTOU-racy.** *Fix:* serialized against other manifest-mutating operations via a shared lock key; re-checks under the lock whether a sample already exists.
- **[v43.2, 07-13] Backup folder-name collision.** *Problem:* second-granularity timestamps let two machines backing up in the same second collide. *Fix:* appended a short random suffix.

#### Sampling / distribution / fold correctness

- **[v41.52, 07-07] Sample draw silently "succeeded" with an all-zero sample.** *Problem:* if every row's stage text failed to match any configured alias, every stage target was 0 and the draw still returned `ok: true` with an empty sample, saved indistinguishably from a legitimate empty draw. *Fix:* fail loudly if all-zero while the input population is non-empty, pointing at Stage Mapping settings.
- **[v41.27, 07-05] Spillover redistribution broke the per-port-actuals invariant.** *Fix:* reconciled spillover rows back into `portAllocations`.
- **[v41.28/43.12/43.13, 07-05 & 07-13] Distribution fold had multiple terminal-state gaps.** *Problem:* a stray late event for an already-`replaced` row could resurrect it; the fold switch had no `default` case, so an unrecognized event type silently reset a live entry to its initial state; re-running bulk assignment on an already-`completed` row silently discarded the submitted answer. *Fix, incrementally:* `replaced` made fully terminal; added a `default` branch preserving existing state; added a terminal guard requiring an explicit `reopened` event to return a completed row to pending; bulk assignment made idempotent against already-live rows; manual reassignment blocked outright for completed rows.
- **[v41.25, 07-05] `totalAssigned` counted dead (replaced) rows**, inflating the stat after any replacement. *Fix:* count only live, non-replaced entries.
- **[v41.33, 07-05] Executive-report completion figure derived from the wrong source** (distribution events describe assignment, not study, state). *Fix:* completion now derives uniformly from submitted answers.
- **[v46, 07-13] Derived distribution snapshot missed its own revision stamp**, permanently freezing mirrors synced from a directly-derived (unstamped) snapshot. *Fix:* the derivation function stamps `logRevision` itself.
- **[v43.6/43.7, 07-13] Cross-supervisor approval races; unguarded reassignment of completed rows.** *Fix:* deterministic first-decision-wins resolution; re-scan of every supervisor's decision file both immediately before and immediately after a write.
- **[v43.11, 07-13] Stale in-memory entry used for an instant replacement; wrong preference between derived and mirror state.** *Fix:* freshness re-check before the instant path proceeds; queue filtering prefers fresh derivation over a possibly-stale mirror.
- **[v42.65, 07-12] New "reopen case" flow layered onto existing machinery without disturbing it** — mirrored the existing referral/replacement request storage shape exactly rather than inventing a new one.

#### Population / config / schema evolution

- **[v5.36, 06-25] 300k-row BI/risk parse crashed via V8's call-stack argument limit.** *Problem:* spread-push patterns (`arr.push(...validRows)`) fail past V8's max call arguments, and the worker's soft-catch swallowed the error with no real diagnostic. *Fix:* loop-push instead of spread-push; freed worksheet objects after parsing; surfaced the real underlying error.
- **[v34.4, 07-01] Report crashed on population data written before a schema addition.** *Fix:* optional-chaining defaults for fields that didn't exist in older files; a regression test built against a deliberately old-shaped row.
- **[v41.14, 07-05] Permission-key naming mismatch silently hid a whole sub-tab for every role, including admin.** *Problem:* the permission lookup built a composite key the registration never matched. *Fix:* renamed the registered id to match.
- **[v41.30/41.31, 07-05] No guard against re-drawing a sample after distribution had started**, or re-processing a month with a sample already drawn. *Fix:* hard block / confirm-dialog gates added.
- **[v41.45, 07-05] A defensive guard against silently persisting an empty derived snapshot** — a stale in-memory state could otherwise **zero out `distribution.current.json` and every employee mirror**, real visible data loss. *Fix:* fall back to loading the on-disk sample master before deriving; refuse to persist an empty result if that's also empty.
- **[v37.0–37.7, 07-01] Whole-codebase folder/file naming migration**, straight rename with no compat shim, every literal centralized in `workspacePaths.ts` constants so future renames touch one place.
- **[v41.32/42.55, 07-05 & 07-12] Month-status field left unwired, then made CAS-safe once real.**

#### Sync / refresh / staleness

- **[v41.20, 07-05] Three views read permissions without subscribing to change events** — stayed frozen after an admin revoked access until an unrelated remount. *Fix:* added the shared subscribe+force-update pattern.
- **[v42.81, 07-12] Unhandled rejection could permanently freeze a view on its loading spinner.** *Fix:* added `.catch` with an explicit error-state transition.
- **[v38.3, 07-02] DataTable "Maximum update depth exceeded" render loop** from an unstable filter-callback identity feeding a memo that recomputed every render. *Fix:* only emit the change callback when filtered rows actually changed (length + identity guard).

#### Workers / build / performance

- **[v5.11, 06-24] Sequential per-month summary loading serialized on one slow folder.** *Fix:* `Promise.allSettled` in parallel.
- **[v42.13–15, 07-08] Vendored the xlsx CDN tarball into the repo; truncated the in-app ChangeLog's raw import to the most recent 20 versions (~21% bundle cut); added CI gated on both.**
- **[v38.4, 07-02] Non-bundled `public/` assets broke the "single self-contained file" guarantee and broke exported-report portability** (relative font URLs). *Fix:* inlined every font as base64, favicon as a data URI; deleted `public/`.

**Recurring patterns in this window:** shared multi-writer files kept needing to be discovered and migrated from same-tab locking to full CAS, piecemeal over three weeks rather than designed in from the start; the distribution fold kept growing new terminal-state/unknown-event edge cases; large-payload serialization kept hitting hard V8 ceilings that only appeared at real production data volumes, never in test fixtures.

### 9.2 — 2026-07-14 → 2026-08-05

#### Storage / CAS / safeWrite / write-permission

- **[v46.3, 07-14] Lock-key collision across months — accepted, not fixed.** A documented, deliberate non-fix: colliding lock keys only over-serialize unrelated writes, they can't corrupt data; a real fix needs threading full workspace paths through every caller.
- **[v48.6, 07-14] Reports had no link back to the exact on-disk revision they were built from.** *Fix:* revision loaders added; reports print a "source revisions" block.
- **[v48.2, 07-14] Several CAS-protected mutation paths never surfaced an exhausted-retry conflict to the user.** *Fix:* explicit conflict messaging at each site.
- **[v55.2, 07-16] `reportDesignStorage`'s per-id write skipped CAS on a wrong "single writer by id" assumption.** *Fix:* wrapped in the same CAS protocol as templates; a same-id concurrent-save test proves it.
- **[v55.2, 07-16] `monthLock.ts` lacked the delayed re-verify** other CAS sites already had, for the file governing whether a closed month stays frozen. *Fix:* added it.
- **[v56.1, 07-17] Automatic backup aborted on transient `NotReadableError`**, a real, spec-documented error distinct from `NotFoundError` that neither backup nor safeWrite tolerated. *Fix:* both now tolerate it the same way.
- **[v56.3, 07-19] Auto-backup aborted entirely when one listed month had no population folder.** *Fix:* tolerate that one dataset returning null instead of throwing.
- **[v57.4, 07-22] Backups could crash with "Invalid array length" and take extremely long**, because routine backups *also* rebuilt redundant 250k-row XLSX copies via SheetJS, exceeding array/heap limits on real 400k+-row workspaces. *Fix:* routine backups write JSON only; XLSX became an explicit, bounded, default-off convenience export that can fail without invalidating the completed JSON backup.
- **[v57.5, 07-22] Workspace connect deferred the write-permission prompt to the point of first actual write** (opens read-only by default). This is a good pattern but **introduced a real regression** (see next entry).
- **[v58.1, 07-22] Six write paths bypassed the new deferred-write-permission boundary**, throwing a raw English `NotAllowedError` on a freshly-restored read-only workspace instead of prompting. *Fix:* routed all six through the shared write-access gate; extended the in-memory test double to actually simulate permission state (previously hardcoded to "granted," making this whole regression class untestable).
- **[v59.12, 07-22] A notification-post CAS loop opened the write permission *inside* the retry loop**, so a permission prompt got misclassified as terminal "access lost — reconnect the whole workspace" instead of a normal one-click prompt. *Fix:* moved the write-access gate outside the loop.
- **[v143/59.143, 08-03] Attach/reconnect requested only "read" permission**, forcing a second separate prompt on first write. *Fix:* request `"readwrite"` directly at both call sites — then a follow-up fix (v59.152) found the *silent* auto-reconnect path still queried read-only, so the bug recurred for the more common path.
- **[v59.185, 08-04] Backup copy/restore had zero retry for transient `NotReadableError`**, exposed once backup concurrency widened from 1 to 8 (making a collision with another writer far more likely to surface). *Fix:* shared the same retry logic `safeWrite.ts` already had.
- **[v59.199, 08-05] Lockfile version drift (15 releases behind package.json)**, which `npm ci` can reject outright.

#### Sampling / four-eyes gate / distribution event log

- **[v49, 07-14] Four-eyes approval gate was session-only, bypassable by a page reload.** *Fix:* derived from a persistent on-disk stamp instead of session state. *(This entire gate was later removed by explicit design decision — v59.135, 08-03 — after being fully built across five releases; the underlying pure rule module was deliberately left in place as a future cleanup candidate.)*
- **[v47.2, 07-14] Distribution events had no schema version**, so a future format change could silently corrupt the fold. *Fix:* `eventSchemaVersion` stamped; unrecognized future versions are dropped-and-preserved rather than crashing the fold.
- **[v57.1, 07-21] Bulk distribution save was fully sequential**, freezing the UI on large samples with zero progress feedback. *Fix:* bounded worker-pool concurrency for independent event-file writes; real phase-by-phase progress reporting.
- **[v59.145/59.150/59.152, 08-03] Several redundant full-event-log re-reads inside the CAS/append/refresh chain**, each doing a full directory re-scan just to compare two scalars, or recomputing state a caller already had. *Fix (three linked commits):* a lightweight scalar-only reader for CAS verification; propagating an already-computed log through the call chain instead of re-deriving it; correcting a stale field on the returned (not the persisted) object.
- **[v59.142, 08-03] Distribution read-dedupe key omitted the sample-rows dimension**, letting two racing callers with genuinely different inputs share the wrong cached result. *Fix:* widened the dedupe key.
- **[v59.9/57.9, 07-22] Supervisor reassignment approval trusted a stale derived-state cache; the interruption-replay guard was non-idempotent.** *Problem:* ownership checks read a rebuildable cache that could be stale-but-valid; an interrupted multi-event batch's replay guard treated "any event with this request id" as proof the whole batch completed, so a retry after partial failure would skip re-sending the missing events. *Fix:* ownership derived by folding the already-loaded authoritative log; replay made idempotent per row, verifying complete transfer before recording approval — safe under interruption at any point.
- **[v59.24, 07-22] Population loader unconditionally read the two largest per-month files even when nothing downstream needed them.** *Fix:* skip once the manifest shows the month has advanced past the stage that needs raw data.
- **[v59.0/59.1, 07-22] Opening the replacement dialog read the entire population (400k+ rows) just to find ~100 candidates.** *Fix:* a bucketed candidate index built once at save time, with a hash-guarded staleness check and full-scan fallback; two subtler bugs caught by adversarial review *before* commit — a monotonic guard that ignored config changes at the same population revision, and an ambiguous null-vs-failure return from bucket reads.
- **[v59.134, 08-03] Replacement-index rebuild wrote up to 10 bucket files sequentially.** *Fix:* parallelized while preserving deterministic manifest ordering.
- **[v59.136, 08-03] Pending/replaced referral rows were hidden from the employee's queue instead of shown with status.** *Fix:* stopped hiding them; color-coded instead.

- **[v59.19, 07-22] Browse per-column filter dropdown collapsed to one option the instant it was used**, because its option list was built from rows already filtered by its own selection. *Fix:* build options from every *other* column's filter, excluding the open column's own.

#### Backup / restore concurrency and integrity

- **[v59.180–59.183, 08-04] A cluster of backup/restore concurrency fixes:** sequential per-month archive-status checks parallelized; nondeterministic manifest ordering fixed by separating the (sequential) file-listing pass from the (concurrent) copy pass; a live async directory iterator held open across concurrent restore writes replaced with a materialize-then-fan-out pattern; two completion sentinels added (`restore.inprogress.json`, removed only on success; `backup.complete.json` written last); **a partial restore could report success** — fixed by threading a `skipped[]` signal through the whole call chain so any skipped subtree flips the result to failure and leaves the in-progress sentinel in place.

#### Sync / refresh signals

- **[v59.106, 08-01] The refresh signal covered only permissions, not the "live queue" data users actually complained about being stale** (reassignments, approvals, notifications). *Fix:* generalized the broadcast/subscribe mechanism and wired it into every affected view.
- **[v59.105, 08-01] Permission/role edits by one admin never reached an already-open session in another tab/machine** — the in-memory permission state was hydrated once per tab and the change event was same-window only. *Fix:* added a narrow, disk-re-read refresh that doesn't trigger a full remount.
- **[v59.168, 08-04] A single global refresh signal defeated a directory cache's own correct per-file invalidation**, resetting it wholesale every periodic tick for no benefit. *Fix:* tagged the broadcast with a `"manual"`/`"periodic"` source; the cache resets only on manual.

- **[v59.137/59.138, 08-03] Every distribution-event read re-scanned the entire append-only directory from scratch**, with no cross-call caching, even though the directory only ever grows. *Fix:* an incremental reader that lists names cheaply every call but reads only not-yet-cached names — caught, before shipping, a draft that still re-scanned-and-re-read the whole directory in memory while *appearing* correct from its return values alone. Paired with in-flight call coalescing and an epoch counter for defense-in-depth, deliberately **not** applied to 9+ correctness-critical sites that exist specifically to observe a concurrent write.

#### Workers / large-population performance (Phase A/B rollout)

- **[v59.111–59.114, 08-01] Phase A — demand/capability-gated Population loading.** A pre-implementation review found ~40% of the proposal's "before" state had already shipped, an undocumented second eager-loading consumer, and a **phase-derivation trap**: deriving "what stage is this month at" from population-row presence alone would misreport an already-sampled month as phase 1 the instant loading became scoped and legitimately skipped population. Fixed *before* the scoped-loading change landed by deriving phase from distribution/sample presence first. A second real bug found while wiring demand-gating: the draw-sample button's disabled condition (`rows.length === 0`) became ambiguous between "genuinely empty" and "not loaded in this view's scope yet" — would have made the new lazy top-up unreachable through the UI.
- **[v59.184, 08-04] Phase A's own implementation was silently lost from git history** — a file the already-committed code imports and calls didn't exist on `main`; a clean checkout failed to typecheck. *Fix:* committed the missing file; noted as its own lesson about session-boundary commit hygiene, independent of the feature's correctness.
- **[v59.189, 08-04] Phase B — worker-owned Population Browse.** Shipped with a **critical** bug not caught until dedicated review: one shared "latest request wins" staleness counter was deciding freshness for three unrelated concurrent query streams (load / table / filter-preview) at once, so whichever settled last silently discarded the other two's results — column filtering did nothing and Browse usually showed "no data" over a correctly-loaded month. All 4 of that plan's own tests mocked the worker with a microtask reply — faster than any real worker could respond, which is exactly what hid the bug. *Fix:* per-lane staleness tracking instead of one global counter. A follow-up review then found the fix's own error-recovery only worked on the *first* load — a failed subsequent load left the previous month's data cached and silently queryable.
- **[v59.94–59.102, 07-29] Report/deck builders converted to chunked-async (`yieldToMain`)**, each preceded by a byte-for-byte golden-snapshot of pre-change output as a determinism baseline. Two golden-snapshot reproducibility bugs found immediately after: CRLF/LF line-ending divergence between the Windows capture machine and Linux CI (fixed via `.gitattributes`); and a snapshot test that called a builder using the real unfrozen `Date` — accidentally correct only because CI happened to run on the same calendar day as capture, breaking on rollover.
- **[v59.75, 07-29] Second-order DOM XSS in the report-viewer's runtime TOC-building script.** *Problem:* a `data-title` attribute (already HTML-escaped in the generated markup) is *decoded back to raw text* by the browser when read via `getAttribute`, and the runtime script then concatenated it into `innerHTML` — undoing the upstream escaping the moment a malicious Excel-derived port name reached the page. This evaded the static-HTML-source XSS test corpus entirely, since it only scans generated markup, not this decode-then-innerHTML runtime path. *Fix:* build the TOC entry via `createElement`/`textContent`, never string-concatenated `innerHTML`.

#### Boot-progress / effect-timing (the five-round saga, all in one evening)

This is the single most heavily-reviewed feature in the whole history — five fix rounds, every one caught by independent review rather than the implementer's own testing, all variants of the same "session identity / mount timing" bug class:

- **[v59.190, 08-04]** Post-login data-source checklist added, deliberately scoped down from a broader ask to avoid regressing the just-shipped demand-gating. Store-reset logic ran during render based on a React effect-ordering assumption that turned out to be subtly wrong.
- **[v59.191]** **Round 1 — the checklist's headline feature didn't work at all.** A hook read the store once via `useState` but only subscribed inside a later effect; per React's child-before-parent effect order, that subscription ran *after* the source it needed to observe had already been marked loading — the publish found zero subscribers and was lost, so the checklist simply never showed (deterministic on one path, a coin-flip race on normal login). *Fix:* rebuilt on `useSyncExternalStore`, closing the whole bug class structurally rather than patching one call site.
- **[v59.192]** **Round 2 — the redesign re-broke the identical bug class.** A per-session "show once" dismissal latch compared its stored key against the *new* session's key at a render where the shared store still held the *previous* session's data (the reset ran in a layout effect, which by definition fires after that render) — the freshly-armed latch read stale "already done" state and dismissed itself before the new session's sources ever registered. *Fix:* latch only when the overlay is actually rendered visible.
- **[v59.195]** **Round 3 — the checklist loaded too fast to ever be read.** Real timestamped instrumentation (not review) found every prior fix was working exactly as designed — the always-registered sources were already-optimized reads completing in under 100ms, so the *state machine* was correct and the *duration* was the bug. *Fix:* a minimum-visible-time floor. **A second, more fundamental bug found while implementing this:** a session-key string comparison isn't sufficient, because React can re-render a component multiple times within one commit *before any effect runs* — the key can match the new session on a render where the data still reflects the old one. *Fix:* a generation counter incremented only inside the actual reset function, immune to same-commit render-count tricks.
- **[v59.196]** **Round 4 — two more regressions found in the "settled" fix**, sent for review purely out of caution. A mount-time bypass of the freshness gate (correct only for a true first-ever mount) could latch off stale data on a genuine remount (an admin role-preview switch, a logout/login cycle) and get permanently stuck showing an empty checklist. A staleness-check ref keyed on a session-key *string*, not unique across genuinely distinct sessions with the same key shape, could silently reproduce the original too-fast-to-read bug in a new guise.
- **[v59.197]** **Final independent verification** — confirmed clean by a pass specifically searching for a *third* variant of the same bug class; found none. One stale doc comment corrected (a claim the round-5 fix had already disproved).

#### Concurrency / race conditions elsewhere in the auth/workspace layer

- **[v59.11, 07-22] Startup session-hydration race silently dropped valid sessions on every reload** — a synchronous startup check ran *before* the workspace's async user-list sync had populated real users, so any real managed-user session failed an "still exists?" check against only the hardcoded seed users and was cleared. *Fix:* defer the *clear* decision, not the read, gated on an explicit hydration-complete flag. **A follow-up regression:** the fix broke demo/viewer login, since a demo session also isn't backed by a "managed user" record — fixed by broadening the exemption.
- **[v59.132/59.163, 08-03/08-04] The same hydration race recurred one layer up (tab menu) and one layer further up (whole authenticated app shell)** — each was independently discovered and fixed with the same "gate rendering on hydration-complete, show a neutral spinner in between" pattern.
- **[v59.16, 07-22] Rapid roster saves silently dropped an admin's edit with no error and no trace.** *Problem:* a bare "in-flight? skip" guard on the write path meant a second edit arriving mid-write was neither written nor queued. *Fix:* a coalesce-to-latest helper — a call arriving mid-write overwrites a pending slot, drained immediately after the in-flight write settles.
- **[v59.116, 08-01] A management screen silently reverted a concurrent admin's disk change** because it seeded local state once and never re-subscribed to the shared store, so a wholesale "save what I have" overwrote a since-changed disk file with no conflict indication. *Fix:* subscribe and reconcile like every sibling consumer already did.
- **[v59.130/59.131, 08-03] Activity-log wiring missed the most common real-world case (a reload-continued session)**, silently turning session logging into a permanent no-op for that path. *Fix:* one effect gated on session truthiness covering fresh logins, demo logins, and reload-continued sessions uniformly.
- **[v59.169, 08-04] A provider could list months before login completed**, since its trigger (a directory handle) can be non-null before authentication. *Fix:* moved the provider inside the authenticated-session render branch.

#### Mount-preservation / stale-data-on-tab-switch (rediscovered independently four times)

A single bug pattern — a hidden-but-mounted child still re-renders/reloads on every unrelated parent re-render — was independently rediscovered and fixed in four different tabs in quick succession, each time requiring the *same two-part fix* (a render-phase-guarded state update, not an effect; a memoized element reference so React can bail out by identity) before it actually stuck. Two later fixes each independently rediscovered that the effect-only version was insufficient before the earlier fix was retrofitted to match.

#### Report-export reliability

- **[v56.12, 07-21] `window.open(...,"noopener")` always returns `null` even on success**, per spec — a helper that branched on that return value always took the "popup blocked" fallback path, producing a duplicate download *and* revoking a blob URL the just-opened tab was still navigating to (a real cause of permanently blank tabs). *Fix:* open a blank same-origin window first (a real handle), then `document.write` into it directly — no blob URL, no revoke race.
- **[v59.103, 07-30] The subsequent async/chunked report-building change reintroduced the identical blank-tab bug through a different door** — if the now-async build threw, the already-opened window was simply abandoned, open and blank. *Fix:* wrap the build in try/catch and close the window before rethrowing. **Confirmed with a failing test first**, proving the pre-fix window really was never closed.
- **[v59.119, 08-01] Only 1 of 7 call sites for the above fix had ever gotten a regression test.** *Fix:* added coverage for the shared helper and the remaining 6 call sites.

**Recurring patterns in this window:** the single most expensive bug class was **stale/premature reads across an asynchronous identity transition** — a component reading shared state at a render or effect that ran before the corresponding reset/hydration had landed. It surfaced independently in auth session hydration, the boot-splash overlay (five rounds), tab mount-preservation (four tabs), and derived-state caches — and every single instance was caught only by a dedicated adversarial review reproducing real production render/effect ordering, **never by the implementer's own test-first pass**, because the unit tests consistently constructed the "safe" ordering rather than the real one.

### 9.3 — 2026-08-07 → 2026-08-25

#### Storage layer (safeWrite / envelope / CAS / locks / compression / error codes)

- **[v62.0, 08-07] Reference-not-copy across derived files.** *Problem:* a 28MB Excel import produced a **385MB workspace (~11×)** — the replacement index stored full population-row objects per bucket (a 6th full copy of the population), and derived files inlined full rows. *Fix:* store minimal field-picks/stubs everywhere a derived file only needs a few fields; added a shared query-cache layer with one invalidation authority; added row virtualization. Workspace size cut 52%.
- **[v61.0, 08-07] One-file-per-event distribution logging didn't scale: 192,063 filesystem operations for 8,000 events, taking 3–6 hours**, because each file creation pays a per-file OS write-through cost on the target share. *Fix:* batch events into append-only per-writer-session NDJSON segments; a persisted fold checkpoint resumes from the last-read offset instead of re-reading everything. **2,462× fewer write operations.**
- **[v60.0, 08-07] Save progress was invisible for 10–15 minutes on a large save; the session store didn't survive a browser restart.** *Fix:* progress callback threaded through the save UI; session storage moved `sessionStorage`→`localStorage` (a deliberate, owner-accepted relaxation).
- **[v80.0, 08-13] Envelope hashing cost 7.1× the `JSON.parse` it was checking; small/contended files only got a weak "does it parse" read-back check.** *Fix:* size-gated the expensive full-payload hash; made read-back verification byte-exact **at every size**, not just large ones.
- **[v79.0, 08-13] NDJSON segments were rewritten whole on every append**, unbounded (measured ~130KB/append average on a 900-event session — quadratic cost, and a wider window for a rewrite to be misread as missing). *Fix:* segments rotate at a fixed size into sealed, never-rewritten siblings.
- **[v78.0, 08-13] Backup/restore silently skipped every distribution event segment entirely** — the file-matching predicate only recognized `.json`, and `.ndjson` fails an `endsWith(".json")` check. A restore could therefore produce assignment state with no justifying events behind it, and an unreadable segment during backup was silently dropped and reported success. *Fix:* a single suffix-exact predicate covering both extensions; segments merge (not replace) on restore; the derived cache is invalidated after any segment-changing restore; unreadable segments now fail the backup instead of being silently skipped.
- **[v77.0/76.0/75.0, 08-13] A cluster of SMB/UNC round-trip and error-classification fixes:** reused already-enumerated handles instead of reopening by name; resolved shared parent directories once instead of repeatedly; a vanished directory entry between listing and open (a real, common SMB shape) now resolves to null instead of aborting the whole enumeration; and — the most consequential — **`NotFoundError` right after a successful write was misclassified as permanent absence**, corrupting a completed write into a reported failure and leaking raw English DOMException text into the Arabic UI. *Fix:* a dedicated module drawing the exact line — retried on the write/verify path only, never on the ordinary read path — plus filtering raw error text out of user-facing messages.
- **[v92.0, 08-16] No stable, quotable error code existed for any user-visible failure.** *Fix:* an append-only catalog of ~86 `XQ-<AREA>-<NNN>` codes tagged onto existing error objects (not wrapped, to avoid breaking existing `instanceof`/`.name` classification elsewhere).
- **[v89.0, 08-16] Two real correctness bugs in the new compressed-storage format**, both **critical**: a truncated file (head-metadata line only, zero body bytes) was misclassified as valid plain data and returned as if it were real content — bypassing `.bak` recovery entirely for exactly the shape that safety ladder exists to catch; and a corrupt live compressed file was byte-copied over the last good `.bak` because the pre-copy check validated envelope *framing* only, not payload integrity. *Fix:* a new "corrupt" classification routes a too-short file to `.bak` recovery; the pre-copy check now fully inflates and CRC-checks before allowing an overwrite of `.bak`.
- **[v99.4, 08-18] Fifth field report of the same intermittent write failure, with no confirmed single root cause.** At the owner's explicit request, six independent defenses were shipped simultaneously rather than waiting for a confirming diagnosis: shortened the one unusually long filename shape in the app (an 80-character segment name, the leading suspect against Windows' 260-char path limit on deep UNC paths) to 22 hashed characters; a more patient write-verification ladder; one retry against a freshly-resolved directory handle; a per-event fallback if batch append still fails; bounded chunked appends instead of one giant write; two new diagnostic error codes.
- **[v123.0, 08-25] A cluster of four independent bugs converging on the same recurring user-facing failure over an 88-minute window, four users affected.** The actual DOMException (`InvalidStateError` — a cached file snapshot no longer matching disk) was recognized by **none** of six independently-written read-retry loops, so it received zero in-place retries and fell through to the coarsest, most write-amplifying outer retry. The error log itself never captured the one field (`.name`) that would have revealed this. A shared-index write-repair was still running on a read/poll path used by every signed-in user every 60 seconds — a failed repair left the index exactly as stale, so every machine retried forever. And a CAS verification failure that *threw* (rather than answering false) was treated as proof of data loss, discarding an already-successful write. *Fix:* the new error name recognized and consolidated onto one shared retry-decision helper across all six duplicated loops; `.name` added to every error-log record end to end; the index repair made opt-in, rate-limited, and merge-not-replace; a thrown verify no longer discards a confirmed write.
- **[v123.2, 08-25] Bundle-size ceiling raised to 30MB raw / 10MB gzip, correcting a standing false assumption held for months** ("gzip governs transfer") that doesn't hold for a `file://`-opened app with no content-encoding negotiation — every raw byte is read on every open regardless of gzip size. The real regression guard becomes a per-PR bundle-size delta report, not the ceiling (26MB of headroom cannot catch a 200KB accident).

#### Sampling & distribution (algorithm, event log, fold, quotas, checkpoints)

- **[v63.0, 08-07] Three independently-computed accuracy folds disagreed in production**, at different grains, two running simultaneously in the same report — a port where level-1 review missed every suspicious case but level-2 caught them all could read "100% accuracy, excellent" on one surface while every other surface flagged it below target. *Fix:* one shared aggregation entry point; every field name now carries its grain so a cross-grain read is a compile error, not a silent mismatch.

- **[v102.0, 08-19] Percentage-method CertScan target rounded per-port instead of per-stage, compounding into a 50%→100% over-draw** — ten ports each allocated one seat at a configured 50% each rounded `0.5→1` independently, drawing 100% CertScan when 50% was asked for. *Fix:* round once at stage level, then apportion the resulting count across ports (matching how the alternate "exact count" method already worked). `SAMPLING_ALGORITHM_VERSION` bumped.
- **[v83.0, 08-15] Percentage stage rules compared a raw percentage value directly against a row count**, inventing a phantom shortfall that over-drew the whole population; separately, an event whose row wasn't in the current sample set still inflated an employee's quota even though it was excluded from the fold. *Fix:* resolve percentage rules to an actual row count before comparing; a separate "absent-row" event set that quota derivation explicitly excludes. Algorithm version bumped again.
- **[v88.0/89.1, 08-16] Employee daily quotas were silently corrupted by ordinary reassignment/replacement** — quota was derived from counting raw `assigned` **events** rather than final ownership state, so a routine reassignment permanently corrupted both employees' counts in normal daily operation, with no corruption or hand-editing involved; undetected because no test covered reassignment and quota together. **The first fix shipped but was inert**: the mirror-sync monotonic guard rejected any write at the same log revision, and a version-bump refold produces exactly that same revision — so the corrected number was computed but never reached the file employees actually read. *Fix:* quota derived from live ownership state; the guard's comparison widened to a `(revision, deriveVersion)` pair so a same-revision, newer-derivation overwrite is allowed.
- **[v93.0, 08-16] CertScan matched by unbounded substring, fabricating the sample's composition** — a pasted device serial containing "2026" matched 117,268 of 117,337 real rows (essentially the entire month), since nearly every ID embeds an 8-digit date. *Fix:* anchor matching to a specific ID segment position, verified against a real characterization of actual ID shapes.
- **[v96.0, 08-16] Every replacement permanently inflated the sample's total-actual count forever**, producing a phantom backlog exactly equal to the replacement count and capping the reported completion rate below 100% — a silent wrong number in the app's primary deliverable. *Fix:* a separate "retired row" set, distinct from the row list used for replacement-dedup, so a replaced row can be excluded from totals without being deletable from the dedup set.
- **[v98.4/98.5, 08-17] Stale-tab assignment could silently transfer another supervisor's already-owned rows; a completed row could be regressed to pending by a stale table snapshot.** *Problem:* the fold's terminal-state guard blocked `assigned`/`reassigned` after `completed` but not `replacement-requested`, so clicking "replace" on a row another machine had already completed regressed its status and orphaned the submitted answer, silently defeating auto-lock and every completion report. Bulk assignment similarly trusted a caller's stale record for gating. *Fix:* every mutating path re-reads the row's fresh on-disk status immediately before deciding anything, rather than trusting whatever the open tab last loaded.
- **[v99.5, 08-19] `NoModificationAllowedError` (SMB lock contention) misclassified as permanent permission loss.** *Problem:* on a shared folder, "locked by another writer right now" and "your access was revoked" share the same DOM error name — the app told users to re-pick their folder for a problem that was actually just contention, which re-picking cannot fix. *Fix:* added to the transient-retry set instead of the terminal-failure set.
- **[v99.6, 08-19] Backup could not run at all on a large legacy workspace** — one file decoding past V8's string-length ceiling (~85% of it, measured on a real customer file) aborted the *entire* backup with no partial credit. Separately, a transient read blip on the user-roster file was silently treated as "no file yet," **re-seeding the whole roster from scratch and wiping real revision history** (measured: a revision-42 file with real users came back as revision 1 after a single blip). *Fix:* byte-windowed, per-file-tolerant backup copying; explicit distinction between "genuinely absent" and "could not read it," aborting rather than reseeding on the latter.
- **[v99.7, 08-19] A completed restore was invisible to every other client on the share.** *Problem:* the one file the app's "did anything change" probe watches for the distribution family is deliberately restore-preserving (to avoid rolling back a newer live revision) — so a restore that merged real events back in left every other client serving stale data indefinitely, with no error and nothing to indicate it. *Fix:* re-mint just the change-detection token (not the revision) after a segment-rewriting restore.
- **[v101.0, 08-19] The derived distribution cache was blind to a whole class of real state change** — a replacement appends a sample row without appending a distribution event, so every cache-freshness signal (revision, event-set digest, derive version) stayed identical while the actual row set to fold against had changed; a cache derived from the pre-replacement rows was served (and, on the checkpoint-resume path, silently *extended*) against a row set it was never actually derived from. *Fix:* an order-sensitive fingerprint over the sample rows themselves, required to match on every cache-acceptance check.

#### Sync / Refresh

- **[v70.0, 08-12] Four compounding problems made the app re-sync far more often than data actually changed, and blank the screen doing it** — an unconditional loading state on every periodic tick; "reload everything" instead of a targeted diff; an unawaited multi-megabyte cache-write side effect on pure reads (N machines opening the same month → N large writes of byte-identical data); warm-up state discarded by an LRU tab-mount cap. *Fix:* a silent-refresh option that swaps rows in place with no spinner; pure reads explicitly opt out of the cache-write side effect; write flows explicitly refresh the cache instead of relying on the next reader to.
- **[v73.0/74.0, 08-13] Three uncoordinated refresh mechanisms shared no code and no concurrency guard between them**, one bug away from a race on shared state; the sync cadence was also a single hard-coded constant, too chatty for some workspaces and too slow for others. *Fix:* one module owns the probe, baseline, and broadcast rule for every trigger with one shared guard; cadence became an admin-configurable setting.
- **[v83.1, 08-15] A large-workspace sync probe opened files one-by-one, and its change-detection compared file size only** — a same-byte-length edit (e.g. a two-digit revision number changing) was invisible, so another user's real change could go undetected indefinitely. *Fix:* bounded-concurrency listing; signature widened to include modification time.
- **[v100.2, 08-19] Notification acknowledgements written to one shared file caused genuine cross-employee write contention** — a field-reported failure class. *Fix:* moved acks to per-employee files, merged with the legacy shared file on read.
- **[v103.2, 08-19] No signal existed at all for a new feedback message arriving.** *Fix:* an unread indicator sourced from a local per-viewer read-marker (deliberately never a server-timestamp comparison, since other machines' clocks can run ahead) plus a bounded sync-probe family for the feedback log.
- **[v114.0/117.4, 08-22/08-24] Approving a request, and submitting an answer, never announced themselves on the refresh signal at all** — every *sibling* mutating flow already did, these two simply never had the one-line broadcast call added. *Fix:* added, each guarded against a view redundantly re-reading its own just-made write.
- **[v117.10, 08-24] After splitting feedback into per-thread files, the sync probe was still watching a file nothing writes to anymore**, silently freezing the unread indicator for every subsequent conversation. *Fix:* probe the actual per-thread files directly.

#### Workers / performance (query worker, workbook worker, memory, chunking)

- **[v80.3/80.4, 08-13] Confirming a replacement froze the main thread parsing the whole population just to keep one row; exporting a filtered table re-sorted the entire dataset once per exported page** (~4,000 full sorts on one export, from an integer-division sentinel bug that silently produced an empty result instead of erroring). *Fix:* a one-shot single-row worker lookup; a single unbounded query request instead of N bounded ones.
- **[v81.0/80.5, 08-15] Every workspace read re-walked its full directory chain, and every lock keyed on the identical leaf-folder name across every month, unrelated months serializing against each other for nothing; a streamed write path also serialized its payload twice.** *Fix:* directory-handle caching with in-flight dedup; full logical paths used for lock keys; the already-verified staged write reused instead of re-serialized on commit.
- **[v86.0/87.0, 08-15] Real customer BI data (573MB, ~85% of V8's string-length ceiling) crashed the whole month save; the three largest workspace files were measured at 92% of total workspace size on a real 28MB-import workspace (35.66× inflation — far above an earlier ~11× assumption).** *Fix:* chunked streaming reads/writes with a rolling hash for byte-exact verification without ever holding a whole giant file as one string; a columnar+gzip storage format for the largest files, gated behind an explicit opt-in never used implicitly. Net effect on the measured workspace: **1,000,805,318 bytes → 44,120,740 bytes (22.7× smaller)**, and the save phase got *faster*, not slower, despite adding compression.
- **[v117.7/117.8, 08-24] The population import worker crashed with an out-of-memory structured-clone error on real large months (~500k rows)**, because it posted the *entire* parsed result in one message — structured clone must serialize the whole object graph as one contiguous allocation. *Fix:* stream results out in bounded batches, releasing each batch's worker-side memory as it's sent.
- **[v97.2, 08-16] A dead/crashed Web Worker produced total silence** — no message, so every promise awaiting only a reply hung forever with nothing on screen and nothing in the error log, worse than a wrong error message. *Fix:* explicit error handlers plus a silence watchdog that terminates and allows recreation of a presumed-dead worker (sized generously, since a legitimate large parse can legitimately take over a minute).

#### Feedback system rework (per-thread storage — a complete before/after case study)

**Before:** one shared file held every conversation as a flat array; every submit **and every reply to any thread** rewrote the entire file, contending across every user's activity.

**After (v117.0–v117.11, 08-24):** one file per conversation (short, time-ordered IDs — deliberately not bare UUIDs, for the same path-length reason as distribution segments) plus a rebuildable summary index touched only on thread creation or status change, **never on an ordinary reply** — the single most common action. A new thread's write needs no CAS at all (a brand-new ID has no possible contender); a reply is a CAS loop scoped to its own one thread file, so two admins replying to *different* threads can no longer contend at all. Legacy history is migrated out lazily and idempotently on first read, never proactively, per the codebase's "detect and permanently support, never migrate" doctrine.

**The specific bug this evolution had to fix at the end (v123.0, tying back into the storage-layer entry above):** the summary index's *read* path was still repairing and *writing back* the index unconditionally on every call — and that read path is polled every 60 seconds by every signed-in user, whether or not they have the feedback panel open. A failed repair left the index exactly as stale as before, so the very next poll (possibly seconds later, from a different machine) rediscovered the same drift and retried — a self-sustaining write storm with no exit condition. *Fix:* the write-back became opt-in (only from an actual human opening the panel) and rate-limited per tab, well past both the feedback poll interval and the general sync cadence.

#### Ad-hoc import rework (a second complete case study)

**Before:** ad-hoc import reused Population's live column-alias configuration and normalizer directly — a data-layer module reaching into a component subtree it does not own — so an admin editing Population's mapping template silently changed how an already-completed ad-hoc import's *saved* mapping would be interpreted on next use.

**After (v105.5 onward, 08-21):** ad-hoc import owns its own field catalog, mapping model, and Arabic text-normalization copy, and **snapshots the mapping actually used at import time** into the import's own record rather than reading live config. One bridge module is the sole point of contact with sampling/distribution/answers, and it deliberately **reuses the real distribution event machinery unchanged** rather than reimplementing it, emitting the same row shape every downstream consumer (fold, reporting, export) already expects.

**Real bugs found during this rework, several with lasting consequences:**
- **[v106.1] Unmapped result fields silently fabricated a "clear" clinical verdict** for every unmapped row — this data flows into the sample and renders indistinguishable from a real finding. *Fix:* required an explicit admin-declared constant value instead of a silent default, so nothing is invented per-row.

- **[v99.10/114.2, 08-19/08-23] A user's entire ad-hoc workload could be invisible to the "safe to delete this user" check**, since that check only walked real month folders, structurally blind to the synthetic ad-hoc storage location; and the ad-hoc visibility index could permanently desynchronize from durably-written assignments if the third of three sequential commit-writes failed (unrecoverable by simply retrying, since the earlier writes' events already exist and would be seen as duplicates). *Fix:* the footprint scan unions real months with ad-hoc storage; a repair path reconciles the index against what's actually durably present on disk by looking for the one artifact only a real assignment write creates.
- **[v111.0, 08-22] A fully-built, fully-tested feature (historical-answer import) had zero UI callers — completely unreachable by clicking** — and exercising it for the first time (by finally wiring it up) immediately exposed a real defect that had been invisible the entire time specifically because nothing had ever called it.

## 10. Recurring failure patterns — the meta-lessons

Reading all 47 files end to end, the same handful of bug *shapes* recur across nine weeks, in completely different subsystems, independently rediscovered each time. These are the lessons most worth carrying into a new app **as design decisions made up front**, not bugs to fix later:

1. **"I could not read it" is never the same claim as "it does not exist."** Every time these two were conflated, the failure mode was the same and it was always dangerous in the same direction: an inconclusive read failure got treated as "empty/absent," which then licensed a write that silently overwrote, re-seeded, or fabricated real data. Build this distinction into the storage layer's type system from day one (a tri-state read result, not a nullable one) rather than discovering it file-by-file.

2. **On a shared multi-writer folder, the fix for contention is architectural, not tunable.** A CAS retry ladder tuned for local-disk timing is not a safety margin on a network share — it can be shorter than the round trip of the write it's racing against. Every time this recurred, the real fix was giving each writer their own file (per-user, per-actor, per-thread, per-supervisor), not a longer retry loop. Design shared-write files this way from the start for anything with a natural per-writer identity.

3. **Stale state read at the wrong moment causes silent data loss more often than any other single cause.** This showed up as: a component reading shared state before an async reset/hydration completed (five review rounds on one feature alone); a mutation acting on an in-memory snapshot instead of re-reading immediately before a durable write; a derived cache accepted as fresh when a dimension of its input had actually changed. The fix is always the same shape — re-read authoritative state immediately before the decision that matters, and make freshness checks include *every* dimension the derivation actually depends on, not just the obvious one (revision number alone is not enough if a sibling field can change independently).

4. **A test suite that always constructs the "safe" ordering will never catch a timing bug that depends on the "unsafe" one.** Every boot-progress/effect-timing bug in this history passed its own unit tests and was caught only by adversarial review reproducing real production render/effect order. If a new app has any async identity transition (login, workspace switch, session restore), write at least one test that deliberately constructs the adversarial ordering, not just the happy one.

5. **Real production data volume invalidates assumptions that never surface in test fixtures.** String-length ceilings, filename-length limits, and workspace-inflation ratios were each discovered only when actual customer files went through the pipeline. Build headroom and streaming paths for "10x what you've tested," not "what fits in a demo fixture."

6. **A budget/ceiling with a lot of headroom stops being a regression signal.** Pair any hard limit (bundle size, retry count, row count) with a per-change delta report, because the ceiling alone cannot catch a small accidental regression once there's slack in it.

7. **Never bank a computed value as free until you've actually measured it.** "Unused in the UI" is not "absent from the bundle." "Already covered by an earlier fix" is not "verified by an independent read." Several real regressions in this history were specifically bugs where an earlier fix's own claim of correctness ("verified," "tested") was taken at face value and turned out to be wrong on the very next dedicated review pass.

8. **Deterministic-by-contract computations (sampling, event folding, report generation) need a snapshot-before-you-touch-it discipline, enforced as process, not memory.** Every one of this codebase's docs that discusses touching these subsystems repeats the same instruction: capture current output first, change the code, diff second — never the other way around.

## 11. Checklist for a new app

If a new project shares this app's core constraint (no backend, disk/shared-folder persistence, browser-only), start with these as defaults rather than re-deriving them under pressure:

- [ ] Build a **stage → verify → commit → re-verify → rollback-or-promote** write helper from day one, not as a later hardening pass. Byte-exact verification, not "does it parse."
- [ ] Make every read function return a **tri-state result** (found / genuinely-absent / could-not-read), never collapsing the last two into "absent."
- [ ] Wrap every persisted file in a **versioned envelope** (schema version, revision counter, non-cryptographic content hash) from the first file format, so schema evolution never needs a migration pass.
- [ ] Classify every storage error by **DOMException `.name`**, never by message text; decide up front which names are transient-retry-worthy and which are terminal, and write that decision down somewhere central (this codebase's error-code catalog is a good template).
- [ ] For any file with a **natural per-writer identity** (per-user, per-thread, per-actor), store it as one file per writer from the start — don't wait to discover the contention.
- [ ] For any file that's genuinely shared and multi-writer, implement **CAS with a write-token and a delayed re-verify**, not just an immediate read-back — the immediate-only version has a real, provable gap.
- [ ] For anything where **order** matters more than "latest wins" (an audit trail, an assignment history), use an append-only event log with a rebuildable derived-state cache, never a directly-mutated "current state" file.
- [ ] Size every retry ladder for **real network-share latency**, not local-disk timing, if the deployment target might be a network share at all.
- [ ] Decide the **numbered-root / legacy-fallback / never-migrate** layout philosophy up front if the storage layout might ever need to change — a lossy migration is worse than permanent dual-path reading when there's no atomic move primitive available.
- [ ] Treat any client-side auth/permission system as **advisory, not a trust boundary**, and say so explicitly in a security-model doc, if there's genuinely no backend to enforce it server-side.
- [ ] Build a `yieldToMain()`-equivalent helper immediately and use it in every loop over more than a few hundred rows — retrofit is much harder than build-in.
- [ ] If shipping as a single bundled file, pick a size ceiling deliberately, know **which** measure (raw or gzip) actually matters for the real deployment mechanism, and pair the ceiling with a per-change delta report from the start.
- [ ] Write at least one test per async identity transition (login, session restore, tab/workspace switch) that **deliberately constructs the adversarial render/effect ordering**, not just the happy path.
- [ ] For anything deterministic-by-contract (sampling, folding, report generation), adopt "snapshot output before you touch the code" as a written rule, not a hope.
