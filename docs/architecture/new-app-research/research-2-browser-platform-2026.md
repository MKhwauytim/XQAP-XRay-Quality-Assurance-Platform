# Browser Platform Reality Check — 2026 (Chromium / File System Access / Shared-SMB Deployment)

Scope: verifying the platform assumptions in `static-html-shared-folder-proposal.md` and the counter-claims in `proposal-critique.md`, against primary sources (MDN, Chrome for Developers, WHATWG spec, Chromium source/bug tracker, blink-dev intent threads) as of August 2026.

---

## 1. FileSystemObserver — status, shape, and the SMB/cross-machine question

**Status.** Not experimental-only anymore, but its recency matters for "already in the target fleet" assumptions. Origin trial ran Chrome 129 → 134 (Sept 11 2024 → Feb 26 2025). The formal **Intent to Ship** (Dec 18 2024) targeted **desktop stable in Chrome 133** ([blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/6oOaFmia2dc), [mail-archive copy](https://www.mail-archive.com/blink-dev@chromium.org/msg12265.html)). Chrome 133 shipped Feb 2025, so as of Aug 2026 it has been stable in Chrome/Edge for roughly a year and a half — safe to build on for a new app, but **desktop only** ("not enabled on WebView"; Android support is explicitly future work, gated on `FileSystemHandle` itself only reaching Android at M132) ([intent thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/6oOaFmia2dc), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemObserver)).

**API shape** (MDN, [FileSystemObserver](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemObserver)): `new FileSystemObserver(callback)`; `observer.observe(handle, { recursive })` where `handle` is a `FileSystemFileHandle`, `FileSystemDirectoryHandle`, or OPFS `FileSystemSyncAccessHandle`; `observer.disconnect()`. Callback receives `records[]`, each with `root`, `changedHandle`, `relativePathComponents`, `type` (`"appeared" | "disappeared" | "modified" | "moved" | "unknown" | "errored"`), and optional `relativePathMovedFrom`. Security model: it only observes handles the user has already granted File System Access permission on — no new capability surface.

**The SMB/remote-machine question — the critique is right, and this is the single most important finding of this slice.** No primary source — not the [Chrome blog](https://developer.chrome.com/blog/file-system-observer), not [MDN](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemObserver), not the [WHATWG proposal doc](https://github.com/whatwg/fs/blob/main/proposals/FileSystemObserver.md) — makes any explicit claim about network/SMB/UNC paths or about visibility of changes from *other machines*. What the spec proposal *does* say is structurally telling: "this proposal does not attempt to specify how exactly a change notification from the operating system maps to a file system change record" and every detail is "best-effort," varying by OS notification primitive (it names Windows' `FILE_NOTIFY_INFORMATION`/`FILE_ACTION_MODIFIED`, and separately notes Linux `inotify` has no native recursive-watch support). That is: **the API is a thin wrapper over the OS's local file-watch primitive**, not a new synchronization mechanism. On Windows, Chromium's watcher (`base/files/file_path_watcher_win.cc` — not directly viewable in this search pass, but its use of `ReadDirectoryChangesW` is the long-established, widely documented implementation for this class of Windows API) inherits that API's own well-known limitation: `ReadDirectoryChangesW`/`FileSystemWatcher`-style notifications are **unreliable-to-nonexistent for changes originating from a *different* machine writing over SMB** — this is a decades-old, independently confirmed problem (see the general research: [FileSystemWatcher and SMB shares don't fire reliably](https://github.com/microsoft/vscode/issues/201103), [.NET issue tracking the same](https://github.com/dotnet/corefx/issues/7576)). MDN documents one concrete cross-platform gap explicitly: **Windows does not support `"moved"` events between directories — Chromium reports them as separate `"disappeared"`/`"appeared"` records instead.**

**Verdict: confirmed, not refuted.** Treat `FileSystemObserver` exactly as the critique and the proposal's own §14 already do — a same-machine, likely-same-process-tree acceleration signal (fast local echo of your own writes, or another tab/app on the *same box*), never a substitute for polling as the correctness path across machines on the share. Nothing in the primary sources contradicts this; the absence of any stated network-share guarantee, combined with the underlying OS-watcher lineage, is itself the evidence.

## 2. File System Access API persistence, permissions, and enterprise policy

**Persistent permissions.** Chrome shipped a UI in 2024 with a three-way prompt — "Allow this time," **"Allow on every visit"** (persistent, until explicitly revoked), "Don't allow" — replacing the old always-reprompt model ([Chrome blog, persistent permissions](https://developer.chrome.com/blog/persistent-permissions-for-the-file-system-access-api)). A **launch icon** next to a page's file-editing indicator opens Privacy & Security settings where users can revoke per-site grants individually. The blog is explicit that permission is retained "indefinitely, unless access is revoked," but also notes automatic revocation for tabs backgrounded for an extended period — so a long-idle background tab is not guaranteed to keep write access without re-prompting. **What survives a full site-data clear vs. a plain restart is not answered by this source and needs to be treated as unverified** — the general rule from `queryPermission()`/`requestPermission()` guidance (MDN, [File System Access API docs](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)) is that permission grants are **not guaranteed** to persist between sessions and every app must call `queryPermission()` on the stored handle before use — exactly what the proposal's startup flow (§18) already does, correctly.

**`id`/`startIn`.** Both options exist as documented ([MDN `showDirectoryPicker()`](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)): `id` lets the browser remember a distinct last-used directory per logical picker-id (so a "select workspace" picker and a "select export folder" picker in the same app don't fight over one remembered path); `startIn` accepts either a `FileSystemHandle` or one of the well-known values (`desktop`, `documents`, `downloads`, `music`, `pictures`, `videos`). With neither option specified, the browser falls back to "last directory used by any picker" — worth setting `id` explicitly so a workspace-connect flow doesn't inherit whatever directory an unrelated picker last opened.

**Enterprise policy.** Chrome Enterprise ships four relevant list policies: `FileSystemReadAskForUrls` / `FileSystemReadBlockedForUrls` and their write counterparts `FileSystemWriteAskForUrls` / `FileSystemWriteBlockedForUrls` ([Chrome Enterprise policy list](https://chromeenterprise.google/policies/file-system-read-ask-for-urls/), [write-blocked variant](https://chromeenterprise.google/intl/en_uk/policies/file-system-write-blocked-for-urls/)), plus the general `DefaultFileSystemReadGuardSetting`/`DefaultFileSystemWriteGuardSetting`. These are **URL-pattern allow/deny lists, not silent pre-grants** — `...AskForUrls` still surfaces the picker/permission prompt for matching origins (it just guarantees the org *permits* asking), it does not auto-grant without a user gesture. For a `file://`-deployed app this matters less than it would for an HTTPS one, since there's no meaningful origin pattern to allowlist by URL for local files — but a managed Edge/Chrome fleet **can** outright block File System API access fleet-wide via the guard settings or blocked-URL lists, which is a real deployment-blocking risk worth a Phase 0 policy check against the target fleet's GPO/CBCM config, not just a runtime capability probe.

## 3. `file://` specifics

**Secure context: yes, confirmed from Chromium's own source semantics, not folklore.** Chromium's `network::IsOriginPotentiallyTrustworthy()` treats the `file` scheme as Potentially Trustworthy by rule (`(file, *, —)` is one of Chromium's recognized secure-origin patterns), which matches the [W3C Secure Contexts spec](https://www.w3.org/TR/secure-contexts/)'s own recommendation that local files be treated as trustworthy since they didn't cross an untrusted network to reach the browser. This is exactly why XQAP already works via `file://` in production — `isSecureContext` is `true`, and every secure-context-gated API that doesn't have an *additional*, narrower restriction is available: `showDirectoryPicker`/`showOpenFilePicker`/`showSaveFilePicker`, `crypto.subtle`, `CompressionStream`/`DecompressionStream`, Web Workers (including from Blob URLs — ordinary browser-side worker construction, no `file://`-specific block found in any source checked), WebAssembly instantiation (`WebAssembly.instantiate`/`instantiateStreaming`, the latter needing a `Response` with a real MIME type, which a `fetch()` of a same-origin `file://` resource or a Blob-backed response satisfies the same as HTTP), and Web Locks. IndexedDB works under `file://` too (see below). None of the individual capability pages fetched in this pass state a `file://`-specific carve-out for any of these — the one genuine nuance is **`WebAssembly.instantiateStreaming` requires the response to carry `Content-Type: application/wasm`**, which `fetch()` against a `file://` URL does not reliably set, so the safe pattern (already implied by the proposal's base64-embedded-WASM plan) is to embed the WASM bytes and use plain `instantiate(bytes)`, sidestepping the MIME question entirely — this is what `hash-wasm` already does in XQAP.

**The shared-origin caveat is real and important.** Per the [MDN same-origin policy page](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) and corroborating historical WHATWG discussion, Chromium implements the HTML-mandated model where **every `file://` page shares one single origin** — there is no per-directory or per-path origin partitioning (Firefox notably diverged from this some years ago, but Chromium did not). Practically: `localStorage`, `IndexedDB`, `BroadcastChannel`, `SharedWorker`, and `navigator.locks` are **all shared across every `file://` page open on that machine, regardless of which folder or file the HTML was opened from** — a second, unrelated static-HTML tool opened as `file:///D:/other-tool/index.html` on the same machine shares the identical `localStorage`/IndexedDB namespace as this app. This is a genuine collision risk worth a namespaced key prefix (which XQAP's `xray_auth_session_v1`-style keys already do informally) and should be called out explicitly as a design rule for the new app, since the proposal doesn't mention it at all.

## 4. CompressionStream / DecompressionStream

Current MDN documentation ([`CompressionStream()` constructor](https://developer.mozilla.org/en-US/docs/Web/API/CompressionStream/CompressionStream), page dated June 2026) lists **five** supported `format` values: `"gzip"`, `"deflate"`, `"deflate-raw"`, `"brotli"`, `"zstd"`. The first three have been "Baseline widely available" since ~2023 and are what XQAP already uses. **Brotli and zstd are materially newer additions to this specific API** (not to be confused with Chrome's much older support for Brotli as an HTTP *content-encoding*, which is a different code path with a different history) — zstd support in the streams API is generally reported as landing around **Chrome 123**; the exact milestone for `"brotli"` as a `CompressionStream` format specifically returned inconsistent/conflated results in this research pass (sources mixed it up with 2016-era HTTP Brotli support), so **treat the brotli-format milestone as unverified** and confirm with a runtime feature probe (`new CompressionStream("brotli")` in a try/catch) against your actual minimum target Chrome/Edge version rather than trusting a specific number. No documentation surfaced any streaming-performance guidance beyond the API's inherent nature (chunked, backpressure-aware, no need to hold the whole payload in memory) — this is a genuine gap in the public docs, and XQAP's own empirical measurement (22.7× on real BI data) remains the best available benchmark to carry forward rather than any vendor number.

## 5. Hard limits that bit XQAP

- **V8 max string length:** confirmed at **536,870,888 UTF-16 code units** (`0x1FFFFFE8`, ~512 MiB) on 64-bit V8/Chrome — this dropped from V8's earlier ~1 GiB (`2^29-24`) ceiling in the Node 12→16 era and is the number XQAP's own docs already cite; Safari's JSC allows a materially higher `2^31-1`, a genuine cross-engine asymmetry worth remembering if Chromium-only stops being true later.
- **Structured-clone / `postMessage` payload:** confirmed no documented hard byte cap — the practical ceiling is memory pressure and the structured-clone algorithm's requirement that the whole payload materialize as one contiguous allocation before transfer, exactly the mechanism XQAP's OOM crash (§7, "streaming rows out in bounded chunks") ran into. **Design rule, not a number**: never post one giant array/object across a worker boundary regardless of engine.
- **IndexedDB value size:** no documented per-record cap; the real constraints are per-origin storage quota (browser- and disk-dependent, e.g. up to 50%/8 TiB in "persistent" storage mode per current MDN storage-quota guidance) and ordinary JS memory limits before IndexedDB itself objects. Worth flagging: **best-effort-mode data (the default, unless `navigator.storage.persist()` succeeds) can be silently evicted by the browser under storage pressure, all-or-nothing per origin** — for a `file://` app that treats IndexedDB purely as a disposable cache (as this proposal correctly does), that's fine; it would be a real risk if anyone were tempted to treat IndexedDB as durable.
- **Windows `MAX_PATH` (260 chars):** confirmed as a real, still-live default limit for the classic (non-`\\?\`-prefixed) Win32 path APIs; long-path opt-in (registry/GPO) raises it to ~32,767 but cannot be assumed present on a target fleet. No primary source directly documents Chromium's `.crswap` staging-file naming convention or its interaction with this limit, but XQAP's own hard-won incident (§9, v99.4: 80-char UUID filenames plus deep UNC paths plus Chromium's own temp-file suffix blew past 260) is first-party evidence this is a real, not theoretical, failure mode — carry forward the same discipline: **budget total path length explicitly** (UNC root + sharded dirs + doc-id + any `.tmp`/`.crswap`-style suffix Chromium appends during a staged write), keep IDs short (hashes, not raw UUIDs, in filenames), and test against the deepest real deployment path, not a shallow dev path.
- **Files-per-directory on NTFS/SMB:** no hard NTFS limit, but confirmed real practical degradation — `FindFirstFile`/`FindNextFile`-based enumeration (which is what directory listing ultimately does, including whatever Chromium's `FileSystemDirectoryHandle` iteration does under the hood) has been measured taking **minutes** at 300,000+ files in one directory, and MFT fragmentation compounds this over time. This directly validates the proposal's sharded `sync/00../ff/doc_.../` layout (§11) and the general "don't let one directory accumulate unboundedly" rule.

## 6. Web Locks scope, and same-machine cross-tab coordination under `file://`

**Web Locks API is strictly origin-scoped** (MDN, [Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API); [W3C spec](https://www.w3.org/TR/web-locks/)) — "all tabs, workers, etc. in the same browser on the same origin share a lock manager." Combined with finding **§3 above (all `file://` pages are one origin in Chromium)**, this yields a conclusion the critique didn't spell out but the proposal implicitly needs: **`navigator.locks` genuinely works for same-tab *and* same-machine cross-tab coordination under `file://`**, because every `file://` tab on that machine is the same origin regardless of which folder the HTML came from — but it remains **completely useless across machines** sharing the SMB folder, exactly as XQAP's own architecture doc already states (Web Locks is explicitly documented there as "does nothing across machines/tabs sharing a disk folder" — read narrowly, that's about cross-*machine*, and cross-tab-same-machine already works and is what XQAP already relies on for its baseline lock). No source found suggests any `file://`-specific carve-out on Web Locks — it isn't gated by anything beyond ordinary same-origin scoping.

**BroadcastChannel and SharedWorker** are likewise scoped to the same single `file://` origin per the same same-origin-policy source, so both are available for same-machine, cross-tab signaling (e.g., "someone else on this box just wrote this document, invalidate your cache") without any extra plumbing — genuinely useful for the proposal's local-echo/acceleration layer, distinct from and no substitute for the cross-machine reconciliation that only the shared folder itself can provide.

## Summary against the two source documents

| Claim | Verdict |
|---|---|
| FileSystemObserver likely only sees local FS events, not other machines' SMB writes (critique) | **Confirmed** — no primary source claims cross-machine visibility; API is explicitly a thin, "best-effort" wrapper over local OS file-watch primitives with known SMB-notification unreliability upstream. |
| FileSystemObserver = acceleration only, never correctness (proposal §14, critique §5) | **Correct as designed** — build as if polling is the only mechanism that matters. |
| `file://` is secure-context-eligible in Chromium (proposal §2) | **Confirmed**, and further confirmed that the full API surface the proposal needs (Workers, WASM, CompressionStream, crypto.subtle, Web Locks, IndexedDB) works there — the one nuance is `instantiateStreaming` needs a real WASM MIME type, so use `instantiate(bytes)` with embedded WASM instead. |
| Handles/permissions are not guaranteed durable across sessions (proposal §2, §18) | **Confirmed**, plus a persistent "Allow on every visit" grant now exists (2024+) that the proposal doesn't mention and could reduce reconnect friction when available. |
| Not addressed by either document: all `file://` pages share one Chromium origin | **New finding** — cross-app localStorage/IndexedDB/BroadcastChannel/lock-namespace collision risk on a shared machine running multiple static-HTML tools; needs an explicit namespacing rule. |
| Web Locks "useless across file:// machines" (critique) | **True for cross-machine**; **confirmed it does work for same-machine cross-tab**, which the critique didn't need to resolve but is worth stating explicitly as a design fact for the new app. |
