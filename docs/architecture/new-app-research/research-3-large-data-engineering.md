# Large-Data Engineering in the Browser — Research for the New App

Anchored against XQAP's measured numbers: **22.7× compression** (1,000,805,318 → 44,120,740 bytes, columnar+gzip, v86.0/87.0), **2,462× fewer write ops** (192,063 file ops → batched NDJSON segments, v61.0), the **573MB `bi.raw.json`** real customer file (~85% of V8's ~536.8M-UTF-16-code-unit string ceiling, v86.0), and **500k-row months** (worker OOM on unbounded `postMessage`, v117.7/117.8).

## 1. Columnar options — Arrow JS / parquet-wasm / hyparquet vs. hand-rolled

**Apache Arrow JS** (`apache-arrow` npm package): reported minified/gzip size varies sharply by measurement method — one comparison puts it at 163KB minified / ~43KB gzipped ([flechette README](https://github.com/uwdata/flechette)), while Bundlephobia's `es5-cjs` build shows 2.82MB compressed ([bundlephobia.com/package/apache-arrow](https://bundlephobia.com/package/apache-arrow)) — the gap is because Arrow JS ships a large surface (compute kernels, multiple format converters, Table/Vector machinery) and tree-shaking effectiveness depends heavily on which subpath you import; there's an open upstream issue about npm-package bloat ([apache/arrow-js#52](https://github.com/apache/arrow-js/issues/52)). It **does** read/write IPC files entirely in-browser with no Node dependency — `tableFromIPC()` works directly off a `fetch()` response or an `ArrayBuffer` ([arrow.apache.org/docs/js](https://arrow.apache.org/docs/js/)). It has a genuine **random-access story**: the IPC *file* format (as opposed to the *streaming* format) has a trailing footer indexing every RecordBatch by byte offset, and Arrow's C++/Python readers expose `get_batch(i)` for O(1) batch lookup without reading the whole file ([Arrow IPC docs](https://arrow.apache.org/docs/cpp/ipc.html)); reads are zero-copy where the source allows it. JS-specific `RecordBatchFileReader` random-access docs are thin in what's public, but the format guarantee (footer + per-batch offsets) is format-level, not implementation-specific.

**parquet-wasm**: Rust-via-WebAssembly bindings onto Arrow. Full read+write+all-codecs brotli bundle is **1.2MB**; a read-only, no-compression minimal build drops to **456KB** brotli-compressed ([kylebarron/parquet-wasm README](https://github.com/kylebarron/parquet-wasm/blob/main/README.md)). It buys real Parquet compatibility (interop with Python/DuckDB/analytics tooling) plus Parquet's own column-level encoding/compression, at meaningfully more bundle weight than Arrow IPC alone, and it needs an Arrow JS install alongside it to consume the output.

**hyparquet**: pure-JS, dependency-free Parquet *reader* (a companion `hyparquet-writer` exists separately). Core engine reported at **~10KB minified+gzipped** ([hyparquet npm](https://www.npmjs.com/package/hyparquet), [GitHub](https://github.com/hyparam/hyparquet)) — two orders of magnitude smaller than parquet-wasm, no WASM instantiation cost, no separate Arrow dependency required to just read. Its design blog explicitly targets "read only the byte ranges you need" ([Hyperparam: Quest for Instant Data](https://blog.hyperparam.app/quest-for-instant-data/)), which is the random-access property you want for a chunk store.

**What each buys over XQAP's hand-rolled columnar-JSON+gzip (22.7×):** XQAP's number already captures most of the win — columnar layout kills per-row key repetition, and gzip mops up the rest. Arrow/Parquet add on top of that: (a) **typed binary encoding** instead of JSON text for numeric columns (no digit-string round-trip, no per-value parse cost), (b) **true random access to a sub-range of rows** without decompressing the whole file (gzip is not seekable — XQAP's format is "read whole file, then gzip-inflate", not "read rows 40,000–40,999"), and (c) column-level statistics/dictionary encoding (Parquet) for further compression on top of generic gzip. What they cost: Arrow JS is a real bundle-weight line item against XQAP's own 30MB raw / 10MB gzip ceiling — even the smallest credible number (~43KB gzip) is non-trivial against a budget where a 200KB regression is flagged, and parquet-wasm's WASM payload is far worse. hyparquet is the outlier that's cheap enough to add almost for free.

**Recommendation by dataset-size tier:**
- **Under ~50k rows / a few MB**: keep XQAP's hand-rolled columnar-JSON+gzip. No format-migration cost, stays human-greppable (a real value per the critique doc — Notepad/`jq` inspection for incident forensics), and the win from a real columnar binary format doesn't clear its own complexity cost at this size.
- **~50k–500k rows, read-mostly, needs partial/paged reads** (XQAP's actual population-month scale): **hyparquet** for reading, optionally `hyparquet-writer` for producing chunks — 10KB is noise against the bundle budget, gets you real per-row-group random access (unlike gzip), and if a future admin needs to open a chunk in DuckDB/Python for forensics, Parquet is a much better lingua franca than a bespoke binary layout.
- **Multi-million-row or cross-tool interop is a hard requirement** (e.g., feeding the same chunks into a separate Python/DuckDB pipeline used by ops): step up to full **Arrow JS + parquet-wasm**, accepting the bundle cost deliberately and documented, the same way XQAP's own bundle-ceiling raises are always justified per feature.

## 2. Compression in practice

**Native `CompressionStream`** (gzip/deflate) calls the browser's built-in zlib — the same path used for HTTP `Content-Encoding: gzip` decompression ([Chrome for Developers blog](https://developer.chrome.com/blog/compression-streams-api/)). Its documented chunking behavior: **"data is always buffered across chunks — many small chunks may be passed in before any compressed data is produced"** ([WHATWG compression explainer](https://github.com/whatwg/compression/blob/main/explainer.md)), which is exactly XQAP's own hard-won lesson (feed 64KB windows, not per-row/per-token chunks) — the API's buffering doesn't crash on tiny chunks, but marshalling many tiny chunks across the stream boundary adds real per-call JS/stream overhead with no compression benefit, since the codec itself only flushes on its own internal window boundaries regardless of how you fed it. Benchmarked behavior is bimodal by payload size: **for data already fully in memory, `CompressionStream` is reported as *slower* than `fflate`** — "fflate tends to be faster even for files that are dozens of megabytes large," and markedly so under 1MB due to marshalling overhead — but **for genuinely streamed data (hundreds of MB), native usually runs 30% faster to 10% slower than fflate**, and Chrome's native compression throughput is cited at ~2× fflate's on the compress side ([fflate README](https://github.com/101arrowz/fflate/blob/master/README.md), [nickb.dev WASM compression benchmarks](https://nickb.dev/blog/wasm-compression-benchmarks-and-the-cost-of-missing-compression-apis/)). No level/dictionary control exists in the standard API — it's a fixed "browser's default" setting with **"no ability to control compression level, poor support for older browsers, no ZIP container"** ([DevTools Blog](https://www.devtools.tools/blog/gzip-compression-explained)).

**fflate** (8KB gzip'd, [github.com/101arrowz/fflate](https://github.com/101arrowz/fflate)) is the pure-JS alternative XQAP should actually consider adding for two specific gaps native `CompressionStream` can't fill: (1) **compression-level control** (native gives you none — if a workspace needs faster writes at the cost of a smaller ratio for interactive saves vs. maximum ratio for cold archival chunks, only fflate/pako offer that knob), and (2) **whole-buffer-in-memory workloads under ~1MB**, which is most of XQAP's own small shared files (permissions, manifests, indexes) — exactly where fflate wins outright per the benchmarks above. Given fflate is already this small, a pragmatic split is: native `CompressionStream` for the large streamed writes (population/dataset chunks, matching XQAP's existing pattern and its 64KB-window lesson) and fflate where level control or small-buffer latency matters — rather than replacing one with the other wholesale.

## 3. IndexedDB as a cache layer

**Blob vs ArrayBuffer**: IndexedDB values must be structured-cloneable (ArrayBuffer, Blob, File, typed arrays all qualify). The practical tradeoff: writing a `Blob` is what several IndexedDB implementations specifically optimize for large binary storage, but **converting an ArrayBuffer to a Blob requires an extra memory copy** — doubling peak memory during the write ([public-webapps mailing list discussion](https://lists.w3.org/Archives/Public/public-webapps/2013OctDec/0902.html), [Scanbot SDK storage comparison](https://scanbot.io/techblog/storage-wars-web-edition/)). For a chunk cache reading back for immediate use (not archival), storing the fetched/decompressed bytes directly as whatever typed-array form you already hold avoids that copy; store as `Blob` only when the write-once/read-rarely access pattern justifies the implementation's storage optimization.

**Relaxed durability**: modern browsers support a `durability: "relaxed"` transaction option — the `complete` event fires once the OS has been told to write, not once it's confirmed flushed to disk, trading a small power-loss-window risk for real throughput ([Speeding up IndexedDB reads and writes — Nolan Lawson](https://nolanlawson.com/2021/08/22/speeding-up-indexeddb-reads-and-writes/)). This is exactly the right tradeoff for a **disposable cache layer** (per both the proposal and the critique: IndexedDB here is never authoritative — the shared folder is), so `relaxed` should be the default for every write to this tier.

**Transaction batching**: the biggest documented win isn't `putAll()` (an abandoned Chrome effort — it didn't move the needle because the real bottleneck was waiting on individual success-event firing before a transaction could commit) but simply **batching many puts into one transaction** rather than one-transaction-per-record — 500–1000 records per transaction is the commonly cited sweet spot, and combined with relaxed durability gives the largest measured improvement ([Nolan Lawson, cited above](https://nolanlawson.com/2021/08/22/speeding-up-indexeddb-reads-and-writes/); [LeKoala: IndexedDB bulk inserts are slow](https://blog.lekoala.be/indexeddb-bulk-inserts-are-slow)). This is the same lesson XQAP already learned the hard way for the *filesystem* layer (per-file-open cost dominates on SMB → batch into NDJSON segments, 2,462× fewer ops) — apply it identically to IndexedDB: never write the chunk cache one chunk-record per transaction.

**Size budgets and eviction**: Chrome allows an origin up to **60% of total disk space**, with an **80% ceiling across all origins combined**; **incognito caps near 5%** ([BSWEN: browser storage quotas & eviction 2026](https://docs.bswen.com/blog/2026-04-07-browser-storage-quotas-eviction/)). Critically, **eviction is whole-origin, not partial** — if an origin is evicted, IndexedDB *and* Cache API *and* everything else for that origin goes together, and eviction under pressure follows **LRU across origins**, least-recently-used origin first ([MDN: Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). `navigator.storage.persist()` exempts an origin from that automatic eviction entirely when granted — Chromium auto-grants/denies based on site-engagement heuristics with no user prompt (Firefox does prompt). **Nothing in current published documentation specifically addresses `file://` origin behavior for `persist()`** — this is exactly the kind of thing the proposal's "Phase 0 environment proof" should test directly against the target deployment (a `file://`-opened, `showDirectoryPicker`-using app is already an edge case for storage-partitioning heuristics) rather than assume from docs written for `https://` origins. Given IndexedDB here is disposable-by-design (per both proposal docs), the practical posture is: budget the cache well under any quota tier (don't approach even the 5% incognito floor), treat eviction as a routine, tested event (not a failure mode), and don't build a persistence request into the correctness path — request it opportunistically as a UX nicety, verify empirically under `file://` in Phase 0.

## 4. Hashing — content-addressing multi-MB blobs

**`crypto.subtle.digest`**: confirmed **one-shot only** — MDN states explicitly: *"this API does not support streaming input: you must read the entire input into memory before passing it into the digest function"* ([MDN: SubtleCrypto.digest()](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest)). Supports SHA-1/256/384/512, all synchronous-computation-wrapped-in-a-Promise. For a multi-MB blob this means either (a) holding the whole blob in memory as one buffer before hashing — fine for anything well under V8's string/array-buffer ceilings but reintroduces exactly the memory-pressure shape XQAP already fixed for `bi.raw.json` (573MB) — or (b) a manual **Merkle/chunk-tree pattern**: hash fixed-size windows independently via repeated `digest()` calls, then hash the concatenation of those digests as a second pass. That gives you streamable memory behavior *and* a structure that's directly useful for content-addressed chunk stores (each chunk's hash is independently a `blobs/<hash>` filename per the proposal's own scheme, with a manifest hash-of-hashes over the whole object) — this is a better fit than trying to force `digest()` into pretend-streaming.

**hash-wasm** (already an XQAP dependency for Argon2id) supports genuine incremental hashing: `createSHA256()` exposes `init()/update()/digest()`, so a blob can be fed in bounded windows with no whole-buffer requirement ([hash-wasm GitHub](https://github.com/Daninet/hash-wasm)). It also ships **BLAKE3** at a **9KB gzip** bundle addition ([hash-wasm npm](https://www.npmjs.com/package/hash-wasm)). hash-wasm's own published benchmarks report SHA-256 throughput around **426 MB/s on 1MB inputs** (dropping to ~64 MB/s on tiny 32-byte inputs, reflecting per-call WASM overhead) — but these don't include a same-methodology comparison against native `crypto.subtle`, so a direct throughput bake-off should be run in Phase 0 rather than assumed from vendor numbers alone. Separately, BLAKE3 is widely cited as **4–10× faster than SHA-256** (one comparison puts BLAKE3 at 15.8 GB/s vs SHA-256's 0.65 GB/s in its home benchmark environment — not browser/WASM-measured) and is not exposed by any browser's native Web Crypto implementation at all, so a WASM library is mandatory to use it ([SHA-256 vs BLAKE3 comparison](https://ssojet.com/compare-hashing-algorithms/sha-256-vs-blake3); [Parsa's Blog: Faster JS Blake3](https://parsa.wtf/blake3/)).

**Recommendation**: use **hash-wasm's streaming SHA-256** for the blob store's content addresses, not `crypto.subtle.digest`. The deciding factor isn't raw throughput (native SHA-256 is almost certainly fine for anything under tens of MB either way) — it's that `digest()`'s one-shot contract forces a whole-blob-in-memory step that XQAP has already independently proven is a real production failure mode at scale (585MB file, worker OOM at 500k rows), while hash-wasm's `update()` loop composes cleanly with a chunked-read pipeline. Keep SHA-256, not BLAKE3, as the default: this is content addressing for a shared, multi-admin, Notepad/grep-inspectable folder (per the critique's greppability argument) where SHA-256 hex strings are a widely recognized, tooling-compatible format; BLAKE3's speed advantage doesn't matter at the volumes involved, and it adds a less-universally-recognized hash format for zero measured benefit here. If a future dataset tier genuinely bottlenecks on hashing throughput, BLAKE3 is a drop-in reconsideration, not a day-one requirement.

## 5. OPFS as a cache tier

OPFS's `SyncAccessHandle` is dramatically faster than IndexedDB for the same operation when available: one measured comparison shows a **100MB ArrayBuffer write at ~90ms via `SyncAccessHandle` vs. ~850ms via IndexedDB** — roughly 9× — attributed to OPFS bypassing structured-clone entirely for raw bytes and avoiding IndexedDB's async-event-loop overhead accumulating across many small operations ([PowerSync: State of SQLite Persistence on the Web](https://powersync.com/blog/sqlite-persistence-on-the-web)). Critically, this synchronous, high-performance API **is only available inside a Worker** — not the main thread, not even a `SharedWorker` — which fits the app's existing pattern of doing large-dataset work off-main-thread anyway ([webspecification.com OPFS](https://webspecification.com/blog/origin-private-file-system/); [renderlog.in OPFS explained](https://renderlog.in/blog/origin-private-file-system-opfs/)). Concurrency has practical limits: a SQLite-over-OPFS project reports reliably handling **8–10 concurrent workers** when lock contention is kept minimal ([PowerSync, cited above]).

**Is it worth adding above IndexedDB, given both are wiped by site-data clear?** For a chunk cache specifically, yes — conditionally. The site-data-clear risk is identical for both (neither changes the "shared folder is the only durable authority" model), so the decision is pure performance/complexity tradeoff, not a durability one. Given the ~9× write-speed gap and OPFS's structured-clone bypass, OPFS is the better fit *specifically* for the large binary chunk cache (dataset/blob bytes read repeatedly across a session) where write/read volume is high enough that structured-clone overhead is a real cost — while IndexedDB remains the right tool for smaller structured metadata (manifests, chunk indexes, cursor/subscription bookkeeping) where its query/index capabilities (which OPFS entirely lacks — it's a flat sync file API, no querying) matter more than raw throughput. Running both is not redundant complexity if scoped this way: OPFS as the *blob/chunk byte cache*, IndexedDB as the *metadata index over it* — matching the proposal's own "derived/cache" data-class split. If the team wants to avoid maintaining two cache backends, IndexedDB alone is still defensible for a v1, with OPFS as a documented, benchmarked upgrade path once real chunk-cache volume is measured (Phase 5 of the proposal's own scale-testing phase, not before).

## 6. Efficient directory-scale patterns

**Content-defined vs. fixed chunking**: fixed-size chunking is simple but suffers the "boundary-shift problem" — inserting even one byte near the start of a large object shifts every subsequent fixed boundary, destroying any chunk-level deduplication across versions of the same evolving dataset. Content-defined chunking (rolling-hash-determined cut points, so a local edit only perturbs the chunks touching it) fixes this at real CPU cost; **FastCDC** is the modern reference algorithm, reported ~5× faster than classic Rabin-based CDC and ~1.5× faster than Gear-based CDC while producing better-balanced chunk sizes ([FastCDC, USENIX ATC '16](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia)). For this app, the practical call is: **fixed-size chunking is almost certainly the right default.** XQAP's own datasets (monthly population imports) are not incrementally-edited large blobs being resynced — they're append/replace-whole-month artifacts (the "archive-and-supersede" pattern already established for `risk.raw.json`), so there's no ongoing edit-locality to exploit via CDC. Reach for content-defined chunking only if a future data class genuinely resembles "large binary object edited incrementally and resynced across machines" (e.g., attached documents with in-place revisions) — not for the population/sample/distribution datasets as currently shaped.

**Manifest design, informed by XQAP's own experience**: the lessons doc's most relevant precedent is the **NDJSON-segment-plus-checkpoint** design for distribution events (§9.3, v61.0/v79.0) — segments rotate at a fixed size into sealed, never-rewritten siblings, and a persisted fold checkpoint resumes from the last-read offset rather than re-reading everything. Applied to a dataset-chunk manifest: (1) the manifest itself should be a small, frequently-read, rarely-written JSON file (schema, partition map, row count, **per-chunk content hash**, compression, creation time — exactly the proposal's own §21 spec), kept well under the size where XQAP's own hash-verification cost-gating (§3.2: skip full-payload hashing above 512KB, since it costs ~5× the parse it's checking) would even bite; (2) chunks themselves are immutable, content-addressed, and never rewritten — sidestepping the entire CAS-loop/contention question the way XQAP's later-stage event segments do; (3) the **replacement-index lesson (v62.0)** — storing full row copies in a derived index produced a measured 385MB workspace from a 28MB import (~11×) until fixed to store field-picks/stubs — generalizes directly to manifest design: a chunk manifest must carry only chunk metadata (hashes, offsets, row counts), never inlined row data, or the same multiplicative-copies mistake recurs in the new app on day one.

**File-count budgets on SMB**: no single numeric ceiling is authoritatively published, but the consistent guidance across Samba/Azure Files documentation is that **very large flat directories (100,000+ entries) cause measurable degradation**, with a specifically-cited cause on Samba being case-insensitive name comparison against every existing entry on each new-file creation ([Samba: Handling Large Directories](https://stuff.mit.edu/afs/sipb/project/samba/OldFiles/swat/help/Samba3-HOWTO/largefile.html); [Azure Files SMB performance guide](https://learn.microsoft.com/en-us/azure/storage/files/smb-performance)). The two consistently repeated remedies are directly compatible with the proposal's own design: **shard directories** (the proposal's `sync/00..ff` two-hex-prefix sharding is exactly this pattern) rather than one flat directory of chunks/segments, and **spread I/O across multiple files rather than concentrating it on one** — which is the same "per-file-open-cost dominates over per-byte-cost" principle XQAP already measured directly (192,063 file operations for 8,000 events, 3–6 hours, before batching into segments cut that 2,462×). The practical rule to carry forward: budget any single directory in the tens-of-thousands of entries at most, shard by a hash prefix well before that, and treat "spread across sharded directories, batch within each" as the same lever XQAP already pulled once at the event-log layer — apply it from day one at the chunk-store layer instead of rediscovering it after a production slowdown.
