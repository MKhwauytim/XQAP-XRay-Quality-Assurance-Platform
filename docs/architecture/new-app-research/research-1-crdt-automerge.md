# CRDTs for a Backend-less Shared-Folder App: Verifying the Automerge Bet

Research scope: verify/refute the proposal's Automerge-Repo recommendation against primary sources (automerge.org docs, automerge/automerge-repo GitHub, Yjs docs). Findings below are organized by the six assigned questions. Where documentation was silent or ambiguous, that is stated explicitly rather than inferred.

## 1. Storage adapter model — is a File System Access API adapter feasible?

Automerge-Repo's `StorageAdapter` is a genuinely narrow interface — five async methods operating on a key/value model where keys are `string[]` ("StorageKey") and values are `Uint8Array` blobs:

```
load(key: StorageKey): Promise<Uint8Array | undefined>
save(key: StorageKey, data: Uint8Array): Promise<void>
remove(key: StorageKey): Promise<void>
loadRange(keyPrefix: StorageKey): Promise<Chunk[]>
removeRange(keyPrefix: StorageKey): Promise<void>
```
(https://automerge.org/automerge-repo/classes/_automerge_automerge-repo.StorageAdapter.html)

Keys are hierarchical prefixes: `[documentId]` matches everything for a doc, `[documentId, "incremental"]` matches only its incremental changes, `[documentId, "snapshot", headsHash]` a specific compacted snapshot (https://automerge.org/docs/reference/repositories/storage/). The docs state directly: "StorageAdapter is designed to be easy to implement. It should be straightforward to build on top of any key/value store which supports range queries" (same page) — and that it's "designed to be safe to use concurrently... multiple Repos talking to the same storage." Two reference adapters ship: `@automerge/automerge-repo-storage-indexeddb` (browser) and `@automerge/automerge-repo-storage-nodefs` (`packages/automerge-repo-storage-nodefs` in https://github.com/automerge/automerge-repo), which "stores its data in a directory on the local filesystem" and is documented as "safe for multiple processes to use the same data directory."

**Feasibility for File System Access API / SMB:** A `[docId, "snapshot"/"incremental", chunkId]` key naturally maps to a directory-per-document with one file per chunk (`sync/<shard>/<docId>/incremental/<hash>.bin`), which is exactly the "immutable, uniquely-named file" write shape XQAP's own lessons converged on independently. This is feasible in principle — nothing in the interface requires true atomic rename, live connections, or locking primitives the File System Access API lacks. `loadRange`/`removeRange` require directory enumeration (`getDirectoryHandle` + async iteration), which the API supports but which is exactly the SMB-latency-sensitive operation XQAP's lessons flag repeatedly (directory listing lag, `NotFoundError` retry ladders). **Unverifiable from docs:** no existing FSA-API adapter was found in searches — Automerge's own ecosystem list covers IndexedDB and Node fs only; a shared-folder adapter would be wholly new code, not a drop-in.

**Sync without a live peer connection — this is the key finding.** Automerge-Repo's peer-to-peer sync protocol (`generateSyncMessage`/`receiveSyncMessage`) is explicitly session-based: "A sync message is always specific to two particular peers, and you need a separate syncState for each connected peer" (https://automerge.org/automerge/api-docs/js/functions/generateSyncMessage.html). That protocol is not the mechanism for file-based exchange. The mechanism that *does* work over files alone is the storage layer itself, and the docs describe it directly: "Multiple tabs or processes can synchronize through shared storage alone. When a new tab loads, it loads all the changes it can find in storage and merges them" using Automerge's CRDT merge (https://automerge.org/docs/reference/under-the-hood/storage/). So: **yes, change exchange can run over files alone** — but via the storage-adapter's load/loadRange, not via the generateSyncMessage/receiveSyncMessage sync protocol. `saveIncremental()`/`loadIncremental()` and `getChanges()`/`applyChanges()` are the underlying primitives for this (Automerge is explicitly "an in-memory data structure library that does not perform any I/O... disk persistence needs to happen in a separate layer outside of Automerge," per the same source). This validates the proposal's core architectural claim (§10, SharedFolderSyncAdapter) but confirms it is a **new-built component**, not a documented off-the-shelf capability — the proposal's critique is correct to flag this as "the same kind of component as XQAP's most bug-prone module."

## 2. Real bundle cost

- **@automerge/automerge (WASM):** "The WASM compilation results in a larger bundle of approximately 320 kB, with a one-time initialization cost of around 50ms" (search-aggregated from https://automerge.org/docs/reference/library-initialization/ and corroborated independently at ~320 KB gzipped by https://www.pkgpulse.com/guides/yjs-vs-automerge-vs-loro-crdt-libraries-2026). An older concrete data point from the crdt-benchmarks repo: Automerge 0.14.1 was 259,763 bytes raw / 61,478 bytes gzipped (https://github.com/dmonad/crdt-benchmarks) — current versions are larger per the ~320 KB gzip figure above, consistent with feature growth since 0.14.
- **Base64 embedding:** documented directly — `automergeWasmBase64` from `@automerge/automerge/automerge.wasm.base64.js` fed to `initializeBase64Wasm()`, described as "an ultimate fallback option, though it will be somewhat slower and larger than a binary object" (https://automerge.org/docs/reference/library-initialization/); base64 inherently adds ~33% over raw bytes, which for this app's `file://`-raw-bytes-matter constraint (per CLAUDE.md: "raw bytes are what the user actually waits on") converts a ~320 KB gzipped WASM into meaningfully more raw bytes once base64-inlined into a single HTML file (gzip does not apply once base64-encoded and inlined as a JS string — this is compounding, not cancelling, the raw-byte cost).
- **Current versions:** `@automerge/automerge` latest is 3.2.6 (April 2026), with 3.0 specifically noted for cutting memory usage "over 10x" versus 2.x (https://automerge.org/blog/automerge-3/). `automerge-repo` ships in parallel alpha/stable lines (v2.5–2.6 series seen in docs URLs).
- **Yjs comparison:** pure JS, no WASM. Bundle size ~18 KB gzipped per pkgpulse's 2026 comparison, corroborated by an older but concrete crdt-benchmarks measurement: Yjs 13.3.0 = 65,923 bytes raw / 19,377 bytes gzipped (https://github.com/dmonad/crdt-benchmarks) — roughly **17× smaller gzipped than Automerge**, and with no WASM init cost, no async-WebAssembly bundler configuration (Vite/Webpack plugins Automerge requires per its own init docs), and no base64 inflation tax. This is a substantial, directly relevant cost difference for a bundle-size-disciplined app (XQAP's own CLAUDE.md treats raw bytes as a hard release gate).
- **y-indexeddb**: confirmed to exist as a browser IndexedDB provider for Yjs (https://github.com/yjs/y-indexeddb, https://docs.yjs.dev/ecosystem/database-provider/y-indexeddb) — no filesystem/shared-folder adapter was found for Yjs either; this is symmetric with Automerge's situation (both would need custom-built file adapters).
- **Yjs updates as files:** documented and idempotent. `Y.encodeStateAsUpdate(doc)` produces a `Uint8Array` "single update message that can be applied on the remote document," and `Y.mergeUpdates()` "merges several document updates into a single document update while removing duplicate information" (https://docs.yjs.dev/api/document-updates). This is functionally the same file-exchange shape Automerge's storage-adapter model offers, at roughly 1/17th the code weight.

## 3. History/compaction story

**Automerge:** documents "hold their entire change histories... a large amount of data but in practice very repetitive and amenable to compression" (search-aggregated from https://automerge.org/automerge-binary-format-spec/ and related pages). `save()` performs compaction — serializing current state without full history — and "documents have to be regularly compacted (losslessly) otherwise they take up a lot of storage space." A real, documented downside: **"the downsides of compacting the history of a document include not being able to synchronize that compacted document with another document that doesn't have a common ancestor"** — i.e., compaction is not free of coordination risk.

The **concurrent-compaction-without-a-coordinator problem is explicitly analyzed** in a third-party deep-dive (https://patternist.xyz/posts/concurrent-compaction-in-automerge-repo/): naive compaction (overwrite one fixed "compressed" key) causes silent data loss when two writers compact concurrently — "if instance 2 finished first and then instance 1, the compressed log on disk will be missing event 5." The documented mitigation is **content-addressed compaction**: write to `compressed/<hash>` (never overwrite), read all `compressed/*` plus any newer individual changes, and let stale entries accumulate as harmless redundant reads rather than being deleted destructively — "we never lose data and we don't have to coordinate between processes." The safety net is per-process tracking of "every change it has loaded from storage" and only deleting those specific changes on compaction, so a slow/stale client's compaction cannot delete a change it never saw. This is a real, load-bearing answer to "what happens when a stale client holds pre-compaction history" — it degrades to redundant reads and storage bloat, not data loss, **provided the adapter implementation follows this pattern**; a naive shared-folder adapter that didn't would reintroduce exactly the race this design avoids.

**Yjs:** growth is controlled via garbage-collected tombstones rather than snapshot/incremental chunking. "Yjs can garbage collect tombstones if it doesn't care about the order of the structs anymore (e.g. if the parent was deleted)... a deleted object's content is replaced with a GC object, which is a very lightweight structure that only stores the length of removed content" (https://github.com/yjs/yjs/blob/main/INTERNALS.md, community discussion at https://discuss.yjs.dev/t/are-gcd-documents-larger-than-non-gc-docs/1840). A specific, honest counter-finding from that same community thread: **"the vast majority of GC'd docs are 10-30% larger"** than non-GC'd docs in practice, despite GC being the size-control mechanism — a real nuance worth weighing. `doc.gc = false` disables collection to preserve full history (needed for undo/time-travel), and is documented as "pretty awful for performance, disk space, and network throughput" — Yjs's history/no-history tradeoff is a single boolean, structurally simpler than Automerge's snapshot/incremental chunk model, but with less of an audit-trail story out of the box.

## 4. Binary opacity — can an admin diagnose a corrupted store without the app?

**No CLI/dump tooling was found for either library** in this research — searches for "automerge cli inspect dump" and similar returned nothing on-topic; the binary-format spec page (https://automerge.org/automerge-binary-format-spec/) documents the format precisely enough that a bespoke inspector *could* be written, but states no existing tool. This directly confirms the critique's concern #3 (opacity vs. XQAP's Notepad/grep-based incident forensics): both Automerge and Yjs files are binary; neither ships an admin-facing inspection utility comparable to `cat`/`grep` on JSON. Building one would be new project work, not reuse.

## 5. Real-world precedent: CRDT sync over a plain shared filesystem, no server

**Found: one documented proof-of-concept, explicitly not production.** Peter Sobot / tonsky-style research (https://tonsky.me/blog/crdt-filesync/, demo at github.com/tonsky/crdt-filesync) uses Automerge for text-edit merging over a Dropbox/Syncthing-like folder, described by its own author as "a very simple proof-of-concept," warning that "conflicting file names are different between providers" and "some providers might not handle conflicts at all," and concluding it's viable mainly for eventual-consistency use cases like photo sync — not offered as a production reference. A second, independent project (`3timeslazy/crdt-over-fs`) surfaced in search results is described as experimental/unfinished. **No production deployment of Automerge or Yjs over a plain SMB/UNC share with no server component was found.** This is a meaningful gap: the proposal's central bet has essentially zero production precedent under this exact deployment shape, and the one authoritative-sounding commentary found in search (https://powersync.com/blog/why-cinapse-moved-away-from-crdts-for-sync) states plainly that "in production the hard parts are not the merge function but persistence, transport, schema migration, access control, and observability" — i.e., a vendor with real CRDT production experience explicitly warns against treating the merge algorithm as the hard part, which is exactly where a from-scratch `SharedFolderSyncAdapter` would spend its effort.

## 6. Failure modes: corruption, duplication, out-of-order application

**Automerge — corruption:** The binary-format spec is strict and unforgiving: 4-byte magic-number check, then a SHA-256 checksum per chunk, and **"implementations MUST abort reading if the checksum does not match"** — there is no documented partial-recovery path at the wire-format level (https://automerge.org/automerge-binary-format-spec/). The Rust reference implementation does offer a softer path at the API level: `load()` has an "on_error" mode for "what to do if the document is only partially loaded... if some prefix of data contains valid data," plus a documented "best-effort rescue for documents which fail strict loading" that recovers a hydrated value but **does not preserve the original change graph** (https://docs.rs/automerge/latest/automerge/struct.Automerge.html) — i.e., recovery from a truncated file is possible but lossy of history. A truncated/corrupted *chunk* file on a shared SMB folder (mid-write torn file, exactly XQAP's own documented `.tmp`/`.bak` motivation) would hit the "abort" path unless the adapter itself does stage→verify→commit before ever exposing the chunk to Automerge — meaning **XQAP's safeWrite discipline is still required underneath any Automerge storage adapter**, not replaced by it.

**Automerge — duplicate application:** Explicitly documented as safe: **"This is idempotent in the sense that if a change has already been applied it will be ignored"** — stated for both `apply_changes()` and `load_incremental()` (https://docs.rs/automerge/latest/automerge/struct.Automerge.html).

**Automerge — out-of-order application:** No single doc page states this as a blanket guarantee, but two independent signals support it: the changelog for a recent point release (3.2.5) specifically lists **"improved the performance of loading many changes out of order in loadIncremental"** (search-aggregated from https://automerge.org/blog/automerge-3/-adjacent changelog coverage) — implying out-of-order loading is an intended, exercised code path, not merely accidental. Countervailing evidence: **closed issue #870**, "Documents are not always eventually consistent: Synchronisation fails in specific scenarios" (https://github.com/automerge/automerge/issues/870), documented a real case where two documents that each generated a null sync message (i.e., both believed themselves synced) nonetheless held different final values after concurrent edits through an intermediate state — a genuine historical violation of the "any order → same result" promise. It is closed/fixed, but its existence is a fact worth weighing: Automerge's convergence guarantee has had at least one documented, real counterexample, not merely a theoretical concern.

**Yjs:** the guarantee is stated more categorically and simply: **"Document updates are commutative, associative, and idempotent... you can apply them in any order and multiple times"** (https://docs.yjs.dev/api/document-updates). No equivalent counter-example issue was located in this research window (absence of evidence, not evidence of absence — a deeper GitHub issue-tracker search was out of scope here). Combined with `Y.mergeUpdates()` deduplicating overlapping updates, Yjs's documented story for "duplicated, out-of-order file" scenarios is at least as strong as Automerge's, arguably stated with less hedging, and comes at a fraction of the bundle-size and tooling-complexity cost.

---

## Bottom line for the proposal's bet

The proposal's core mechanical claim — that Automerge-Repo's storage-adapter model can, in principle, support file-based sync with no live peer connection, via `load`/`loadRange`/incremental save-load rather than the peer-to-peer `generateSyncMessage` protocol — **is verified**, not refuted, by primary sources. The concurrent-compaction race is a real, previously-solved problem with a documented content-addressed-key mitigation, not a hand-wave. Idempotent duplicate-application is documented for both libraries.

But several of the critique's concerns are independently corroborated by this research and deserve weight in a final decision: **(a)** no FSA-API/SMB adapter exists for either library — this is 100% new, unproven code regardless of which CRDT is chosen; **(b)** no production precedent exists for CRDT-over-plain-shared-filesystem with zero server component — the only public example is an explicit proof-of-concept; **(c)** Automerge's bundle cost (~320 KB gzip WASM, inflated further by base64 embedding) is roughly 17× Yjs's (~18 KB, pure JS, no WASM tooling burden) for a project whose own sibling app (XQAP) treats raw bundle bytes as a hard release gate; **(d)** binary opacity is real for both — no inspection tooling exists for either format, a genuine loss versus XQAP's grep-able JSON; **(e)** Automerge's own convergence guarantee has at least one documented historical counterexample (issue #870, closed) worth factoring into risk tolerance for an audit-grade system. None of this is disqualifying, but it reframes "Automerge as settled architecture" into "Automerge (or Yjs) as an unproven bet requiring the bake-off the critique recommends" — and on pure bundle-cost and documentation-clarity grounds surfaced here, Yjs is the stronger candidate to bake off against a home-grown append-only log, not merely a fallback to Automerge.
