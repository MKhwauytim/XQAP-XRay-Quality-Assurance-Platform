# Research Slice: Prior Art for File-Based Multi-User Sync & No-Backend Security Model

*Compiled 2026-08-25 for the new static-HTML/shared-folder app proposal. Six questions, dense answers, citations inline. Flags where I could not verify a claim.*

## 1. Prior art: filesystem-as-transport for multi-user sync, no server

**Obsidian Sync** (proprietary, not filesystem-only but instructive as the closest real "notes app on a shared plain-file store" product): for markdown files it runs a **three-way merge via Google's diff-match-patch algorithm**, auto-combining edits from multiple devices by default; as of 1.9.7 users can instead opt into "create conflict file" mode, which preserves the remote version live and drops a separate file with the loser for manual reconciliation. For every *non*-text file type (canvases, binaries) it falls back to plain **last-modified-wins** — i.e. Obsidian itself only attempts real merging where content is diffable text, and accepts LWW everywhere else. [Synchronization and Conflict Resolution (DeepWiki)](https://deepwiki.com/obsidianmd/obsidian-help/2.3-synchronization-and-conflict-resolution)

**Syncthing** is the purer filesystem-as-transport case: no merge logic at all. On a genuine conflicting edit it renames the *losing* copy to `<name>.sync-conflict-<date>-<time>-<deviceID>.<ext>` and lets both files propagate normally afterward. The loser is picked by newest-mtime-wins, and ties are broken by comparing the first 63 bits of device ID — a deterministic, clock-adjacent tiebreak with no server. Syncthing explicitly does **not** merge or offer a resolution UI; that job is delegated to third-party scripts that git-three-way-merge the conflict file against the original. [Understanding Synchronization](https://docs.syncthing.net/users/syncing.html), [Automatically resolve Syncthing conflicts using a three-way merge](https://www.rafa.ee/articles/resolve-syncthing-conflicts-using-three-way-merge/)

**KeePass** is the closest 20-year analog to this project's exact shape (shared mutable file on SMB, no server, multiple concurrent desktop clients). Its model: a `.lock` file signals "someone has this open for writing," and — notably — **it self-expires**: if not refreshed within 10 minutes it's assumed stale and ignored, which is a lease pattern, not a hard mutex. Real merge safety comes from KeePass 2.x's **built-in database synchronization**: each entry carries its own last-modified timestamp, and merging two divergent copies is an object-level (not file-level) three-way reconciliation of entries/groups, so two people editing *different* entries never lose either edit; two edits to the *same* entry fall back to newest-wins. The documented safe usage discipline is even *not* "everyone writes the shared copy directly" — the recommended pattern is a synced local copy per user with periodic trigger-based sync into the shared master. [Multiple Users – KeePass](https://keepass.info/help/base/multiuser.html), [Synchronization – KeePass](https://keepass.info/help/v2/sync.html)

**Git** as a design pattern (not proposed as the transport itself, but its object model is the cleanest existing proof that "immutable content-addressed objects + a small set of mutable named refs" scales as a sync primitive with zero server coordination): every object is addressed by the hash of its own content, so two independent writers can never collide on a filename — they either produce byte-identical objects (free convergence) or genuinely different ones (irreconcilable, surfaced explicitly as a merge). Only the small set of *refs* (branches/tags) are truly mutable pointers, and updating a ref is the one place where a real conflict-resolution step is required — which is exactly the "immutable objects + narrow single/CAS-writer pointer" shape XQAP and the proposal both converge on independently. [Git's database internals I: packed object store (GitHub Blog)](https://github.blog/open-source/git/gits-database-internals-i-packed-object-store/), [Understanding Git Internals (Ken Muse)](https://www.kenmuse.com/blog/understanding-how-git-stores-data/)

**Fossil** is worth naming as the other end of the spectrum: it deliberately does *not* use loose files at all — an entire repository (including all history) is one SQLite database file, and multi-site sync happens over an HTTP push/pull/autosync protocol, not raw shared-filesystem access. It's the "single self-contained file, but requires a network sync protocol rather than a shared folder" alternative — useful as a contrast, not directly transferable, since this app's constraint (no server, folder-only) rules out its sync transport. [Fossil Sync Protocol](https://fossil-scm.org/home/doc/trunk/www/sync.wiki)

**Local-first (Ink & Switch)**: the foundational essay frames CRDTs as the technology that lets independent replicas "make changes without coordinating, with a mathematical guarantee of convergence when updates are eventually exchanged" — this is the theoretical backbone the proposal's Automerge bet leans on. It does **not**, however, specifically address plain-filesystem-as-transport (that's a deployment detail below the essay's abstraction level); Ink & Switch's own reference implementations use their own sync-server or peer network, not a shared SMB folder. [Local-first software (Ink & Switch)](https://www.inkandswitch.com/essay/local-first/)

**Extracted per-system takeaways, mapped to the proposal's own four sub-questions:**
- *Conflict handling*: real systems split into "diffable text → attempt real merge" (Obsidian) vs. "everything else → last-write-wins + a visible loser artifact" (Syncthing, Obsidian-non-text). None of them silently discard a loser — they always leave a trace file. This directly supports the proposal's own choice to model business-decision conflicts (approve/reject) as explicit append-only events rather than trusting CRDT merge to be semantically correct — see the critique's §12 point, which this prior art corroborates rather than merely asserts.
- *Torn-write safety*: none of the three surfaced an atomic-rename primitive as their safety net (the File System Access API doesn't have one either, which the proposal and XQAP both already work around via stage→verify→commit). KeePass's lease-file self-expiry is the one directly transferable *lock* pattern (see §6 below).
- *Discovery/polling*: Syncthing and Obsidian both rely on their own long-running sync daemon/service with a real network protocol — neither is a clean analog for "a static HTML page polls a shared folder," which is closer to what §14 of the proposal already proposes from scratch.
- *Compaction*: none of the three publish a detailed public compaction algorithm; this looks like a genuinely under-documented area across prior art, not just this proposal — flagging as **unverified/thin** rather than solved elsewhere.

## 2. Event sourcing in the browser: patterns, idempotency, versioning, checkpoint pitfalls

The general literature (Azure Architecture Center, Marten, event-driven.io) converges on a small set of patterns that XQAP already independently discovered and that the new app should adopt as named, not reinvented:

- **Idempotent event application** is the load-bearing property: "event sourcing requires idempotent consumers since events may be replayed," typically via an idempotency key attached to the event so a re-applied event is a no-op rather than a double-effect. [Event Sourcing Patterns with Kafka](https://www.conduktor.io/glossary/event-sourcing-patterns-with-kafka) This maps directly onto XQAP's fold, which already keys on `eventId` and rejects re-application of terminal-state events — worth carrying forward explicitly as "every event carries a globally unique id, and the fold is defined as a set-fold over ids, not a sequence-fold," which is also what makes it safe for two clients that discovered events in a different order (XQAP's "commutative digest over folded event IDs," §3 of the lessons doc) to agree.
- **Schema versioning via upcasting**: "registering transformation functions that convert older event schemas to current schema during deserialization, which can be chained so application code only handles the latest version." [How to (not) do the events versioning? – Event-Driven.io](https://event-driven.io/en/how_to_do_event_versioning/) This generalizes XQAP's `eventSchemaVersion`/`samplingAlgorithmVersion` stamps into a proper upcaster chain instead of ad hoc version-branching inside the fold — a real improvement to propose, since XQAP's fold switch statement mixing multiple event-type-version concerns was flagged in its own lessons doc as its single most bug-prone piece.
- **Checkpoint/snapshot pitfalls** are a documented, recurring production failure class, not a hypothetical: one cited war story describes "a bug corrupted projections, and replaying 2 weeks of events took 18 hours and missed SLAs" — i.e. exactly XQAP's "poisoned checkpoint" failure shape (a bad derived cache treated as trustworthy because its revision number matched). [When Event Sourcing Fails: War Stories from Production](https://dev.to/alex_aslam/when-event-sourcing-fails-war-stories-from-production-1nk2) The generic industry mitigation is the same one XQAP shipped (`DERIVE_VERSION` gate, §9.1 v41.39 in the lessons doc): **never trust a cache/snapshot by revision number alone — gate it by a fold-algorithm version too**, and prefer "rebuild from source on any doubt" over "trust the snapshot unless proven wrong."
- No mainstream JS library specifically targets "event sourcing over a shared filesystem, no server" — the closest published shape is generic CQRS/event-sourcing guidance (Azure, AWS Prescriptive Guidance, Marten) written for server-side event stores (Kafka, Postgres, Cosmos DB), none of which face XQAP's actual constraint (torn writes, SMB latency, no atomic append). **This is a genuine gap**: the browser-plus-SMB-plus-no-backend event-sourcing problem is not solved anywhere in public prior art; XQAP's own append-only-event-file + rebuildable-fold design is, as far as this search surfaced, closer to novel infrastructure than "borrowed pattern." Flag this honestly rather than implying an off-the-shelf answer exists. [Event Sourcing Pattern – Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)

## 3. Tamper-evidence without a server: signed events vs. hash chains

**Is client-side ECDSA-P256 signing a practical upgrade over XQAP's unsigned djb2 hash chain?** Yes, and there is real prior art for exactly this shape: a from-scratch tamper-evident log built with "vanilla JavaScript and the Web Crypto API with no npm packages, no build tools, or external dependencies," combining per-record signing with hash chaining. [Building a Tamper-Evident Audit Log with SHA-256 Hash Chains](https://dev.to/veritaschain/building-a-tamper-evident-audit-log-with-sha-256-hash-chains-zero-dependencies-h0b) The Web Crypto API's `crypto.subtle` natively supports ECDSA generate/sign/verify in-browser with no dependency, and — critically — verification fails if a single byte of the signed record changes, giving a real cryptographic (not merely "recomputable by anyone with a text editor," per XQAP's own honest caveat about djb2) tamper-evidence guarantee. [Understanding ECDSA Signatures with the Web Crypto API](https://dev.to/ktaka/understanding-ecdsa-signatures-with-the-web-crypto-api-4j15)

The rigorous version of this pattern is **Certificate Transparency (RFC 6962)**: an append-only Merkle tree of signed entries, where the log periodically signs the tree root (a "Signed Tree Head") and third parties can request compact inclusion/consistency proofs without downloading the whole log. [RFC 6962 – Certificate Transparency](https://www.rfc-editor.org/rfc/rfc6962.html) Sigstore's Rekor service is a modern, actively maintained implementation of the same idea for software-supply-chain signatures, and is a good concrete reference to study for "how do you structure a Merkle-tree transparency log with periodic signed roots" without inventing the format from scratch. [Sigstore Security Model](https://docs.sigstore.dev/about/security/) **The honest caveat that applies to all of these**: CT-style transparency logs assume a semi-trusted log operator distinct from the party producing entries, specifically so a compromised writer can't rewrite its own history undetected by others. In this app's per-writer-segment-file model, each user *is* their own writer and (per XQAP's advisory-only trust model) has filesystem-level write access to their own segment — so ECDSA signing here defends against a **different, narrower** threat than CT does: it proves "this specific event was authored by the holder of this private key at this content," which lets *other* users' clients detect if someone edited a peer's file by hand (a real, cheap, valuable property), but it cannot stop the key-holder from signing something false, nor can it stop someone with OS-level write access from deleting the file outright (SMB access is what actually gates that, per §4). Frame it in the new app's docs exactly this way — "tamper-evident against a different-user editor, not tamper-proof against the file's own legitimate writer" — to avoid the same kind of overclaim XQAP's own docs deliberately avoided for its hash chain.

**The key-storage problem is the real blocker, and I could not find satisfying browser-specific prior art.** General cryptocurrency-wallet literature (private-key-encrypted-by-passphrase-via-PBKDF2, with a separate recovery key as backup) is the closest analog, but it's written for a very different threat model (self-custody of funds) and doesn't map cleanly onto "an office worker on a shared Windows machine needs to keep signing audit events across a browser-data wipe." [Private key encryption and recovery in blockchain literature] No public writeup surfaced describing exactly this app's scenario: **a non-extractable WebCrypto keypair generated in-browser, its public key registered in the shared workspace, and a re-enrollment flow when local storage (and therefore the private key) is wiped.** Practical implications worth stating plainly, since this is where the design actually needs original thought rather than borrowed pattern:
  - A `CryptoKey` marked non-extractable in IndexedDB is exactly as durable as XQAP already knows browser storage to be — i.e. **not durable**; an admin's "clear site data" wipes it just as it wipes the workspace-handle cache the proposal already accounts for.
  - The two realistic options are (a) **passphrase-derived key** (PBKDF2/Argon2id over a user passphrase → deterministic keypair, so the user can always regenerate the identical key by re-entering the passphrase) — recoverable but reintroduces a password-strength/offline-crackability concern for every signing key, mirroring the exact risk XQAP already accepts for the bootstrap admin hash; or (b) **re-enrollment**: on wipe, generate a *fresh* keypair and publish a new public-key registration event, with all *prior* events still verifiable under the *old* key (append-only key history, not replacement) so past signatures don't retroactively become "unverifiable." (b) is more consistent with the "advisory, not a strong security boundary" posture this app already inherits from XQAP, and avoids inventing passphrase-strength policy for a second credential. **Recommend (b) and flag that this specific design has no direct precedent found in this research pass** — it should go through the same kind of deliberate, documented risk-acceptance XQAP gave its own trust boundary (`SECURITY_MODEL.md`), not be treated as solved by analogy.

## 4. Auth without a backend

**Argon2id via hash-wasm remains correctly chosen.** Current OWASP guidance is unchanged from what XQAP already implements: baseline **m=19 MiB, t=2, p=1** (~100ms verification on a modern core), with a higher-memory alternative (m≈46 MiB, t=1, p=1) for servers with memory to spare. [Password Storage Cheat Sheet – OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) XQAP's parameters match the baseline exactly — no change indicated. One nuance worth carrying into the new app's docs: the "spend less CPU, more memory" alternative profile only makes sense on hardware with real memory headroom, which is a poor fit for a browser Argon2id call running on an arbitrary office desktop (the actual "server" here) — so the low-memory baseline, not the high-memory alternative, remains the right choice for this deployment shape specifically, and that reasoning should be written down rather than left implicit.

**Passkeys/WebAuthn under `file://`: confirmed infeasible.** WebAuthn is scoped to secure contexts and requires an HTTPS/TLS origin; there is no path to using it from a `file://`-opened static HTML page. [Secure Web Authentication – Passkeys & WebAuthn API (Infinum)](https://infinum.com/blog/secure-web-authentication-passkeys-webauthn/) This closes the door definitively — don't spend design time on it, and say so explicitly in the new app's architecture doc the way XQAP's own doc explicitly documents *why* it can't use a real backend, so a future reader doesn't waste time re-investigating. Note that the app being served over an internal HTTP(S) origin instead of opened via `file://` would flip this, so if the deployment model ever moves off raw `file://` (e.g. served statically from an internal IIS/nginx box, which the CLAUDE.md notes is XQAP's *own* now-standard alternative to a desktop shortcut) WebAuthn becomes newly viable — worth flagging as a concrete reason to prefer HTTP-served deployment over `file://` if the org can support it at all.

**Windows ACL layering — real, but coarse.** Confirmed: Windows enforces **two independent, cooperating permission layers** — SMB share-level permissions (who can connect at all) and NTFS permissions (what an authenticated user can do to a specific file/folder) — and the *effective* access is always the intersection (most restrictive of the two). [Windows File Share Permissions Best Practices](https://en.ittrip.xyz/windows-server/share-vs-ntfs-acls) NTFS ACLs genuinely can be set per-directory (root, subdirectory, or individual file), which does make a `public-read/`, `user-write/`, `admin-write/` layout (as §38 of the proposal suggests) **operationally realistic in principle** — this is standard, well-supported Windows Server administration, not exotic. [Configure SMB Storage Permissions](https://learn.microsoft.com/en-us/fslogix/how-to-configure-storage-permissions)

The caveat that matters for this app specifically: NTFS ACLs are managed by whoever administers the file server (IT/domain admins), **entirely outside the application's control** — the app cannot provision or verify these permissions itself, it can only assume they've been set correctly by an org's IT team and degrade gracefully (typed permission-denied errors, per XQAP's own `NoModificationAllowedError`-vs-permission-loss classification lesson) when they haven't. This means "per-user write-restricted subdirectories on one share" is realistic **only where an organization already runs disciplined AD-group-based NTFS ACL management** — plausible for a hospital/regulated-industry IT department (XQAP's actual deployment context), but it is an operational precondition the app must document as a *deployment requirement*, not something the client-side code can enforce or verify. The proposal's own framing — "ACLs are coarse boundaries; app model is workflow-level authorization; don't make workflows constantly modify Windows permissions" — is exactly right and matches this finding: treat ACLs as a slow-changing, IT-owned perimeter, and keep all fine-grained (per-record, per-role) authorization in the app's own advisory layer, never expect the two to be kept in lockstep.

## 5. Sync-engine patterns worth stealing: version vectors, Lamport timestamps, Merkle discovery

**Version vectors formalize exactly what XQAP already does informally.** The distinction confirmed in the literature: a *vector clock* tracks general event causality across a whole system, while a **version vector** is the narrower, replication-specific case — "each node increments its counter in the vector solely when it updates the data item, and the version vector accompanies the data item as it is replicated across nodes." [Understanding Version Vectors in Distributed Systems](https://www.educative.io/courses/distributed-systems-practitioners/version-vectors) A **per-writer monotonic counter, where each writer owns its own segment file**, is precisely a degenerate/simplified version vector: the vector's dimensionality collapses to "one entry per writer," and because writers never touch each other's counters, there is no merge step for the counter itself — only for reconciling the union of segments at read time. This is worth stating explicitly in the new app's architecture doc as "XQAP's per-writer-file pattern, and this app's proposed per-writer bounded segments, **are** a version-vector scheme, just with the vector implicit in the set of filenames rather than serialized as a data structure" — naming it correctly makes it easier to reason about (e.g. "has segment writer X caught up to what I last saw" becomes a direct version-vector comparison) and easier to explain to a future maintainer. **Dotted Version Vectors** (Preguiça et al.) is the refined form worth citing if per-writer counters ever need to survive a writer being retired/replaced without leaving a permanent phantom dimension in the vector. [Dotted Version Vectors: Logical Clocks for Optimistic Replication](https://arxiv.org/pdf/1011.5808)

**Lamport timestamps solve a different, narrower problem than clock-based ordering**, and the literature confirms they should be adopted specifically where the app needs *some* deterministic total order across writers without trusting wall-clock time: "the happened-before relation is defined without using physical clocks... Lamport clocks order concurrent events arbitrarily (using IDs), which might not match real-world logic." [Distributed systems: Logical Time Explained (Medium)](https://medium.com/@armironenko/distributed-systems-logical-time-explained-5f97949f180f) This directly validates the critique's flag #3 (cross-machine clock skew) — a Lamport-style logical counter, combined with a stable per-writer tiebreak (the writer's own segment/session ID, alphabetically or hash-ordered — exactly XQAP's own fix for locale-dependent tie-breaks in Hamilton apportionment, §9.1 v41.37 of the lessons doc) gives a **reproducible total order for display/audit purposes** without ever asserting it reflects true real-time simultaneity. The right framing for this app: use wall-clock timestamps for *display* ("assigned at 14:02"), but never for *correctness-bearing* ordering decisions (which segment/event "wins") — use a Lamport counter or the append order within a writer's own segment for that instead.

**Merkle-tree/hash-list discovery is genuine, well-proven prior art for "what changed cheaply."** The general pattern: build a tree of hashes over the data set, compare root hashes first, and only walk into subtrees whose hash differs — "instead of comparing potentially gigabytes of data, these systems can compare root hashes and then drill down to find discrepancies and sync only the files that have changed." [Delta Sync & Merkle Trees – System Design Sandbox](https://www.systemdesignsandbox.com/learn/delta-sync) This is directly transferable to the proposal's §16 "cheap discovery" goal: a per-partition (or per-shard, per the proposal's `sync/00..ff` layout) rolling hash-of-hashes lets a client answer "has anything in this partition changed since I last looked" from a handful of small file reads (segment list + mtimes/sizes + optionally a manifest hash) rather than opening and parsing every file — this is essentially what the proposal's §16 already describes without naming it a Merkle structure; naming it explicitly makes the manifest format design (hash the sorted list of `{segmentId, size, contentHash}` per partition, roll that into a partition-level hash, roll partition hashes into a workspace-level root) a much more concrete, testable target than "compare filenames/sizes/mtimes" alone. HashiCorp's own production writeup on Merkle-tree-based anti-entropy sync (used in Consul/Serf-style gossip) is a good second reference for the "periodic reconciliation, not full-tree scan every time" discipline the proposal's §48 already calls for. [Replication Overview and Merkle Sync Loop Analyses – HashiCorp](https://support.hashicorp.com/hc/en-us/articles/20457140183443-Replication-Overview-and-Merkle-Sync-Loop-Analyses)

## 6. Locking/lease patterns that actually work on shared filesystems

**KeePass's `.lock` file is the most directly transferable prior-art pattern for the rare admin-only compaction/migration case.** Its mechanics, confirmed above: a sentinel file signals "in use for writing," and — the important part — it is a **lease, not a mutex**: it must be refreshed within a bounded window (10 minutes) or any other client is entitled to treat it as abandoned and proceed. [Multiple Users – KeePass](https://keepass.info/help/base/multiuser.html) This is exactly the right shape for SMB, where a genuine OS-level exclusive lock is unreliable (client crash, network partition, or a laptop closing mid-operation leaves a true mutex permanently stuck) — a heartbeat lease degrades gracefully instead of deadlocking the whole workspace. Recommend copying this almost verbatim for the new app's admin-only compaction lock: a `compaction.lease.json` containing `{ holderId, acquiredAt, expiresAt, heartbeatIntervalMs }`, refreshed on a timer while the operation runs, and any client is allowed to steal the lease once `now > expiresAt` — with the steal itself going through the same CAS-with-verify-read-back discipline XQAP already uses everywhere else, so two clients racing to steal a dead lease can't both believe they won.

**The File System Access API does now offer a real create-exclusive primitive, but its scope needs to be verified rather than assumed, and I could not fully confirm cross-machine behavior.** Confirmed from Chrome's own developer documentation: Chrome 121+ added an optional `mode` parameter to `createWritable()`, where `"exclusive"` mode "only allows one writer to exist at a time" and throws `NoModificationAllowedError` if a second writer attempt is made while one is open — a real, named, browser-native equivalent to POSIX `O_EXCL`-style exclusive-open semantics, replacing the default `"siloed"` behavior (where multiple independent writers each get their own swap file and the last close wins). [API Improvements for working with files in the browser (Chrome for Developers)](https://developer.chrome.com/blog/new-dev-trial-for-multiple-readers-and-writers) **What I could not verify with confidence**: whether this exclusivity is enforced by the browser's own internal bookkeeping only (i.e., meaningful only against *other writers from the same browser/origin*) or whether it's backed by a genuine OS-level file lock that a *second machine's* SMB client would also observe and be blocked by. The WHATWG spec issue thread that defines this mode discusses "exclusive-in-place" vs. "exclusive-atomic" (swap-file) variants without settling the cross-process/cross-machine question in the material I could access. [whatwg/fs issue #148](https://github.com/whatwg/fs/issues/148) **Recommend treating this as an optimization/fast-fail signal only, not a substitute for the CAS-verified lease pattern above** — exactly the same caution the proposal itself already applies to `FileSystemObserver` (fast path, never correctness path) should extend to `createWritable({mode:"exclusive"})` until Phase 0 environment-proof testing (the proposal's own §54) empirically confirms whether a second *machine* opening the same UNC path in exclusive mode actually gets rejected, or merely a second tab on the same machine does. This is a concrete, cheap Phase-0 test to add to the proposal's existing environment-proof checklist.

**`FileSystemObserver` is confirmed unlikely to see other machines' writes, which validates the critique's flag #5 directly.** It remains an **origin-trial-stage API** (trial ran Chrome 129→134, Sep 2024–Feb 2025; I could not confirm from available sources whether it has since shipped as a stable, non-flagged feature as of August 2026 — **flagging this as needing a live version check against the actual deployment Chrome build before relying on it at all**). [The File System Observer API origin trial](https://developer.chrome.com/blog/file-system-observer) Functionally, it reports `"appeared"`/`"disappeared"`/`"modified"`/`"unknown"` events sourced from the local OS's file-change-notification mechanism (inotify/ReadDirectoryChangesW-equivalent) — which is fundamentally a **local-filesystem-driver-level** mechanism. No source found confirms it propagates a *remote* machine's write on a shared SMB volume as an observable event on a *different* machine's browser process, and general OS-level experience with `ReadDirectoryChangesW` over SMB is notoriously unreliable (missed/coalesced events, vendor-dependent). The proposal's own §14 already correctly demotes it to "acceleration only, never correctness" — this research confirms that demotion is the right call, not overcaution, and the new app's design should assume **targeted polling is the only mechanism that will reliably see a peer machine's write**, full stop, with `FileSystemObserver` treated as a same-machine, same-tab convenience for faster local-echo UI updates at best.

## Summary of unverified/flagged items

1. **No public prior art found** for the specific combination "event-sourced append-only log, replicated purely via a shared OS filesystem, no server, browser-only" — XQAP's and the proposal's designs here are closer to novel infrastructure than borrowed pattern; treat the failure-injection test list (proposal §43) as the primary validation method, not literature review.
2. **No direct prior art found** for "non-extractable WebCrypto signing keypair, re-enrollment flow after a browser-storage wipe, public key registered in a shared workspace" — recommend append-only key-registration-history over passphrase-derived keys, but this is original design, not an adopted pattern; give it the same explicit written risk-acceptance treatment XQAP gave its own trust boundary.
3. **Could not confirm** whether `createWritable({mode:"exclusive"})` enforces exclusivity across separate machines on the same SMB share, or only within one browser/origin — needs an empirical Phase-0 test, not an assumption either way.
4. **Could not confirm** whether `FileSystemObserver` has shipped stable (vs. still flag-gated/origin-trial) as of the current Chrome version in August 2026 — verify against the actual deployment browser build before any design relies on it even as an accelerator.
5. Compaction/GC on a shared, concurrently-read filesystem with no coordinator is **not solved anywhere in the prior art surveyed** (Obsidian, Syncthing, KeePass, Git, Fossil all sidestep it via full-history retention, server-mediated sync, or single-file-atomic-swap architectures the new app doesn't have) — this remains the correctly-hardest open problem the critique already flagged, and no external reference closes it.
