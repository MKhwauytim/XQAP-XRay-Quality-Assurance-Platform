# Employee Answer Saves — Append-Only Rewrite Proposal

**Date:** 2026-08-27 · **Status:** approved by owner (verbal sign-off in session) · revision 4, after THREE independent adversarial design reviews — round 1 found the single-writer premise false, round 2 found two correctness regressions in the round-1 fix, round 3 (focused specifically on the Stage 0 extraction) confirmed the extraction boundary is sound but found one previously-hidden serious risk (the backup/restore system independently reads and rewrites the same on-disk format outside distribution's own test coverage) plus several precise, fixable gaps — including that the round-3-preceding `authority`-as-primary-ordering-key design would have broken the reopen→correct workflow, the app's core correction loop. This revision incorporates round 3's fixes surgically; the structural approach (generalize `src/data/distribution/distributionEventStore.ts` rather than write a parallel implementation) is unchanged and now independently confirmed safe to attempt.
**Decision order:** Stage 0 (extract generic primitives from distribution's code, zero behavior change to distribution, validated against distribution's own full test suite PLUS a new generic-module test suite) → Stage 1 (answers-specific fold logic on top of the generic primitives, isolated) → Stage 2 (wire read/write, including the backup-system and `loadAllEmployeeFiles` fixes round 3 found) → Stage 3 (validation) → Stage 4 (ship). Each stage is independently revertible.

## 0. History — why this revision looks different from rounds 1 and 2

- **v1** claimed answer files are single-writer and dropped distribution's cross-machine machinery on that basis. **False**: five cross-user write paths exist (quality-note edits, bulk reopen, bulk reassignment, supervisor replacement requests, instant reopens), three of them supervisor bulk loops.
- **v2** restored the machinery, scoped request queues out of the new event stream, redesigned the on-behalf refusal, and fixed the cache-write performance claim. Round 2 found this still had two live defects:
  - **A new shared-write hotspot.** v2's fix for the workspace-sync freshness gap was a single per-month CAS-stamped file bumped by every employee's save — structurally identical to the exact pattern that caused the XQ-IO-032 incident two days ago (`docs/audit/XQ-IO-032_MULTI_MODEL_FINDINGS_2026-08-25.md:470`: *"removing the write from the read path entirely… the herd load is gone, not argued away by ladder arithmetic"*). v2 also mis-cited its own precedent — the actual distribution mechanism for this exact problem is a **read-only** bounded directory-listing signature, zero extra writes.
  - **Legacy-file corruption.** v2 kept the three request queues on the existing whole-file-rewrite path "unchanged," but that path reads via the same loader that also returns folded segment data — so a routine referral request would write the newly-folded item state back into the file v2 elsewhere promises is "never rewritten," corrupting the exact separation the whole design depends on.
  - Round 2's overall verdict, honestly: after two rounds of closing gaps, the design had re-accumulated nearly all of distribution's complexity (writer-session naming, rotation, checkpoint, late-event detection, dedup, cache validation) while writing it a second time, independently — the "simpler than distribution" framing no longer held, and a second independent implementation of subtle SMB-safety mechanics was itself a real risk (four rounds of hard-won fixes already went into the one that exists).
- **v3** acted on round 2's recommendation: generalize the mechanics instead of re-implementing them. Round 3 verified the extraction boundary itself field-by-field against the actual code and confirmed it is genuinely clean (no `AssignmentDistributionEvent`-specific coupling in the append/rotate/verify path), but found:
  - **Two module-level writer memos (`openSegmentSeqByWriter`, `writtenSegmentsThisSession`) key only on device+session, not on which consumer is writing** — sharing them between distribution and answers in the same tab would make each consumer see the other's segments as "already known," causing spurious 11-second stalls and sparse/skipped sequence numbers.
  - **The proposed `authority`-first ordering (v3 §4) was wrong and would have broken the reopen→correct workflow** — the single most important correction flow in the app — by making every reopen event permanently outrank the self-authored fix it exists to invite.
  - **The backup/restore system (`backupStorage.ts`) independently reads, classifies, and rewrites the same `.ndjson` format** through code that is not part of `distributionEventStore.ts` and is not exercised by distribution's own test suite in the relevant way — a real, previously-unidentified silent-data-loss path once answer segments exist on a real share.
  - Smaller gaps: the digest function should not be parameterized (it is already fully generic and parameterizing it only adds risk); the generic module needs its own fault-injection test suite in generic vocabulary, not reliance on distribution's suite alone; the segment-naming scheme must be reconciled to one form with a length cap (the 260-char Windows path limit is a *proven* incident source — XQ-IO-031 — not a theoretical one); and `loadAllEmployeeFiles` bypasses the merge entirely today, so eight real call sites (referral/replacement/reopen approval, orphan scan, executive report KPIs, Power BI export, backup) would silently freeze at pre-migration state without an explicit Stage 2 fix.
- **This revision (v4)** incorporates all of the above.

## 1. What actually generalizes vs. what stays domain-specific

Distribution's code has always mixed two concerns: durable, ordered, append-only storage **mechanics** (segment naming, rotation, checkpointing, late-event/duplicate detection), and distribution's own **business logic** (the 7-member `eventType` union, transition-legality table, quota-fact accumulation). Only the first category is reusable — extracting the second would just be a different way of forcing answers into distribution's shape.

**Extracts into a new generic module**, `src/data/storage/appendOnlyEventLog.ts`:
- Writer-session-hashed segment naming, rotation by size/line cap, per-writer-chain lock, re-read-before-append, post-write size verify — today's `distributionEventStore.ts:192-486`, made generic over the event's shape (a type parameter) and the directory/suffix (a parameter). **The segment base name is `{consumerNamespace}-{deviceHash}-{sessionHash}[-{seq}]`** — round 3's Gap 1a fix: every module-level writer memo (`openSegmentSeqByWriter`, `writtenSegmentsThisSession`, and any future one) is keyed `{consumerNamespace}|{scopeId}|{fileName}`, not `{scopeId}|{fileName}` alone, so distribution and answers writing in the same tab/session/month can never observe or collide with each other's segment state. `consumerNamespace` is a short fixed literal per consumer (`"dist"`, `"ans"`), not user-controlled, so it adds no meaningful length. Per-user identity for answers is carried by the directory layout (§3's flat per-month directory groups files by content, not by a name component), not by embedding the username in the segment name — round 3's Gap 1c: `distributionEventStore.ts:138-176` documents the 260-char Windows path limit as a *proven* incident source (XQ-IO-031), and an unbounded `safeWorkspaceFilePart(username)` in a segment name is exactly the kind of unbounded-length component that caused it. The generic module asserts the constructed base name is ≤ a fixed character budget, as a real check, not a convention.
- Checkpoint shape and the resume/dedup contract: `segmentOffsets`, **`knownEventIds` dedup across the checkpoint boundary** (the exact mechanism round 2 found missing from v2 — `distributionStorage.ts:895-916`), a `deriveVersion` gate, and **one fixed, non-parameterized digest function**, `eventSetDigest(ids: Iterable<string>): string` — round 3's Finding 3: `distributionEventSetIdFromIds` (`distributionEventStore.ts:1050-1062`) is already fully generic and pure (no domain assumption about what an id is), so making it caller-suppliable adds a real risk (a wrong-but-plausible implementation could be non-commutative or non-deterministic, silently breaking the cache-validity binding that depends on it) for zero benefit. It moves into the generic module unchanged; both distribution's `distributionEventSetId(events)` and answers' equivalent become one-line adapters that just extract ids and call it.
- Late-event detection: a generic `isEventOutOfOrder(newEvent, entry, compare)` where `compare` is the SAME comparator the caller's own fold uses for total order (not a separately-specified `(eventAt, eventId)` pair) — round 3's Gap 1b: a late-event guard that uses a different order than the fold it guards is not a guard; requiring one shared comparator makes that impossible by construction. Matches `findLateEvent`'s conservative "missing prior-order marker counts as late" rule (`distributionDerivation.ts:275-298`). On a positive result, the generic module's contract is the same as distribution's: **the caller must do a full refold, never patch in place.**
- **The generic module gets its own fault-injection test suite**, in its own vocabulary, against a synthetic minimal event type with no distribution or answers fields — round 3's Finding 4. At minimum: rotation-write-fails-outright, both branches of verify-not-a-failure, unreliable-baseline-forces-rotation, and checkpoint↔digest binding. A one-line comment at the top of the module states plainly: two consumers, any change here requires the whole-repo `npm run test:run`, never a scoped run — CI already does this (`.github/workflows/ci.yml` runs unscoped `test:run` on every push), but the module should say so for whoever edits it without reading CI config first.

**Stays in `distributionEventStore.ts` / `distributionDerivation.ts`** (untouched in meaning, refactored only to call through the generic module for the mechanics above): the `AssignmentDistributionEvent` type, `isIllegalTerminalTransition`, quota-fact accumulation, `foldDistributionEvents`'s own business rules.

**Lives in the new `src/data/answers/answerEventStore.ts`** (built on the same generic module): the `AnswerEvent` type (§3 below), `foldAnswerEvents`'s own business rules (upsert-by-id, valueHistory/history append, the append-then-confirm on-behalf protocol).

## 2. Stage 0 — the generalization itself, validated in isolation

This is the highest-risk part of the whole proposal, because it touches code a production incident was fixed in two days ago. The discipline:

1. Extract the generic module with distribution's **existing exported function signatures completely unchanged** — `appendDistributionEventSegment`, `readSegmentTails`, `sortDistributionEventsForFold`, etc. keep their names, parameters, and return types; internally they become thin calls into the generic primitives.
2. **Zero behavior change is the acceptance bar**, proven by running distribution's own full test suite (all 30 files in `src/data/distribution/`, unmodified) against the refactored code and requiring byte-identical pass/fail results — not "still passes," but the same tests, unedited, green.
3. A dedicated before/after diff review: for every distribution test that exercises a fault-injection scenario (`distributionEventSegmentRotation.test.ts`'s "loses no events and writes none twice when the rotation write fails outright", `segmentVerifyNotAFailure.test.ts`, `distributionCheckpointSidecar.test.ts`), confirm the refactored code path is the *same* code, not a re-derivation that happens to pass today's assertions.
4. Only after Stage 0 is independently validated (its own adversarial review, given the stakes) does Stage 1 begin.

## 3. Target write/read model for answers (built on the generic module)

```ts
type AnswerEvent = {
  eventId: string;              // stable per-user-action id (see §4) — NOT a
                                  // fresh uuid per attempt, so a retried
                                  // append after an ambiguous failure is a
                                  // detectable duplicate, not a silent replay
  eventType: "item-saved" | "item-reopened" | "quality-note-set" | "migration-seed";
  eventAt: string;
  eventBy: string;
  authority: "self" | "supervisor";   // tie-break ONLY at exactly equal
                                        // eventAt — see §4. NOT the primary
                                        // sort key (that was v3's mistake).
  xrayImageId?: string;          // absent only for migration-seed
  answers?: FieldAnswer[];
  status?: "draft" | "submitted";
  answeredBy?: string;
  answeredOnBehalfBy?: string;
  qualityNote?: string;
  eventSchemaVersion?: number;
};
```

Storage: `2-samples/{month}/answers.events/{sortableTimePrefix}-{consumerNamespace}-{deviceHash}-{sessionHash}[-{seq}].ndjson` — **one flat per-month directory across all employees** (not one directory per employee, and not keyed by username at all — see §1's Gap 1c fix), so the new freshness-signal probe (§6) is a single bounded listing, matching distribution's own layout shape. This is the one segment-naming scheme used everywhere in this document — v3 had two inconsistent schemes across §3 and §6; this revision reconciles them into this single form, matching the length-budget assertion in §1.

## 4. Concurrency and ordering — closing round 2's Finding 1 correctly this time

Writer-session naming (from the generic module, now correctly namespaced per §1's Gap 1a fix) makes two uncoordinated writers physically unable to collide on one segment file — this closes the *lost-write* half of round 2's finding for all five cross-user paths (quality-note edits, bulk reopen, bulk reassignment, supervisor replacement requests, instant reopens), including the two (`item-reopened`, `quality-note-set`) that stayed in the item-event stream after request queues were scoped out.

**Ordering: `(eventAt, eventId)` is the primary total order, matching today's actual last-write-wins behavior in all five paths and matching `isEventEarlierThanEntry`'s existing rule** (`distributionDerivation.ts:288-297`). `authority` is used **only** as the tie-break at exactly equal `eventAt`, replacing `eventId` as the final tiebreaker in that narrow case — never as a primary ranking.

Round 3 found the earlier draft of this section (authority as the PRIMARY key) was wrong and would have broken production behavior: `upsertItemAnswerOnBehalf`'s own docblock and `answerOnBehalf.test.ts` pin that an assignee's later self-save *does* win over an earlier on-behalf save, and — far more importantly — `reopenItemAnswer` is itself supervisor-authored, so making supervisor events permanently outrank later self events would have made the reopen→correct workflow (reopen an item specifically so it CAN be corrected, then the employee corrects it) stop working, which is close to the whole point of the reopen feature. Demoting `authority` to a same-instant tie-break only reproduces today's real behavior in every case that matters and removes the ordering inconsistency round 3 flagged between the fold and the late-event guard (§1): both now use the exact same comparator, because there is only one comparator.

## 5. The on-behalf refusal — closing round 2's Finding 3

Append-then-confirm (as in v2), but the confirmation is **scoped to one item**, not a whole-file or whole-checkpoint fold: `foldSingleItem(events, xrayImageId)` replays only that image's events (small by construction — an item accumulates at most a handful of save/reopen/note events per month) to determine whether the append actually took effect under the true fold order. This closes round 2's cost objection (an unbounded refold on every on-behalf save) without weakening the guarantee: the single-item fold uses the exact same `(eventAt, eventId)`-with-`authority`-tiebreak comparator (§4) as the full fold, so its answer is consistent with what a full fold would produce for that item.

## 6. Freshness signal — closing round 2's Finding 5 correctly this time

**No new writes.** Add `safeAnswerSegmentsSignature = boundedSizeSignature(answersEventsDir, ".ndjson")` — a read-only, bounded (top-N by name) directory listing, the same primitive distribution already uses for exactly this purpose (`workspaceSync.ts:411-419`, `directoryScan.ts`'s `boundedSizeSignature`) — feeding the existing `answers` change-signature family in `workspaceSync.ts`. One listing per 45 s tick, zero additional writes, no new shared-file contention. Segment names are prefixed with a sortable time component so an ongoing session's most recent appends are never evicted from the top-N the bounded signature actually stats.

## 7. Request queues — closing round 2's Finding 6a/6b

Round 2 showed keeping the queues on `updateEmployeeAnswerFile` "unchanged" actually corrupts the frozen-legacy-file premise, because that function's read side returns folded (segment + legacy) state, and its write side writes that whole merged object back. **Fix:** give the three request queues their own file, `{username}.requests.json`, split out of `EmployeeAnswerFile` entirely rather than kept inside it. This is a strictly smaller, cleaner change than v2's "leave them where they are": the legacy `.answers.json` stops being written *at all* after migration (truly frozen, as originally intended), the request-queue file keeps today's exact whole-file-rewrite mechanics (low volume, already correct, not worth touching), and `loadRequestLogs`'s read cost (round 2's Finding 6b) drops rather than growing, since it now reads a small dedicated file instead of folding item-event history it never needed.

`loadEmployeeAnswers` becomes a merge of exactly two sources: item state (legacy-seed-or-segments, per §8) and `{username}.requests.json` — still returning the identical `EmployeeAnswerFile` shape to every existing caller.

**Round 3's Finding 5c — `loadAllEmployeeFiles` is a separate reader that bypasses this merge entirely, and it has eight real consumers.** `answerStorage.ts:565-580` reads `*.answers.json` directly via a raw directory scan — it does not call `loadEmployeeAnswers` per file. Left unfixed, `referralStorage.loadRequestLogs` (the entire supervisor referral/replacement/reopen approval surface), `orphanScanLoader` (B3 integrity scan), `reportModel.ts`'s reviewer-referral KPIs, `powerbiExport/exportManager.ts`, `backupStorage.ts`'s manifest/verification, `Reports/TabView.tsx`, `ReportDesigner/ExecutiveRowsProvider.tsx`, and `XrayInspectionResults.tsx`'s oversight branch would all silently freeze at pre-migration state — no new items, no new requests — the moment a month's first employee migrates. **Fix, required in Stage 2, not deferred:** convert `loadAllEmployeeFiles` into an enumerate-then-`loadEmployeeAnswers` fan-out (enumerate the union of `*.answers.json` stems, `*.requests.json` stems, and segment-owner usernames), preserving its existing `onUnreadable: "skip"` per-file isolation. Because most of those eight consumers only need the request queues, not item state, the fan-out should expose a requests-only variant so `loadRequestLogs`'s read cost genuinely drops (per-employee `{username}.requests.json` reads only) rather than rising to a full item-segment fold it never needed — this must be confirmed with a real measurement in Stage 3, not assumed.

## 8. Migration marker — closing round 2's Finding 6c

The marker must be **independently durable and immune to a mis-scoped backup restore**, not stored in a rebuildable checkpoint sidecar (round 2's contradiction: v2 named the sidecar as the marker's home in one place and treated it as absent-until-first-checkpoint in another). **Fix:** the marker is the first event ever appended for an employee's first segment — a `migration-seed` pseudo-event (`{ eventType: "migration-seed", legacyContentHash, at }`). Being an ordinary segment event, it is covered by the exact same backup classification as every other event (`merge-events`, not `skip-derived`/`replace`), so a restore can never silently revert or duplicate it.

Round 3 confirmed this is sound (`distributionEventStore.ts:214-218, 373-383`: a sealed segment is never rewritten, renamed, or deleted by rotation — only new names get created — so a busy first day cannot displace the marker), with one wording correction: because §1's Gap 1a fix means a writer's very first append can itself trigger the "unreliable baseline forces rotation" branch, the marker is not reliably at a literal `seq 0` filename — it is reliably in **the earliest segment belonging to that writer's chain**, identified by the sortable time prefix in §3's naming scheme, not by a hardcoded sequence number. Fold precedence: segments present → look for `migration-seed` in the earliest-timestamped segment for that employee → found → seed from the named legacy content hash once, never again → segments present with no `migration-seed` anywhere in the chain → pre-migration rollback residue (see §9) or a corrupted first segment, treated as a hard read failure per §10, not silently guessed at.

## 8a. Backup and restore — a gap round 3 found that was outside every prior round's stated scope

`backupStorage.ts` independently reads, classifies, and rewrites `.ndjson` segment files — it is not part of `distributionEventStore.ts`, is not exercised by distribution's own test suite in the relevant way, and was not covered by any earlier round of this proposal. Left unfixed, it is a silent-data-loss path the moment answer segments exist on a real share:

- `restoreActionFor` (`backupStorage.ts:751-752`) correctly classifies any `.ndjson` file as `merge-events` by suffix alone — this part needs no change, and confirms §8's claim above.
- `mergeEventSegment`'s conflict detection (`backupStorage.ts:870-894` → `distributionEventStore.ts:935-949`'s `sameEvent`) compares a fixed list of `AssignmentDistributionEvent` fields. For an `AnswerEvent`, every distribution-only field it compares is `undefined === undefined` on both sides — **two different-content answer events sharing an `eventId` are declared identical, and one is silently dropped instead of the throw `merge-events` exists to produce.** Since §3 deliberately makes `eventId` stable across retries (so a retried append after an ambiguous failure is detectable, not a silent replay), same-id-different-content is a real, not hypothetical, case this comparator must handle correctly.
- `collectJsonRestoreEntries` (`backupStorage.ts:833`) captures the cache-invalidation directory only when `entry.name === DISTRIBUTION_EVENTS_DIR`, a literal string. A restore that merges `answers.events/` therefore never invalidates the answers checkpoint sidecar — whose `segmentOffsets` are byte offsets into files the restore just rewrote. A stale sidecar with offsets into rewritten files either mis-parses or silently skips real events on the next incremental read.

**Fix, required in Stage 2, not deferred:** generalize `collectJsonRestoreEntries`'s cache-directory capture to any directory ending in a registered events-directory suffix (not a literal name match), and give `mergeEventSegment` a per-consumer content comparator (or a safe default — whole-object deep-equal — for any event shape it doesn't specifically know, which is strictly more conservative than field-subset comparison and cannot silently under-detect a conflict).

## 9. Generic module's own test suite and naming/retry-ladder pins (round 3's Finding 2 and 4)

In addition to §1's requirement that the generic module carry its own fault-injection suite: Stage 0 also adds (a) a golden-name pin test asserting literal expected segment filenames for fixed device/session/namespace inputs, so a future change to the naming format is caught explicitly rather than passing because both sides of a comparison moved together, and (b) an explicit assertion of which retry ladder (`TRANSIENT_WRITE_RETRY_DELAYS_MS` vs the patient verify-readback ladder) each code path takes, via a fake clock and a sleep-count assertion — round 3 found no existing test pins this, so a refactor could silently swap "first append of a session resolves promptly" for "sleeps ~11s" and stay green.

## 10. Rollback

Unchanged from v2's plan: reverting resumes writing `.answers.json` directly; a subsequent roll-forward must not re-fold segments written after the revert against a legacy file that has since diverged. Rollback procedure includes renaming `{username}.answers.events/` directories (now `answers.events/` at the month level, per §3) to a `.disabled` suffix, via script, as an explicit step — not left as "nothing to undo," which v1 incorrectly claimed.

## 11. Explicitly not doing

- Not touching `{supervisor}.decisions.json`.
- Not implementing segment compaction, matching distribution's own choice.
- Not defining corrupt-segment recovery beyond "throw" (matching `distributionEventStore.ts:325-338` and this module's own P0-1 "unreadable never becomes empty" contract).
- Not migrating `saveEmployeeAnswers` (whole-array replace) — stays on the legacy path, documented as test/seed-only usage (per round-1 Finding 7c, unchanged in this revision).
- Not touching `adhocHistoricalImport.ts`'s bulk `upsertItemAnswer` loop in Stage 1 — flagged by round 2 as a sixth bulk-writer path; addressed in Stage 2's wiring review, not a Stage 0/1 concern since ad-hoc months are a separate synthetic-folder code path already.

## 12. Validation plan

**Stage 0** (generalization): distribution's own full test suite, unmodified, byte-identical pass/fail against the refactored internals; the new generic-module fault-injection suite (§1, §9) in generic vocabulary; golden-name and retry-ladder pin tests (§9).
**Stage 1** (answers-specific module, isolated): unit tests for `AnswerEvent` fold logic, the `(eventAt, eventId)`-with-`authority`-tiebreak comparator (§4) — including a regression test for the specific case round 3 found broken (a later self-save after an earlier on-behalf save must still win, and a later self-save after an earlier reopen must still win), `foldSingleItem`, the `migration-seed` marker (§8) — zero production call sites touched.
**Stage 2** (wiring): every existing contract test in `src/data/answers/` and every cross-module test enumerated in round 1's research (`answerOnBehalf.test.ts`, `answerValueHistory.test.ts`, `reopenAnswer.test.ts`, `readContract.test.ts`'s P0-1 test, `staleSnapshot.test.ts`, `pipeline.workflow.test.ts`, `InspectionPanel.test.tsx`, `sampleMirrorDropToZero.test.ts`) must pass unmodified. Plus, required per §7/§8a and not deferrable: the `loadAllEmployeeFiles` fan-out (with a requests-only fast path, measured, not assumed) and the `backupStorage.ts` generalization (cache-directory capture by suffix not literal name, a real per-consumer or safe-default event comparator) — both need their own new tests exercising an answers-shaped restore, since neither is covered by any existing distribution test.
**Stage 3**: full whole-repo gate, a real before/after latency measurement (append-only save cost, excluding the now-async cache refresh, measured separately), and independent adversarial validation of the diff before it ships.

This proposal has now been through three independent adversarial reviews (single-writer premise → concurrency/hotspot/legacy-file correctness → Stage 0 extraction safety). Stage 0 may begin.
