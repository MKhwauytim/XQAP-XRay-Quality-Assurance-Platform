## v153.25 — 2026-10-13 — Change (employee-workspace): month load reads only the employee's own files — scoped ad-hoc probe, own request queue, one-pass mirror trust check, read-fold cache persist, Results mirror fast path

**Why:** An employee's month load on an SMB share read every employee's request file, opened every ad-hoc import in the workspace, stat'ed every distribution segment twice for the mirror trust check, and refolded the whole distribution on every mount whenever the mirror was untrusted (read-side folds were never persisted). The Results sub-tab had no mirror path at all.

**What changed:**
- Ad-hoc probe scoped to the selected month (`views/adhocReads.ts` extracted from XrayReferrals; XrayInspectionResults passes `selectedMonth`). `storesToOpen` skips only imports linked to a DIFFERENT month. Owner ruling: imports with no linked month stay visible in every month.
- `loadRequestLogs` / `loadReferralLog` / `loadReplacementLog` / `loadReopenLog` accept `{ scopeToUser }`; new `loadEmployeeRequestQueues` (requests file first, else memoised legacy `.answers.json` arrays; `null` when neither exists), reused by the all-user scan. Only XrayReferrals scopes. Owner ruling: XrayInspectionResults stays unscoped, because its audit table shows rows referred TO the user, which live in other employees' files. A corrupt own requests file is logged and yields empty queues.
- `eventStoreMatchesScan` lists `distribution.events/` once via `listSizedAndNamedEntries(dir, ".ndjson", ".json")`: `.ndjson` sized, legacy `.json` names only.
- `loadOrDerive…ForRead` gains opt-in `persistAfterReadFold` (XrayReferrals, XrayInspectionResults). When a read leaves the on-disk cache stale, `distribution.current.json`, its checkpoint and the mirrors are queued for persistence. A read is stale after a full read-side fold, or after a `checkpoint` resume that folded at least one newer event (`resumedWithNewEvents` on the outcome). That second case is the field case after a failed write-path persist. The persist is NOT awaited: the read returns at once, the writes and any 1–3 s retry sleep run behind it on the month's persist chain, and a failure is logged as `distribution:persist-after-read-fold` from a `.then`. It is skipped in read-only sessions, on memo hits (`source: "memo"` added), on `displayOnly` folds, and on a closed month. The closed-month check uses monthLock's TTL-cached `isMonthClosed` and logs `distribution:persist-after-read-fold:month-closed` once per (workspace, month) per session. The shared persist job never replaces an on-disk cache that covers strictly more events (equal coverage rewrites, so `.tmp` recovery still works).
- `listSizedAndNamedEntries` takes an optional dead-segment `scopeKey`; `eventStoreMatchesScan` passes the same scope `readEventSegmentDelta` uses, so a confirmed-dead segment is skipped without an open (absent from the listing, as a failed open left it, and it has no recorded offset either).
- Tests: `persistAfterReadFold` drains the persist chain (`flushPendingDistributionPersist`) before every disk assertion, and adds a checkpoint-resume case and a closed-month case. The read-only case asserts no `createWritable` and no ≥1 s timer instead of a wall-clock bound, and the "served from cache" case asserts `kind === "ok"` first. `XrayReferrals.saveBroadcast` drains the chain before its log assertions. `XrayInspectionResults.mirrorFastPath`'s reassignment case asserts the `محالة/منقولة` label in IMG-A's row. A new `directoryScan.sizedDeadSkip` test is added.

**Ruling (spec §9.3, signature short-circuit): infeasible as specified, so not built.** File System Access API directory listings carry no sizes, so a `(count, totalBytes)` signature cannot be built without a stat per file. The one-pass listing above is the achievable form.

## v153.24 — 2026-10-13 — Fix (answers): stop the save-failure spiral on flaky shares — retry refused replace before rotating, two-name extension probe, dead-segment registry, 256 KiB segments

**Why:** The field error log from a real workspace on an SMB share (employee `hihaloraini`, 2026-10-11/12) showed four linked failures. (1) About 70 segment rotations in two days, each after a single 20 ms retry on `InvalidStateError` at close, although the share accepted the replace a few hundred ms later. (2) A false `XQ-IO-033 extension-blocked` verdict: `.ndjson` creation was confirmed working by hand on the same share, so one flaky probe name was enough to condemn the extension. (3) Five listed-but-unopenable colleague segments were re-probed every ~30 s and failed every `strict: true` read, so `PendingAnswerReplayRunner` never replayed queued answers (frozen since 2026-10-11). (4) Roughly 2,000 segment files in one month folder, from the 128 KB / 2,000-line rotation cap.

**What changed:**
- `appendOnlyEventLog.ts`: the refused-replace retry ladder is widened and exported (~4.2 s worst case, inside the 30 s interactive deadline), and the rotation log line is tagged `rotationReason=blocked-replace`. Rotation is still the single bounded last resort.
- `transientFileErrors.ts`: `extension-blocked` now needs two distinct probe names (`-a` and `-b`) to both vanish. When only the first fails, the probe no longer returns at once: it falls through to the path-length probe, so a flaky first probe cannot hide a `name-too-long` diagnosis, and yields `unknown` only if that also clears.
- New `deadSegmentRegistry.ts` (session registry: 3 failed opens spanning at least 5 min means confirmed dead). `directoryScan.ts` `readSegmentTails` skips confirmed-dead names, logs once per (scope, name), and returns `deadNames`. A strict read skips them only when the caller opts in with `tolerateConfirmedDead` (threaded through `readAnswerEventDelta`, `readAllAnswerEventsForMonth` and `loadAllEmployeeFiles`), and the ONLY caller that opts in is `pendingAnswerReplay.ts`. Every other strict reader is unchanged and still throws `EventSegmentUnreadableError` on a confirmed-dead name: `populationOverwriteGuard` (used by population save, recovery and selective restore) and distribution's `strictSegments` readers. A guard that cannot see whether a month has work in a segment must refuse. Skipped dead names get no offset, so checkpoint protection holds and a later successful open reads from byte 0. The non-strict path skips them and logs once. `SegmentEventsDelta` gains `unreadableNames`. A manual refresh in `workspaceSync.ts` calls `clearDeadSegmentRegistry()`.
- `MAX_OPEN_SEGMENT_BYTES` 131,072 to 262,144 (256 KiB) and `MAX_OPEN_SEGMENT_LINES` 2,000 to 4,000. Each append rewrites the whole open segment, so the cap trades file count against bytes per save: 256 KiB halves the file count against 128 KiB and only doubles the average upload (1 MiB would have made it 8x). It is a bounded, unmeasured compromise until Plan 2's compaction removes the file-count problem. Field evidence 2026-10-13: ~2,000 segments in one month folder.
- Existing tests updated: `appendOnlyEventLog.test.ts` (cases a/a2) and the `answerSaveInvalidStateRotation.test.ts` R5 variant now import the ladder constant; `extensionBlockedProbe.test.ts` and `notFoundCauseProbes.test.ts` use the new probe names; rotation-forcing tests (`distributionEventSegmentRotation`, `distributionSegmentResilience`) import the cap constants and use cap-relative filler. New tests: `appendOnlyEventLog.blockedReplace`, `deadSegmentRegistry`, `directoryScan.deadLog`, `transientFileErrors.extensionProbe`, `answerStorage.deadSegments` (tolerant read passes after confirmation; strict without the flag still throws after confirmation; the guards' `loadAllEmployeeFiles(dir, month, { strict: true })` shape throws on a confirmed-dead segment), plus a `workspaceSync` registry-clear case. `transientFileErrors.extensionProbe` also covers the fallthrough: a short name stays `unknown`, a 24+ character name whose length probe fails gives `name-too-long`.

**Deliberate deviation from spec §8.1:** the spec allowed rotation only after a NotFound. Rotation after the extended refused-replace ladder is kept on purpose, because field logs showed replace refusals persisting 30+ s on one name. The cost if that is wrong is one extra segment per persistent refusal.
