## v153.24 — 2026-10-13 — Fix (answers): stop the save-failure spiral on flaky shares — retry refused replace before rotating, two-name extension probe, dead-segment registry, 256 KiB segments

**Why:** The field error log from a real workspace on an SMB share (employee `hihaloraini`, 2026-10-11/12) showed four linked failures. (1) About 70 segment rotations in two days, each after a single 20 ms retry on `InvalidStateError` at close, although the share accepted the replace a few hundred ms later. (2) A false `XQ-IO-033 extension-blocked` verdict: `.ndjson` creation was confirmed working by hand on the same share, so one flaky probe name was enough to condemn the extension. (3) Five listed-but-unopenable colleague segments were re-probed every ~30 s and failed every `strict: true` read, so `PendingAnswerReplayRunner` never replayed queued answers (frozen since 2026-10-11). (4) Roughly 2,000 segment files in one month folder, from the 128 KB / 2,000-line rotation cap.

**What changed:**
- `appendOnlyEventLog.ts`: the refused-replace retry ladder is widened and exported (~4.2 s worst case, inside the 30 s interactive deadline), and the rotation log line is tagged `rotationReason=blocked-replace`. Rotation is still the single bounded last resort.
- `transientFileErrors.ts`: `extension-blocked` now needs two distinct probe names (`-a` and `-b`) to both vanish. When only the first fails, the probe no longer returns at once: it falls through to the path-length probe, so a flaky first probe cannot hide a `name-too-long` diagnosis, and yields `unknown` only if that also clears.
- New `deadSegmentRegistry.ts` (session registry: 3 failed opens spanning at least 5 min means confirmed dead). `directoryScan.ts` `readSegmentTails` skips confirmed-dead names, logs once per (scope, name), and returns `deadNames`. A strict read skips them only when the caller opts in with `tolerateConfirmedDead` (threaded through `readAnswerEventDelta`, `readAllAnswerEventsForMonth` and `loadAllEmployeeFiles`), and the ONLY caller that opts in is `pendingAnswerReplay.ts`. Every other strict reader is unchanged and still throws `EventSegmentUnreadableError` on a confirmed-dead name: `populationOverwriteGuard` (used by population save, recovery and selective restore) and distribution's `strictSegments` readers. A guard that cannot see whether a month has work in a segment must refuse. Skipped dead names get no offset, so checkpoint protection holds and a later successful open reads from byte 0. The non-strict path skips them and logs once. `SegmentEventsDelta` gains `unreadableNames`. A manual refresh in `workspaceSync.ts` calls `clearDeadSegmentRegistry()`.
- `MAX_OPEN_SEGMENT_BYTES` 131,072 to 262,144 (256 KiB) and `MAX_OPEN_SEGMENT_LINES` 2,000 to 4,000. Each append rewrites the whole open segment, so the cap trades file count against bytes per save: 256 KiB halves the file count against 128 KiB and only doubles the average upload (1 MiB would have made it 8x). It is a bounded, unmeasured compromise until Plan 2's compaction removes the file-count problem. Field evidence 2026-10-13: ~2,000 segments in one month folder.
- Existing tests updated: `appendOnlyEventLog.test.ts` (cases a/a2) and the `answerSaveInvalidStateRotation.test.ts` R5 variant now import the ladder constant; `extensionBlockedProbe.test.ts` and `notFoundCauseProbes.test.ts` use the new probe names; rotation-forcing tests (`distributionEventSegmentRotation`, `distributionSegmentResilience`) import the cap constants and use cap-relative filler.
