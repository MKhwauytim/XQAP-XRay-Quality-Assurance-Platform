# Edit Log — 2026-08-10

## v67.0 — 2026-08-10 — Change (population): CertScan + seed into settings, auto-process phase 2, drop unwanted controls, raw summary on upload

**Why:** the last outstanding items from the owner's end-to-end walkthrough. Every one had been specified in the rework plan and then **never executed** — the performance and correctness workstreams consumed the agents assigned to this tab, and completeness was reported without verifying these. Caught by grepping for the offending strings, which were all still present.

Their shared theme, in the owner's own experience: **the wizard exposed internals at the step where a decision was wanted, and deferred the information needed until the step after.**

### What changed

**1. CertScan entry moved into `إعدادات المعالجة` (W3).** CertScan config is workspace-global (`certscan.global.json`), so it belongs with the other processing configuration rather than as a separate step below the comparison. `MappingSettingsModal` renders it in a processing-mode-only section; `PhaseTwoReportAndProcessing` no longer does.

> The new **CertScan match-preview panel stays exactly where it was**, immediately before the process button. Moving the *configuration* into settings must not move the *warning* out of the path where it is acted on — that panel is what makes a 30-vs-30,000 port mismatch visible before processing commits.

**2. RNG seed moved into `إعدادات المعالجة` (W14).** The owner explicitly values the capability (*"which is great"*) — this was about location only. Phase 3 now shows the active seed read-only as a `<code>` reference so a draw remains self-describing; editing happens in settings. `onSampleSeedChange` was dropped from `PhaseThreeSampling`'s props since it no longer edits.

**3. Three unwanted controls removed (W8)** — `تقرير المعالجة` and the mismatch-table `تصدير Excel`, plus their now-dead handlers and an unused `xlsx` import. The primary `معالجة المجتمع` / `إعادة معالجة المجتمع` button is **kept**: it is the manual re-process affordance that item 5 depends on.

> **A correction to this entry's own brief.** The instruction said `تقرير المعالجة` was the only route to the per-row drill-down of dropped rows, and must not be removed without relocating it. Reading `reportHtmlBuilder.ts` disproved that: **the report only ever showed aggregate counts** — per-row detail lives in the retained final-population Excel export. So the stated blocker did not exist. Rather than treat that as licence to remove and move on, a genuine drill-down was added: a collapsible **"تفاصيل الصفوف المستبعدة"** section in `PopulationProcessingReport`, fed from `removedRows`/`duplicateRows`/`invalidResultRows` already in memory (zero extra reads), capped at 50 rows per category with a pointer to the export for the remainder. The signal is now *more* reachable than before, not merely preserved.

**4. `معاينة المجتمع النهائي` removed (W11).** It read already-in-memory data, so removal costs nothing and frees vertical space. `previewRows` remains in the prop type — the aggregate persistence added in v63.0 uses that shape.

**5. Phase 2 processes automatically (W9).** Arriving at Phase 2 with unprocessed data now runs processing without a button press.

> **The guard is the substance here, not the trigger.** It keys on the exact `riskWorkbookResult` **object reference** already attempted, not merely on "no result yet". A failed attempt therefore does not retry forever, while a genuinely new upload (new reference) retries once. Already-processed months reconstruct their result from disk, so the effect never fires for them at all. This repo has a documented history of effect-timing bugs surviving self-review, so the guard was written to fail closed.

**6. Raw-file summary on the upload page; parse and process decoupled (W4/W10, partial).** `parsePhaseOneWorkbooks` now parses and **stays on Phase 1**, rendering a summary card (rows/sheets, from the already-parsed workbook — no extra reads) beneath the upload cards. A second "التالي" advances to Phase 2, where item 5 immediately processes and shows the comparison. That is the owner's requested shape: *upload → see general info → next → process → compare*.

**Not attempted:** moving population processing itself onto the upload page, or merging the phases. That is the larger restructure, and the two-step decoupling already satisfies the complaint. A half-restructured wizard would be worse than an unrestructured one.

**Migration/rollback:** UI-only. No workspace file format changed and no data is read or written differently. Rollback is a code revert.
