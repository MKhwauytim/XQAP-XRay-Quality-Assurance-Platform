## v63.0 — 2026-08-07 — Add (reports): distribution per-stage/per-port sections + management progress model; unify accuracy grain naming; month aggregate + auto-lock; oversight bulk reassign

**Why:** four separate owner-reported gaps, plus one reporting bug that was already shipping wrong numbers.

### 1. The accuracy bug that was live in production

Three independent per-port accuracy folds existed at different grains, and two ran **simultaneously in the same generation run**. Golden-mastering before any change proved how bad it was. For a port where **L1 missed 25 suspicious cases and L2 caught them all**:

| Grain | Accuracy | Missed suspicion | Status |
|---|---|---|---|
| Image (`buildPortProfiles`) | **100%** | **0%** | **"excellent"** |
| Decision-combined | 75% | 50% | below target |
| Per-level | L1 **50%**, L2 100% | — | — |

The image grain's `L1 ∨ L2` combination **completely masked a first-level inspector detecting nothing**. A failing port could read "excellent, 0% missed" in the executive workbook and narrative while every other surface flagged it below target. `deck2/section3/workloadAccuracy.ts:38-41` already carried a comment warning about this and patching around it — for deck2 only. **The executive document and workbook were never patched.**

**Fixed by making `decisionFactTable.ts` the single entry point:** `aggregateDecisions(records, grain, keyOf)` with `grain: "decision" | "image"`. Combined-vs-per-level is purely the caller's `keyOf` — there is no second code path to drift.

Grain assigned per surface on the principle *population profile = image, review accuracy = decision*:
- `model.population.byPort` → image grain, `accuracy` → **`accuracyByImage`**
- `model.portAccuracy` → decision grain, `accuracy` → **`accuracyByDecision`**
- new `model.portAccuracyByLevel` → **`accuracyByDecisionLevel`**

Deleted `buildPortProfiles`' independent fold and `collectLevelAccuracyRows`' manual re-fold. **Two numbers deliberately changed**, each verified: `PortProfile.status` (which drives the narrative's "ports needing intervention" sentence) now derives from decision grain — the fixture flips `"excellent"` → `"priority"`; and `workbook.ts`'s port sheet now sources decision-grain models, which was the literal "document says X, workbook says Y" divergence.

**The root enabler was naming**, so it was closed too: `missedSuspicionRate` carried the same identical-name-across-grains collision and is now `missedSuspicionRateByImage` / `...ByDecision` / `...ByDecisionLevel`. A cross-grain read is now a compile error. Verified as a pure rename — the suite returned **exactly** its pre-rename count with no snapshot or numeric assertion changed.

> One brief correction found during the work: `suspiciousDetectionRate` was assumed to collide as well. It does not — the decision grain's equivalent is already named `detectionRate`. Only the image-grain field took a suffix.

### 2. R2 — Distribution report: per-stage and per-port sections

### 4. Month aggregate + auto-lock (the owner's "sit in stone" requirement)

> *"once data is processed and finished … it never load the population or raw it read the static the final output"*

New `population.aggregate.json` beside `processing.summary.json`. Enforcement is centralized in `loadMonthForEditing`: once `manifest.status === "closed"`, population and raw reads are skipped **regardless of what `MonthLoadScope` requested**, so a caller cannot accidentally opt back in.

Admin reopen is gated on `canMutate("archive.closeMonth")`. The lock mechanism itself is unchanged — only the trigger and the distinction are new.

### 5. Oversight bulk reassignment — and the bug behind the original report

## v62.0 — 2026-08-07 — Refactor (perf): reference-not-copy across derived files, slim replacement index, shared query cache, virtualization

**Why:** the owner's workspace was **~312 MB of JSON from ~28 MB of source Excel (~11×)**, and every page that needed data reloaded it independently. v61.0 fixed the distribution *write* path; this entry attacks what remained: duplicated row storage, no shared cache, and no virtualization.

**Measured on real data throughout** (Risk.xlsx + BI.xlsx → 70,297-row population, 8,000-row sample, 15 employees), via the `scripts/bench/` harness added in v61.0.

### The headline: workspace disk 384.9 MB → 184 MB (52% smaller, 2.1×)

| Artifact | Before | After |
|---|---|---|
| `replacement-index/noncertscan.third.json` | **137.7 MB** | **15.4 MB** (−89%) |
| `distribution.current.json` | 18.8 MB | **6.8 MB** |
| `main.samples.json` | full-row sized | **5.5 MB** |
| each `{username}.samples.json` | full-row sized | **~540 KB** |
| **total workspace** | **384.9 MB** | **184 MB** |

**The single largest waste was found during verification, not by any earlier audit.** `replacement-index/noncertscan.third.json` measured **137.7 MB — the same size as `population.final.json` itself**. The replacement index stored complete `PreparedPopulationRow` objects bucketed by `(certScanStatus, stage)`, and because nearly every real row is `noncertscan` + `third`, one bucket held essentially the whole population. Prior documentation described it only as "up to 10 bucket files" and never as a full-population duplicate. It was a **sixth** copy of every row, on top of the five already known.

### What changed

**1. The replacement index stores a 6-field projection, not full rows.** Reading every consumer established exactly what candidate *selection* needs: `isEligibleCandidate` (`replacement.ts:73-86`) reads only `xrayImageId` and `certScanStatus`; the cascade filters read `stage` and `portName`; the dialog renders `xrayEntryDate` and `plateOrContainerNumber`. Nothing else is read before a candidate is chosen. The new `ReplacementIndexRow` is exactly that `Pick`.

The full row is now resolved **by id, for the one chosen candidate only** — never for the pool. `approveReferral.ts` already did this; `XrayReferrals.tsx`'s immediate-replace path now does too.

**Determinism preserved:** selection, cascade, and the seeded `capSeeded` cap are untouched, and the existing equivalence-with-full-scan tests assert identical candidate ids **and order**. `REPLACEMENT_INDEX_FORMAT_VERSION` 1 → 2, so an old full-row index is treated as stale and rebuilt by the existing non-fatal background path — simpler and safer than dual-shape reading.

**2. Derived files reference rows instead of inlining them.** `DistributionEntry.row` now carries `EmployeeMirrorRowStub` (a strict `Pick`) rather than the full row. Because `main.samples.json` and every `{username}.samples.json` are direct copies of `DistributionEntry[]`, one change fixed three files.

**The stub field set was derived from the actual JSX**, not from the type: all three employee-facing views (`XrayReferrals`, its `subComponents`, `XrayInspectionResults`) read the same 17 fields via `entry.row.*`. A new contract test (`employeeMirrorFields.contract.test.ts`) regex-scans those files' real source and **fails if any component reads a field outside the manifest** — because the guarantee that an employee never has to load the 500k-row population is only as good as the stub's completeness, and static enumeration would erode on the next feature.

Migration is free: the stub is a strict subset, so old full-row entries satisfy it structurally.

**3. `rawRow` — a correction to an earlier claim.** It was reported as ~2× of the population file. **It is not persisted at all** — `Tabs/Population/index.tsx` strips it before every `saveMonthRun`. Two genuine post-processing consumers exist (`populationExporter`'s unmapped-columns export; the executive workbook's "Raw — Risk" sheet), so removing the field would have silently broken two live features. Instead `stripRawRow()` guards the one boundary where it could still leak: a draw run on freshly-processed, not-yet-saved rows.

**4. Shared data layer (TanStack Query v5).** `queryClient.ts` with `staleTime: Infinity` and all automatic refetch triggers disabled. `queryRefreshBridge.ts` wires the **existing** 3-minute tick and manual refresh into `invalidateQueries`.

> **One invalidation authority, deliberately.** The app already had a single tick deciding staleness. Letting Query's heuristics *also* decide would reintroduce the duplicate-load problem this layer exists to remove.

Migrated: the four duplicated `listMonthFolders` call sites (`App.tsx`, `Archive` ×3, `GlobalMonthProvider` ×2). Deliberately **not** migrated: the Population wizard's `useMonthLoad` and the Employee Workspace loaders — they carry hand-tuned token/race guards from the boot-splash bug saga, and converting them safely needs its own pass.

**Scope boundary:** Query's cache is per-tab and in-memory. It fixes cross-page duplication, **not** cold start — that is v61.0's on-disk checkpoint.

**5. `DataTable` row virtualization (TanStack Virtual).** RTL decided the library: react-window's RTL support is documented-broken and v2 drops it from `List` entirely; TanStack Virtual's gap is horizontal-only, irrelevant for vertical rows. The DOM shape (table/tr/td, sticky columns, expand rows) is unchanged, so RTL and sticky-offset CSS are untouched — only *which rows exist* changed.

**6. React Compiler + `scheduler.postTask()`.** Compiler enabled via `@rolldown/plugin-babel` (Vite 8 is rolldown-powered; `@vitejs/plugin-react` v6 no longer accepts the classic babel option). `yieldToMain` now prefers `scheduler.postTask({priority:"user-visible"})` with a `setTimeout` fallback, which is the only path under Node/jsdom.

Now classifies by `error instanceof RangeError` plus a wording-tolerant message test — matching `casLoop.ts`'s deliberate `error.name` pattern. Tested against both wordings.

The folder-numbering convention (numeric = ordered pipeline stage; unprefixed = unordered collection) is now documented in `data-system-report.md`. **No existing root was renamed** — workspace migration has no safe apply path.

## v61.0 — 2026-08-07 — Refactor (distribution): per-writer NDJSON segments + persisted fold checkpoint

**Why:** the owner reported `تطبيق وحفظ التوزيع التلقائي` taking **3–6 hours** for a ~9,000-row sample, and the whole app being slow on any screen needing distribution state. Both trace to one cause: **one immutable JSON file per assignment event**.

Research settled the direction before any code was written. The per-file cost is a **Chromium platform tax**, not an app inefficiency: `createWritable()` routes every write through a swap-file + verification pipeline (Chromium bug 40899722); the "in-place write" mode that would bypass it is unimplemented and blocked indefinitely, and the WICG spec has no batching or transaction API. **Reducing file count is the only available lever.** Tuning the write protocol, raising the concurrency ceiling, and waiting for the platform were each evaluated and rejected.

**Measured against the owner's real data** (Risk.xlsx + BI.xlsx → 70,297-row population, 8,000-row sample, 8,000 assignment events, 15 employees) with a new Node harness that drives the app's real pipeline:

| | Before | After | Change |
|---|---|---|---|
| Write — filesystem ops | **192,063** (24.0/event) | **78** (0.01/event) | **2,462× fewer** |
| Write — wall time | 18,958 ms | 909 ms | 21× faster |
| Cold fold (page reload) — ops | **32,023** | **30** | **1,067× fewer** |
| Cold fold — wall time | 2,317 ms | 225 ms | 10× faster |
| Files on disk | **16,046** | **49** | **327× fewer** |

The measured write cost was **24 ops per event**, materially worse than the ~10 estimated from code reading — the existence check alone accounts for ~11 failed lookups per new file.

> **These are Node `fs` numbers.** Operation counts, file counts and fold costs are faithful; **absolute wall-clock is not a browser prediction**, because `node:fs` has no equivalent of Chromium's swap-file pipeline. The op-count reduction is what translates to the browser, and it is where the hours went.

**What changed:**

**1. Per-writer append-only segments.** `distribution.events/{deviceId}-{sessionId}.ndjson` — one segment per writer session, with a whole batch appended in **one** write instead of one write per event. `deviceId` persists in `localStorage`; `sessionId` is fresh per session, so two machines and two tabs never share a segment.

**The collision-free multi-writer guarantee is preserved** — uniqueness moved from per-event to per-writer-session, a coarser but equally safe partition. This is what local-first systems (Automerge, Yjs) do: batched per-client change logs, not a file per change.

**2. Legacy files are read forever.** Existing `{eventId}.json` files are still read and merged, and are **never rewritten or deleted** — a machine on an older build may still be reading them.

**3. Persisted fold checkpoint.** `{segmentOffsets, legacyEventFileNames, knownEventIds, quotaFacts, deriveVersion}` resumes a fold from where it left off, reading only new segment tails. This is what takes cold load from 32,023 ops to 30 — and unlike the previous in-memory cache, **it survives a page reload**, which is why every session previously re-read all ~9,000 files.

**4. Late events force a full refold — never an in-place patch.** `findLateEvent` compares each new event's `(eventAt, eventId)` against the entry's last, per `xrayImageId`; any out-of-order event discards the checkpoint entirely. **This fold is not commutative** — it enforces legal terminal transitions (assigned → completed → replaced), so incremental application of an out-of-order event would silently produce a wrong terminal state on real audit data. On a shared network folder with several machines this is routine, not an edge case. Golden-fixture tests assert the refold output is identical to folding from scratch.

**5. Change detection by segment byte size**, compared against the checkpoint's recorded offset — monotonic and clock-skew-immune. **`lastModified` is deliberately not the deciding signal**: it is wall-clock and unsynchronized across machines on a network share. A directory name listing is also insufficient, because segments *grow* — a name diff misses new events entirely.

**6. Cheap write verification.** The full read-and-parse verify became a `File.size` check; Chrome's `close()` already performs its own finalization.

**7. A regression caught by measurement, then fixed.** The first implementation *awaited* the cache write, reasoning it was "one small JSON file, never proportional to event count". Benchmarking disproved that: `distribution.current.json` measured **18.8 MB** for this month, because every entry embeds a full population row. Awaiting put a multi-megabyte write on the hot path and made warm re-derive **~6.7× slower than before this work**. Reverted to fire-and-forget with failures surfaced through the error ring buffer — the cache and checkpoint are an optimization, never a correctness input. **Had this shipped unmeasured, the change would have made the most common interaction worse while the headline numbers looked excellent.**

**8. `getDistributionDeviceId()` fallback bug**, found and fixed during implementation: with no `localStorage` it generated a *new* random id on every call, fragmenting every batch into its own segment — the exact degraded case that most needs consolidation.

**Deliberately NOT done — segment compaction.** Reliably distinguishing a closed writer session from a crashed tab cannot be proven safe within this scope, so segments are never compacted. Correctness over tidiness; the file count is already 327× lower.

**Migration/rollback:** additive and dual-read. Existing per-event files remain valid and are never touched; new writes go to segments. Rollback is a code revert — but note that events written to segments meanwhile would then require the newer build to read, since the older build has no segment reader. No existing file is rewritten or deleted at any point.

**Files:** `src/data/distribution/**` (event store, storage, derivation, log, types, plus new `distributionFoldCheckpoint.test.ts`), `src/data/storage/directoryScan.ts` (new `readSegmentTails`), `src/components/Sidebar/Tabs/Population/populationWorkflowHelpers.test.ts`, and a new `scripts/bench/` harness (4 files) that runs the real pipeline over real Excel input.

**Before:** (one file per event; any append forces a blind full refold)
```ts
// distribution.events/{eventId}.json — one file per event
await writeImmutableDistributionEvent(dir, month, event);   // ~24 fs ops each
// any append invalidated the cache, forcing a full re-fold of every event
```

**After:** (one batch append; reads resume from a checkpoint)
```ts
// distribution.events/{deviceId}-{sessionId}.ndjson — whole batch, one write
await appendDistributionEventSegment(dir, month, events);
const resumed = await tryResumeFromCheckpoint(...);         // 30 fs ops, not 32,023
```

**Verification:** all tier-3 gates green.
- `npm run lint` clean · `npm run typecheck` clean
- `npm run test:run` — **196 files / 1649 tests passed** (was 195/1642 → +1 file, +7 tests)
- `check:complexity`, `check:hex-literals`, `check:vendor` clean
- `npm run build` succeeds · `check:bundle-size` **3008.4 kB / 1000.7 kB gzip** (budget 3.6 MB / 1.3 MB)
- `check:release` consistent at v61.0.0
- Before/after benchmarked on real data by swapping `main`'s distribution code into the working tree, measuring, then restoring — numbers above.

With the cache write no longer awaited, a second immediate call may re-derive rather than read the just-persisted cache, stamping a timestamp 1 ms later. The entries are identical; the test now excludes `derivedAt`, a derivation timestamp rather than business data. The test's intent — that both paths agree on distribution *state* — is unchanged.

## v60.0 — 2026-08-07 — Fix (p0): comma input, modal portal, KPI shared load+template, sampling total, save progress, session persistence

**Why:** the owner walked the app end-to-end on real data (500k+ rows) and reported 42 defects, recorded verbatim in `docs/product/APP_WALKTHROUGH_FEEDBACK_2026-08-07.md`. A six-agent code-grounded study (`REWORK_PHASE1_STUDY_2026-08-07.md`) verified each against source rather than trusting the report — **and refuted two of the three defects that had been ranked most critical.** This entry ships the P0 slice: items that are blocking, already producing wrong output, or fixable at near-zero risk.

Two hypotheses were **rejected after investigation** and deliberately not "fixed":
- *CertScan % applied additively, causing 7,000 → ~9,000.* Refuted: quota is `Math.min`-capped at three layers and `hamiltonApportionment` allocations sum exactly to the request. **The draw algorithm was not touched.**
- *Stage aliases overlapping L1/L2 result aliases in source.* Refuted: `stage: ["STAGE", "المستوى"]` is disjoint everywhere. A first pass at overlap validation flagged the shipped defaults as broken — that was a **false positive** (see below) and was corrected before shipping.

**What changed:**

**1. The comma could not be typed into alias fields (blocking).** The inputs were controlled off a *parsed array*: `parseMappingAliases` does `.split(",").filter(Boolean)`, so a trailing comma produced an empty token that was filtered out, and the next render rebuilt the string via `.join(", ")` — erasing the comma before it could persist. Multi-alias entry was structurally impossible. New `useDelimitedListInput()` keeps raw text in local state as the input's `value` and parses only on blur/Enter, tracking the last commit so an external reset re-syncs without clobbering in-progress typing. `DelimitedListInput` wraps it for use inside `.map()` loops. Applied to **all 10 affected inputs** — column-mapping Risk/BI aliases (system + custom), the four stage-mapping inputs, and both sheet-pattern inputs.

**2. Alias-overlap validation — namespace-scoped.** Detects one field's alias appearing in another's. **The first implementation compared across namespaces and therefore flagged the untouched shipped defaults.** `"المستوى الاول"` is legitimately both a *column-header* alias for `xrayLevelOneResult` and a *cell-value* alias for stage `first` — column names and cell values are matched against entirely different things and never compete. A warning that fires on a clean install trains users to ignore every warning, which is the same failure mode as item 3. `AliasFieldGroup` now carries an `AliasNamespace` (`"column" | "stage-value"`) and overlap is only reported within one namespace.

**3. `نوع الحركة` reported as an unmatched column.** `movementType` is derived 100% from the sheet name (`detectMovementType`) and never consults a column alias, so "no clear match" was structurally guaranteed. Sheet-derived fields now say so instead.

## v59.200 — 2026-08-07 — Change (edit-log): tier the protocol by blast radius + generate entries; refresh stale CLAUDE.md facts

**Why:** a CLAUDE.md audit scored the file 81/100 (B) — architecture and gotcha coverage are strong, currency is not — and surfaced that the edit-log protocol itself had become the dominant per-task cost. Measured across all 687 historical entries: 52,587 lines, averaging 76.5 lines/entry, of which only 13.9% sits inside code fences. The `Before:`/`After:` snippets are *not* the expense; the expense is three things the protocol never intended:

1. **An emergent full-gate `**Verification:**` convention.** It isn't one of CLAUDE.md's seven required fields, but every recent entry runs all nine gates plus a build. v59.198 was a **three-line comment-only change** and still paid the 193-file suite, `tsc -b`, `lint`, `check:complexity`, `check:hex-literals`, `check:bundle-size`, `check:release` and a full `build`. That is minutes of wall-clock proving nothing about a comment.
2. **`Lines:` cost three commands** (`count-lines` before, `count-lines` after, `git diff --stat`) and was quietly wrong: `git diff --stat` never lists untracked files, which is why v59.199's `Lines:` line degenerated into a hedging paragraph enumerating five new test files by hand.
3. **The metric measured itself.** `count-lines` counted `docs/edit logs/` — 52,557 of the old 291,010-line total, **18%** — so every entry inflated the next entry's number and the trend line tracked documentation growth as much as code.

Plus a structural double-write: "record it **before** applying any code edit" forces writing the `After:` snippet before the code exists, then revising it once the edit settles.

**What changed:**

**1. Tier ladder replaces the flat protocol.** Tier 1 (comments, docs, typos, test-only) → 1–2 sentences, no snippets, `lint` + `typecheck` + the affected test file. Tier 2 (most fixes/features, the default) → `Why:` + `What changed:`, snippets, full suite. Tier 3 (refactors, architecture, data formats, releases) → full prose, snippets, all nine gates + build. Tier 3's sweep is now explicitly the **release** gate, not the per-edit gate, with `RELEASE_CHECKLIST.md` named as the authority when actually cutting one.

**2. Entries are generated, not hand-written.** New `scripts/editlog.mjs` (`npm run editlog`) fills in version, date, changed-file list and `**Lines:**`, then prints the tier's gate list. It counts untracked files explicitly rather than trusting `git diff --stat`. `--append` inserts into today's file (creating it if absent, refusing a second file per date); `--sync-package` keeps `package.json` in step so `check:release` passes. Major versions are emitted as `{N}.0` rather than a bare `vN`, because `check:release` compares the heading against `package.json`'s first two segments and a bare `v60` can never match — 23 historical headings have that bare form and would fail the gate if one were ever the newest.
