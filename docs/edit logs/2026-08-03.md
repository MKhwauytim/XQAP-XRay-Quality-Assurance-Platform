## v59.133 — 2026-08-03 — Refactor (population): parallelize saveMonthRun's independent file writes

**What changed:** `saveMonthRunLocked` (inside `saveMonthRun`, the population-save pipeline) previously `await`ed each file write in strict sequence — `risk.source.*` copy, `bi.source.*` copy, `risk.raw.json`, `bi.raw.json`, `population.final.json`, the replacement-index rebuild, `processing.summary.json`, then `month.manifest.json` — even though most of these target disjoint files with no data dependency between them. Per the design spec's write-ordering rule ("parallelize the writes that have no ordering dependency; only the manifest/index needs to commit last"), regrouped the write sequence into three stages: (1) the four independent writes — the two optional source-file copies and the two raw-JSON writes — now run concurrently via `Promise.all`, each conditional branch wrapped in an IIFE so the array passed to `Promise.all` is uniform regardless of which conditions are true; (2) `population.final.json` still writes on its own immediately after, since the replacement-index rebuild that follows reads back this file's envelope revision (a genuine data dependency); (3) the replacement-index rebuild and the `processing.summary.json` write — independent of each other, each depending only on the already-awaited `population.final.json` — now run concurrently via a second `Promise.all`. `month.manifest.json` is unchanged: it still writes strictly last, after everything else has committed. `saveMonthRun`'s public signature and `SaveMonthRunResult` return type are unchanged; only internal write concurrency changed, not external behavior.

## v59.131 — 2026-08-03 — Fix (auth): cover reload-continued sessions for activity-log wiring

**What changed:** Code review of v59.130 found that its three scattered explicit `configureAuthActivityLogWorkspace(...)` call sites (the removed effect's replacement in `applySession()` and the demo-login effect) missed a real case: a session that survives a page reload. `AuthGate`'s `session` state initializes synchronously from `getInitialSession()` → `readRealSession()`, which returns non-null immediately for a valid persisted `sessionStorage` session (SEC-02). For that path neither `applySession()` (no explicit login happened) nor the demo-login effect (`!session` guard is false) ever runs, so `configureAuthActivityLogWorkspace` was never called for the rest of that tab's life — silently turning `recordAuthActivityHeartbeat()`/`endAuthActivitySession()` into permanent no-ops. Fix: replaced the three scattered calls with a single effect gated on `session` truthiness (`if (!session) return;`), covering fresh logins, demo logins, and reload-continued sessions uniformly, since it re-fires whenever `session` or `workspaceStatus` changes regardless of which code path made `session` truthy. Also strengthened the "no active session" characterization test (added in v59.130) to prove the flush actually ran (asserting the `5-system` folder was created) rather than only asserting an empty log — the latter is also trivially true if the flush never happened at all — and added a regression test (`AuthGate.test.tsx`) for the reload-continuation case, verified RED against the v59.130 code (0 calls) and GREEN against this fix.
