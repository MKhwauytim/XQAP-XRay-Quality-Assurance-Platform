## v141.0 — 2026-09-28 — Fix (audit): stop per-save whole-file rewrites of the growing action and error logs

**Why:** After 1-2 hours of work, answer saves got progressively slower. The per-actor action log and per-user error log are whole-file JSON on the share. Past the 2,000-entry cap every append re-read and rewrote the whole per-year archive, which grows unbounded until year end (measured 11.6 MB read / 7.9 MB written per save at 8,000 archived entries). The error log rewrote a ~1,500-entry file for each isolated warning, a persistently unreadable segment logged a new error on every read (feeding that rewrite), and a failed flush could re-send entries under new ids or fire a failing write per new error.

**What changed:**
- `appendWorkspaceAction` and `appendUserErrors` trim to a 1,500-entry low-water mark in ONE archive write once the live log exceeds 2,000, so the archive is rewritten about once per 500 appends. Side effect: the admin actions view (and the error export) now shows 1,500-2,000 live entries per actor or user once past the cap instead of always 2,000; archived entries remain readable through the existing archive readers and no entry is dropped.
- `errorLogSink.ts`: minimum 2-minute (120 s) interval between timer-driven flushes of the live error file (batch of 25, `pagehide` and tab-hidden still flush immediately). Entry ids are assigned once at enqueue, a failed write keeps the same entries queued (nothing dropped, same ids on retry), and after a failure the batch-size bypass is suppressed until the throttled timer fires, so a sick share sees one attempt per interval, not one per error.
- `appendUserErrorsChecked` (new; `appendUserErrors` wraps it) reports success and dedups the batch by id against the live file, so a landed-then-retried batch is idempotent.
- `directoryScan.ts`: a persistently skipped segment is logged once per session per file (keyed by the full directory path, so months do not collide).
- Archives are NOT chunked: file names and JSON shapes are unchanged, so no migration is needed.

**Before:** `const overflowCount = combined.length - maxActionEntries;` (archive rewritten on every append past the cap); `toPersisted` minted a new id on every flush attempt; `void flushErrorLogNow()` after a 5 s timer for every isolated error and on every batch-size hit; `logVanishedEntries` logged on every read.
**After:** `const trimTarget = Math.min(lowWaterActionEntries, maxActionEntries); const overflowCount = combined.length - trimTarget;` (same in `appendUserErrors`); ids minted at enqueue and deduped on append; timer delay `max(flushDelayMs, minFlushIntervalMs - sinceLastFlush)` with `retryBackoffUntil` after a failure; `logVanishedEntries` filters `context|directoryResourceKey(dir, name)` already reported this session.

**Migration/rollback:** none needed; on-disk shapes and file names are unchanged and reverting the commits restores the previous behaviour in both directions.

## v140.26 — 2026-09-28 — Fix (storage): stop false "damaged file" reports from stale cached live reads

**Why:** `safeReadJson` declared a healthy live file "damaged" from a single read. On the UNC/SMB share, `getFile()` can return a `File` with a stale cached size (a leftover 0-byte `create:true` entry, or an older size than the file just written) with no exception; `slice(0, size)` decodes to `""` or a truncated prefix, validation fails, and the read fell through to `.bak`/`.tmp` and logged "the live file is damaged". 30 `storage:bak-recovery` rows from one user's machine (09-13 to 09-22) were this, while no other user ever logged one. Separately, when `safeWriteJson`'s post-commit read-back threw, `.tmp` was left behind for a later stale read to be served from.

**What changed:**
- `safeReadJson` retries a found-but-invalid live read with a wait (150 ms, then 600 ms, bounded by a new `deadline` option) and a fresh read, before `.bak`/`.tmp`. A 0-byte read always retries. Only a complete-document failure (hash or envelope structure) that repeats identically (same size and content hash) stops after one retry; `json-parse`, compressed-CRC and torn-head failures (all possible truncated views) take the full ladder. A throwing retry read falls through to `.bak`/`.tmp` and never propagates.
- The `storage:bak-recovery` entry now carries evidence: snapshot size, bytes read, failure stage (`json-parse`, `envelope`, `hash`, `compressed-crc`, `torn-head`), retry count. Hash and byte count are computed only for reads that already failed validation.
- `safeWriteJson`: a throwing post-commit read-back removes `.tmp` (best effort), logs `safeWrite:post-commit-readback` once per file path per session, and rethrows the original error.

**Before:**
```ts
const live = await readPayload<T>(dir, fileName, { retryMissing });
if (live.payload !== null) return { ok: true, ... };
// found-but-invalid falls straight to .bak/.tmp
...
const verify = await readText(dir, fileName, { retryMissing: true, deadline });
```

**After:**
```ts
let live = await readPayload<T>(dir, fileName, { retryMissing, deadline });
while (live.found && live.payload === null && retries < LIVE_INVALID_RETRY_DELAYS_MS.length) {
  if (!(live.reportedSize === 0) && previousInvalid && isCompleteDocumentFailure(live) /* hash|envelope only */
      && sameInvalidReadResult(previousInvalid, live)) break;
  const delay = nextRetryDelayMs(LIVE_INVALID_RETRY_DELAYS_MS[retries]!, deadline);
  if (delay === null) break;
  previousInvalid = live; await wait(delay); retries += 1;
  try { live = await readPayload<T>(...); } catch { break; }
}
...
try { verify = await readText(dir, fileName, { retryMissing: true, deadline }); }
catch (error) { logPostCommitReadbackFailureOnce(dir, fileName, error); await removeQuietly(dir, tmpName); throw error; }
```

## v140.21 — 2026-09-28 — Fix (distribution): with port restrictions, a stage shortfall is made up in the employee's other stages so monthly totals stay equal

**Why:** With a port restriction active, `calculateBulkAssignment` computed each employee's target per stage. When a restricted employee's allowed rows in one stage fell short of their share, the surplus silently went to other employees and nothing compensated in the employee's other stages — e.g. a cross-stage fixture landed at 220/220/220/140 instead of an even 200 each. The owner's decision (2026-09-28) is that the excluded employee should take extra from their other ports first, and when a stage alone can't cover it, the make-up comes from the employee's other stages, so every employee ends the month at the same total.

**What changed:** `calculateBulkAssignment` now sums each employee's per-stage Hamilton targets into a month target (`monthTargets`) and records which employees are allocated in each stage (`stageUsernames`). After the existing per-stage/per-port assignment pass, a new deterministic step (`rebalanceTowardMonthTargets`) walks newly generated events from the end backwards and moves individual events from any employee above their month target to any employee below it, but only where the receiver has an active allocation in that row's stage, is port-eligible for that row's port, and — for a CertScan row — is licensed. Events that already carry a daily-quota stamp never move, so a following step (`restampDailyQuota`) recomputes and reapplies that stamp using each employee's post-rebalance count within its original stage/port group. Unrestricted runs are untouched (the new code returns immediately when no restriction is active); this was verified against the pre-change snapshot baseline (`8ef4331`) — every `[no-restriction]` snapshot entry is byte-identical. The same rebalance also evens out a CertScan Case B imbalance (one licensed employee absorbing all of a group's CertScan rows and landing over their stage share while an unlicensed colleague falls under theirs, `bulkAssignment.ts` ~245-249) whenever it occurs inside a **restricted** workspace and the shortfall employee has a reachable group to draw from — it is not CertScan-specific, just the general equal-month-target rule applied to whatever caused the imbalance.
