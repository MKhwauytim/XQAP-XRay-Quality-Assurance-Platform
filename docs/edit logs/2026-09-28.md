## v140.10 — 2026-09-28 — Fix (storage): read answer/distribution segment tails in parallel

**Why:** Every answer-save attempt (`readAllAnswerEventsForMonth` → `readAnswerEventDelta` → `readSegmentTails`) opened every matched segment file in the month sequentially. On a Windows SMB share, every file open is a network round trip, so a month with many segments turned each save into one SMB round trip per segment, serialized even though each individual read is small. The sibling directory-scan helpers in the same file (`listDirectoryEntriesWithSize`, the bounded-signature reader) already use the shared `forEachBounded(..., DIRECTORY_READ_CONCURRENCY, ...)` helper for exactly this reason; `readSegmentTails` was the one remaining sequential walk.

**What changed:** `readSegmentTails` now reads its matched segment files through `forEachBounded(matched.length, DIRECTORY_READ_CONCURRENCY, ...)` instead of a plain `for` loop, writing each segment's `{size, tail}` result (or `null` on a vanished/exhausted-retry file) into a pre-sized array by index. A second, synchronous loop then walks that array in the original name-sorted `matched` order to populate `sizeByName`/`tailTextByName` and the `vanished` list exactly as the old loop did — so output ordering, the vanished/skip semantics that `appendOnlyEventLog.ts`'s strict mode relies on (`matchedNames` minus `sizeByName` = vanished), and the shared per-call `VanishRetryBudget` are all unchanged; only the file opens themselves now happen with up to `DIRECTORY_READ_CONCURRENCY` (8) in flight at once instead of one at a time.

## v140.9 — 2026-09-28 — Fix (referrals): stale reload can no longer downgrade a submitted answer

**Why:** A background silent reload of the employee referrals queue (triggered by the 45s auto-sync tick or the manual refresh button) could start reading an employee's answers *before* a submit's write landed on disk, and then resolve and commit its stale copy *after* the submit finished. Because `loadData`'s `commit` called `setAnswers(answerItems)` unconditionally, that stale read silently overwrote the just-submitted row back to "not submitted" — the employee sees their submission vanish and has to resubmit, with no error and no indication anything went wrong.

**What changed:** Added a save-generation guard (`XrayReferrals/localSubmissions.ts`: `useLocalSubmissionGuard`) that is separate from the existing `loadTokenRef` (which continues to guard only month-switch/user-change races — bumping it on every save was considered and rejected, since it would leave a real in-flight month switch stuck in `loading` with no load left to finish it). Each `loadData` pass captures a generation number at its start (`beginLoad`); `handleSave` records every successful submission against the guard's current generation (`record`, called right after the write succeeds). When a pass is about to commit its loaded answers, `settle` merges back any locally recorded submission whose generation is *newer* than the pass's start generation over a loaded copy that is missing or has an older `lastSavedAt` — this is exactly the case where the load started before, and resolved after, the submit — and then prunes submissions the pass's own generation already covers (it started after them, so disk is now authoritative for those).

**Before:**
```ts
        setAnswers(answerItems);
        setLoadState("ready");
```

**After:**
```ts
        setAnswers(localSubmissions.settle(answerItems, loadGeneration));
        setLoadState("ready");
```
