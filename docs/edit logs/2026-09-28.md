## v140.2 — 2026-09-28 — Fix (population): refuse a population overwrite that would orphan a worked sample

**Why:** `saveMonthRunLocked`'s TOCTOU guard only re-checked for a sample when `confirmedOverwrite` was false — `confirmedOverwrite: true` skipped the data layer entirely, so a month that already had a distribution and answers could be overwritten by a population sharing none of the sampled ids. Reports key on `xrayImageId`, so every sampled id missing from the new population silently vanished from them — the field incident this fixes was a re-import from the wrong period that zeroed a month's reports.

**What changed:** New `populationOverwriteGuard.ts`: `loadPopulationOverwriteImpact` reads the month's sample, distribution and answers (strictly — see below), and pure `assessPopulationOverwrite` computes which live sampled ids (`liveSampleRows`) are absent from the new rows by delegating the set difference to `scanReferentialIntegrity(...).sampleOrphans` (B3's existing orphan scan) rather than a second implementation, and decides `blocked` (distribution or answers exist AND at least one live sampled id is missing). `saveMonthRunLocked` now runs this check unconditionally, under the manifest lock, before the existing TOCTOU `sampleExists` check, and refuses with a new typed `overwriteBlocked` field on `SaveMonthRunResult`'s failure arm and the new `population_overwrite_blocked_error` label — whatever `confirmedOverwrite` says. Per the controller's F21 ruling, the distribution/answers reads are strict: `loadPopulationOverwriteImpact` uses `loadOrDeriveDistributionCurrentStrictForRead` (throws `DistributionUnreadableError` on an unreadable distribution) and `loadAllEmployeeFiles` (already rethrows on a failed scan, per its own doc comment) rather than the brief's null-swallowing `loadOrDeriveDistributionCurrentForRead` — a read failure propagates out of `saveMonthRunLocked` and is caught by its existing outer try/catch, which turns it into a coded refusal instead of silently treating an unreadable month as having no work. Per F12, the fixture builders (`makePopulationRow`, `makeSampleMaster`) used by this test and future Tasks 4/8 live in a new shared `populationTestFixtures.ts`, not inline in the test file.

## v140.0 — 2026-09-28 — Fix (integrity): boot self-check no longer flags the deck-preference files in 6-templates as unrecoverable

**Why:** The admin boot self-check reported a healthy `executive-deck-edition.json` (and `deck2.style-choices.json`) as an unrecoverable template on every admin sign-in. `inspectAllTemplateFiles` treated every `*.json` in `6-templates` as a template except two hard-coded names (`templates.index.json`, `template.selection.json`); the deck-edition and deck2 style-choice preference files also live in that folder with no `templateId`/`fields`, so `classifyLive` misclassified them as `corrupt`, no sibling qualified for recovery, and `recoverTemplateFile` returned `unrecoverable`, which `bootIntegrityScan.ts` surfaced as a `needs-attention` finding.

**What changed:** `templateStorage.ts`, `templateSelectionStorage.ts`, `deckEditionPreference.ts` and `deck2/styleChoices.ts` now each export their own file-name constant (`TEMPLATES_INDEX_FILE`, `TEMPLATE_SELECTION_FILE`, `DECK_EDITION_PREFERENCE_FILE`, `DECK_STYLE_CHOICES_FILE`) instead of keeping it module-private. `templateFileRecovery.ts` imports all four into one lazily-built `isNonTemplateFile()` set and gains a new `TemplateCandidate` member, `{ kind: "not-a-template" }`, for readable JSON that has no `templateId` — distinct from `corrupt` (damaged/unreadable JSON), so it is never flagged and never fed to the repair path. `inspectAllTemplateFiles` filters directory entries through `isNonTemplateFile()` instead of two hard-coded string comparisons, and additionally drops any report whose `live.kind` is `"not-a-template"` before it reaches the boot scan.
