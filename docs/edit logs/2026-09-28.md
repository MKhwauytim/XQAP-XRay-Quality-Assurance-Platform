## v140.4 — 2026-09-28 — Fix (population): thread strict reads through the segment-tail primitive itself

**Why:** A scoped re-review of v140.3 re-ran the ORIGINAL reproduction on a clean copy of that commit and found both findings still open, plus a distribution twin: with a `NotReadableError` fault on ONLY an individual `.ndjson` segment file (no directory-open fault, no `distribution.log.json` fault), the overwrite guard still reported `answerCount`/`distributionCount` 0 and `saveMonthRun` still returned `{ ok: true }`, overwriting an answered/distributed month. Cause: `readSegmentTails`/`readListedEntry` (`directoryScan.ts`) treats a persistent per-file `NotReadableError` as a "vanished" listing entry and silently excludes it without ever throwing — v140.3's `strict` flags on `loadAllEmployeeFiles` and the distribution strict reader only stop catching an ALREADY-thrown error, and this read never threw one. v140.3's own F21 tests never caught this because their fault sets also included a directory-open or `distribution.log.json` fault, which throws for unrelated reasons and masked the `.ndjson` portion being inert.

**What changed:** `readEventSegmentDelta` (`appendOnlyEventLog.ts`) — the shared primitive both distribution's and answers' `.ndjson` segment reads bottom out at — gains `options?: { strict?: boolean }`; strict mode throws a new `EventSegmentUnreadableError` naming any segment `readSegmentTails` would otherwise have silently skipped, before building the returned delta (so an incremental read cache downstream can never persist a partial result as complete). Threaded end-to-end on both sides: answers via `readAnswerEventDelta` → `readAllAnswerEventsForMonth({ strict })` → `loadAllEmployeeFiles`'s strict branch (which was calling the event-log read with no options at all); distribution via `readDistributionEventSegmentDelta` → `readCurrentDistributionSource`/`readNewEventsSinceCheckpoint` → `loadDistributionLogDetailed`/`tryResumeFromCheckpoint` → `loadOrDeriveDistributionCurrentOutcome`'s new `strict` option → `loadOrDeriveDistributionCurrentOutcomeForRead` (dedupe key now strict-aware, so a lenient and a strict reader for the same month never share an in-flight promise) → `loadOrDeriveDistributionCurrentStrictForRead` (which was also calling through with no options). The in-session derive memo is now bypassed entirely when strict, so a strict caller can never be served a result an earlier non-strict read of the same month already computed. `populationOverwriteGuard.ts` needed no changes — it already asked both entry points for a strict read; they just could not honor it before this. Added a faithful `.ndjson`-only regression test (no other fault) at both the guard and unit level for both distribution and answers, a `readEventSegmentDelta` strict-mode unit test, and corrected two now-false comments claiming a per-segment fault could never reproduce the incident.

// appendOnlyEventLog.ts
export async function readEventSegmentDelta<TEvent>(
  parentDir: DirectoryHandleLike,
  knownOffsets: Record<string, number>,
  config: AppendOnlyEventLogConfig,
  options?: { strict?: boolean }
): Promise<SegmentEventsDelta<TEvent>> {
  const strict = options?.strict ?? false;
  // ...
  const { tailTextByName, sizeByName, matchedNames } = await readSegmentTails(eventsDir, {
    suffix: config.segmentSuffix,
    knownOffsets,
  });

  if (strict) {
    const skipped = matchedNames.filter((name) => !sizeByName.has(name));
    if (skipped.length > 0) throw new EventSegmentUnreadableError(skipped);
  }

  const events: TEvent[] = [];
  for (const name of matchedNames) {
    const tailText = tailTextByName.get(name);
    if (tailText) events.push(...decodeEventLines<TEvent>(tailText, name, config.diagnostics.segmentParseError));
  }
  return { events, offsets, segmentNames: matchedNames };
}

## v140.2 — 2026-09-28 — Fix (population): refuse a population overwrite that would orphan a worked sample

**Why:** `saveMonthRunLocked`'s TOCTOU guard only re-checked for a sample when `confirmedOverwrite` was false — `confirmedOverwrite: true` skipped the data layer entirely, so a month that already had a distribution and answers could be overwritten by a population sharing none of the sampled ids. Reports key on `xrayImageId`, so every sampled id missing from the new population silently vanished from them — the field incident this fixes was a re-import from the wrong period that zeroed a month's reports.

**What changed:** New `populationOverwriteGuard.ts`: `loadPopulationOverwriteImpact` reads the month's sample, distribution and answers (strictly — see below), and pure `assessPopulationOverwrite` computes which live sampled ids (`liveSampleRows`) are absent from the new rows by delegating the set difference to `scanReferentialIntegrity(...).sampleOrphans` (B3's existing orphan scan) rather than a second implementation, and decides `blocked` (distribution or answers exist AND at least one live sampled id is missing). `saveMonthRunLocked` now runs this check unconditionally, under the manifest lock, before the existing TOCTOU `sampleExists` check, and refuses with a new typed `overwriteBlocked` field on `SaveMonthRunResult`'s failure arm and the new `population_overwrite_blocked_error` label — whatever `confirmedOverwrite` says. Per the controller's F21 ruling, the distribution/answers reads are strict: `loadPopulationOverwriteImpact` uses `loadOrDeriveDistributionCurrentStrictForRead` (throws `DistributionUnreadableError` on an unreadable distribution) and `loadAllEmployeeFiles` (already rethrows on a failed scan, per its own doc comment) rather than the brief's null-swallowing `loadOrDeriveDistributionCurrentForRead` — a read failure propagates out of `saveMonthRunLocked` and is caught by its existing outer try/catch, which turns it into a coded refusal instead of silently treating an unreadable month as having no work. Per F12, the fixture builders (`makePopulationRow`, `makeSampleMaster`) used by this test and future Tasks 4/8 live in a new shared `populationTestFixtures.ts`, not inline in the test file.
