## v123.2 — 2026-08-25 — Chore (build): raise the built-app size ceiling to 30 MB at the owner's direction

**Why:** The owner set the ceiling for the built app at **30 MB**. The previous limits — 4.00 MB raw / 1.30 MB gzip in `scripts/check-bundle-size.mjs` — had been raised five times in eight days (3.60 → 3.75 → 3.80 → 3.90 → 3.95 → 4.00), each time to pay for one feature, each time leaving the next feature to negotiate for another few kilobytes. At 3868.5 kB the build was sitting on ~1 % of raw headroom, so the gate had stopped measuring risk and started rationing ordinary work.

This is a policy decision, not another feature-by-feature raise: nothing grew, and no feature is being paid for. Hence the minor bump despite the tier — the shipped app is byte-for-byte unchanged.

**What changed:** `MAX_BYTES` 4_000_000 → 30_000_000 and `MAX_GZIP_BYTES` 1_300_000 → 10_000_000 in `scripts/check-bundle-size.mjs`, with a dated note in the same style as the five raises above it.

**Gzip had to move too, or the raise would have been a no-op.** The two limits are checked with `||`, so whichever binds first is the real ceiling — and at 1.30 MB gzip the effective raw cap was about 4 MB. Leaving it alone would have kept the old gate under a new number. 10 MB is the same ~3.1× ratio this bundle actually achieves, so raw stays the binding constraint at the value the owner named.

**Raw is the figure that matters in this deployment, contra every earlier note in that file.** Those notes all say "gzip governs actual transfer", which is true of a static-server deployment and false of this one: the app is copied onto a Windows share and opened directly — the 2026-08-25 error logs show `file:///Y:/…html` and `file:///Z:/…html` — and a `file://` load performs no content-encoding negotiation at all. Every byte of the raw figure is read off the SMB share on every open. If the app is ever served over HTTP instead, gzip becomes meaningful again and that reasoning inverts; the note says so.

**The drift guard moves rather than disappears.** 26 MB of headroom cannot catch a 200 kB accident, so the ceiling is no longer the regression check — the `Measure (pr)` CI job is. It builds the PR and `main` and reports raw/gzip Δ in the PR comment on every push, so unexplained growth stays visible per-change regardless of where the ceiling sits. The file now says explicitly which of the two is the hard stop and which is the guard.

`CLAUDE.md`'s build note was stale independently of this (it still quoted "~3.34 MB raw, ~1.11 MB gzip; budget 3.6 MB / 1.3 MB", two raises out of date) and is corrected to the current figures, the new ceiling, and the `Measure (pr)` delta as the thing to actually read.

**Migration/rollback:** No runtime or on-disk effect whatsoever — this file is a CI/release gate and is not part of the shipped bundle. Rollback is reverting the two constants. Nothing that ships changes size, and no existing workspace is touched.

Load time off a contended share scales with the raw figure, and the browser parses the whole inlined module graph before first paint, so the users who hit the XQ-IO-032 contention are the same ones who would pay for a larger file. The font-subsetting optimisation the file describes (~100 kB+ reclaimable by subsetting the two Arabic families to the glyphs actually used) remains the right piece of work whenever it is worth doing; it is simply no longer urgent.

## v123.1 — 2026-08-25 — Fix (auth/errorlog): attribute a RESTORED session's errors to their role, not to nobody

**Why:** The admin's XLSX export of the 2026-08-25 error log (44 rows, four users) showed `الدور` empty on **20 of 44** rows — and not randomly. The split is per-user and total: `jalgahamdi` carries a role on all 22 of their rows; `saalhijji` (16) and `admin` (2) carry none on any.

`setErrorActor` was called from exactly one place, `writeSession` — i.e. only on an explicit login. `readRealSession`'s restore branch rehydrates the session from `localStorage` on a fresh page load and starts the auth-activity session, but never set the error actor. So every error logged during a **restored** session was attributed to nobody for the whole page load.

Two things hid this. `username` looked fine, because `errorLogSink.toPersisted` substitutes its own `fallbackUsername` when the ambient one is absent — `role` has no such fallback and was simply dropped. And since the SEC-02 relaxation persists the session across a browser restart, a restore is the NORMAL way a user arrives, so the broken case was the common one rather than an edge.

The cost is not cosmetic: role is what tells a triager whether a failure is permission-shaped, and `ErrorEntry.role` is documented as "that user's REAL role — never an admin's previewed role", a distinction the log could not make when it recorded no role at all.

**What changed:** `readRealSession`'s restore branch now calls `setErrorActor(runtimeSession.username, runtimeSession.role)` alongside the `startAuthActivitySession` it already made. It is placed in `readRealSession` rather than `readSession` deliberately: that is the preview-ignoring reader, so the log records the real role even while an admin is previewing another one. An expired restored session still attributes nothing — the call sits inside the same `!isExpired` guard.

New `authSessionErrorActor.test.ts` covers all four cases (login, restore, restore-under-role-preview, expired restore). It is a separate jsdom file because the restore path reads `localStorage`, which does not exist in this repo's default node test environment — under node `readRealSession` would find nothing to restore and the tests would pass vacuously. `__dropRuntimeSessionForTests` drops the in-memory session without touching storage, which is what a page reload does and the only way to reach that branch from a test.

**Also in this entry — paying back the `max-lines-per-function` headroom v123.0 spent.** The PR report on #106 flagged `XrayReferrals` at **1450 / 1450, zero headroom**, +4 from that entry's `useUnsavedWork` call, with its own standing note that "past raises were paid for with a refactor, not a bigger number". Pure function, byte-identical logic, every import it needs already present in that module; the caller keeps the memo and its dependency array unchanged. `XrayReferrals` drops to ~1423 lines — **~27 lines of headroom restored**, and the ceiling is untouched.

## v123.0 — 2026-08-25 — Fix (storage): classify and retry Chromium's stale-snapshot InvalidStateError (XQ-IO-036), and stop the feedback index write storm

**Why:** On 2026-08-25 four users (`admin`, `saalhijji`, `jalgahamdi`, `amonem`) on the shared SMB/UNC workspace hit repeated write failures reported as **XQ-IO-032**. `jalgahamdi` failed eleven consecutive answer saves across 88 minutes. Every entry in all four exported error logs carried the same underlying exception sentence — *"An operation that depends on state cached in an interface object was made but the state had changed since it was read from disk."* — which is Chromium's fixed text for DOMException **`InvalidStateError`**: the `(size, mtime)` snapshot an interface object cached no longer matched disk when the operation touched the bytes. `getFile()` snapshots and the later `text()`/`slice()` compares; `createWritable()` snapshots and the later `close()` compares.

That DOM name was classified **nowhere**: not in `classifyFileSystemError` (which fell to `default: return null`), not in `isTransientWriteError`, and not in any of the six read-retry loops in `safeWrite.ts` — each of which gated on `isNotReadableError` alone. So the fault received **zero** in-place retries from any of the ladders this repo had built for exactly this class of SMB timing failure, received no error code, and fell out to `casLoop`'s `resolveErrorCode(lastCause) ?? "XQ-IO-032"` — a code whose own catalog meaning is literally *"the exception carried no more specific code."* The only thing that retried it was `casLoop`'s outer loop, which re-runs the entire ~9-pass read-modify-write, 14 times on the answer path. That is the coarsest and most write-amplifying granularity available, and each retry's own write re-arms the same staleness race.

**Rejected: widening the retry ladder.** Commit `85a965a`, the evening before, had already widened `ANSWER_SAVE_MAX_RETRIES` to 14 × 150 ms for these exact failures. The incident happened the next morning under that ladder. More attempts add write amplification to a share that is already the problem.

**Rejected: redefining XQ-IO-032.** The catalog is append-only by doctrine (`errorCodes.ts`) and by test (`errorCodes.test.ts` pins the whole map). XQ-IO-036 is appended instead.

**Rejected: a `localStorage` answer draft.** Inspection answers are business data, and this repo's two-persistence-layers doctrine puts business data on the workspace side. Pinning the tab achieves the same protection without crossing that line; a draft cache would need an owner decision and a `storageRegistry.ts` key.

A second, independent bug surfaced in the same logs and is fixed here too: a CAS **write** to the single shared `threads.index.json` ran on the feedback **read** path, which `FeedbackUnreadProvider` mounts app-wide and polls every 60 s for every signed-in user on every page. That is why a manager sitting on `reports/kpi` appears writing a feedback file. It could not converge — a repair that fails leaves the index exactly as stale as it found it, so the next poll rediscovers the same ids and tries again, on every machine, forever.

The diagnosis itself was the third finding: `logError` recorded `.message` and `.stack` but never `.name`. A DOMException's name is the only stable, non-localised thing about it and is what every classifier switches on, so the one field that would have named this fault was absent from the artifact meant to reveal it.

Full multi-model analysis, per-model verdicts, contested points and the solution design: `docs/audit/XQ-IO-032_MULTI_MODEL_FINDINGS_2026-08-25.md`.

**What changed:**

**1. The fault is retried, classified and named.** `isSnapshotStaleError` (`transientFileErrors.ts`) recognises `InvalidStateError` by DOM name and joins `isTransientWriteError`, so `retryTransientWrite` covers the write path — `writeText` already re-opens the handle per attempt, so every retry takes a genuinely fresh snapshot rather than repeating a call that can never succeed. New code **XQ-IO-036** in `errorCodes.ts` plus a `classifyFileSystemError` case, and label `err_io_036_stale_snapshot` whose Arabic says what happened, what did *not* (the file is not damaged, the workspace grant is not lost) and what to do.

**2. All six read paths share one retry decision.** `readText`, `readContent`, `classifyFile`, `openFile`, `streamFileChunks`'s window reader and `readEnvelopeMetadataTolerant` had six hand-written copies of the same `isNotReadableError` branch — which is why this class could be fixed in five places and still be broken in the sixth. They now share `readRetryDelayMs` over a per-read `ReadRetryBudget` that counts the two conditions separately. `fileSystemAccess.ts`'s own read (login, every sync tick) gets `readTextRetryingStaleSnapshot`, which retries **only** the stale snapshot — never `NotFoundError`, which on a read means absent and must stay prompt.

`SNAPSHOT_STALE_RETRY_DELAYS_MS` is `[20, 60, 150, 400]`, deliberately the same shape as the existing write ladder and deliberately not longer: an inner ladder multiplies against `casLoop`'s outer one and makes one machine hold a contended file longer. The inner ladder absorbs a blip without discarding the whole cycle; the outer ladder owns the long tail.

**3. `readContent` touches a small file's bytes once, not twice.** It sliced for classification and then called `text()`, with awaits between — two validations of the same snapshot, so two chances at the fault on every small-file read, and one extra SMB round trip. Its own doc comment had always claimed otherwise. A file the 8 KB head window fully covers is now decoded from that window, guarded on strict `window.byteLength === file.size`; compressed, damaged and larger files take the unchanged paths.

**4. `casLoop` no longer discards a write because it could not confirm it.** The delayed `verify()` sat inside the outer `catch`, so a verify that **threw** was treated as a detected lost update — discarding a write that had already passed its in-attempt read-back and re-running the whole cycle, adding another write to a share that had just failed a read.
