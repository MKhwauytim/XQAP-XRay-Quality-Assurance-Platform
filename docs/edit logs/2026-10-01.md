## v150.45 — 2026-10-01 — Fix (answers): a pending answer already on disk is announced once, not every 30 s

**Why:** One employee's PC (`jalgahamdi`) reloaded data in a loop after load while other PCs were fine. `replayPendingAnswers` runs every 30 s; when a pending answer is already on disk it calls `markSynced` (`mirrorAnswerLocally`), which is best-effort and swallows every IndexedDB failure. On a PC whose browser storage cannot record the confirmation the record stays pending forever, so every pass re-read the month, counted `alreadyOnDisk`, and broadcast `notifyLocalDataChange(["answers"])`, which makes every mounted view reload silently. The loop was per-PC because the pending queue lives in that browser's IndexedDB. The same share also refuses replace-on-close (XQ-IO-036), which is why that PC's answer chain had 147 rotated segments, but that is a separate, share-wide condition and is not changed here.

**What changed:** `pendingAnswerReplay.ts` remembers, per session, each pending item (user + month + item + its `lastSavedAt`) it has seen on disk or written. A remembered item is still counted and its `markSynced` is still retried (storage may recover), but it is not re-read from disk and not re-announced; the broadcast fires only for a write that landed or an item seen on disk for the first time. A newer save of the same item has a new `lastSavedAt`, so it is treated normally. Remembered items whose pending record is gone are pruned each pass.

**File:** `src/data/answers/pendingAnswerReplay.ts`

**File:** `src/data/answers/pendingAnswerReplay.test.ts`

**After:**
