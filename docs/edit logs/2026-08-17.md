**1. The reported create-workspace ritual ("fails once, works after re-pick + re-grant") — root-caused as a four-link chain, three links closed.**

## v98.6 — 2026-08-17 — Fix (distribution): rotate away from an unreadable own segment instead of failing the save (XQ-IO-031)

**Why:** Fourth field report of `XQ-IO-031`, this time explicitly *after* the v98.0 patient ladder and the v98.3 extension probe — the owner's Phase 4 bulk save still ends in a red XQ-IO-031 bar. Tracing the fatal paths again confirms v98.3's map is still accurate: `safeWriteJson`'s exhausted read-backs surface as XQ-IO-009/010, so the only site that can put **031** on the screen from a Phase 4 save is `appendDistributionEventSegment` when the pre-append re-read of a segment **this session wrote** exhausts its ladder.

That path was fatal *for a reason*: the exhausted re-read fell back to `""`, the append then **rewrote the segment without lines that may still be on the share**, and the unconfirmable post-close check was the only signal of that possible data loss (v97.1 deliberately kept it fatal). More patience (v98.0) and better diagnosis (v98.3) both left the underlying hazard in place — a write to a file whose current content we provably could not read.

**What changed:** the hazard is removed instead of reported. When the baseline is unreliable, the writer **rotates**: the unreadable segment is abandoned in place — never rewritten, its bytes still on the server, its events still part of the log the moment the share shows it again (every reader discovers segments by `.ndjson` suffix glob, and sealed segments were already never touched) — and the batch lands in the next segment of the chain, whose empty baseline is trustworthy. The existing bounded-rotation machinery (v85) provides the naming, the memo, and the reader semantics; this adds one rotation trigger. An unconfirmable post-close check on the fresh segment is then benign (`XQ-DIST-007`, per v97.1's committed-write doctrine) instead of fatal, so there is **no remaining read-back-invisibility path that fails a Phase 4 save** — failure still surfaces where it is real: the write itself erroring, or a read-back that *sees* a wrong size (`XQ-DIST-008`).

The rotation target cannot collide: `openSegmentSeqByWriter` and the written-segment memo advance together, so the current seq is the highest this session ever wrote, and no other writer shares a `{device}-{session}` chain. At `MAX_SEGMENT_SEQ` (unreachable in practice) the old fatal behaviour is retained.

**File:** `src/data/distribution/distributionEventStore.ts` — rotation on `!existing.reliable`

**File:** `src/data/distribution/distributionEventStore.notFound.test.ts` — the "still fails when the file stays invisible" pin is REWRITTEN to pin the rotation: append resolves `"verified"`, the abandoned segment keeps its exact bytes, the batch and all subsequent appends land in the rotated sibling, and the exhausted-retry classifier still logs the lag

**File:** `src/data/distribution/replacement.notFound.test.ts` — the unreliable-baseline case flips from "STILL fails, in Arabic" to "succeeds by rotating": under a total `.ndjson` read blackout the replacement now returns ok, every event folds once the view clears, and the share's misbehaviour is recorded in the error log rather than shown as failure

## v98.5 — 2026-08-17 — Fix (distribution, adhoc-import): fresh terminal-state gates + on-disk ad-hoc record

**Why:** A parallel read-only audit of v98.4's own blast radius — "where else does this exact bug shape live?" — confirmed the reassign/complete paths were protected on the *assignee* side (the fold's `priorTransitionValues` reads the existing on-disk entry, not the event, pinned by the golden tests) but found the *status* side open, plus one sibling of the bulk-assign bug in ad-hoc import.

**1. `handleRequestReplacement` could regress a completed row — the fold does not stop it.**

`isIllegalTerminalTransition` blocks only `assigned`/`reassigned` after `completed`. A `replacement-requested` event folds straight through, so a supervisor whose Phase-4 table was loaded before another machine completed row R could click استبدال and **regress `completed` → `replacement-requested`**. Downstream that is not cosmetic: `executeReplacement`'s terminal guard tests for `"completed"`, which no longer matches — the already-answered row could be retired from the sample, **orphaning the submitted answer** — and `autoLockWhenFullyDistributed` never fires, and every report under-counts completions. This handler and `handleMarkComplete` are the *only* emitters of these event types, so gating them closes the hole without touching fold semantics (no `DERIVE_VERSION` bump).

All three remaining mutating handlers now gate on the row's **fresh on-disk** entry via a shared `readFreshEntry` (the same read `handleAssign` gained in v98.4, now hoisted into one helper): request-replacement requires fresh `pending`; reassign refuses fresh `completed`/`replaced`/missing; mark-complete refuses fresh `completed` (a fold-accepted no-op that still advanced the last-activity stamp), `replaced` (fold-dropped), or missing. `replacement-requested` → complete stays allowed on purpose — completing supersedes the pending request. Refusals repaint from the fresh log and use the new `msg_row_state_changed_on_disk`, which also ends the false «تم …» success messages the fold-dropped events used to produce. Reassign/complete events are now built from the fresh entry, so the event's "from" side names the actual owner in row history instead of this tab's stale guess.

**2. `assignAdhocRowsToEmployee` trusted the caller's tab record — the bulk-assign bug's sibling.**

The record handed in is React state, hours old on a shared workspace, and `saveAdhocImportRecord` is a whole-document overwrite (its CAS loop reads the existing record only to compute `nextRevision`; Web Locks are per-browser and mean nothing across machines). So a stale tab could: assign into an import another machine had **closed** and revert its status to open on save; durably assign a row an admin had **excluded** meanwhile, writing the exclusion away; and rebuild `rows` from its stale copy, wiping every other machine's `assigned`/`assignedTo`/`assignedAt` bookkeeping. The distribution-event side was already covered by the `ownedIds` guard — the *record* side was not.

The function now re-reads the record from disk first and uses that fresh copy for the closed-status gate, the excluded/assigned row filters, and as the base of the rewrite, so other machines' bookkeeping survives.

## v98.4 — 2026-08-17 — Fix (distribution): stale-snapshot assign guard + resumable partial replacement

**Why:** The two Phase-4 findings recorded as "deliberately NOT in this entry" under v98.0, both reported live on the owner's shared UNC/SMB workspace, and neither requiring an algorithm-version bump.

**1. Assignment was idempotent only against this tab's snapshot — a stale tab silently transferred rows.**

`calculateBulkAssignment`'s owned-row filter and `handleAssign`'s "unassigned" rendering both read `distributionCurrent` — React state from whenever this tab last loaded the month, potentially hours old on a shared folder. Every row another supervisor assigned since then looked free, and the fold's `assigned` handler overwrites `assignedTo` unconditionally (only `completed`/`replaced` are terminal), so committing the batch moved those rows to new owners with no `reassigned` event, no notification, and nothing in the audit trail. The original assignee's queue just shrank on the next mirror sync.

Both handlers now re-read the on-disk log immediately before the durable write. The bulk path drops events whose row already has an entry and reports the skipped count (new labels `msg_bulk_assign_stale_skipped` / `msg_bulk_assign_all_taken`); the manual path refuses with the current owner's name (`msg_assign_row_already_owned`) and repaints via `refreshDistribution`. The residual race is the append window itself, which no backend-free design can close — this shrinks "hours" to "milliseconds", which is what is achievable here (see CLAUDE.md's ordering note).

**2. XQ-DIST-005 was a permanent dead end — a partial replacement could never be completed.**

`executeReplacement` appends the sample row (retiring the dead id in the same CAS write) and then writes the events. When the events write failed on the flaky share, every retry hit the replacement-taken guard — `approveReplacement` step 3b and `XrayReferrals.handleReplace` both read "row already in the sample" as a conflict — and returned `stale-ownership`, forever. The dead row stayed live, the appended row stayed stranded with no owner, and the request could be neither approved nor withdrawn usefully.

The new `classifyReplacementRowAvailability` (in `replacement.ts`, used by both call sites) recognizes the partial-write fingerprint — row in sample **and** unowned **and** the dead id recorded in `replacedRowIds` — as `"resume-partial"`: the retry proceeds, the sample append no-ops, and only the missing events are emitted. Every other occupied state stays `"taken"`, including an unowned drawn row whose dead partner was never retired (normal in a partially-distributed month).

The secondary trap is also closed: retrying with a *different* candidate in that state used to slip past every guard and reach `appendSampleRow` as a plain enlargement — `totalActual` +1 forever plus a permanently stranded first-candidate row. `appendSampleRow` now refuses when `replacesXrayImageId` is already retired but the incoming row is new, with the new **XQ-SMP-008**, whose Arabic says the actual remedy: retry the original replacement, don't pick a new row.
