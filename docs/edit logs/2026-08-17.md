## v99.0 — 2026-08-17 — Fix (distribution): short segment names, chunked appends, and a per-event fallback so a Phase 4 save survives every share failure mode

**Why:** Fifth field report of `XQ-IO-031` on the owner's shared workspace — after v97.1 (keep a committed write), v98.0 (an ~11 s read-back ladder), v98.3 (the extension probe) and v98.6 (rotate away from an unreadable segment). Four fixes, four reports: that is no longer a failed hypothesis, it is a wrong model, so this entry stops adding patience and instead removes the assumptions the model rests on.

What the code proves after v98.6, by elimination: `safeWrite`'s exhausted read-backs return `null` and surface as XQ-IO-009/010, `verifySegmentSize` is only fatal on an unreliable baseline (which v98.6's rotation all but removes), so the one remaining site that can put **031** on screen during a Phase 4 save is the segment **write itself** — `getFileHandle(create:true)` / `createWritable()` raising `NotFoundError` through `retryTransientWrite`. And `031` is by definition the verdict *after* `classifyNotFound` created `.fs-reachability-probe.tmp` **and** round-tripped `.fs-extension-probe.ndjson` in that same directory. A folder that takes both probes but permanently refuses this write is not flaky and is not extension-blocked: it is refusing this **name**.

The owner also reports every other feature — Phases 1–3, reports, answers, approvals — saving and reading normally. Only `distribution.events/` fails, and it is the only place the app writes an 80-character name (`{deviceUuid}-{sessionUuid}.ndjson`, 87 with Chromium's `.crswap` sibling) inside the deepest directory in the tree. Every other file it writes is short: `distribution.log.json` 21 characters in the same folder's parent, `sample.master.json` 18, and the pre-segment `{eventId}.json` 41. Windows caps a path at 260 characters, so on a deep UNC workspace path the 26-character probes fit while the segment name does not — which is exactly a permanent, per-name `NotFoundError` in a genuinely writable directory.

**This entry is written WITHOUT a confirming measurement, deliberately and at the owner's instruction** ("can't do tests now, add all possible fixes for all possible scenarios"). So it does not bet on the length hypothesis: it closes every candidate cause, each independently, and adds the diagnosis that names which one it was on the next report. A probe script for the real share (`probe-share-writes.ps1`, short/long/`.crswap`/2 MB cases with an async-survival re-check) is with the owner; the remaining datum is the `distribution:append-segment` error-log line.

**What changed — six independent defences:**

**1. Segment names are 22 characters, not 80.** `segmentBaseName` now takes 8 filename-safe characters of the device id and 6 of the session id (`{8}-{6}.ndjson`), shorter than the legacy per-event names that worked for months, with 2^56 of distinctness between concurrent writers. Compatibility is free and needs no migration: readers discover segments by `.ndjson` suffix glob, so long-named files from earlier versions keep being read and folded; a writer simply never appends to them again, and nothing is renamed, so `foldCheckpoint.segmentOffsets` stays valid. A collision would only mean two writers sharing one chain, which the read-modify-write append already survives.

**2. The write itself gets the patient ladder.** The post-close read-back has used the ~11 s ladder since v98.0 while the write it verifies still gave up in ~630 ms. Failing here aborts a whole month save, so there is nothing to buy by giving up early.

**3. One retry against a freshly-resolved directory handle.** `getSampleMainDir` answers from the workspace directory-handle cache, and a handle held since mount goes stale when an SMB session idle-disconnects — the documented "works after re-picking the folder" ritual. On a failed append the storage layer purges that cache, re-resolves, and retries the chunk once.

**4. Per-event `{eventId}.json` fallback.** If the NDJSON append still fails, the batch is written in the pre-segment layout that every reader already merges (`loadImmutableDistributionEvents`, and the checkpoint path's `legacyEventFileNames`). Names are 41 characters and the extension is `.json`, so this survives an `.ndjson`-blocking scanner. It is slower, and that is the right trade against refusing to distribute the month. Degradation is restricted to `NotFound`/`NotReadable` — a revoked grant, a full disk or a browser without `createWritable` fails the per-event path identically, so those keep failing fast with their own already-classified code (XQ-IO-017 / XQ-IO-020 / XQ-DIST-006) instead of burning one write per event to reach the same error. Engaging the fallback logs the new **XQ-DIST-009**, so an admin learns the fast path is unusable here rather than silently paying per-event costs forever.

**5. No single giant write.** `shouldRotate` deliberately lets an oversized batch exceed the cap once (an empty segment must never rotate, or a large batch would never land) — which put one ~2.3 MB write on the share for a whole-month bulk assignment, the slowest and most failure-prone write the app performs. `chunkEventsForSegmentAppends` bounds every append by `MAX_OPEN_SEGMENT_BYTES`/`MAX_OPEN_SEGMENT_LINES`, so a 9,000-event month is many ~128 KiB writes and a failure costs one chunk. Chunk order preserves input order, so fold order is unchanged. The save-progress bar now advances per chunk instead of jumping 0 → 100.

**6. Two causes the classifier could not see.** `classifyNotFound` now (a) re-checks the extension probe after a 1.2 s delay, because antivirus/DLP/sync clients quarantine asynchronously and always won an instant round trip — that verdict is the existing XQ-IO-033; and (b) probes with a **same-length, same-extension** name, whose failure is the new **XQ-IO-034**, whose Arabic says the only remedy that works: move the workspace closer to the share root. Both are on the already-exhausted failure path, so a healthy share pays nothing.

**Migration/rollback:** No data migration and no format flag. New writes land in `{8}-{6}.ndjson` (and `-{seq}` siblings); every previously written `{36}-{36}.ndjson` segment, and every legacy `{eventId}.json`, is still read, merged and folded — the reader contract was always a suffix glob. Fold output for an unchanged event set is unchanged (chunking only splits the writes; `mergeDistributionEvents` and `distributionEventSetIdFromIds` dedupe by `eventId`, so a retry or fallback writing an event twice is absorbed). Rollback is reverting these files: older builds read the short names as ordinary segments, since nothing about the name is interpreted on the read path.

## v98.7 — 2026-08-17 — Fix (workspace, population, sampling): unreachable is not missing; audit round across all four phases

**Why:** Three parallel read-only audits of Phases 1–2, Phase 3, and the end-to-end workflow (the owner asked for a full sweep after two live field reports). This entry lands every finding that is confirmed, caller-side, and does not touch a deterministic-by-contract algorithm. The owner-decision and higher-risk findings are recorded at the end, not swept in.

**1. The reported create-workspace ritual ("fails once, works after re-pick + re-grant") — root-caused as a four-link chain, three links closed.**

`checkWorkspaceStructure` read EVERY probe rejection as a missing folder, so a live workspace on an idle-disconnected SMB session was reported `missing_structure` — whose admin card offers «إنشاء بنية مساحة العمل». `createWorkspaceStructure` then (a) had zero transient tolerance on the folder creates — the session's *first* write-shaped touch of the share, exactly the operation that fails once after an idle disconnect — and (b) unconditionally overwrote `workspace.manifest.json` (new workspaceId) and `users.permissions.json` (every account, role and Argon2id hash replaced by defaults) when run over an existing workspace. And the only recovery surface offered was the picker, which is why the re-pick + re-grant ritual "worked": the OS dialog re-established the SMB session.

Now: only a named NotFoundError counts as missing — any other probe failure returns the **error** status with the new **XQ-FS-015**, whose Arabic says retry/reconnect and explicitly not to create (the error card has no create button, and the same code path also covers the required-file reads: `permission_denied`/`read_failed` are no longer classified as "invalid"). The folder phases ride `retryTransientWrite`. And the create **keeps** a healthy (valid envelope, current schema) manifest/users file byte-for-byte — the invalid-structure repair still recreates corrupt or wrong-version files — while a file it cannot READ refuses the create outright instead of overwriting what it could not verify.

**2. A users-file read flake could end in the real user set being wiped.** `loadWorkspaceFiles` returned `null` for an unreadable `users.permissions.json`, the provider hydrated the shipped default users, and the next admin edit persisted that default set wholesale (userSync writes full in-memory state). It now throws XQ-FS-015 — the structure check that just passed proves the file was readable moments ago — and `applyWorkspaceHandle` fails the mount to the error card instead of proceeding on defaults. `reconnectWorkspace` also clears demo read-only mode, same one-line hardening `selectWorkspace` got in v97.0.

**3. CRITICAL one-day regression: `rawRow` was serialized for every row without BI extras.** v98.1's non-enumerable guarantee held only on the extras branch; the empty-extras branch (`row.rawRow = base`) re-created an enumerable own property — and that branch is the COMMON one: risk-only imports, BI-unmatched rows, matches with no extra keys. Every such row's full raw Excel row went into `population.final.json`, roughly doubling it and every read of it, silently reversing the fix's stated guarantee. Now `Object.defineProperty(..., enumerable: false)` on both branches, and the regression test covers the empty-extras shape (it fails pre-fix).

**4. A transient config read failure destroyed `config.json`.** `loadPopulationConfig`'s catch wrote `DEFAULT_POPULATION_CONFIG` over the file for ANY throw — custom mapping templates, stage aliases, sampling rules, employee allocations gone, from a path that runs on every wizard mount. Defaults are now seeded only on a genuine NotFound (fresh workspace); any other failure logs and returns defaults in memory without writing.

**5. Phase 3 wizard guards (all caller-side; `drawSample` itself untouched, no `SAMPLING_ALGORITHM_VERSION` bump):**
- **Empty draw refused.** A config whose stage targets all resolve to 0 "succeeds" with an empty sample (golden-pinned caller trap); saving it wrote an empty `sample.master.json` and irreversibly advanced the month to `sampled` (status is monotonic). `handleDrawSample` now refuses with the new `msg_sample_draw_empty_refused`.

- **Sampling proof only on a successful save** — a failed master save no longer writes a proof describing a draw that is not in `sample.master.json`.

Reprocess-confirm dialog stamped to its month.** The dialog survived a global month switch and `commitSaveToDisk` recomputes its target from the current render, so confirming after switching wrote month A's population into month B with `confirmedOverwrite: true` bypassing the TOCTOU sample re-check. ## v98.6 — 2026-08-17 — Fix (distribution): rotate away from an unreadable own segment instead of failing the save (XQ-IO-031)

**Why:** Fourth field report of `XQ-IO-031`, this time explicitly *after* the v98.0 patient ladder and the v98.3 extension probe — the owner's Phase 4 bulk save still ends in a red XQ-IO-031 bar. Tracing the fatal paths again confirms v98.3's map is still accurate: `safeWriteJson`'s exhausted read-backs surface as XQ-IO-009/010, so the only site that can put **031** on the screen from a Phase 4 save is `appendDistributionEventSegment` when the pre-append re-read of a segment **this session wrote** exhausts its ladder.

That path was fatal *for a reason*: the exhausted re-read fell back to `""`, the append then **rewrote the segment without lines that may still be on the share**, and the unconfirmable post-close check was the only signal of that possible data loss (v97.1 deliberately kept it fatal). More patience (v98.0) and better diagnosis (v98.3) both left the underlying hazard in place — a write to a file whose current content we provably could not read.

**What changed:** the hazard is removed instead of reported. When the baseline is unreliable, the writer **rotates**: the unreadable segment is abandoned in place — never rewritten, its bytes still on the server, its events still part of the log the moment the share shows it again (every reader discovers segments by `.ndjson` suffix glob, and sealed segments were already never touched) — and the batch lands in the next segment of the chain, whose empty baseline is trustworthy. The existing bounded-rotation machinery (v85) provides the naming, the memo, and the reader semantics; this adds one rotation trigger. An unconfirmable post-close check on the fresh segment is then benign (`XQ-DIST-007`, per v97.1's committed-write doctrine) instead of fatal, so there is **no remaining read-back-invisibility path that fails a Phase 4 save** — failure still surfaces where it is real: the write itself erroring, or a read-back that *sees* a wrong size (`XQ-DIST-008`).

The rotation target cannot collide: `openSegmentSeqByWriter` and the written-segment memo advance together, so the current seq is the highest this session ever wrote, and no other writer shares a `{device}-{session}` chain. At `MAX_SEGMENT_SEQ` (unreachable in practice) the old fatal behaviour is retained.

**File:** `src/data/distribution/distributionEventStore.ts` — rotation on `!existing.reliable`

**File:** `src/data/distribution/distributionEventStore.notFound.test.ts` — the "still fails when the file stays invisible" pin is REWRITTEN to pin the rotation: append resolves `"verified"`, the abandoned segment keeps its exact bytes, the batch and all subsequent appends land in the rotated sibling, and the exhausted-retry classifier still logs the lag

**File:** `src/data/distribution/replacement.notFound.test.ts` — the unreliable-baseline case flips from "STILL fails, in Arabic" to "succeeds by rotating": under a total `.ndjson` read blackout the replacement now returns ok, every event folds once the view clears, and the share's misbehaviour is recorded in the error log rather than shown as failure

## v98.5 — 2026-08-17 — Fix (distribution, adhoc-import): fresh terminal-state gates + on-disk ad-hoc record

**Why:** A parallel read-only audit of v98.4's own blast radius — "where else does this exact bug shape live?" — confirmed the reassign/complete paths were protected on the *assignee* side (the fold's `priorTransitionValues` reads the existing on-disk entry, not the event, pinned by the golden tests) but found the *status* side open, plus one sibling of the bulk-assign bug in ad-hoc import.

**1. `handleRequestReplacement` could regress a completed row — the fold does not stop it.**

`isIllegalTerminalTransition` blocks only `assigned`/`reassigned` after `completed`. A `replacement-requested` event folds straight through, so a supervisor whose Phase-4 table was loaded before another machine completed row R could click استبدال and **regress `completed` → `replacement-requested`**. Downstream that is not cosmetic: `executeReplacement`'s terminal guard tests for `"completed"`, which no longer matches — the already-answered row could be retired from the sample, **orphaning the submitted answer** — and `autoLockWhenFullyDistributed` never fires, and every report under-counts completions. This handler and `handleMarkComplete` are the *only* emitters of these event types, so gating them closes the hole without touching fold semantics (no `DERIVE_VERSION` bump).

All three remaining mutating handlers now gate on the row's **fresh on-disk** entry via a shared `readFreshEntry` (the same read `handleAssign` gained in v98.4, now hoisted into one helper): request-replacement requires fresh `pending`; reassign refuses fresh `completed`/`replaced`/missing; mark-complete refuses fresh `completed` (a fold-accepted no-op that still advanced the last-activity stamp), `replaced` (fold-dropped), or missing. `replacement-requested` → complete stays allowed on purpose — completing supersedes the pending request. Refusals repaint from the fresh log and use the new `msg_row_state_changed_on_disk`, which also ends the false «تم …» success messages the fold-dropped events used to produce. Reassign/complete events are now built from the fresh entry, so the event's "from" side names the actual owner in row history instead of this tab's stale guess.

**2. `assignAdhocRowsToEmployee` trusted the caller's tab record — the bulk-assign bug's sibling.**

The record handed in is React state, hours old on a shared workspace, and `saveAdhocImportRecord` is a whole-document overwrite (its CAS loop reads the existing record only to compute `nextRevision`; Web Locks are per-browser and mean nothing across machines). So a stale tab could: assign into an import another machine had **closed** and revert its status to open on save; durably assign a row an admin had **excluded** meanwhile, writing the exclusion away; and rebuild `rows` from its stale copy, wiping every other machine's `assigned`/`assignedTo`/`assignedAt` bookkeeping. The distribution-event side was already covered by the `ownedIds` guard — the *record* side was not.

The function now re-reads the record from disk first and uses that fresh copy for the closed-status gate, the excluded/assigned row filters, and as the base of the rewrite, so other machines' bookkeeping survives.

## v98.4 — 2026-08-17 — Fix (distribution): stale-snapshot assign guard + resumable partial replacement

**Why:** The two Phase-4 findings recorded as "deliberately NOT in this entry" under v98.0, both reported live on the owner's shared UNC/SMB workspace, and neither requiring an algorithm-version bump.

**1. Assignment was idempotent only against this tab's snapshot — a stale tab silently transferred rows.**

`calculateBulkAssignment`'s owned-row filter and `handleAssign`'s "unassigned" rendering both read `distributionCurrent` — React state from whenever this tab last loaded the month, potentially hours old on a shared folder. Every row another supervisor assigned since then looked free, and the fold's `assigned` handler overwrites `assignedTo` unconditionally (only `completed`/`replaced` are terminal), so committing the batch moved those rows to new owners with no `reassigned` event, no notification, and nothing in the audit trail. The original assignee's queue just shrank on the next mirror sync.

Both handlers now re-read the on-disk log immediately before the durable write. The bulk path drops events whose row already has an entry and reports the skipped count (new labels `msg_bulk_assign_stale_skipped` / `msg_bulk_assign_all_taken`); the manual path refuses with the current owner's name (`msg_assign_row_already_owned`) and repaints via `refreshDistribution`. The residual race is the append window itself, which no backend-free design can close — this shrinks "hours" to "milliseconds", which is what is achievable here (see CLAUDE.md's ordering note).

**2. XQ-DIST-005 was a permanent dead end — a partial replacement could never be completed.**

`executeReplacement` appends the sample row (retiring the dead id in the same CAS write) and then writes the events. When the events write failed on the flaky share, every retry hit the replacement-taken guard — `approveReplacement` step 3b and `XrayReferrals.handleReplace` both read "row already in the sample" as a conflict — and returned `stale-ownership`, forever. The dead row stayed live, the appended row stayed stranded with no owner, and the request could be neither approved nor withdrawn usefully.

The new `classifyReplacementRowAvailability` (in `replacement.ts`, used by both call sites) recognizes the partial-write fingerprint — row in sample **and** unowned **and** the dead id recorded in `replacedRowIds` — as `"resume-partial"`: the retry proceeds, the sample append no-ops, and only the missing events are emitted. Every other occupied state stays `"taken"`, including an unowned drawn row whose dead partner was never retired (normal in a partially-distributed month).

The secondary trap is also closed: retrying with a *different* candidate in that state used to slip past every guard and reach `appendSampleRow` as a plain enlargement — `totalActual` +1 forever plus a permanently stranded first-candidate row. `appendSampleRow` now refuses when `replacesXrayImageId` is already retired but the incoming row is new, with the new **XQ-SMP-008**, whose Arabic says the actual remedy: retry the original replacement, don't pick a new row.
