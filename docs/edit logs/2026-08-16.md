## v98.0 — 2026-08-16 — Fix (storage, distribution): stop failing writes that succeeded, and stop losing events to a poisoned checkpoint

**Why:** The owner reported `XQ-IO-031` on a real SMB share and asked, plainly, to make it work — then for a 0-to-100 revision of sample processing and distribution. Two parallel audits covered Phase 2/3 and Phase 4. This entry lands the reliability fixes; the audits' remaining findings are recorded at the end rather than rushed.

**1. The read-back ladder was far too impatient — this is the reported failure.**

`XQ-IO-031` specifically means the post-retry probe found the containing directory **reachable and writable**: the write landed, and only one directory entry was temporarily invisible. The app gave up waiting after ~630 ms.

That number came from sharing one backoff ladder between two situations that are not comparable. On an ordinary read, "not found" is a *question* — the file may genuinely not exist, so resolving fast is right. On a post-write verification read (`retryMissing: true`) it is not a question: `close()` has already resolved, so the file provably exists and its absence can only be a stale view. Nothing is gained by giving up quickly; the sole outcome is failing an operation that succeeded.

`VERIFY_READBACK_RETRY_DELAYS_MS` (8 attempts, ~11 s) now serves that path in `safeWrite`, and in `distributionEventStore`'s segment verify. `readExistingSegment` gets it too, but **only** when this session knows it wrote the segment — exhausting that path falls back to `""` and rewrites the file without lines still on the share, so patience there directly shrinks a data-loss window. A fresh writer session keeps the short ladder, because absence is the expected answer there.

11 s is a long time. It is paid only on the failure path, and it replaces aborting a whole month save.

**2. The fold checkpoint permanently swallowed events — silent, unrecoverable data loss.**

The worst finding of either audit. `foldDistributionEvents` absorbs an event whose `xrayImageId` is absent from the `sampleRows` it was handed. The resume path then advanced `segmentOffsets` and `knownEventIds` **past that event anyway** and persisted the sidecar, which is accepted forever after — so the event was never read from disk again.

Absorption is almost always a stale snapshot, not a real orphan: another machine commits a replacement while this one holds a `sample.master` loaded hours earlier. The existing entry guard only caught `sampleRows.length === 0`; stale-but-non-empty is the normal case on a shared folder. The result was an assignment vanishing permanently from the derived state, every employee mirror, the KPI counts, **and** the footprint check that decides whether a user is safe to delete — with no self-heal and no symptom beyond one ring-buffer line.

`deriveCurrentDistributionIncremental` now reports `absorbedAbsentRows`, and the resume declines to checkpoint when it is set. Cost: one re-read next time. **Fold output is unchanged** — this alters only which events reach the fold.

**3. A supervisor action erased replacement rows from employees' mirrors.**

`refreshDistribution` derived from `sampleDrawResult` — React state from whenever this tab last loaded the month — and its guard only fired when that array was *empty*. Every row another machine had added since (i.e. every replacement) was missing, and the derived snapshot is the sole input to `syncSampleMirrors`. The monotonic guard could not help: this write carries a higher `logRevision`, so it wins. Assignees watched replacement rows disappear from their queue. It now always reloads `sample.master.json` first — one small read on a path already doing a full log read.

**File:** `src/data/storage/transientFileErrors.ts` — `VERIFY_READBACK_RETRY_DELAYS_MS`

**File:** `src/data/storage/safeWrite.ts`, `src/data/distribution/distributionEventStore.ts` — use it on read-back paths

**File:** `src/data/distribution/distributionLog.ts`, `distributionStorage.ts` — `absorbedAbsentRows`; refuse to checkpoint past it

**File:** `src/components/Sidebar/Tabs/Population/useDistributionActions.ts` — always reload the sample master

**File:** `src/data/storage/patientReadback.test.ts (new)` — ladder ordering, a lag the old ladder could not absorb, and that ordinary probes stay fast

**Verification:** `lint`, `typecheck`, `test:run` **2579 passed / 291 files**, `build` ✓, `check:release` v98.0.0, `check:bundle-size` 3417.3 kB / 1140.1 kB, `check:complexity` clean. The new suite fails against the old ladder at **643 ms** — the reported failure, reproduced. Two existing tests needed a 40 s timeout: they drive the ladder to exhaustion deliberately, so the longer wait is the behaviour under test, not incidental slowness. That is also the honest cost of this change: an operation that genuinely fails now takes ~11 s to say so.

**Migration/rollback:** No on-disk format change. Existing checkpoints stay valid; the change only prevents writing new poisoned ones — it does **not** repair a checkpoint already poisoned on the owner's share (see below). Rollback is a straight revert.

**Known damage this does not repair.** A checkpoint already poisoned before this fix keeps hiding its absorbed events until something forces a full refold (a `DERIVE_VERSION` bump, a deleted sidecar, or a late-event hit). Deleting `distribution.checkpoint.json` in an affected month forces a clean refold and is safe — it is derived state.

This is almost certainly the live 20 MB-import failure. It is **not** fixed here because `rawRow` is still read by `populationExporter.ts` and `columnMappingHints.ts`, so stripping in place would break Phase 2 export; the correct fix streams the strip through the serialiser and needs care rather than speed.

*Also outstanding:* `replacedRowIds` has exactly one reader, so every `sample.rows` consumer is N rows too large and the executive deck can report >100 % completion on a replaced month; the `exact` CertScan method silently under-fills a mandatory quota in ~12 % of fuzzed configs with no shortfall recorded; a zero-target stage config saves an empty sample and irreversibly advances the month to `sampled`; dedup runs before the validity gate so a duplicate pair can lose its good twin; answer submission emits no `completed` event, leaving the fold's terminal-state protections dormant; bulk assignment is idempotent only against this tab's snapshot, so two supervisors can silently transfer ownership; `XQ-DIST-005` remains a permanent dead end.

## v97.2 — 2026-08-16 — Fix (population): a Web Worker that dies must not hang the UI in silence

**Why:** The last of the audit's "no error code at all" findings, and the worst-shaped one: a Web Worker that **dies** sends no message, so every call site awaiting a promise only `onmessage` could settle waited forever. Nothing on screen, nothing in the error log — strictly worse than a wrong code.

Three sites, all reachable at this workspace's data volume (a 20 MB two-workbook import expanding to hundreds of MB of JSON):

- `populationRowLookup` — the promise never settled, so the `finally` that terminates the worker never ran (leaking it) and the replacement confirm dialog spun with no error. This function exists *because* `population.final.json` is big enough to freeze the main thread, i.e. big enough to OOM the worker parsing it.
- `usePopulationBrowseWorker` — `isLoaded` stayed false, every `runQuery` promise stayed unsettled, and `inFlightLanesRef` never drained so `isQuerying` stayed true. ## v97.1 — 2026-08-16 — Fix (distribution): an unconfirmable read-back is not a lost write

**Why:** The most severe finding of the error-code audit, and the only one with live data-integrity consequences.

`appendDistributionEventSegment` writes the segment, awaits `close()` — at which point the bytes **are** committed; the code says so itself, recording the segment in `writtenSegmentsThisSession` *before* the check for exactly that reason — and only then reads the file back to verify its size. On a UNC/SMB share that read-back can fail with `NotFoundError` purely because the directory entry is not visible yet.

That threw, which aborted `appendDistributionEvents` **before** its projection `casLoop`. So the events were durable on disk while `distribution.log.json`'s revision never advanced — and revision is the staleness authority everywhere:

- `XrayReferrals` judges an employee's mirror current when `sourceLogRevision >= stamp.revision` and short-circuits the derive, so **the assignee did not see the assignment even after a full page reload**.
- The 45 s sync tick probes the distribution family by revision stamp alone, so it never fired, on any machine.
- The operator's own `distributionCurrent` was never refreshed, so a retry ran against the pre-append snapshot, defeating `bulkAssignment`'s idempotency guard and emitting a second set of events with fresh ids.
- And the operator was told the write failed, for a write that had succeeded.

**What changed:** two outcomes that were conflated are now separated.

A file we could not **read** is inconclusive, not failed: log `XQ-DIST-007` and commit the projection, so on-disk state and derived state agree and the assignment reaches its assignee. A size we **did** read and found wrong is a genuine bad write and still throws (`XQ-DIST-008`).

**The relaxation is conditional, and that condition is the important part.** `readExistingSegment` falls back to `""` when it cannot re-read a segment this session wrote — meaning the append is about to rewrite the file *without lines that may still be on the share*. In that case the unverifiable read-back is the **only** signal that events may have just been dropped, so it must stay fatal. `readExistingSegment` now reports `reliable`, and `verifySegmentSize` only treats an unreadable file as benign when the baseline was trustworthy.

That distinction was not in the original design of this fix. It was caught by an existing test — `distributionEventStore.notFound.test.ts`'s "still fails when the file stays invisible on every attempt" — whose scenario is precisely the unreliable-baseline case. Without it this change would have silently dropped events on exactly the flaky share it was written to help.

**File:** `src/data/distribution/distributionEventStore.ts` — `SegmentVerification`; `ExistingSegment.reliable`; conditional relaxation

**File:** `src/data/distribution/distributionStorage.ts` — propagate the outcome; do not abort on `unverified`

**File:** `src/data/storage/errorCodes.ts`, `src/data/labels/labelsStore.ts` — XQ-DIST-007, XQ-DIST-008

**File:** `src/data/distribution/segmentVerifyNotAFailure.test.ts (new)` — projection commits, revision advances, lag is recorded, clean path unaffected

**File:** `src/data/distribution/replacement.notFound.test.ts` — the never-recovers case now asserts success; a new unreliable-baseline case preserves the original no-raw-English guard

**Verification:** `lint`, `typecheck`, `test:run` **2569 passed / 288 files**, `build` ✓. The new suite fails against the pre-fix code (the append rejected and no events were readable). Three existing tests changed: two were `resolves.toBeUndefined()` on a function that now returns its outcome; the third asserted the bug as intended behaviour and was rewritten with its guard preserved in a case that still fails.

**Rollback:** revert the listed source files; XQ-DIST-007/008 stay in the catalog per the append-only rule. No on-disk format change — `unverified` is a runtime outcome, never persisted.

## v97.0 — 2026-08-16 — Fix (storage): stop destroying error codes between the throw site and the screen

**Why:** A six-agent parallel audit of all 89 error codes, prompted by two field reports in a row (`XQ-IO-028`, then `XQ-IO-027`). The audit found that the two bugs already fixed were **instances, not the disease**. The same shape — *the app determines the cause, then destroys it before the user sees it* — was present at every layer, and fixing individual call sites could not work because they were each handed an already-destroyed error.

Four independent agents converged on the same root causes.

**What changed:**

**1. `casLoop` — the root cause, upstream of most of the rest.** Nearly every CAS-protected write funnels through here: answers, notifications, the month manifest and lock, the replacement index, sync settings, the distribution projection. On an exception it did `lastError = err.message` and dropped the error object, so `resolveErrorCode` never ran and a full disk, a revoked grant and a moved workspace folder all reached the UI as the same raw English string — which `userFacingErrorText`, receiving a bare string, could only report as XQ-IO-028. It also silently overwrote the caller's Arabic conflict sentence with English the moment any attempt threw, making a genuine write conflict indistinguishable from an I/O fault. The loop now keeps the error, classifies it, logs it, and separates "an attempt threw" (new **XQ-IO-032**) from "every attempt lost the revision race" (the caller's Arabic sentence, now intact).

**2. `tagError` overwrote instead of preserving — `tagErrorOnce`.** The property is `writable: true` and tagging runs innermost-first as an exception unwinds, so an outer `taggedStep` erased the specific code the inner layer had just attached. `createWorkspaceStructure` carefully stamped `XQ-FS-006`…`XQ-FS-010` to say *which phase* failed; `taggedStep("XQ-WS-005", …)` overwrote every one, making all six unreachable at the UI. It also erased XQ-IO-030/031 — re-burying the "retry" vs "re-pick the folder" verdict one frame above where v96.4 had just surfaced it. Both `taggedStep` helpers are now first-writer-wins, which keeps the most specific code.

**3. Read-only mode leaked into real workspaces — and this is the reported `تعذر فتح مساحة عمل`.** `enterDemoWorkspace` sets the flag; only it and `clearWorkspace` cleared it. The demo entry sits on the same screen as "choose a folder", so demo → pick a real folder left the flag on against a live workspace. Folder creation is not mode-guarded so all six folders were created, then the first `safeWriteJson` threw `ReadOnlyModeError` — surfacing as the bare "could not open workspace" on a brand-new empty folder with permission already granted, and leaving a half-built structure so the retry failed *differently*. `selectWorkspace` now clears it.

**4. Three more discard sites on the user's own pipeline.** Phase 2 `saveMonthRunLocked` flattened the whole five-file month write to `.message`; Phase 3 `saveSampleMaster` hard-coded XQ-SMP-007 without ever calling `resolveErrorCode`; `distributionErrorText` — wired into **all five** Phase 4 actions — resolved the code correctly and then printed the generic sentence anyway, whose text ends "أعد المحاولة". That advised retrying for XQ-IO-030, the one cause where retrying can never succeed, and for XQ-IO-020, a full disk.

**5. Two read-failure-as-absence bugs with irreversible consequences.** `loadEmployeeSampleMirror`'s bare catch made `getUserWorkspaceFootprint` skip its authoritative fold and report `pendingCount` 0 — which User Management reads as "no active assignments, safe to delete". One transient share fault could orphan a live workload, and deleting a user is not undoable. `monthLock`'s `readManifest` failed open on a read fault, silently **unlocking a closed month** so answers and distribution events could land in an already-reported period — and the verdict was TTL-cached, so one bad read kept it open. Both now distinguish a genuine absence (still null) from a failure to look (throws).

**File:** `src/data/storage/errorCodes.ts` — `tagErrorOnce`; XQ-IO-032

## v96.4 — 2026-08-16 — Fix (storage): tell the user WHICH not-found they hit, since the app already knows

**Why:** Follow-up to the same field report. With the XQ-IO-028 masking fixed, the next thing the user saw in Phase 4 was `XQ-IO-027` — *"الملف أو المجلد المطلوب غير موجود"*. Honest, but unactionable, and the app already knew more than it was saying.

`classifyNotFound` (`transientFileErrors.ts`) probes the containing directory once the retry ladder is exhausted, and separates two causes with **opposite remedies**:

- `directory-writable` — the share momentarily lost sight of one entry. Retrying is right.
- `directory-unreachable` — the workspace folder was moved, renamed or re-created since the handle was restored from IndexedDB. **Retrying can never work**; the user has to re-pick the folder.

That verdict was computed, written to the log, and dropped. Both causes rendered the same sentence — useless advice in the first case and *wrong* advice in the second, since the user would keep retrying an operation that cannot succeed. Identical shape to the v96.3 bug one level up: the app knew and didn't say.

A second half turned up while testing: `thrownErrorText` hard-coded `msg_unexpected_write_error` and merely appended the resolved code. So even a correctly classified failure rendered "خطأ غير متوقع أثناء الحفظ" — throwing away the one thing the code existed to carry. XQ-IO-020 is not "unexpected", it is a full disk, and no amount of retrying (which that sentence advises) fixes it.

**What changed:**

`logExhaustedNotFound` now tags the error with the code its own probe implies and returns the cause: `directory-unreachable` → **XQ-IO-030** (new), `directory-writable` → **XQ-IO-031** (new), `permission-denied` → the existing XQ-IO-017. `unknown` is left untagged on purpose, so `classifyFileSystemError` supplies the plain XQ-IO-027 rather than asserting a cause that was never established.

Tagging (not wrapping) is required, not stylistic: the data layer branches on `error.name === "NotFoundError"` and `isNotFoundError` all over, and those verdicts guard against overwriting a month. `tagError` mutates in place and returns the same object, so identity, name, message, stack and cause survive — a regression test pins that, including that the property stays non-enumerable so nothing that spreads or serializes the error changes shape.

`thrownErrorText`/`userFacingErrorText` now render the **code's own label** via `codedMessage`. XQ-IO-028's label *is* `msg_unexpected_write_error`, so the unclassified path is byte-identical to before; every classified path now says the thing that helps.

All four `logExhaustedNotFound` call sites — two in `safeWrite.ts`, two in `distributionEventStore.ts` — inherit this with no changes of their own.

**File:** `src/data/storage/transientFileErrors.ts` — cause→code map; tag and return the cause

**File:** `src/data/storage/errorCodes.ts` — XQ-IO-030, XQ-IO-031 (append-only, catalog rules respected)

**File:** `src/data/storage/writeErrorText.ts` — render the code's own label instead of a hard-coded generic

**File:** `src/data/labels/labelsStore.ts` — two Arabic labels; the XQ-IO-030 one explicitly says retrying alone will not work

**File:** `src/data/distribution/replacement.notFound.test.ts` — the flaky-share case now asserts XQ-IO-031

**File:** `src/data/storage/errorCodes.test.ts` — pinned catalog extended

**Before:**

**After:**

## v96.3 — 2026-08-16 — Fix (distribution): keep the real error code when a Phase 4 event write fails

**Why:** Reported from the field: Phase 4 (distribution) failed with `XQ-IO-028`. That is the catch-all whose own catalog meaning is *"unclassified write/read failure"* — the least useful code we can show. It was being shown for a failure the app had **already identified**.

## v96.0 — 2026-08-16 — Fix (audit): sample totals, CAS-protected writes, and the nested-dialog Escape root cause

**Why:** Remaining accepted findings from the Phase 16/17 verification pass. Each has a regression test proven to fail against the pre-fix code.

---

### P1-A — every replacement permanently inflated `totalActual`

`appendSampleRow` appended the replacement row without retiring the dead one, so `totalActual` grew by one per replacement, forever. Consequences, all silent wrong numbers in the app's primary deliverable: `remainingImages` showed a phantom backlog **exactly equal to the replacement count** (a retired row can never be answered), `completionRate` could never reach 100% on a fully studied month, and `fulfillment` read above 100%.

**Semantics chosen from the consumers, not from preference:** `totalActual` = rows the sample *currently consists of*. Six consumers were checked and every one wants the live reading — `executiveReportData.ts:216,217`, `sampleReport.ts:193,194`, `samplingPlanStorage.ts:224,231`, and two UI counters.

**The obvious fix would have created a worse bug.** Deleting the retired row from `sample.rows` looks correct, but `rows` is simultaneously the audit trail **and the replacement dedup set** — both `buildExclusionSets` (`replacement.ts:63`) and `approveReferral`'s already-owned guard exclude ids present in it. Removing a retired row would let a known-dead image be re-drawn as somebody else's replacement. So `rows` stays append-only and retirement is recorded separately in a new optional `replacedRowIds`.

`incrementPort/StageAllocations` became `adjust…(…, delta: 1 | -1)` with clamping, so a cross-port replacement moves the new row in and the dead row out and the invariant `sum(portAllocations.actualTotalDrawn) === totalActual` survives (tested). Append and retirement are decided independently, so a CAS retry, crash-retry or approval re-run cannot double-count. `executeReplacement` is the single funnel for both call sites.

⚠️ **Already-persisted months are left exactly as stored, not recomputed on read.** `sample.master.json` carries no record of which rows past replacements retired — that exists only in the immutable `distribution.events/` `replaced` events, which `loadSampleMaster` neither reads nor should. So a month drawn before this fix stays inflated by one per pre-fix replacement and self-corrects only for replacements performed *after* it. Remediation sweep, possible but not written: per month, count events with `"eventType": "replaced"`, subtract from `totalActual`, backfill `replacedRowIds` from their `xrayImageId`s.

Proven failing first: all 5 cases — `expected 3 to be 2` (totalActual, including via `executeReplacement` and the KPI path) and `expected 2 to be 1` (the dead row's port never decremented).

### P1-B — `deleteTemplate` clobbered a CAS-protected file

It wrote `template.selection.json` with a raw `safeWriteJson`, bypassing the `casLoop` that file is protected by: a concurrent admin edit was lost and the revision counter reset. Consequence: a workspace-wide blank inspection form.

Both writers now share one CAS path. **A second bug fell out of it:** the "does the selection point at this template?" check previously ran *outside* the write, so an admin who switched selection in between was blanked anyway; it now runs inside the loop against a fresh read. A no-op clear returns without burning a revision.

Proven failing first: `expected undefined to be 4` (revision and token dropped entirely) and **`expected 1 to be 10`** — the literal counter rewind.

**Three more raw-writes over CAS-protected files were found.** One fixed here. Two reported with reasoning rather than changed: the template *tombstone* fallback (a delete losing a concurrent edit is arguably the intended outcome, and a CAS-aware tombstone needs a shape that is not a `TemplateSchema`), and `saveMonthRun`'s manifest write (it holds the shared `manifestLockKey` so same-tab is serialized, but a cross-machine `closeMonth` is lost — reprocessing a month plausibly *should* reset the manifest, so this needs an owner decision). `reportDesignStorage.ts:211` has the same tombstone shape.

### P1-C — nested-dialog Escape closed the parent too (root cause)

Every trap registers `keydown` on `document` in the **capture** phase. `stopPropagation()` governs node-to-node traversal only — listeners on the *same* node all still fire — so one Escape ran every active trap's handler. Live in `MappingSettingsModal` (discarding unsaved mapping edits), and reproduced against the `ModalShell` + `ConfirmDialog` pairing that v94.0 had just made the standard pattern.

**`stopImmediatePropagation` alone is the wrong fix, because registration order is not nesting order:**
- a nested dialog opened from an already-open parent registers **second**, so the parent's handler runs **first** and has already closed it;
- when parent and child mount in the same commit, React runs effects child-first, giving the **opposite** order for the same nesting;
- `enabled`-gated traps re-register on every toggle, reshuffling order arbitrarily.

Replaced with a module-level LIFO stack of active containers. `handleKeyDown` returns unless its container is topmost, decided by explicit containment rather than listener order: a trap nested inside mine wins; mine nested inside another loses; **unrelated** containers (the ModalShell/ConfirmDialog case — both portalled to `<body>`, so neither contains the other) resolve by later activation. **Tab is gated too**, so two live traps can no longer fight over it either. 19 call sites; full suite green. 3 of 4 new hook tests proven failing first.

- **Browse picker + filter menu mutual exclusion** — `DataTable` already had the pattern; `BrowseDataView` omitted it, so both could be open and one Escape closed both.
- **Filter-menu trap never re-armed on a direct column A→B switch** — the menu lives inside the open column's own `th`, so A's node is destroyed and a new one built while `enabled` stays `true`, leaving the effect holding a detached container. New optional `resetKey` folded into the effect deps.
- **`FeedbackWidget`'s `aria-modal` dropped**, `role="dialog"` kept. It is deliberately non-modal — no backdrop, no portal — because you open it *while* working to report what you are looking at. Making it genuinely modal would be a product change disguised as an a11y fix. No existing test encoded the bug; one now asserts the attribute is absent.

Printing now works as the rule was written.

- **Internal scroll** added to `ReassignModal`, the `RequestList` bulk-confirm list, and `MonthLockDialog`, which previously clipped long content or pushed the action row past the viewport.

**Left flagged, not fixed:** `FeedbackWidget` still traps Tab while being non-modal (removing it changes keyboard behaviour for a panel that only just gained a trap); `RestoreDialog` shares `MonthLockDialog`'s unbounded panel and has the same latent overflow.

### The dominant defect: 759 dead `var()` fallbacks, 55 of them lying

**Correction (2026-08-16 verification pass): two claims in this section were false, caught after landing.**

The original text asserted "every token is defined at `:root` in `index.css`." That is false — **11 of the tokens guarded by a stripped fallback were defined nowhere**: `--c-ink-1`, the whole `--color-*` namespace (AdhocImport's private namespace), `--app-text-muted`, `--app-surface-2`. Their fallbacks were **live**, not dead code. Stripping them was only safe because each of those 11 sites was *simultaneously remapped* onto a real token in the same pass — the fallback removal and the retargeting were one inseparable edit, not "delete dead code, done." Framing it as "every token is defined" understates the actual risk that was taken, and **there is no lint rule or CI gate that would catch the next `var(--token, fallback)` strip deleting a live color** — `check-hex-literals.mjs` counts literals, it does not verify a referenced custom property resolves. That is a real, standing hazard for the next person who does this kind of sweep, not a closed loop.

The original text also asserted `index.css` is "loaded first in `main.tsx`," and used that as the reason the fallback strip was safe. That is false too: `index.css` **is** imported first in `main.tsx`'s source (`import "./index.css"` precedes `import "./styles/primitives.css"`), but the single-file production bundle does not preserve that — verified by building and locating the token block inside `dist/index.html`: it sits at roughly the **92nd percentile of the file**, i.e. it is emitted essentially **last**, not first. The strip was safe anyway, but for a different reason than stated: CSS custom-property resolution is cascade-order-independent within `:root` — a `var(--x)` resolves against wherever `--x` is declared regardless of source position, so "loaded first" was never actually the load-bearing fact. Someone reasoning from the original (wrong) claim about load order could reach a wrong conclusion about a genuinely order-sensitive change elsewhere.

Every `var(--token, fallback)` in the app guards a token that is *supposed to be* defined at `:root` in `index.css`. Where that held, the fallback branch was unreachable dead code — yet it accounted for **~60% of all raw hex literals**. Worse, **55 fallbacks disagreed with the token they guard** (e.g. `var(--c-danger, #ef4444)` where `--c-danger` is `#9F1624`), so a file *read* as one color and *rendered* another. ### P0-1/2 — "I couldn't read the file" was treated as "the file is empty"

One pattern, **nine sites** (the audit found seven; two more surfaced during the work). `safeReadJson` distinguishes `missing` from `corrupt` and can also **throw** past its ~2-retry/80 ms budget, but every read-modify-write base read discarded that distinction and substituted an empty default.

- **`answerStorage`** — one transient `NotReadableError` rewrote an employee's answer file with a single answer: 20 → 1, revision reset, `{ok: true}` returned, nothing logged. It also destroyed the referral/replacement/reopen requests sharing that file.
- **`distributionStorage` / `distributionEventStore`** — one unreadable event file made `loadDistributionLog` return **zero** events, so the re-draw hard block read "nothing distributed yet" and let `drawSample` overwrite `sample.master.json`, **orphaning a month of assignments and answers**.
- **`readNewEventsSinceCheckpoint`** *(8th site, not in the audit)* — worse than the rest: it feeds a checkpoint that **advances**, so an event missed there is missed permanently.
- **`readArchiveFile`** *(9th site, not in the audit)* — `archiveOverflow` rewrites the archive from this value, so an empty shell discarded **a year of actions** and simultaneously unblocked the live-log trim.
- Plus `actionLog`, `approvalStorage` (truncating the B5 hash chain, so approved requests revert to pending and become re-approvable), `notificationStorage`, `sampleStorage`.

**The contract:** only a genuine `NotFound` maps to the empty default; everything else propagates. Implemented as a tagged `OptionalReadOutcome` (`found | absent`) in `safeWrite.ts`, because several sites read from two directories and "absent here, unreadable there" needed a defined answer — `readOptionalJson` holds back the first inconclusive outcome, keeps trying later locations, and throws only if none supplied a value. So **a legacy path that is genuinely absent stays `absent`**, while an unreadable current location can never be laundered into absence. Not invented here: `distributionStorage.ts:119` already did exactly this.

**Enabling fix:** `workspacePaths.getRoot` threw a plain `Error` for a missing root — indistinguishable *by name* from a permission failure, so the new rule could not classify it. Now a named `NotFoundError` (message unchanged; `backupStorage.ts:391` matches its prefix). Found by a test, not by reading.

**A test-design correction worth recording.** A *permanent* `NotReadableError` is **not** the bug — it fails `safeWriteJson`'s pre-write read too, so even the old code aborted. The real hazard is a **transient** fault that outlives the retry budget and then clears, letting the write proceed on a truncated base. The tests fire the fault exactly 3 times to hit that window. A naive test here passes against the broken code and proves nothing.

13 of 13 site tests failed against pre-fix code, both fault flavours (throwing and corrupt) per site; 22/22 pass now. P0-1 reproduced verbatim: `expected […] to have a length of 20 but got 1`, with `upsertItemAnswer` returning `{ok: true}`.

**Caller audit:** every non-test `loadDistributionLog` and `loadSampleMaster` caller was checked individually — all fail safe. ### P0-3 — CertScan matched by substring, fabricating the sample composition

`certScanParser.ts` matched pasted serials as substrings. On the real month a serial containing `"2026"` matched **117,268 of 117,337 rows** — and since `certScanStatus` drives the stratified CertScan/NonCertScan split, the month's sample composition was fabricated. The preview panel shared the matcher, so it confirmed the wrong answer instead of warning.

**Real-data characterization first.** X-ray IDs have exactly two shapes, both placing the device code on a boundary around an embedded 8-digit date: `[device][YYYYMMDD][seq]` and `[YYYYMMDD][device][seq]`. 311,697 distinct IDs, 99.91% pure digits, only 148 (0.05%) with no parseable date — so essentially every ID contains `2026`.

| rule | legitimate paste | `"2026"` | `"0260"` | `"202605"` |
|---|---|---|---|---|
| substring (old) | 20,315 | **117,268** | 117,268 | 117,267 |
| naive `startsWith` | **174** | 20,045 | 0 | 20,045 |
| **head/tail anchored (new)** | **20,239** | **10** | **10** | **0** |

**The obvious fix would have created the mirror-image P0.** Naive prefix-anchoring drops legitimate matches from 20,239 to 174, because it only understands shape A. `splitXrayIdSegments` splits each ID at its first valid embedded `YYYYMMDD` and requires a snippet to be anchored at the start of the head **or** tail segment — never inside the date or the sequence interior. All 76 rows that substring-matched but no longer do are demonstrable coincidences inside sequence digits (serial `2366` "matching" `95|20260503|422366`).

Two deliberate loosenesses guarding against false negatives: head-**prefix** rather than head-equality (so a family stem `96601` still matches device `96601PB04`; scores identically on real data, so the looser rule is free), and undated IDs degrade to whole-ID prefix rather than becoming permanently unmatchable.

**Part 1, shipped alongside:** an implausibly-HIGH match warning (>90%) to complement the existing <5% one. Threshold justified against data — the most generous legitimate paste the real month supports tops out at **17.31%**, leaving ~5× margin. The "N serials vs N rows" ratio heuristic was **measured and rejected**: one legitimate serial (`851530`) backs 19,952 rows, so no ratio separates it from the defect. A per-port threshold was also rejected — small ports legitimately hit 100% (جديدة عرعر, 66/66).

## v92.0 — 2026-08-16 — Add (observability): stable XQ error codes for every user-visible failure

**Why:** The failure that motivated v91.1 is still not diagnosable at the level that matters. v91.1 added `logError` plus the raw exception text, which tells us *an* exception happened — it does not tell us **which of the three steps** inside `createInitialStructure` raised it, and a user reading an Arabic sentence with a Chromium DOMException stapled to it has nothing short and stable to quote back to us.

The specific defect that started this: `createInitialStructure`'s single catch spanned `createWorkspaceStructure` → `checkWorkspaceStructure` → `loadWorkspaceFiles` and blamed **write permissions unconditionally** — it named a cause it had never established. It still does not reproduce headlessly (the full chain runs clean against a real Node fs adapter), so it is specific to the real File System Access API in the user's environment. The only way to close that loop is to give every distinguishable failure a **stable identifier the user can read aloud**.

**Rejected:** wrapping errors in a new `XqError` class. Half the data layer classifies failures by `error.name` (`NotReadableError`, `AbortError`, `NotFoundError`) and by `instanceof` (`MonthClosedError`, `ReadOnlyModeError`, `WorkspacePermissionError`); wrapping would silently change those verdicts. Codes are attached to the *existing* error object as a non-enumerable property instead, so identity, name, message, stack and cause survive untouched.

**What changed:**

**New: `src/data/storage/errorCodes.ts`** — an **append-only** catalog of 86 codes shaped `XQ-<AREA>-<NNN>` across seven areas (`WS`, `FS`, `IO`, `AUTH`, `POP`, `DIST`, `SMP`). Each entry carries an English `meaning` (for the log and for us) and a `labelKey` into `DEFAULT_LABELS` (the Arabic sentence, so it stays Settings-overridable like every other string). ## v89.1 — 2026-08-16 — Fix (samples): let a newer derivation rewrite a mirror at the same log revision

**Why:** v88.0 fixed employee quota derivation and bumped `DERIVE_VERSION` 2 → 3, which correctly invalidated `distribution.current.json` and the checkpoint sidecar. **But the corrected quota never reached the employee.** `syncSampleMirrors`'s monotonic guard skipped any mirror whose `sourceLogRevision >= sourceLogRevision`, and a version-bump refold produces the *same* `logRevision` — so every mirror was skipped. Since the mirror is the **primary** read for an employee's own queue under Design B, a month with no further events would have kept showing the old, wrong quota indefinitely. The fix was landed but inert.

**What changed — the guard is now ordered on the pair `(sourceLogRevision, deriveVersion)`**, tested in this exact order:

- `existing.revision > ours` → **return, unconditionally.** No version comparison is reachable in this branch, so a newer derive version can never defeat it. They hold newer DATA; overwriting would resurrect stale entries.
- `existing.revision === ours` → return only if `(existing.deriveVersion ?? 0) >= ours`; otherwise overwrite. Same data, better derivation — this is the case that unblocks the v88 refold.
- `existing.revision < ours` → overwrite, unchanged.

Deliberately **not** collapsed into one combined comparison: the first case must not be defeated by a version difference. Inverting that would resurrect stale assignments, which is worse than the bug being fixed.

**The stamped version is `current.deriveVersion ?? DERIVE_VERSION`, not a flat `DERIVE_VERSION`.** A mirror's derivation quality is the quality of the snapshot it projects, so a snapshot folded by an older build must not stamp itself as *this* build's derivation and lock out the corrected write. An unstamped snapshot cannot come off the storage path — `loadOrDeriveDistributionCurrent` refolds anything whose `deriveVersion !== DERIVE_VERSION` — so it is hand-built by this build and carries this build's semantics.

**The index had to follow, or the fix would have been silently defeated.** `2-employees/_index.json` exists precisely so one read replaces N mirror parses; without `deriveVersion` in it the fast path could not evaluate the new tie-break, on every month that already has an index — which is every month. Entries now carry `deriveVersion`, and the file carries `pendingDeriveVersion` alongside `pendingRevision`.

**A second path the brief missed:** `pendingRevision` is an index-only mechanism that raises the effective revision during a crash-interrupted projection. It needed the same treatment, hence `pendingDeriveVersion` and the rename of `maxRevision` → `maxStamp`, folding both into a lexicographic `(revision, version)` max. This preserves the existing "over-stating is the safe direction" property on both axes: an interrupted run at the same revision with an unknown-but-possibly-newer derivation makes the guard **skip**, never clobber.

**A legacy index missing the field reads as `0`, rather than falling back to reading mirrors.** Justification: `0` makes the guard overwrite at equal revision, and that overwrite comes from the newest derivation available, so it can only improve the file. The revision comparison — the axis that actually guards against resurrecting stale entries — is untouched, so the unsafe direction is unreachable. Cost is one redundant rewrite pass per legacy month, after which the index carries versions. Falling back to N mirror reads would cost more and buy nothing. `isMirrorIndex` accepts an absent `deriveVersion` but rejects a present non-number, so a malformed index is rejected whole and the mirrors are read.

**Regression tests, three of four proven to fail first** (verified by restoring `git show HEAD:` over the file, running, then restoring):

```
× a mirror at the SAME revision but an OLDER deriveVersion is rewritten with the corrected quota
    AssertionError: expected 9 to be 4   ← the mirror kept the old dailyQuota, the exact bug
× the index carries deriveVersion, so the fast path can evaluate the rule at all
× a legacy mirror with NO deriveVersion is rewritten exactly once
```
The fourth — `DANGEROUS DIRECTION: a HIGHER existing revision is never overwritten, even by a newer deriveVersion` — **passed before and after**, which is exactly the point: it pins behaviour that must not regress.

**Golden-master diffs — three, all purely additive** `deriveVersion: 2` (what that suite's `current()` helper stamps), with no field reordered, removed or changed in value: the per-employee split, the `_index.json` pin (plus a new `pendingDeriveVersion === null` assertion), and the dual-read rewrite pin. It is a module-top `const` read inside a function body, so nothing is touched at module-eval time.

**Migration/rollback:** Additive and reversible. `deriveVersion` is optional on both the mirror and the index, so older clients ignore it and dual-read holds in both directions. Rolling back restores the inert-fix behaviour; no data is lost either way.

## v89.0 — 2026-08-16 — Fix (storage): classify a head-only compressed file as corrupt, and validate the payload before overwriting .bak

**Why:** Two **regressions introduced by v87.0** (the compressed-storage format), found by a pipeline audit on real data rather than by the test suite. Both are data-safety defects in the safe-write layer.

**P1 (CRITICAL) — a truncated compressed file was served as a SUCCESSFUL read.** In `classifyHeadWindow`, the size gate `fileSize < bodyStart + 3` returned `plain` **before the head line was ever parsed**. So a file consisting of exactly its head line and zero body bytes was read as plain text, `JSON.parse`d into the head *metadata* object, and passed through `unwrap()` (which tolerates bare objects by design) as **the payload**. The `.bak` recovery ladder was bypassed even with a good backup sitting next to it.

That is precisely the torn-write shape: `writeCompressedFile` writes the head as its own `write()` before the body, and `close()` — which *commits* the frame — was being called on the error path. Body lengths 1–3 already reported corrupt; only 0 was broken. This affects the three largest business files. Bogus data presented as success is the one failure a safe-write layer must not have.

**P3 (HIGH) — `hasCurrent` validated framing, not payload.** A live compressed file with a damaged gzip body (one flipped byte past the magic) was byte-copied over the good `.bak` on the next save, **destroying the last recoverable revision** — while the plain path correctly refused. In the other direction, a bare legacy un-enveloped file (a shape the reader explicitly tolerates) yielded `hasCurrent=false`, so no `.bak` was taken at all and a failed commit destroyed the only copy.

**A third instance, not in the brief and found during the work:** the *plain* write path (`safeWriteJson`) and `safeWriteJsonText` made the same framing-only decision via `compressedHeadFromText(current) !== null`. Since `population.final.json` crosses the 2,000-row compression gate in normal use, a damaged compressed live file destroyed the good `.bak` on a **plain** save too. All three now require `isRecoverableCompressedFile`.

**What changed:** a file shorter than `bodyStart + 3` now has its head line parsed first; if it carries `format:"xqapz-gzip-1"` it is classified **`corrupt`** — a new classification kind that keeps the intact head for metadata reads but is never treated as plain. `readContent` maps it to `damaged` so the `.bak` → `.tmp` ladder runs; `streamFileText` raises `CompressedReadError`; `classifyFile`/`readEnvelopeMetadata`/`readCompressedHead` still see compressed framing, so byte-copy and revision continuity are unchanged. `writeCompressedFile`'s catch path now `abort()`s rather than `close()`s, guarded for `abort` being optional, falling back to `close()`.

`hasCurrent` goes through a new `hasRecoverableCurrentFile`: a compressed live file must pass `isRecoverableCompressedFile` (full inflate, CRC32/ISIZE) before being byte-copied to `.bak`; a `plain` result with null metadata falls through to `parseValidJson` (and `readOversizedEnvelopeMetadata` for oversized files) rather than concluding "nothing to back up".

**`jsonEnvelope.ts` was deliberately NOT changed.** Its tolerance of bare objects is load-bearing — legacy files depend on it, and so does P3's own bare-legacy branch. The defect was misclassification upstream, not the unwrap.

**The cost, measured and accepted.** The brief estimated "~ms for the 2.3 MB compressed population file". That was wrong by roughly 1000×: the 2.33 MB file holds **117.7 MB** of text, and validating a gzip member requires inflating it, because CRC32/ISIZE are trailers.

| file | on disk | inflated | save without fix | save with fix |
|---|---|---|---|---|
| `risk.raw.json` | 2.33 MB | 117.7 MB | 14.8 s | 17.1 s |
| `bi.raw.json` | 5.25 MB | 316 MB | 38.4 s | 39.7 s |
| `population.final.json` | 1.05 MB | 23.4 MB | 8.2 s | 8.5 s |

So **0.1–2.9 s per save, 3–16%** of saves that already cost 8–40 s. The bare-legacy branch adds 269 ms at 15 MB and 1.6 s at 78 MB, once per file. This was flagged rather than shipped quietly, and accepted deliberately: the alternative is knowingly destroying the last recoverable revision, and there is no cheaper way to validate a gzip member. Data safety outranks 3–16% on an already-long operation.

**Every regression test was proven to fail against v87.0 first**: `expected 'plain' to be 'corrupt'` at body=0; `expected {ok:true,value:{…}} to deeply equal {ok:false,reason:'corrupt'}`; `recoveredFromBak` false; `.bak` unreadable after a damaged-live save (both follow-up formats); and the bare-legacy payload gone with `tag` undefined. Body lengths 0–3 are all pinned, so the boundary is genuinely covered.

**One pre-existing assertion was strengthened, not weakened:** `classifies edge windows` asserted head + 2 magic bytes → `plain`; it is now `corrupt`. That assertion *was* the defect shape.

**Collateral considered and dismissed:** for a genuine plain file to be misclassified as corrupt it would need a first line that parses as a JSON object containing `"format":"xqapz-gzip-1"` **and** end within two bytes. No writer in this repo emits that key — `wrap()` produces `metadata`/`data`, and a pretty-printed envelope's first line is the single character `{`, which does not parse. Unreachable.

**Migration/rollback:** No format change. A file previously readable stays readable; the only behavioural difference is that a *corrupt* file now reports corrupt instead of returning its own head as data, and a corrupt file no longer overwrites a good `.bak`. Rolling back restores both defects.
