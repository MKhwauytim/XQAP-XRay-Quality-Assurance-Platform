# Edit Log — 2026-08-16

## v88.0 — 2026-08-16 — Fix (distribution): derive employee quota from live ownership, and drop unknown events outright

**Why:** Two defects in `foldDistributionEvents`/quota derivation, both confirmed against real customer data by a pipeline audit. The first is not theoretical — it fires on ordinary daily use.

**P2 — employee daily quotas were wrong whenever a row moved.** `sampleCount` was derived by counting raw `assigned` **events** rather than final entry state, so a reassignment corrupted **both** employees permanently and each replacement inflated by one. Referral approval emits reassign events, so this happened in normal operation with no corruption, no hand-edited files and no version skew. The wrong number was copied into every employee mirror and rendered as that person's daily target. Known and deferred since before 2026-07-20; it survived because **no golden test covered reassignment and quota together**.

Measured on the real month (30 employees, 50 reassignments emp01→emp30): **emp01 displayed 215 while owning 165; emp30 displayed 211 while owning 261.** After the fix both agree — 165/165 and 261/261 — and the mirrors written in that run carry the corrected values. Replacement case: emp02 after 5 replacements shows **215** (220 entries, 215 live), where it previously showed 220.

**P5 — an unknown `eventType` was recorded as dropped and *still* rewrote the entry**, stamping `lastEventAt`/`lastEventId`. That silently rewrote the user-facing distribution-date column in employee views and six report call sites, and a **future-dated** unknown event permanently defeated the v85 fold checkpoint (measured 404 ms vs 53 ms per read, forever). Reachability requires foreign or hand-edited events or client version skew — but events are read with bare `JSON.parse` and no validation, and this repo's trust model explicitly includes hand-edited JSON.

**What changed:**

*P2.* `deriveEmployeeQuotas[WithFacts]` now takes the folded entry set and derives `sampleCount` from a new `countLiveEntriesByEmployee(entries)` — entries with `status !== "replaced"`, grouped by `assignedTo`. `QuotaFacts` is still collected and still resumable, but now sources only the assignment **window** (`assignedAt`, `daysRemainingAtAssignment`), which genuinely *is* a property of the first assign event. On the incremental path the fold re-emits every resumed entry, so the count is whole even though the facts only extend.

*P5.* The inline event-type allowlist is replaced by `isKnownEventType` (keyed off `TRANSITION_HANDLERS`), evaluated **before** the transition is computed, with `continue` after `recordDroppedEvent`. `transitionForEvent`'s "preserve existing / null" fallback became unreachable and was removed.

**`DERIVE_VERSION` 2 → 3**, with a per-version changelog in its docblock.

**Golden-master diffs — all deliberate, none blind-recorded:**
1. `SURPRISE: unknown event type … still rewrites the entry` → **`CHANGED (P5)`**: `lastEventAt/lastEventId` stay at `e1` instead of advancing to the dropped `e2`. This is the deliberate flip of the pin deferred in the 2026-08-15 log; the test comment records what it was, why it was wrong, and that the flip is intentional.
2. `SURPRISE: duplicate assigned events for the SAME image inflate sampleCount` → **2 becomes 1**. Unplanned but correct: two events, one owned row. `facts.assignmentCounts` still pins 2, so raw event volume is not lost.
3. Absent-row phantom, legacy bare-`Set` shape → `sampleCount: 1` becomes **`quotas: undefined`**. With an empty entry set the phantom can no longer leak back through the old exclusion shape.
4. `pins that dropped assignment events are excluded` **rewritten** as a *real* drop (an assign onto an already-completed row, rejected by the terminal guard) rather than a hand-made exclusion set over two live images — that construction stops being meaningful once the count comes from entries.
5. `dropping ONLY the first assignment` — entries now folded from only the surviving event, keeping the case self-consistent. Values unchanged.
6. **New pins**: REASSIGN (emp-a 1 / emp-b 2), REPLACE (2, not 3), and "reassigns everything away ⇒ drops out of quotas". These were written and confirmed against the **pre-fix** code first (a scratch run pinned emp-a 2 / emp-b 1 and 3) before any source change — snapshot-then-change, per CLAUDE.md.

`distributionLog.test.ts` — "a stray late event cannot resurrect a replaced row": `emp1.sampleCount` 2 → **1**, which now agrees with the `totalAssigned: 1` the same test already pinned. No other golden test moves: mirrors, distribution report and KPI tests build `quotas` by hand and pin only the copy/render; the PowerBI export carries no quota field.

**The version bump was verified to actually invalidate caches, not assumed.** A new test rewrites **both** `distribution.current.json` and the `distribution.checkpoint.json` sidecar as a v2 client would (same revision and `eventSetId`, old assign-counted quotas), clears the session memo, and asserts the reload refolds to the correct numbers. It is a real guard: forcing `DERIVE_VERSION` back to 2 makes it fail with the stale cache served.

**`hasQuotaForAssignedEmployees` had to be adjusted.** It required a quota row for every employee that ever received an `assigned` event; under P2 an employee who reassigned everything away legitimately has none, so the cache would have been rejected on every load, forcing repeated full refolds and multi-MB rewrites. It now requires quota rows only for employees still owning live entries.

**KNOWN GAP — employee mirrors do NOT regenerate on the version bump alone.** `syncSampleMirrors` skips any mirror whose `sourceLogRevision >= current.logRevision`, and a version-bump refold produces the *same* `logRevision`. Reproduced: the derived cache reads the corrected quota while the on-disk mirrors keep the stale one. Since the mirror is the **primary** read for an employee's own queue, a month with no further events will keep showing the old quota until the next append. Tracked and fixed separately in v88.1.

**Pre-existing gap left open, now documented in code and pinned by two tests:** an employee who only ever received rows *by reassignment* has no assign event, therefore no assignment window, therefore no quota row at all — they own rows but appear in neither `firstAssignments` nor `quotas`. Closing it needs a decision on which window to use.

**Migration/rollback:** No on-disk format change; the change is to derived output. Existing caches and checkpoints are invalidated by the `DERIVE_VERSION` bump and refold automatically — no migration step. Quota numbers visibly change for existing months, to correct values. Rolling back restores the old (incorrect) counts and re-invalidates caches the same way.

## v87.1 — 2026-08-16 — Fix (sampling): surface unmapped stage rows, and stop restore serving stale derived mirrors

**Why:** Two defects confirmed by a pipeline audit run against real customer data (117,336-row month), both found by adversarial verification rather than by the test suite.

**P4 — rows with an unmapped stage value were silently dropped from the drawn sample.** `getStageKey` resolves anything absent from `stageMappings` to `"unknown"`, and the draw excluded those rows with **no diagnostic at all** on the success path; only a 100%-unmapped population hard-failed. It did not fire on the real data — but note *why*: that data contains the misspellings `SECOND_STAG` and `FORTH_STAGE`, which happen to already be aliased in `DEFAULT_STAGE_MAPPINGS`. Real-world typos in this column demonstrably occur; the next one simply will not be on the list. In a regulatory sampling context, quietly drawing from a subset of the population with no counter anywhere is not acceptable.

**P6 — restore brought back derived per-employee mirrors from the backup**, so a restored mirror could be *older* than the restored event log. `getUserWorkspaceFootprint` then trusted mirror `entries` with no revision cross-check, serving stale assignments as current.

**What changed:**

*P4.* `SampleMasterData` gains optional `unmappedStageRowCount` and `unmappedStageRawValues` (capped at 20 distinct values). `buildStagePlan` counts rows resolving to `"unknown"` and collects the raw values; `drawStageSample` threads them into the result. `drawLegacySample` never classifies by stage, so it passes nothing and the fields stay `undefined` — deliberately distinct from `0`, which would claim "checked, none found". A new `UnmappedStageWarning` (mirroring the existing `CertScanShortfallReport` pattern, `role="alert"`) renders at the top of `SampleResultReport`. Three Arabic label keys added to `DEFAULT_LABELS` rather than hard-coded strings, per CLAUDE.md.

**`SAMPLING_ALGORITHM_VERSION` deliberately NOT bumped** — draw semantics are unchanged; this only reports what was already happening. Verified: `sampleAlgorithm.ts` has an empty diff and still reads `"1.1"`, and a test pins it. The sampling golden master needed **no edit** — its stage assertions check subsets (`stageAllocations`, `portAllocations`, `certScanShortfalls`), never the whole `SampleMasterData`, so additive optional fields do not disturb it.

*P6.* `restoreActionFor` now classifies `{username}.samples.json` (suffix match — the prefix is per-user) and `_index.json` (exact) as **`skip-derived`**, following the existing `distribution.current.json` / `distribution.checkpoint.json` precedent. Constants are imported from `sampleMirrorStorage.ts` rather than re-declared, so the two cannot drift. `getUserWorkspaceFootprint` now reads the cheap `readDistributionLogStamp` per open month and compares it against the mirror's `sourceLogRevision`; on staleness it falls back to a real fold via `loadOrDeriveDistributionCurrent`, paying that cost **only** in the rare stale case rather than on the common path.

This creates a deliberate circular import with `distributionStorage.ts` (which already imports `syncSampleMirrors` from this module) — safe because neither side uses the other's exports at module-eval time; confirmed by `tsc` and the full suite.

**Every fix has a regression test proven to fail first.** Reverting the P4 counter made 3 tests fail with `expected undefined to be 3/0/30`. Reverting the `restoreActionFor` branch made both restore tests fail — the mirror was overwritten, and `_index.json` reappeared after deletion. Reverting the footprint cross-check made a real, newer pending assignment **silently vanish** (`expected [] to have a length of 1`) — the dangerous direction, and exactly the bug.

**Two corrections to the task description, worth recording:** `stageHelpers.ts` lives under `src/data/population/`, not `src/data/sampling/`. And `distribution.current.json` was **already** `skip-derived` — the real gap was only the per-employee mirrors and `_index.json`.

**Migration/rollback:** Additive and fully reversible. The two new sample fields are optional on a stored schema, so older clients ignore them and files stay readable both directions. The restore classification changes behaviour only during a restore, and in the safe direction — derived files regenerate from the event log, which is authoritative.
