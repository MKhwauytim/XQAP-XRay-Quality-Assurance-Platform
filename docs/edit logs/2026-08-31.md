## v130.15 — 2026-08-31 — Fix (distribution): gate the immediate-replace button behind an outstanding replacement request

**Why:** A whole-app multi-agent audit (Wave 1) flagged a state-consistency
gap in «صور الأشعة المحالة»'s replacement flow. `handleReplace`'s
non-recommended branch (`XrayReferrals.tsx`) files a `ReplacementRequest`
into the referral store and waits for supervisor approval — but that write
is not a distribution event, so the entry's derived `status` stays
`"pending"` the whole time the request sits in the queue (only
`"replacement-requested"` distribution events flip it, and none is
appended here). The panel's replace button was gated only on
`status === "pending"`, so it stayed enabled the entire time a request was
outstanding: an employee could reopen the dialog and pick a *recommended*
candidate, which replaces immediately with no approval needed, while the
first request was still pending. The row ends up replaced by the second
candidate, but the stale first request stays live in the approval queue,
pointing at an original xrayImageId that no longer needs a replacement —
exactly the kind of orphaned/racing write this repo's `casLoop`/append-only
event patterns exist to prevent, just missing here because the two paths
(referral-store request vs. distribution-event replace) never cross-checked
each other.

**What changed:** `openReplacementDialog` now checks `pendingReplacementIds`
(already computed by `loadData` via `getPendingReplacementIds`, previously
used only for row-coloring) and refuses to open — with an Arabic status
message — when a replacement request is already outstanding for that row.
The panel's `onReplace` render condition gets the same check, so the button
disappears entirely once a request is filed, instead of staying clickable
and failing (or worse, silently racing) on click. Defense in depth: the
dialog-open guard covers any future second call site, the render guard is
the visible UI safety net for this one.

## v130.14 — 2026-08-31 — Fix (backup): broadcast a full data-refresh after a workspace restore

**Why:** Same Wave 1 audit. A backup restore (`Archive/index.tsx`'s
`handleRestore` → `restoreBackupSnapshot`) overwrites live month files
directly on disk — the single most consequential write in the app, per its
own `backup-restored` audit-log comment. Every *other* mounted view
(distribution, referrals, answers, notifications, ...) learns about disk
changes only through two paths: a write it made itself (which calls
`notifyLocalDataChange`) or the 45s sync tick's bounded-signature probe.
Restore goes through neither — it is not a normal write path, so nothing
bumps a workspace epoch or announces which families changed, and the sync
tick's probe is not guaranteed to catch every family a restore can touch
(`answers.events` in particular has no persisted checkpoint of its own —
see `backupStorage.ts`'s own restore-scope comment). A supervisor with the
distribution tab open during someone else's restore would keep looking at
pre-restore rows for up to 45 seconds, or indefinitely if that tick's probe
happened not to notice.

**What changed:** `handleRestore` now calls `broadcastDataRefresh("manual")`
right after a successful restore — the same full-cache-discard signal the
admin toolbar's own manual refresh button sends, which is the correct scope
for an operation that can touch every family at once and bypasses every
normal invalidation path.

## v130.13 — 2026-08-31 — Fix (auth): lock out the hidden bootstrap-admin passcode modal after repeated wrong attempts

**Why:** Same Wave 1 audit. `AuthGate.tsx`'s normal login form already
locks out after `LOCKOUT_AFTER_ATTEMPTS` (3) wrong passcodes against the
bootstrap-admin secret (`failedAttempts`/`lockoutUntil`, `LOCKOUT_DURATION_MS`
= 30s), but the hidden Alt+A/Alt+T shortcut modal — a second, undocumented
entry point that checks the exact same `resolveAdminPasswordHash()` secret
via `loginAsBootstrapAdmin()` — had no lockout wiring at all. An attacker
(or a script) who discovered the shortcut could brute-force the bootstrap
admin passcode with unlimited attempts and no backoff, entirely bypassing
the guard the normal form already enforces for the identical secret. There
was also zero test coverage anywhere in the repo for either lockout path.

**What changed:** `loginAsBootstrapAdmin()` now shares the same
`failedAttempts`/`lockoutUntil` component state as the normal form: it
checks the lockout guard before attempting verification, calls
`registerFailedAttempt()` on a wrong passcode, and resets the counter on
success. The modal's input and submit button gained the same
disabled-with-countdown treatment (`labels.auth_lockout_wait`) the normal
form already shows once locked out.

**File:** `src/auth/AuthGate.tsx`

**File:** `src/auth/AuthGate.test.tsx`

## v130.12 — 2026-08-31 — Fix (DataTable): sticky columns overlap after reordering or adding columns

**Why:** The owner reported real visual bugs on «مساحة العمل»: adding or
reordering columns makes them overlap, and reported this as applying to "any
page with tables" — i.e. the shared `DataTable` component, not one screen.
Root-caused with a real headless-Chromium session against the dev server
(`?sim=1&role=admin`, «صور الأشعة المحالة», which pins `xrayImageId`/
`answerStatus` via `stickyColumnIds`): `DataTable`'s sticky-column `right`
offset was computed from `colCfg.widths`/`widthFr` as a percentage of
`totalFr`, correct only if the table's rendered column widths are exactly
proportional to those fr weights. `.dt-table` deliberately uses
`table-layout: auto` (widthFr/manual resize are documented as "preferences",
not hard percentages — DataTable.css), so the browser sizes each column by
its content, and the real rendered width routinely diverges from the
fr-based percentage. That divergence is invisible while small, but a column
reorder or an added column changes what actually precedes a sticky column
without changing that sticky column's own fr share, so the percentage
offset goes stale relative to the real DOM. Measured directly: after
dragging one column ahead of two sticky ones, the computed `right` offset
was off by up to 154.5px, and two sticky header cells rendered on top of
each other by 71.5px. No existing test could have caught this —
`stickyColumns.test.tsx` ran in jsdom, which performs no table layout at
all, so it only ever pinned the percentage *arithmetic*, never checked it
against a real rendered column.

**What changed:** `DataTable`'s sticky offset is now computed from the
ACTUAL rendered width of every visible header cell (via refs +
`getBoundingClientRect()`), not from fr weights. A `useLayoutEffect` keyed
on `[visibleCols, colCfg.widths]` re-measures synchronously after every
reorder, add/remove/hide, manual resize, or auto-fit — before the browser
paints, so there is no visible flash of a wrong offset — and a
`ResizeObserver` on the table wrap catches a pure viewport resize that
changes `table-layout: auto` widths without touching any of those. The old
percentage-only `stickyMeta` is split into `stickyOrder` (unchanged
z-index-stacking logic) and the new `stickyOffsetsPx` (measured pixels).
`stickyColumns.test.tsx`'s existing jsdom test is rewritten to stub
`getBoundingClientRect()` per header cell (jsdom cannot lay out a table, so
this is the only way to give the offset math real numbers to check against)
and gains a new regression case that drags a column ahead of a sticky one
and asserts the offset actually moves. A new Chromium e2e test
(`table-columns.spec.ts`) reproduces the real-browser scenario end-to-end:
widen the column set, drag a column ahead of the sticky ones (restricted to
cells already on-screen, since dragging an off-screen cell makes
Playwright's own auto-scroll-during-drag the thing under test instead of
the app), and assert no two header cells' bounding rects overlap.
