## v113.0 — 2026-08-22 — Add (e2e): autonomous Playwright suite driving the whole app in a real browser

**Why:** Owner request: "a way to do an entire App test from 0 to 100 all features code base, autonomously without human interaction". Until v110.0 this was impossible — the app gates on `showDirectoryPicker()`, which needs a real user gesture and a real folder, so every UI change in this repo had only ever been verified in jsdom. CLAUDE.md records that effect-timing and state-machine bugs here survived self-review five times running, and jsdom is precisely the tool that misses them: it performs no layout, dispatches no real events through a real event loop, and never evaluates the built module graph.

The `?sim=1` writable simulated workspace (v110.0) removed the gate. This is what it was built for.

**What changed:** 14 spec files, **112 tests, all passing, zero flaky, zero skipped, 5m37s**, confirmed across five full runs — the last two against a clean tree with the managed dev server. **Zero `waitForTimeout` in the suite**: every synchronisation is a web-first assertion or an explicit wait, because a flaky browser suite gets ignored and an ignored suite is worse than none.

Coverage runs boot/auth (21 tests — including the exact top-level AND sub-tab set each of the five roles is granted, and admin role-preview re-gating live), population browse and the four-phase process, the employee queue (a real answer → submit → completed round trip moving the stats 14→15 and 20→19), answer-on-behalf (all three `resolvePanelAuthoring` outcomes, plus granting the feature live and re-testing), reassignment (including the approval that actually moves 34→33 / 29→30), the exceptional-case import (TSV paste, header-click mapping, all four assign modes, and the imported rows landing in the reviewer's «حالات استثنائية» chip), reports (the executive deck really building — 27 pages, no page error), archive, notifications, user management, the action log and settings. Expected numbers come from `e2e/helpers/seed.ts`, mirroring `SIM_SEED_PROFILE`.

`@playwright/test` is pinned **exactly** to `1.56.1` — the only stable release whose bundled Chromium revision is 1194, matching the pre-installed browser. A `^` range would request a revision that is not on disk.

**The suite runs against the DEV SERVER, not `dist`**, and that is a deliberate limitation worth stating: `?sim=1` is stripped from production builds by three independent guards, so it cannot exist in the shipped artifact. The suite therefore proves the FEATURES work; `ci.yml`'s `build` + `check:bundle-size` prove the shipped bundle works. Different failure classes, both covered, neither substituting for the other.

**Three real application bugs found — the entire point of driving the real thing:**

1. **A sub-tab click is silently dropped when its parent tab is not yet mounted** (~80% reproducible). `Sidebar.handleSubTabClick` sets `activeSubTabId` synchronously — painting `aria-current="page"` — then fire-and-forgets a `window` CustomEvent (`pop-set-subtab`) that the owning tab only subscribes to inside a mount effect. On a first visit to a lazily-mounted tab the listener does not exist yet: the rail highlights what was clicked while the content shows the parent's default sub-tab. The helper `openSubTab` therefore REQUIRES a content locator and re-clicks until the content agrees — the workaround is documented as a workaround, not passed off as normal.
2. **A label override cannot be reverted from the row that changed it.** The value saves and propagates everywhere (the sidebar updates live), but the row's «استعادة القيمة الافتراضية» stays disabled and the `is-custom` marker never appears until remount. `LabelRow` reads `isCustomized()` / `getLabels()` without `useLabels()` — it writes to a store it does not subscribe to, a shape the React Compiler is free to memoize.
3. **Approving a referral leaves the sibling queue stale for up to 45 s.** `broadcastDataRefresh` has exactly two callers, both in `workspaceSync.ts`; no domain action broadcasts. With the referrals tab still mounted behind the approvals tab, the approved row stays listed and selectable until the timer fires.

Smaller issues documented but not chased: a KPI heat-map titled «يوليو 2,026» (thousands-separated year, and the wrong month) on a June dataset; «دقة الفحص الإجمالية 93.3%» rendered directly above «من 0 قراراً قابلاً للتقييم»; `population/process` readiness showing «المجتمع —» for a 320-row month; and `ew/inspection-form` labelled differently in the rail than in `tabCatalog.ts`.

**No `data-testid` was added.** Three structural selectors were unavoidable and are tabulated in the docs — one of which is itself a finding: the FEATURE permission matrix's toggles are visually-hidden inputs inside an unlabelled `<label>`, while the PAGE matrix beside it carries proper `aria-label`s. The two are inconsistent, and a screen-reader user hears a bare "checkbox" on one of them.

**Migration/rollback:** Additive and test-only. No production source changed, no data format touched. `@playwright/test` is a devDependency; the new workflow is inert until a PR runs. Rollback is a plain revert — though note `lint:ci` widened to cover `e2e/`, so a revert must take that with it or lint will point at a directory that no longer exists (the exact failure this branch already hit once, in the opposite direction).

## v112.1 — 2026-08-22 — Add (dev): seed the simulated workspace's action log so its filters are exercisable

**Why:** The action-log filter bar shipped in v112.0.0 could not be exercised in a browser at all: `?sim=1` seeds a population, sample, assignments, answers, template and users, but **no action-log entries**, so the viewer rendered `0 من 0 سجل`. Verified in Chromium — the controls render, there is simply nothing to filter. That also blocks the E2E suite, which will hit the same wall.

**What changed:** 171 `WorkspaceActionEntry` records seeded into `5-system/audit/actions/`, one file per actor, chosen so every filter dimension has something to narrow:

- **All 47 action types** appear at least once, so no checkbox in the grouped picker is a dead control. Both high-volume types are present in bulk (`answer-submitted` ×40, `label-override-changed` ×8), so the default view is 123 rows — **above the 100 page size**, meaning paging exists without touching the type picker, and enabling the hidden types takes it to 171.
- **7 actors with deliberately unequal counts** (56/30/19/19/18/17/12), so narrowing to one is visibly different from another.
- **21 consecutive days**, every day populated; an inner window catches 59 and leaves real rows on both sides. Types are scattered across days by a stride coprime with the window length, so the date and type dimensions are not correlated — a filter test cannot pass by accident.
- `target` and `details` populated on most entries, searchable in both KEYS and VALUES.

**The real writer is deliberately bypassed here — the only place the sim seed does so.** `appendWorkspaceAction` stamps `at: new Date().toISOString()` and a crypto `id` itself. `at` is fatal to the purpose: a log where every entry is "now" cannot exercise a date filter, which is the whole reason for seeding it; the random id separately makes cross-build determinism unassertable. Entries are therefore built directly, but the FILES still go through the real layer — same `getAuditActionsDir`, `actionsFileName`, `WorkspaceActionUserLogFile` shape and `safeWriteJson` call — and a test proves they round-trip through the real `readWorkspaceActions`. A later genuine append treats them as ordinary history.

**Coherence is enforced by construction and re-checked independently.** Every row id is read back out of the month the seed just wrote rather than invented, and the test then verifies: the actor is in the roster with a matching role; the month folder is the seeded one or null; anything matching the xray-id pattern in `target` or any detail value is a real population row; row-level entries name a drawn row assigned to whoever the entry holds responsible; every `answer-submitted` has a matching submitted `ItemAnswer` on disk for that actor and row; and every username-bearing detail names a real account. Deleted subjects (`user-deleted`, `template-deleted`) are enumerated and asserted ABSENT, so the roster check cannot quietly permit them.

`simModePlugin`'s production-leak guard was widened to `sim(Mode|Workspace|ActionLog)\.ts` so the new module is covered by the same fail-closed assertion.

## v112.0 — 2026-08-22 — Add (audit): log every activity with filters; delete dead v1 mapping module; correct the bundle-reserve note

**Why:** The action log declared 18 event types and **four of them had no call site at all** — `user-created`, `permission-changed`, `feature-permission-changed` and `backup-restored`. Backup restore is the most destructive operation in the app and left no trace in the one log that exists to record exactly that. Answer submission — the core activity of the product — was invisible too, so the log could not answer "who did this work" about the work the product is for.

`DataTable` was tried for the filter bar and rejected. It cannot seed a filter, and seeding one is the whole point: `answer-submitted` has to arrive already unchecked or the default view is one high-volume type drowning everything else.

The bundle note is corrected here rather than left standing, because an earlier claim of mine — recorded in `check-bundle-size.mjs` and repeated in v110.0 and v111.0 as "the reserve" — turned out to be false, and a release budget that names a reserve which does not exist is worse than one that admits it has none.

**What changed:** 18 → 47 action types, each wired to a real call site **in the success branch** and fire-and-forget, so a logging failure cannot break the user's operation. The new coverage: answers (including on-behalf, recording the real author alongside the assignee), quality notes, reopen requests, replacements, population saves, per-row distribution changes, exceptional-case imports, templates and template selection, notifications, users and password resets, both permission matrices, backups, label overrides, sync interval, admin account, and report/export generation.

Exports are logged deliberately: an export is a read that leaves the workspace carrying population and per-employee answer data, and "who took a copy of month X" is what this log is for.

**Volume was decided on measured numbers, not a guess.** The cap is 2,000 entries per **actor**, overflow is archived before trimming, and a failed archive blocks the trim. An entry is 254 bytes, so a full log is ~0.49 MB per actor, and at ~542 answers per reviewer per month the cap is reached in ~3.7 months. That is safe — but it is the per-actor split plus working archival that makes it so, not the raw type count. High-volume types default OFF in the filter picker; on-behalf deliberately does **not**, since it is the accountability record and hiding it by default would defeat its purpose.

**Real bug fixed:** `appendWorkspaceAction` computed the filename *outside* its `try` block, so a non-string actor rejected the promise — breaking the documented never-throws contract at exactly the fire-and-forget callers that rely on it.

Filtering is by grouped type, actor, date range and free text, composing by AND, with a shown/total count so withheld rows are never withheld silently. `actionCatalog.ts` (new) is the grouped type vocabulary the picker renders from, and `actionLogCoverage.test.ts` (new) is the guard that a declared type without a call site cannot come back.

`adhocImportMapping.ts` was deleted with each of its six assertions accounted for; six further gaps found while checking were ported and mutation-verified. `adhocImportAssignment.ts` was **kept** — six suites use it as a fixture builder, and the bundle rationale for removing it turned out to be false.

**The bundle claim was wrong, and correcting it is part of this change.** Deleting the orphaned v1 modules reclaims **zero** bytes: they are orphaned from the production module graph too, so Rollup had already tree-shaken them — deleting both produced a byte-identical bundle. "Orphaned from the UI" is not the test. The budget is raised 3.90 → 3.95 MB with the real position documented in the script: 348 kB is fonts needed by both the UI and the standalone reports, Somar was already deduplicated, and `vite-plugin-singlefile` rules out code-splitting. Font subsetting is the one genuine win left, and it is its own piece of work.

## v111.0 — 2026-08-22 — Fix (ui): anchored popovers escape their clip; wire historical study import; open ارفاق حالات استثنائية to admin control

**Why:** Four owner reports, one of which was a feature described as delivered but never connected.

**The popover diagnosis is the interesting part, because the suspected cause was refuted.** The report read as an RTL wrong-side bug; a survey of all 56 `position: absolute|fixed` declarations found five broken surfaces and no sign error anywhere — the logical properties were already correct. The real faults were four different ones: `DataTable`'s filter menu computed `right: innerWidth - anchor.right` with **no left clamp**, so for the leftmost columns of a wide RTL table it resolved to a negative left and sat entirely off-screen; Browse's filter was `absolute` inside a `th` inside an `overflow: auto` scroller, so it was clipped by its own ancestor; both column pickers grew to ~460px with no vertical clamp; and both `DataTable` popovers snapshotted the anchor rect at click time, so scrolling stranded a fixed menu away from its button — the "wrong location" half of the report. Fixing the five surfaces individually was rejected: they share one geometry problem, and five copies of a clamp is five places for it to drift.

`adhocHistoricalImport.ts` had been built and tested at v107.0/v108.0 with **zero callers** — a documented feature that no user could reach.

**What changed:** One shared `Popover/` replaces the per-surface positioning. `anchoredPosition.ts` is pure geometry — flip, two-axis clamp, direction taken as an input — and `AnchoredPopover.tsx` portals to `body` and **re-measures the anchor element** on scroll and resize instead of caching a rect. The JS offsets stay physical on purpose: direction is already folded into the number, and using logical properties on top would flip it twice.

Portalling exposed a knock-on that had to be fixed with it: `GlobalMonthSelector`'s outside-click check was a `contains()` on its own subtree, which no longer holds the portalled popover, so clicks inside the month grid would have closed the very popover they landed in.

**Historical study import is now reachable.** Choosing that import kind reveals a template picker, a phase-grouped mapping of the template's answer fields with `answeredBy` / `submittedAt` provenance, and a plan summary that commits through `applyHistoricalImport`. It is gated on `adhoc-import.assign`, not on ingest, because committing writes assigned+completed events and an `ItemAnswer` into **another user's** file.

**Wiring it up exposed a real defect:** `normalizeMapping` silently dropped `answeredBySource` / `submittedAtSource` on read, so a re-planned import resolved every row to a blank reviewer and then refused itself — the exact failure those fields exist to prevent, reached by the round-trip nobody had exercised while the feature had no callers.

The rename to **ارفاق حالات استثنائية** is text only; ids and keys stay as they are, because they are wired into the permission matrix and into stored files. The restricted cells the owner reported came from a **role ceiling**, not from the feature matrix — the matrix was already correct. The ceiling is widened to employee/supervisor/manager/admin; guest is excluded because it is a read-only role and this screen only creates work. Defaults are unchanged: grantable, and still granted to nobody but admin.

## v109.0 — 2026-08-22 — Add (employee queue): employee picker, answer-on-behalf permission, individual reassign

**Why:** A supervisor needs to be able to work one employee's queue — the motivating case is an employee on leave sitting on ~500 unfinished samples. **The option list unions the assignable roster with every distinct `assignedTo` present in entries.** Roster-only would drop a deactivated employee still holding 500 rows — which is the motivating case — and entries-only would hide an employee who currently holds none.

`answer-on-behalf` is a new grantable feature, **off by default for every managed role including supervisor**, because it attributes one person's work to another. Individual reassign from the panel is gated on `bulk-reassign-referrals` rather than on row ownership. That required splitting `InspectionPanel`'s footer gate — the whole footer hung off `!readonly`, which hid the reassign button on exactly the rows that need it.
