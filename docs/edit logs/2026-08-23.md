## v114.2 — 2026-08-23 — Fix (adhoc-import): surface assignments the index lost, and show the operator's own xray id

**Why:** Two field reports from the same workspace, both about ad-hoc («حالات استثنائية») rows.

**1 — «حالات استثنائية» showed 0 in an established workspace while a brand-new one worked.** An ad-hoc assignment commits in three writes: sample rows, then the distribution events, then the record — and the record's save is what refreshes `adhoc-imports.index.json`. The events are the durable part and they land SECOND, while `assignedRows > 0` on the index was the ONLY gate deciding whether anybody could see them. So any failure on the third write — a share hiccup, a workspace handle that went stale (the reported one surfaced as XQ-IO-030), a CAS conflict — left rows genuinely assigned on disk and invisible to every reader. Worse, it was unrecoverable by the obvious remedy: re-running the assignment finds its own events already there and answers «كل الصفوف المحددة معيّنة بالفعل», so the bookkeeping can never catch up on its own. A fresh workspace never hits it because there is nothing yet for the third write to trip over.

**2 — the xray id rendered as «random stuff».** An ad-hoc row's `xrayImageId` is namespaced `ADHOC-{importId}-{original}` so it cannot collide with a real population row, and that namespace was going straight to the screen: a 55-character prefix in every table cell, panel header, aria-label and XLSX export, with the id the operator actually matches against the source file pushed off the end of the column.

**What changed:** Visibility now follows what is on disk, and the queue shows the operator's own id.

**1 — a repair path next to the index (`storesToOpen` in `adhocImportEmployeeView.ts`).** The index half is untouched and is still the fast path, `linkedMonths` scoping included. Added to it: `2-samples/` is listed for `adhoc-*` store folders, and any store the index cannot vouch for (`assignedRows: 0`, or no entry at all) is opened too. A folder alone proves nothing — every SAVE of an ad-hoc record writes its `sample.master.json`, so an uploaded-but-unassigned import has a folder as well — so the discriminator is `distribution.events/`, which only `appendDistributionEvents` ever creates. That is one directory probe per unvouched candidate, no file read. A store the index DOES report as assigned and the month filter then excluded stays excluded: month scoping is a deliberate decision the repair path must not quietly undo.

**2 — `displayXrayImageId(entry)`**, over a new `originalXrayImageId(namespaced, importId)` in `adhocImportModel.ts`. Exact rather than heuristic: the prefix is rebuilt from the `adhocImportId` the entry already carries, so a string that does not carry it — every real-population id — comes back untouched, which is what lets one helper serve a mixed queue. Wired into the referrals table, the results table, the inspection-panel header, the replacement dialog subtitle, the referral-id chips and the row-selection aria-labels. **Display only**: selection, answer keys (`${xrayImageId}::${assignedTo}`), folder routing and every write still go through the namespaced id, which remains the identity.

Not fixed here, because it is a different failure: XQ-IO-030 itself. That code means the workspace directory handle no longer resolves — the app's probe created a file in the folder and the OS said the folder is not there — and no read-side change can make a write to a vanished folder succeed. What this edit removes is the *permanence*: work already committed before such a failure is now visible and answerable instead of stranded.

## v114.1 — 2026-08-23 — Change (template): gate phase two on «هل يمكن الاطلاع على البيان» and give every «أخرى» option its own text box

**Why:** Owner request. Phase 2 («تحليل البيان الجمركي») assumed the reviewer could always pull up the customs declaration and asked eleven questions about it unconditionally. When the declaration is not reachable, none of those questions have an answer — but three of them are `required`, so the phase could not be completed and the stepper would not advance. The phase needed a way to end after one question.

Second, «أخرى» appeared as an option in five fields and recorded only that the reviewer had something to say, never what it was. Phase 1's «اسباب انخفاض جودة الصورة» already had a companion free-text box; the four phase-2 fields did not, and the phase leaned on one shared notes field to carry all of them — which cannot be attributed back to the option that prompted it.

**What changed:** Two edits to the default 3-phase study template. Both are template *data*, not engine behaviour: `isFieldVisible`, `collect()` and the phase-completion check already do everything needed, and no runtime file was touched.

**1 — phase 2 opens with an access gate.** New first field «هل يمكن الاطلاع على البيان» (`dropdown`, required, `["نعم","لا"]` — two options, so InspectionPanel renders it as a segmented control). It carries the image gate that every phase-2 field used to repeat: `fHasImage equals "نعم"`.

Every other phase-2 field now conditions on the **gate** instead of on the image. `isFieldVisible` walks a condition's source field recursively, so the original "no image ⇒ no declaration work" rule survives intact through the chain rather than being restated eleven times. Answering «لا» leaves the gate as the only visible field in the phase; `getVisibleRequiredFields` counts visible required fields only, so the phase reads as complete and the stepper advances — and `collect()` persists visible fields only, so a «لا» answer stores one field, not eleven nulls.

**2 — every «أخرى» option gets its own text box.** Four new `textarea` companions — «نوع البيان (أخرى)», «طبيعة البضاعة المصرح بها (أخرى)», «طبيعة البضاعة الظاهرة بالأشعة (أخرى)», «أسباب عدم المطابقة (أخرى)» — each conditioned `equals "أخرى"` on its own source field, matching the shape phase 1's «سبب انخفاض الجودة (أخرى)» already used. On the two multiselect sources this works because `evaluateCondition` reads `equals` against a multiselect as "is this option among the picked ones?", so the box survives the reviewer picking a second category alongside «أخرى». Unpicking «أخرى» hides the box, and a hidden field is dropped from the saved answer.

They are `required: false`, following the existing phase-1 companion: a blank «أخرى» box is worse data, but a required one blocks phase advancement, and that trade was not the owner's to inherit silently. Flipping `required` to `true` on all five is a one-word change per field if wanted.

Phase 1's option was spelled `"اخرى"` (no hamza) while every other field spelled it `"أخرى"` — invisible on screen, but the two group separately in every report, and it would have defeated the "every «أخرى» has a box" invariant test. Normalised to `"أخرى"`, along with the condition that reads it. This affects new templates only.

Scope note: `buildDefaultInspectionTemplate` generates fresh field ids on every call and is only invoked for a **new** template. A workspace whose template already exists on disk keeps its current structure and its recorded answers keep resolving — the gate and the «أخرى» boxes reach it only by creating a new template, or by adding the same conditional fields by hand in the Template Builder. Nothing auto-adds a box to an admin-authored field that offers «أخرى»; that would be an engine change to the Template Builder, not a template edit.

Five new tests, three of them invariants rather than transcriptions of the data: every «أخرى» option has a matching companion in the same phase; the phase ends with one visible field and no unmet required field on «لا»; and no field spells the option `"اخرى"`. Three existing tests were updated — the phase-2 field order, the yes/no-field census (the gate is the second one, and it asks whether the declaration can be *read*, not whether it *matches*), and the image-gating test, which now asserts the transitive chain and checks it end to end.
