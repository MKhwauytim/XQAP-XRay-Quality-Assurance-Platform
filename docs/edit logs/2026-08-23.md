## v115.3 — 2026-08-23 — Add (xray-referrals): admin resize grip for the queue/panel split

**Why:** Owner request: an admin wants to resize the «صور الأشعة المحالة» queue table and the inspection-panel («study form») on its right, by dragging a corner, and have the result apply to everyone rather than just their own browser.

**What changed:**

- **A drag grip, not two separate handles.** `.ew-xr-resize-grip` sits at the table's bottom-start corner (RTL: bottom-left, against the panel) and drags both dimensions in one motion, like a native `<textarea>`'s resize corner: horizontal movement re-splits the queue/panel `fr` ratio, vertical movement resizes the shared table height. Only rendered for `configure-referral-columns` holders (the same permission already gating this page's column-width admin-shared write) and only once they toggle it on via a new `ResizeModeToggle` pill in the toolbar — the grip stays out of the way otherwise.
- **Geometry lives in CSS custom properties** (`--ew-xr-queue-fr`, `--ew-xr-panel-fr`, `--ew-xr-split-height`) set via inline style, with the handoff's original hardcoded values (`1.15fr` / `1fr`, the viewport-derived `--ui-queue-floor` clamp) as the CSS-level fallback — so a user who never resizes sees byte-for-byte the old layout.
- **Persistence reuses the exact machinery this page already had for column widths**: `BrowseDatasetPreset` gains an optional `layout: { queueFr, panelFr, heightPx }`; a drag saves through `saveUserBrowseDatasetPreset` (personal) always, and `saveAdminBrowseDatasetPreset` (shared) when the dragger holds `configure-referral-columns` — which they must, to see the grip at all. Every other user's `loadAdminBrowsePreset` pulls it as their default (personal-over-admin, same precedence the column layout already uses), which is what "reflect to all" means here.
- **`useQueuePanelResize`** (new hook in `subComponents.tsx`) holds all of the above — state, the drag math (pointer-position-based, not delta-accumulated, so a long drag can't drift), and persistence — pulled out of `XrayReferrals.tsx` to keep that component under `check:complexity`'s per-function line budget.
- `uiScaleCss.contract.test.ts` updated: its floor-value assertion for XrayReferrals.css now expects `min-height: var(--ew-xr-split-height, var(--ui-queue-floor));` instead of the bare `var(--ui-queue-floor);`, since the fallback value — what the test actually pins — is unchanged.

## v115.1 — 2026-08-23 — Fix (tables): give every data table a column picker, and make the picker's popup scrollable

**Why:** Owner report, two halves.

**1 — «some tables I can edit the columns of, others I can't».** Accurate, and the reasons differed per table. `DataTable` has had a column picker all along and defaults it ON; three call sites hard-coded `canConfigureColumns={false}` with no comment saying why, and a fourth gates it on a per-role permission. The ad-hoc review table was the worst of them: it ships with several mapped columns hidden by `defaultVisible` AND had no picker, so that data was on screen in principle and unreachable in practice.

**2 — «the popup is broken, can't scroll down using it».** Reproduced in Chromium at 1280×620: the Population browse column picker had 1136 px of options in a 276 px box, `overflow-y: auto`, and a `scrollTop` that stayed pinned at 0 — not merely jumpy, immovable, even when set programmatically.

**What changed:**

**1 — the popover could not scroll itself (`AnchoredPopover.tsx`).** `position()` clears its max-height clamp before measuring, because reading a clamped box would feed the clamped height back into the flip decision. Clearing it also un-overflows the element, and an element with nothing to scroll has its `scrollTop` reset to 0 by the browser — silently, and not restored when the clamp comes back. That alone would have been a jump; what made it immovable is that the reposition ran *in response to the popover's own scroll event*: the listener is registered capture-phase on `window` (deliberately — a scroll event does not bubble and the anchor usually lives in a scrolling table wrapper), so it saw every scroll in the document including the popover's own. Every wheel notch scrolled the list and then instantly reset it.

Both halves are fixed: the scroll handler ignores events originating inside the popover, and `position()` saves and restores `scrollTop` across the measurement. A popover scrolling inside itself has not moved relative to its anchor and has nothing to recompute, so skipping is right on its own terms too.

**2 — the same popover was misplaced under the new UI scale.** Found while verifying the above, and it would have shipped in v115.0. `getBoundingClientRect` and `window.innerWidth/Height` report DEVICE pixels; `style.top` is read as CSS pixels and then multiplied by the element's zoom. Those agree only at 100 %. Measured at `zoom: 0.7`: a picker whose anchor ended at y=231 was drawn at y=166 — above and across the button it belongs to. Every filter menu and column picker in the app, at every scale but 100 %. The four written offsets are now divided by `node.currentCSSZoom` (the cumulative effective zoom for that element, so it stays right if a zoom is ever introduced between the root and the portal target), guarded to 1 where the property is absent — never 0, which would write `Infinity` and put the popover nowhere at all.

**3 — the pickers themselves.** `canConfigureColumns` enabled on all three tables that hard-disabled it: «نتائج فحص الأشعة» (studies), its movement-history table, and the ad-hoc import review table.

«نتائج فحص الأشعة» needed more than flipping the flag. Its sample-derived columns were **pre-filtered** by the referrals table's saved layout before `DataTable` ever saw them, so a picker there could have hidden more columns but could not have revealed one — a control that works in one direction only, which is worse than none. `getVisibleSampleColumns` is now `orderSampleColumns` (order only) plus `defaultVisibleSampleColumnIds`, and the visibility decision moved to `defaultVisible` + the table's own picker. The default appearance is byte-for-byte what it was; the difference is that the hidden columns are now reachable.

**4 — layouts persist.** New `useColumnPreset` hook: load-on-mount, save-on-change, personal-over-shared, and columns added in a later version default to visible rather than being read as deliberately hidden. It is XrayReferrals' behaviour — which was the only table that had it — made reusable. XrayReferrals is deliberately NOT refactored onto it: that component sits 28 lines under its `max-lines-per-function` ceiling, and rewriting working code inside it to save duplication elsewhere is the wrong risk. `BrowsePresetDatasetKind` gains three keys; both preset files hold a `Partial<Record<…>>`, so a file written before a key existed simply lacks it.

**Left alone, deliberately.** «صور الأشعة المحالة» keeps its `configure-referral-columns` permission gate (default: manager and admin only) — that is a documented per-role grant an admin owns, not a hard-coded `false`, and flipping a permission default is the owner's call, not a bug fix. The remaining hand-rolled tables are not candidates: the action log documents in its own source why it is not a `DataTable`, and the permission matrices and the KPI screen-reader tables have no row data whose columns could meaningfully be hidden.

## v115.0 — 2026-08-23 — Add (ui): admin-settable UI scale, and sign in with the keyboard left on Arabic

**Why:** Two unrelated owner reports, both about the interface getting in the way of work that is otherwise fine.

**1 — the screen is too small for the data.** On «صور الأشعة المحالة» the action buttons sit below the fold and the columns run past the right edge, so reading one row means scrolling in two directions. The request was explicit: let an admin scale the interface, and have it apply everywhere rather than to one page.

**2 — the keyboard is on the wrong layout.** The password is `mhmd`; the operator's keyboard is still on Arabic; the four keys they press produce `ةاةي` and the login is rejected. Nothing is wrong with their memory or their typing — same physical keys, same order — and the field masks its content, so there is nothing on screen to explain it either. In an Arabic-first deployment this is a daily occurrence, not an edge case.

**What changed:**

**1 — `--ui-scale`, a root zoom (`src/data/preferences/uiScaleStore.ts`).** Two controls in Settings: interface size (60–140 %) and data-table height (50–200 %), both applied live as the slider moves and persisted per browser in `localStorage`.

`zoom` on the ROOT element, and both halves of that were forced rather than chosen. Not a root font-size: this app's CSS is px-dominant (~4,400 px literals against ~175 rem), so scaling type would move almost nothing. Not a transform or a nested `zoom` on a container: a transformed ancestor becomes the containing block for every `position: fixed` descendant, which would tear the sidebar, the dialogs, the popovers and the feedback widget off the viewport. At the root, Chromium treats it as browser zoom and fixed stays fixed. Chromium-only is already the baseline — the workspace needs `showDirectoryPicker`.

The correction that makes it work is `--app-vh`. Measured in Chromium at 1280×800 with `zoom: 0.8`: an element sized `100vh` renders **640** device px, not 800 — `vh` resolves against the viewport in CSS pixels and the result is *then* scaled. Every viewport-height rule therefore comes out short by exactly the zoom factor and leaves a dead band at the bottom of the screen. `--app-vh` (`calc(100vh / var(--ui-scale))`) divides it back out, and all 34 raw `100vh`/`100vw` uses across 15 stylesheets now go through it. Width needs no equivalent and that is the point of the feature: the root simply gains `1280 / 0.8 = 1600` CSS px of room, so more columns fit and the table stops scrolling sideways.

**Two bugs the browser suite caught that the unit tests could not**, both worth naming because both would have shipped:

- **`min-height` beats `max-height` in CSS.** `.dt-table-wrap` on the reviewer's queue carried a flat `min-height: 560px`. Lowering the table-height control changed its computed `max-height` to 336px and its rendered height not at all — the control did nothing on the one page it was asked for. The 560px floor is now `--ui-queue-floor`, scaled by the same multiplier and shared by the queue, the inspection panel and the empty-panel placeholder so all three still agree on where the fold is.
- **The reset button never enabled.** `isUiScaleCustomized()` was called straight from the render — module state the component does not listen to, and, since the call takes no arguments, something the React Compiler may hoist out of the render entirely. Exactly the hazard `useIsCustomized` in `useLabels.ts` already documents. It is now `useIsUiScaleCustomized`, over `useSyncExternalStore`.

Applied in `main.tsx` before React mounts, so the first painted frame is already at the chosen size rather than jumping.

**2 — `src/auth/keyboardLayout.ts`.** Maps between what the keys PRODUCE on Arabic (101) and on English, so one submitted password can be checked against the other reading of the same keystrokes. All three `verifyPasswordHash` call sites in `AuthGate` route through `verifyPasswordWithLayoutFallback`.

Two details carry the correctness. First, it returns **the plaintext that matched**, not a boolean — because the transparent Argon2id rehash on login re-hashes whatever it is handed, so returning `true` and letting it hash the typed string would silently replace an operator's stored hash with one for `ةاةي`, changing their password to something they never chose and cannot reproduce deliberately. Second, `لا` has **two** valid readings (the single `b` key, and `g`+`h` as `ل`+`ا` — the Arabic layout is not injective), so both are offered rather than one being guessed; a round-trip test found this rather than a review.

Security: one submitted attempt is now checked against at most four candidates — a factor-4 reduction in an attacker's work, which is nothing against Argon2id (m=19 MiB, t=2) behind a five-attempt lockout. It does not widen what counts as a correct password; every candidate is verified against the stored hash in full. The lockout counts submitted attempts, not candidates, so it cannot be used to buy extra guesses. A correctly-typed password still costs exactly one verification, since the literal string is checked first.

**Migration/rollback:** No data-format change; nothing is written to the workspace. `xray_ui_scale_v1` is a new `localStorage` key (registered in `storageRegistry.ts`), absent until someone moves a slider, and removed again on reset — so "never touched it" and "set it back to normal" stay indistinguishable. Rollback is a revert: with the key present but the code gone, it is simply ignored. The keyboard fallback stores nothing and changes no hash; reverting it only makes wrong-layout logins fail again, as before.

## v114.2 — 2026-08-23 — Fix (adhoc-import): surface assignments the index lost, and show the operator's own xray id

**Why:** Two field reports from the same workspace, both about ad-hoc («حالات استثنائية») rows.

**1 — «حالات استثنائية» showed 0 in an established workspace while a brand-new one worked.** An ad-hoc assignment commits in three writes: sample rows, then the distribution events, then the record — and the record's save is what refreshes `adhoc-imports.index.json`. The events are the durable part and they land SECOND, while `assignedRows > 0` on the index was the ONLY gate deciding whether anybody could see them. So any failure on the third write — a share hiccup, a workspace handle that went stale (the reported one surfaced as XQ-IO-030), a CAS conflict — left rows genuinely assigned on disk and invisible to every reader. Worse, it was unrecoverable by the obvious remedy: re-running the assignment finds its own events already there and answers «كل الصفوف المحددة معيّنة بالفعل», so the bookkeeping can never catch up on its own. A folder alone proves nothing — every SAVE of an ad-hoc record writes its `sample.master.json`, so an uploaded-but-unassigned import has a folder as well — so the discriminator is `distribution.events/`, which only `appendDistributionEvents` ever creates. ## v114.1 — 2026-08-23 — Change (template): gate phase two on «هل يمكن الاطلاع على البيان» and give every «أخرى» option its own text box

**Why:** Owner request. Phase 2 («تحليل البيان الجمركي») assumed the reviewer could always pull up the customs declaration and asked eleven questions about it unconditionally. When the declaration is not reachable, none of those questions have an answer — but three of them are `required`, so the phase could not be completed and the stepper would not advance. The phase needed a way to end after one question.

Second, «أخرى» appeared as an option in five fields and recorded only that the reviewer had something to say, never what it was. Phase 1's «اسباب انخفاض جودة الصورة» already had a companion free-text box; the four phase-2 fields did not, and the phase leaned on one shared notes field to carry all of them — which cannot be attributed back to the option that prompted it.

**What changed:** Two edits to the default 3-phase study template. Both are template *data*, not engine behaviour: `isFieldVisible`, `collect()` and the phase-completion check already do everything needed, and no runtime file was touched.

**1 — phase 2 opens with an access gate.** New first field «هل يمكن الاطلاع على البيان» (`dropdown`, required, `["نعم","لا"]` — two options, so InspectionPanel renders it as a segmented control). It carries the image gate that every phase-2 field used to repeat: `fHasImage equals "نعم"`.

Every other phase-2 field now conditions on the **gate** instead of on the image. `isFieldVisible` walks a condition's source field recursively, so the original "no image ⇒ no declaration work" rule survives intact through the chain rather than being restated eleven times. Answering «لا» leaves the gate as the only visible field in the phase; `getVisibleRequiredFields` counts visible required fields only, so the phase reads as complete and the stepper advances — and `collect()` persists visible fields only, so a «لا» answer stores one field, not eleven nulls.

**2 — every «أخرى» option gets its own text box.** Four new `textarea` companions — «نوع البيان (أخرى)», «طبيعة البضاعة المصرح بها (أخرى)», «طبيعة البضاعة الظاهرة بالأشعة (أخرى)», «أسباب عدم المطابقة (أخرى)» — each conditioned `equals "أخرى"` on its own source field, matching the shape phase 1's «سبب انخفاض الجودة (أخرى)» already used. On the two multiselect sources this works because `evaluateCondition` reads `equals` against a multiselect as "is this option among the picked ones?", so the box survives the reviewer picking a second category alongside «أخرى». Unpicking «أخرى» hides the box, and a hidden field is dropped from the saved answer.

They are `required: false`, following the existing phase-1 companion: a blank «أخرى» box is worse data, but a required one blocks phase advancement, and that trade was not the owner's to inherit silently. Flipping `required` to `true` on all five is a one-word change per field if wanted.
