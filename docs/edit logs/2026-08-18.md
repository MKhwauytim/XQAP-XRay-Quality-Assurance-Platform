## v99.4 — 2026-08-18 — Fix (distribution): short segment names, chunked appends, and a per-event fallback so a Phase 4 save survives every share failure mode

**Why:** Fifth field report of `XQ-IO-031` on the owner's shared workspace — after v97.1 (keep a committed write), v98.0 (an ~11 s read-back ladder), v98.3 (the extension probe) and v98.6 (rotate away from an unreadable segment). Four fixes, four reports: that is no longer a failed hypothesis, it is a wrong model, so this entry stops adding patience and instead removes the assumptions the model rests on.

What the code proves after v98.6, by elimination: `safeWrite`'s exhausted read-backs return `null` and surface as XQ-IO-009/010, `verifySegmentSize` is only fatal on an unreliable baseline (which v98.6's rotation all but removes), so the one remaining site that can put **031** on screen during a Phase 4 save is the segment **write itself** — `getFileHandle(create:true)` / `createWritable()` raising `NotFoundError` through `retryTransientWrite`. And `031` is by definition the verdict *after* `classifyNotFound` created `.fs-reachability-probe.tmp` **and** round-tripped `.fs-extension-probe.ndjson` in that same directory. A folder that takes both probes but permanently refuses this write is not flaky and is not extension-blocked: it is refusing this **name**.

The owner also reports every other feature — Phases 1–3, reports, answers, approvals — saving and reading normally. Only `distribution.events/` fails, and it is the only place the app writes an 80-character name (`{deviceUuid}-{sessionUuid}.ndjson`, 87 with Chromium's `.crswap` sibling) inside the deepest directory in the tree. Every other file it writes is short: `distribution.log.json` 21 characters in the same folder's parent, `sample.master.json` 18, and the pre-segment `{eventId}.json` 41. Windows caps a path at 260 characters, so on a deep UNC workspace path the 26-character probes fit while the segment name does not — which is exactly a permanent, per-name `NotFoundError` in a genuinely writable directory.

**This entry is written WITHOUT a confirming measurement, deliberately and at the owner's instruction** ("can't do tests now, add all possible fixes for all possible scenarios"). So it does not bet on the length hypothesis: it closes every candidate cause, each independently, and adds the diagnosis that names which one it was on the next report. A probe script for the real share (`probe-share-writes.ps1`, short/long/`.crswap`/2 MB cases with an async-survival re-check) is with the owner; the remaining datum is the `distribution:append-segment` error-log line.

**What changed — six independent defences:**

**1. Segment names are 22 characters, not 80.** `segmentBaseName` now takes 8 filename-safe characters of the device id and 6 of the session id (`{8}-{6}.ndjson`), shorter than the legacy per-event names that worked for months, with 2^56 of distinctness between concurrent writers. Compatibility is free and needs no migration: readers discover segments by `.ndjson` suffix glob, so long-named files from earlier versions keep being read and folded; a writer simply never appends to them again, and nothing is renamed, so `foldCheckpoint.segmentOffsets` stays valid. A collision would only mean two writers sharing one chain, which the read-modify-write append already survives.

**2. The write itself gets the patient ladder.** The post-close read-back has used the ~11 s ladder since v98.0 while the write it verifies still gave up in ~630 ms. Failing here aborts a whole month save, so there is nothing to buy by giving up early.

**3. One retry against a freshly-resolved directory handle.** `getSampleMainDir` answers from the workspace directory-handle cache, and a handle held since mount goes stale when an SMB session idle-disconnects — the documented "works after re-picking the folder" ritual. On a failed append the storage layer purges that cache, re-resolves, and retries the chunk once.

**4. Per-event `{eventId}.json` fallback.** If the NDJSON append still fails, the batch is written in the pre-segment layout that every reader already merges (`loadImmutableDistributionEvents`, and the checkpoint path's `legacyEventFileNames`). Names are 41 characters and the extension is `.json`, so this survives an `.ndjson`-blocking scanner. It is slower, and that is the right trade against refusing to distribute the month. Degradation is restricted to `NotFound`/`NotReadable` — a revoked grant, a full disk or a browser without `createWritable` fails the per-event path identically, so those keep failing fast with their own already-classified code (XQ-IO-017 / XQ-IO-020 / XQ-DIST-006) instead of burning one write per event to reach the same error. Engaging the fallback logs the new **XQ-DIST-009**, so an admin learns the fast path is unusable here rather than silently paying per-event costs forever.

**5. No single giant write.** `shouldRotate` deliberately lets an oversized batch exceed the cap once (an empty segment must never rotate, or a large batch would never land) — which put one ~2.3 MB write on the share for a whole-month bulk assignment, the slowest and most failure-prone write the app performs. `chunkEventsForSegmentAppends` bounds every append by `MAX_OPEN_SEGMENT_BYTES`/`MAX_OPEN_SEGMENT_LINES`, so a 9,000-event month is many ~128 KiB writes and a failure costs one chunk. Chunk order preserves input order, so fold order is unchanged. The save-progress bar now advances per chunk instead of jumping 0 → 100.

**6. Two causes the classifier could not see.** `classifyNotFound` now (a) re-checks the extension probe after a 1.2 s delay, because antivirus/DLP/sync clients quarantine asynchronously and always won an instant round trip — that verdict is the existing XQ-IO-033; and (b) probes with a **same-length, same-extension** name, whose failure is the new **XQ-IO-034**, whose Arabic says the only remedy that works: move the workspace closer to the share root. Both are on the already-exhausted failure path, so a healthy share pays nothing.

**Migration/rollback:** No data migration and no format flag. New writes land in `{8}-{6}.ndjson` (and `-{seq}` siblings); every previously written `{36}-{36}.ndjson` segment, and every legacy `{eventId}.json`, is still read, merged and folded — the reader contract was always a suffix glob. Fold output for an unchanged event set is unchanged (chunking only splits the writes; `mergeDistributionEvents` and `distributionEventSetIdFromIds` dedupe by `eventId`, so a retry or fallback writing an event twice is absorbed). Rollback is reverting these files: older builds read the short names as ordinary segments, since nothing about the name is interpreted on the read path.

**Two defects fixed during the pre-merge review** (an adversarial review of this change against
`main`, run before merging):

- **The 56-bit distinctness claim was false for two of the three id shapes.** `shortenSegmentIdPart`
  sliced the HEAD of the compacted id, which is uniform only for a UUID. `ephemeral-{uuid}` (used
  when localStorage is unavailable) begins with the literal `ephemera` every time, contributing zero
  bits; the no-`crypto.randomUUID` fallback `{Date.now()}-{random}` gave a device part that is a
  100-second bucket and a session part a 2.78-hour one, so two machines starting in the same window
  produced a byte-identical base. It now HASHES the whole value with the file's existing
  `createSimpleHasher`, so every shape gets the same distribution (verified: 200k ephemeral pairs,
  zero collisions). The accompanying comment claiming a collision is harmless because "the
  read-modify-write append already survives" it was also wrong and is corrected — `withResourceLock`
  is Web Locks, per-origin and per-browser, so it serialises nothing between two machines on a share;
  both would write `existing + own lines` and the second would drop the first's events.
- **The degradation cascade was paid per chunk instead of per save.** The causes this degrades for
  are properties of the NAME, not the moment, so they fail identically for every chunk — but each
  chunk re-paid the full ~11 s write ladder, ~1.2 s classification, and a second ~11 s ladder on the
  re-resolved handle. An 18-chunk month spent roughly 7 minutes asleep reaching the same conclusion
  18 times, and paid it again before surfacing an error if the fallback also failed, turning what was
  a 2-second error on `main` into a 7-minute one. A `segmentPathUnusable` latch now makes the
  diagnosis once per save; it is scoped to the call, so a genuinely transient failure never latches
  beyond the operation it hit. Pinned by a new test that fails (by timing out) without the latch.

  sorted before `"2026-9"` and a tie between October and November broke toward the **later** month,
  contradicting the documented "ties break toward the earlier month" contract. Zero-padded; the

## v99.1 — 2026-08-18 — Fix (population, auth, workspace): ten defects found by a multi-agent bug hunt

**Why:** A five-agent bug hunt swept the app category by category (population pipeline, employee
workspace, reports, auth/admin, workspace core). Each hunter was required to *execute* a probe rather
than reason from reading, and each fix was re-verified against the code before being applied. The
sweep surfaced twenty-one candidates; ten are fixed here, two sampling findings are deferred to an
owner decision, and one was refuted.

Three of the ten could destroy real data silently, with no error surfaced to the user, which is what
justifies fixing them together rather than one per branch.

**What changed:**

**Data-loss defects (the reason this entry exists).**
- `fileSystemAccess.ts` treated an *unreadable* `users.permissions.json` the same as an *absent*
  one. A corrupt file (live + `.bak` both damaged) returned `null`, `WorkspaceProvider.applyDiskUsers`
  hydrated the six shipped default accounts and the default permission matrix over it, and the next
  `syncUserManagementToDisk` persisted those defaults over every real account. `refreshPermissions`
  runs this on every 45s sync tick, so the swap happened mid-session with nothing shown to the user.
  `invalid_json` now joins `permission_denied`/`read_failed` in the XQ-FS-015 throw — only a genuinely
  absent file may hydrate defaults. Separately, `readJsonFile`'s recovery ladder was live/`.bak` only;
  it now also probes `{file}.tmp`, matching `safeReadJson`'s documented ladder — `.tmp` is exactly
  the artifact `safeWriteJson` leaves behind on a failed commit.
- `userManagement.ts` re-seeded the same six default accounts (with their default passwords) whenever
  the roster was empty, so deleting the last managed user resurrected them, and the resurrection
  survived reloads. Seeding is now keyed on the roster being *absent* rather than empty: `[]` is an
  administrative decision and stays empty. Fresh workspaces still seed, via `workspaceDefaults`.
- `adhocImportStorage.ts` seeded `{ imports: [] }` when the index read came back corrupt, so the next
  save left an index naming only the newest import while every earlier record sat on disk unreachable
  (the index is the only lister). `corrupt` and `missing` are now distinguished; only `missing` may
  seed.

**Correctness defects.**
- `populationProcessor.ts` applied Excel's 1900-leap-year correction twice. The constant 25569 already
  absorbs the phantom 29-Feb-1900, so the extra `serial - 1` shifted **every imported date one day
  early** — a row dated the 1st landed in the previous month, moving it in month-scoped reports, KPI
  buckets and Browse filters. Verified against the vendored SheetJS's own `XLSX.SSF.parse_date_code`,
  which is what read the cell in the first place. Six table-driven expectations in the test file had
  the one-day-early values pinned, which is why the suite was green; they now pin the SheetJS values.
  **Months processed before this fix carry off-by-one dates on disk and are not retroactively
  corrected.**
- `templateRuntime.ts`: an unanswered source field collapsed to `""` for equality tests, so
  `notEquals X` fired on every fresh form — showing, and when required gating on, a field whose branch
  the employee had not chosen. Because `collect()` persists exactly the fields the predicate returns,
  the branch that should have been asked was never stored. An unanswered source now satisfies neither
  branch. An untouched checkbox is the one exception: `InspectionPanel` renders it visibly unticked

- `notificationStorage.ts` omitted the delayed `verify` re-read that `actionLog` and `userSync`
  already pass to `casLoop`, so two machines acknowledging the same notification lost one
  acknowledgement while reporting success to both.
- `authActivityLog.ts` replaced a corrupt activity log with a one-session log and reported success. A
  present-but-unreadable log now aborts the flush and leaves the pending entries in memory for a later
  attempt, instead of overwriting the history.
- `passwordCrypto.ts`: a malformed legacy PBKDF2 record threw `InvalidCharacterError` out of `atob`,
  through both unguarded `AuthGate` submit handlers. A damaged record is now an ordinary
  authentication failure, so the message, the failed-attempt counter and the log all still run.
- `AdminAccountSection.tsx` applied a new admin passcode (and the sign-in-method flip) to runtime state

  already live. The write now happens first and runtime state commits only after it resolves.
- `workspacePaths.ts`: `getRoot(..., create: true)` created a numbered `1-population/` even when a
  legacy `Population/` already held the data, after which the legacy month folders became invisible
  and `getPopulationMonthDir` threw. The create branch now probes the numbered *and* legacy names
  before creating anything. No migration is introduced — `workspaceSchema.ts` still only detects.
- `labelsSnapshot.ts` imported unknown keys into the overrides map, where the Settings UI (which
  iterates `DEFAULT_LABELS`) could never reach them to reset. Filtered through a new `isLabelKey`
  guard, which also removes an `as LabelKey` cast.

**Feature — multi-file BI import.** Up to 10 BI files, `.xlsx/.xls/.csv`, appended into one BI
population. The worker protocol takes `biFiles: File[]` and returns per-file results with per-file
soft failure. `mergeBiWorkbookResults` concatenates rows (no dedupe), stamps each sheet summary with
its source file, and sums totals — downstream (`buildBiMatchMap`, `populationExporter`) still
receives exactly one `BiWorkbookResult` and needed no change. CSV goes through the SAME parser: the
single parsed sheet is renamed to the file's base name so `بحري وارد.csv` classifies exactly as the
same-named sheet in an `.xlsx` would. Files can also be dropped onto either source card.

**Bug fixes found by review (2 HIGH, 3 MEDIUM, 2 LOW) and by the owner (3).**
- *HIGH, data loss:* removing a BI file mid-parse did not cancel it out of the merge — its rows still
  landed in the saved population even though the row was gone from the UI and the file was correctly
  excluded from the raw archive. `applyBiFileResults` now intersects outcomes against the ids still
  attached at merge time.
- *HIGH, misreporting:* the Phase 4 matrix totals row summed `exact`-method allocations (row counts)
  together with percentages and compared to 100, so a correctly configured mixed stage read as wrong
  — or, by coincidence, as "ok". Mixed stages now render a neutral note instead of a false verdict.
- *MEDIUM:* a total worker failure reset in-flight BI rows to "ready" (indistinguishable from "fine,
  not read yet") instead of "error".
- *MEDIUM:* a Phase 2 column filter picked on one month survived a month switch, showing "no rows
  match" with no visible active filter — indistinguishable from genuinely clean data. It now falls
  back to "all" when the selected column is absent from the current mismatch set.
- *MEDIUM:* a legacy `isActive: false` allocation carrying a nonzero value rendered identically to an
  active cell while contributing nothing. It is now marked.
- *LOW:* percentage-method inputs accepted values above 100; `sourceFiles.bi` recorded only the first
  attached file.
- *Owner-reported:* the app froze after a Phase 1 upload. `compareAccuracy` ran fully synchronously
  inside a render-time `useMemo` — millions of iterations blocking the main thread on a real
  population. Added `compareAccuracyAsync`, which chunks and yields via `yieldToMain()`; a test
  asserts it produces byte-identical results to the synchronous version.
- *Owner-reported:* report exports showed English Excel headers instead of the configured Arabic
  names. **Pre-existing at HEAD, not a regression.** `populationExporter.ts` built its "unconfigured
  raw fields" exclusion set from `fieldKey` values, but `rawRow` is keyed by original Excel headers —
  so every source column reappeared under its raw English header and, where a raw header equalled a
  configured one, overwrote it. The exclusion set now also covers the configured `exportHeader` and
  every known source alias, normalized.
- *Owner-requested:* the Phase 2 تفاصيل الاختلافات section is collapsed by default; the inspection
  panel's always-on missing-required-fields banner was removed (the header progress bar carries the
  same information passively, and submit-time validation is unchanged).

**Migration/rollback:** No on-disk schema migration. Two write-side widenings, both
backwards-compatible on read:
- `1-raw/` now archives EVERY BI source file (`bi.source.1.xlsx`, …) instead of only the first; a
  single-file import still writes the historical `bi.source.<ext>` name. Without this a multi-file
  month was not reproducible from its own archived sources.
- `month.manifest.json`'s `sourceFiles.bi` widened from a single metadata object to an array.
  Verified write-only — no reader exists in the codebase — so nothing needs a compatibility path.

The raw bundle budget was raised 3.60 → 3.75 MB for the two redesigns, after deleting the orphaned
CSS above. The GZIP budget is deliberately unchanged and still has ~100 kB of headroom; gzip is what
governs transfer, and holding that line is what keeps this a budget rather than a rubber stamp.

Rollback is a plain revert: no data written by this version is unreadable by the previous one.
