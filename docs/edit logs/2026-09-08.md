## v134.1 — 2026-09-08 — Fix (storage): record every .bak/.tmp recovery instead of only flashing a banner

**Why:** A deployment reported a warning about a "backup/tmp file" on **every sign-in, for every user, admin included** — which by itself says a SHARED bootstrap file is damaged rather than a per-user one. The 1,707-row error log exported from that same workspace could not name the file, and the reason turned out to be in the app: `safeReadJson`'s `.bak`/`.tmp` fallback, and the bootstrap `readJsonFile` fallback beside it, fired a `window` CustomEvent and called `logError` **never**. The recovery was visible to whoever happened to be looking at the banner, and to nobody afterwards — not to the durable per-user error log, and therefore not to the admin XLSX export that the whole `errorLog/` module exists to produce.

That is the same defect class this file has been closing all day, in the layer that reports the others: a real, durable, workspace-level fact — some file's live copy is damaged and every reader is limping along on a snapshot — that the app knew and did not write down. The banner also said only "recovered from the backup", naming neither which copy answered nor that it would keep happening, so a user had nothing they could usefully report.

Rejected: logging every recovery (`users.permissions.json` is re-read by the 45 s sync tick, so that is ~80 entries per user per hour written onto the same contended share this app is trying not to hammer — the condition is a property of the FILE, not of the read).

## v134.0 — 2026-09-08 — Fix (approvals): recover a decision file that cannot be read, and stop reporting failed reads as empty history

**Why:** Follow-up to v133.0, from a full pass over the same 1,707-row production error log. v133.0 fixed the three mechanisms behind the reported symptoms; this one closes the case that pass turned up and v133.0 missed, plus the two places the same defect was still live.

The find, and a correction to what v133.0's own notes said. `casLoop:exhausted(approvals:decisionEvent)` is 55 rows of the log, and v133.0 characterised them as the 2026-09-08 share outage surfacing on the approvals write path. The dates say otherwise: **52 of them are byte-identical, name ONE file, and span 2026-08-31 → 09-08** (45 on 09-03 alone), all for the same user — `approvals:9-september-2026/malrogi: malrogi.decisions.json exists but could not be read (invalid envelope, and no usable .bak or .tmp)`. That is not a transient flake. That file is damaged on disk, `appendDecisionEvent` re-reads it as the base of its read-modify-write on every casLoop attempt, and `loadSupervisorDecisions` throws — correctly, since substituting an empty shell would replace the whole B5 decision chain. So the supervisor could not record a single approval decision for that month, for over a week, and the app offered no way out of it. It is still failing today.

Two more things were wrong in the same area:

1. `loadAllSupervisorDecisions` used `onUnreadable: "skip"` plus `catch { return [] }` — the exact silent-empty conflation v133.0 fixed elsewhere, still live, and directly contradicting its own single-file sibling one function above, whose docblock spells out why an unreadable decision file must never become an empty one ("every already-approved request silently reverts to pending and becomes re-approvable"). The aggregate read feeds the ENTIRE referral/replacement/reopen approval surface, so the skip did that to a whole supervisor's history with nothing on screen to say a file had been dropped.
2. `readWorkspaceActions` resolved with `[]` when the per-actor audit scan could not be established, and UserManagement's actions view both rendered that as "nothing has ever happened" AND stamped its `actionsLoadedForRef` cache with it — one failed read blanked the audit history for the rest of the session.

Rejected: repairing the damaged file automatically on read (a repair that runs unasked, on data whose correct contents nobody can verify, is worse than the outage); hard-deleting the unreadable file (CLAUDE.md's post-launch policy, and the `messages.json.migrated` precedent, require archiving); and giving the audit log the same reject-on-unreadable treatment per file (a log legitimately wants "show me what you have", so its per-file skip stays — what it lacked was any way to know a skip had happened).

**What changed:** `src/data/approvals/decisionFileRecovery.ts` (new) — diagnosis and recovery for a decision file that exists but cannot be read, with the two scenarios kept explicitly apart.

- `inspectDecisionFile` reports what is actually at the live name and at its `.bak` / `.tmp` siblings: `absent`, `readable` (with its decision count), `corrupt` (the share answered; the bytes are not usable content) or `unavailable` (the share did not answer — says nothing at all about the contents). It reads the live name through `safeReadJson`'s `recoveredFromBak` flag, which is what separates "this file is fine" from "a sibling is covering for it": the second still reads, so nothing is blocked, but the live file is damaged and the workspace is one lost `.bak` from the incident above. Hence two distinct flags — `needsRepair` and `blocked`. Also reports `chainBreakAt` from `verifyDecisionChain`, as a finding for a human, never something to auto-repair.
- `inspectMonthDecisionFiles` scans the whole month and sorts blocked-first, because an admin looking at a stuck approval surface does not know which supervisor's file is at fault — the error log named it, the app never did.
- `recoverDecisionFile` handles both scenarios. **Data still exists**: restore from the readable sibling, after archiving the damaged original. **Data does not exist**: only with the caller's explicit `allowReset`, archive and start a fresh, empty chain; without it the outcome is `unrecoverable` and nothing is touched. Every displacing path copies the live file's BYTES (it has no parseable content — that is the whole problem) to `{fileName}.unreadable-{timestamp}` and only then removes the original, so an interruption leaves both copies rather than none.
- **The one safety property, pinned by its own test:** `unavailable` is refused outright, whatever the caller passed. Archiving or resetting on a share that merely is not answering would destroy a healthy decision chain on the strength of a network fault — and 715 of the 1,707 log rows are exactly that condition.
- Restoring from `.bak` gives back the PREVIOUS COMMITTED state, so the most recent decision may not be in it. The outcome carries the count and the source, and the Arabic notice says so, rather than presenting the result as "everything is back".

`DecisionRepairSection` (new, Settings tab) makes it reachable: pick a month, scan, and per damaged file either restore or — behind a ConfirmDialog — archive and restart. Gated on `canMutate("view-error-log")` for the same reason StorageSection is (the settings tab admits `guest` for read-only viewing), so it stays admin-only by default with no new permission-matrix row. Deliberately does NOT call `useGlobalMonth`: a damaged file is usually in a month the admin is not looking at, and that hook throws outside `GlobalMonthProvider`, which would couple the whole Settings tab to a provider none of its other sections need — tried, and it took the tab's own suite down.

`approvalStorage.loadAllSupervisorDecisions` now rejects on an unreadable decision file and on a failed scan; a month where nobody has decided anything is still `[]`. `readWorkspaceActions` rejects when the per-actor scan cannot be established, and a skipped actor file now names itself under `audit:read-skipped` / `audit:read-archive-skipped` with the word INCOMPLETE — previously a skip was entirely invisible. `referralStorage.loadRequestLogs`'s failure-domain docblock is rewritten: it described the degrade-to-`[]` behaviour as a feature, and that behaviour was the bug.

**Migration/rollback:** No schema or on-disk format change. One new file NAME can appear in `2-samples/{month}/3-approvals/`: `{supervisor}.decisions.json.unreadable-{ISO timestamp}`, written only by an admin-initiated repair. Nothing reads it — it is a manual-recovery copy, exactly as `messages.json.migrated` is — so a rolled-back client ignores it and behaves as before. Rollback is a plain revert; a repaired workspace stays repaired, since the repair's product is an ordinary, readable decision file.

## v133.0 — 2026-09-08 — Fix (workspace-reads): a failed read is no longer presented as empty data

**Why:** Three production reports on 2026-09-08, all from the same shift on the shared folder: an employee's assigned samples vanished mid-inspection and the queue showed 0 (a page refresh brought them back, but the day's work had to be redone); an admin opening نتائج الفحص saw one employee credited with 2 completed samples when they had done far more; other employees hit a startup error naming a `.tmp`/backup file. The exported error log (1,707 rows, 424 of them from that day) says what actually happened: `NotReadableError` accounts for 314 of the day's 424 entries, spread across every file the app reads — `users.permissions.json`, the notification file, the sync tick's revision probes, the distribution log — for every one of the four signed-in users, from 09:07 onward. The share stopped answering reads for a while. It did not lose any data.

The app's response to that is the defect. Two separate mechanisms turned a temporary read failure into a factual-looking statement about the data, and a third made the outage noisier than it was:

1. `loadOrDeriveDistributionCurrent` catches every failure and returns `null` — and `null` is ALSO how it reports the honest "this month has no distribution events yet". Both queue-rendering views wrote `?? []` over that and called `setLoadState("ready")`. A failed read therefore rendered as a finished, successful, EMPTY queue, with nothing on screen to say otherwise. That is the "0 samples" report, and — on نتائج الفحص, where the same `?? []` drops every row — the "he only finished 2" report. The error log has both call sites failing that day: `distribution:load-or-derive` at 09:23:12, `xrayReferrals:loadData:silentRefresh` eleven times.
2. `loadAllEmployeeFiles` / `loadAllEmployeeRequestFiles` folded a failure of the SCAN ITSELF into `[]`, and `listAnswerDirStems` returned a half-finished listing as if it were the whole one. The candidate stems are the set of employees the caller reports on, so a listing that died partway told a supervisor that every employee it never reached had done no work. `answerStorage:loadAllEmployeeFiles` failed twice that day and `…RequestFiles:employee` 44 times.
3. `NOT_READABLE_RETRY_DELAYS_MS` was `[20, 60]` — 80 ms and two retries, the shortest ladder in the app, against ~630 ms for a stale snapshot and ~11 s for a post-write read-back. The rationale in the comment ("another Chromium process swaps a file") is a local-disk story. Four clients on one SMB share do not clear an unreadable handle in 80 ms, and all 314 of those log entries are ladders that had already run out.
4. The durable error log fed the storm it was recording. `errorLogSink` skips contexts starting with `errorlog:`, but `casLoop` reports its own exhaustion as `casLoop:exhausted(errorLog:userFile)`, which does not match that prefix — so each failed error-log write enqueued a fresh error destined for the same failing file. 44 such entries in one day.

Rejected: widening the retry ladders further (patience at the wrong layer makes share contention worse — every extra moment inside one attempt is a moment this machine holds a shared file open while others want it); and changing `loadOrDeriveDistributionCurrent`'s return type outright (fifteen call sites, most of them write paths whose `null` handling is correct as it stands).

**What changed:** The policy `readOptionalJson` already states in safeWrite.ts — *"a caller that turns the result into an empty default gets the empty default only when emptiness is a fact"* — and that T-08 already applied to `population.final.json` via `PopulationUnreadableError`, extended to the distribution and answer reads.

- `distributionStorage.ts` — new `DistributionUnreadableError` and an internal `DistributionCurrentOutcome` (`ok` / `absent` / `unavailable`). The load's body now returns that outcome: `absent` for the one case that is a fact about the data (the event log read cleanly and holds no events), `unavailable` for the outer catch and for "events exist but the row set came back empty" (the shape a failed `sample.master.json` read produces at the caller). `loadOrDeriveDistributionCurrent` and `loadOrDeriveDistributionCurrentForRead` are unchanged thin wrappers over it that still map everything but `ok` to `null`, so all fifteen existing call sites keep byte-for-byte behaviour. New `loadOrDeriveDistributionCurrentStrictForRead` throws on `unavailable` and shares the same dedupe key — and therefore the same in-flight read — with its `null`-returning sibling.
- `XrayReferrals.tsx` and `XrayInspectionResults.tsx` — both queue reads, and `ensureReplacementContext`'s exclusion-set read, switched to the strict variant. Each view's existing catch already does the right thing with a throw: a first load shows the error state with a retry button, a silent background refresh logs it and leaves the rendered queue and any open inspection form exactly as they were.
- `answerStorage.ts` — `listAnswerDirStems` no longer returns a partial listing: a genuinely missing answers directory is still absence (`NotFoundError` → empty set), anything else propagates. The outer catches of `loadAllEmployeeFiles` and `loadAllEmployeeRequestFiles` rethrow instead of returning `[]`. The deliberate per-employee `catch` inside the fan-out — one employee's unreadable file must not abort the scan — is untouched.
- `safeWrite.ts` — `NOT_READABLE_RETRY_DELAYS_MS` aligned with its closest sibling `SNAPSHOT_STALE_RETRY_DELAYS_MS`: `[20, 60, 150, 400]`, ~630 ms, paid only on the failure path.
- `errorLogSink.ts` / `errorLogStorage.ts` — the casLoop context is now the exported `ERRORLOG_CAS_CONTEXT`, and the sink's re-entrancy guard recognises both shapes its own write path produces.

Not addressed here, and deliberately: nothing in this change makes the share answer reads. It stops the app from stating, as fact, things a failed read cannot support.

**Migration/rollback:** No on-disk format changes and no schemaVersion bump — this is read-path error propagation only, so nothing written before or after this version differs. Rollback is a plain revert; a rolled-back client reads the same files identically and simply resumes reporting a failed read as an empty month.
