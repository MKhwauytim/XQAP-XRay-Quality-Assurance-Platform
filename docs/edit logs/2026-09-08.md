# Edit Log — 2026-09-08

## v133.0 — 2026-09-08 — Fix (workspace-reads): a failed read is no longer presented as empty data

**Why:** Three production reports on 2026-09-08, all from the same shift on the shared folder: an employee's assigned samples vanished mid-inspection and the queue showed 0 (a page refresh brought them back, but the day's work had to be redone); an admin opening نتائج الفحص saw one employee credited with 2 completed samples when they had done far more; other employees hit a startup error naming a `.tmp`/backup file. The exported error log (1,707 rows, 424 of them from that day) says what actually happened: `NotReadableError` accounts for 314 of the day's 424 entries, spread across every file the app reads — `users.permissions.json`, the notification file, the sync tick's revision probes, the distribution log — for every one of the four signed-in users, from 09:07 onward. The share stopped answering reads for a while. It did not lose any data.

The app's response to that is the defect. Two separate mechanisms turned a temporary read failure into a factual-looking statement about the data, and a third made the outage noisier than it was:

1. `loadOrDeriveDistributionCurrent` catches every failure and returns `null` — and `null` is ALSO how it reports the honest "this month has no distribution events yet". Both queue-rendering views wrote `?? []` over that and called `setLoadState("ready")`. A failed read therefore rendered as a finished, successful, EMPTY queue, with nothing on screen to say otherwise. That is the "0 samples" report, and — on نتائج الفحص, where the same `?? []` drops every row — the "he only finished 2" report. The error log has both call sites failing that day: `distribution:load-or-derive` at 09:23:12, `xrayReferrals:loadData:silentRefresh` eleven times.
2. `loadAllEmployeeFiles` / `loadAllEmployeeRequestFiles` folded a failure of the SCAN ITSELF into `[]`, and `listAnswerDirStems` returned a half-finished listing as if it were the whole one. The candidate stems are the set of employees the caller reports on, so a listing that died partway told a supervisor that every employee it never reached had done no work. `answerStorage:loadAllEmployeeFiles` failed twice that day and `…RequestFiles:employee` 44 times.
3. `NOT_READABLE_RETRY_DELAYS_MS` was `[20, 60]` — 80 ms and two retries, the shortest ladder in the app, against ~630 ms for a stale snapshot and ~11 s for a post-write read-back. The rationale in the comment ("another Chromium process swaps a file") is a local-disk story. Four clients on one SMB share do not clear an unreadable handle in 80 ms, and all 314 of those log entries are ladders that had already run out.
4. The durable error log fed the storm it was recording. `errorLogSink` skips contexts starting with `errorlog:`, but `casLoop` reports its own exhaustion as `casLoop:exhausted(errorLog:userFile)`, which does not match that prefix — so each failed error-log write enqueued a fresh error destined for the same failing file. 44 such entries in one day.

Rejected: widening the retry ladders further (patience at the wrong layer makes share contention worse — every extra moment inside one attempt is a moment this machine holds a shared file open while others want it); and changing `loadOrDeriveDistributionCurrent`'s return type outright (fifteen call sites, most of them write paths whose `null` handling is correct as it stands).

**What changed:** The policy `readOptionalJson` already states in safeWrite.ts — *"a caller that turns the result into an empty default gets the empty default only when emptiness is a fact"* — and that T-08 already applied to `population.final.json` via `PopulationUnreadableError`, extended to the distribution and answer reads.

- `distributionStorage.ts` — new `DistributionUnreadableError` and an internal `DistributionCurrentOutcome` (`ok` / `absent` / `unavailable`). The load's body now returns that outcome: `absent` for the one case that is a fact about the data (the event log read cleanly and holds no events), `unavailable` for the outer catch and for "events exist but the row set came back empty" (the shape a failed `sample.master.json` read produces at the caller). `loadOrDeriveDistributionCurrent` and `loadOrDeriveDistributionCurrentForRead` are unchanged thin wrappers over it that still map everything but `ok` to `null`, so all fifteen existing call sites keep byte-for-byte behaviour. New `loadOrDeriveDistributionCurrentStrictForRead` throws on `unavailable` and shares the same dedupe key — and therefore the same in-flight read — with its `null`-returning sibling.
- `XrayReferrals.tsx` and `XrayInspectionResults.tsx` — both queue reads, and `ensureReplacementContext`'s exclusion-set read, switched to the strict variant. Each view's existing catch already does the right thing with a throw: a first load shows the error state with a retry button, a silent background refresh logs it and leaves the rendered queue and any open inspection form exactly as they were.
- `answerStorage.ts` — `listAnswerDirStems` no longer returns a partial listing: a genuinely missing answers directory is still absence (`NotFoundError` → empty set), anything else propagates. The outer catches of `loadAllEmployeeFiles` and `loadAllEmployeeRequestFiles` rethrow instead of returning `[]`. The deliberate per-employee `catch` inside the fan-out — one employee's unreadable file must not abort the scan — is untouched.
- `safeWrite.ts` — `NOT_READABLE_RETRY_DELAYS_MS` aligned with its closest sibling `SNAPSHOT_STALE_RETRY_DELAYS_MS`: `[20, 60, 150, 400]`, ~630 ms, paid only on the failure path.
- `errorLogSink.ts` / `errorLogStorage.ts` — the casLoop context is now the exported `ERRORLOG_CAS_CONTEXT`, and the sink's re-entrancy guard recognises both shapes its own write path produces.

Not addressed here, and deliberately: nothing in this change makes the share answer reads. It stops the app from stating, as fact, things a failed read cannot support.

**Migration/rollback:** No on-disk format changes and no schemaVersion bump — this is read-path error propagation only, so nothing written before or after this version differs. Rollback is a plain revert; a rolled-back client reads the same files identically and simply resumes reporting a failed read as an empty month.
