## v131.11 — 2026-09-03 — Refactor (employee-workspace): extract the queue's selection helpers so XrayReferrals clears the max-lines gate again

**Why:** Two things, both fallout from the v131.9/v131.10 review pass.

First, a hard CI failure. v131.9 removed 24 lines from `XrayReferrals.tsx`'s MODULE scope (`buildAnswerStatusFilter` moved to its own sibling file) but added 3 lines INSIDE the `XrayReferrals` component function, because the `rowMatchesFilter` memo grew a second argument and wrapped onto four lines. That function was already sitting one line under the ceiling, so it went from 1450 to 1451 and `npm run check:complexity` — a gate CI runs on every commit regardless of the edit's tier — started failing with `max-lines-per-function`. Raising the ceiling is not an option here: this repo's own policy is that past raises were paid for with a refactor, not a bigger number.

Second, v131.10 redefined «مستهدف المؤشر» to mean "came through the regular population pipeline" and stopped reading `targetedByRiskEngine`, but three comment blocks elsewhere still asserted the OLD rule as current fact and named the case-queue as `engineVerdictOf`'s second consumer. `riskEngineVerdict.ts`'s header justified the module's own existence with a consumer it no longer has, and `labelsStore.ts` — the file this repo treats as the source of truth for what a UI string means — still documented the chip as "the risk engine actually said yes … a blank is never targeted". A reader landing on either would have implemented against a rule the code had already abandoned, and the two measures share a near-identical Arabic name space («مستهدف بالمخاطر» the column vs. «مستهدف المؤشر» the chip), which is exactly how they get conflated.

**What changed:**
1. Extracted the queue's three row-selection helpers (`toggleSelect` / `selectAll` / `clearSelection`, 21 lines of the component body) into a new sibling module `XrayReferrals/queueSelection.ts` as `createQueueSelection(setSelectedIds)` — the same split `caseFilter.ts` and `answerStatusFilter.ts` already use, and the same module-level-factory-over-setters shape as this file's own `createOpenReassignModal`. Deliberately NOT memoized: the plain function declarations it replaces were rebuilt every render too, nothing downstream keys off their identity, and a `useCallback` would have changed behaviour rather than preserved it. `XrayReferrals` drops to 1432 lines and `check:complexity` passes.
2. New `queueSelection.test.ts`: 6 tests over the set transitions the component could only exercise through a full page render — add/remove, idempotence both ways, that `toggleSelect` copies rather than mutating the previous set (React would not re-render otherwise), that `selectAll` REPLACES rather than merges, and that a burst of toggles in one batch survives cumulatively, which is the reason the functional updater is there.
3. Corrected the three stale comment blocks to state the post-v131.10 split: `labelsStore.ts`'s chip documentation, `riskEngineVerdict.ts`'s header (its remaining consumers are deck2's `riskEngineAgreement.ts` and deck3's `slides.ts` — plus an explicit "NOT the employee queue's chip … do not reconcile them" note), and `riskEngineAgreement.ts`'s two references to the case-queue applying the same rule.
4. Filled in the empty notes cell for `targetedByRiskEngine` (row 27) in `docs/reference/DATA_DICTIONARY.md` with the same warning, since that table is where a future reader looks up what the column means before they look at any code.

No behaviour change: (1) is a pure move, (3) and (4) are comments and docs.

## v131.10 — 2026-09-03 — Change (employee-workspace): مستهدف المؤشر now means 'from the regular population pipeline', not a risk-column read

**Why:** Following up on v131.9, the owner corrected the domain meaning of the queue's «مستهدف المؤشر» chip. It previously read the row's own `targetedByRiskEngine` risk-file column (via `engineVerdictOf`), excluding a row whenever that column was blank or held a spelling the vocabulary doesn't recognize — the exact discrepancy the owner reported (7,166 sampled rows, only 6,358 counted "targeted"). The owner clarified that membership in this indicator is NOT a per-row column read: any row that reached the queue through the regular monthly population process (إدارة بيانات الأشعة › معالجة البيانات) off the attached Risk file IS, by construction, targeted by the indicator — only a row routed through ad-hoc exceptional-case import (ارفاق حالات استثنائية) is not. That makes «مستهدف المؤشر» the exact logical complement of «إحالات استثنائية», so the two chips now partition «جميع الحالات» exactly instead of overlapping as three independent lenses.

**What changed:**
1. `caseFilter.ts`'s `matchesCaseFilter("risk-targeted", …)` now returns `!isAdhocEntry(entry)` instead of `engineVerdictOf(entry.row.targetedByRiskEngine) === "اشتباه"`. The `engineVerdictOf` import is gone from this file — it was only ever needed for the old read.
2. Deliberately left the SHARED `riskEngineVerdict.ts`/`engineVerdictOf` untouched: it still backs the executive deck's risk-engine agreement/accuracy figures (`riskEngineAgreement.ts`), a genuinely different feature that needs the real per-row flag to measure agreement between the risk engine and the actual result. Only this queue chip's definition changed.
3. Rewrote the module header's bucket documentation to record the new rule and why the old one was wrong, and updated `caseFilter.test.ts` and `XrayReferrals.caseFilter.test.tsx` for the new semantics — including the "zero results" and "unsaved draft" scenarios, which now need an ad-hoc row (not a blank-risk-column row) to exercise a row the chip excludes.

## v131.9 — 2026-09-03 — Fix (employee-workspace): queue الحالة filter no longer misses مستبدلة rows or conflates معلق with مكتملة

**Why:** The owner reported the employee queue's «الحالة» column filter as "broken and outdated." Tracing `buildAnswerStatusFilter` (the queue table's `rowMatchesFilter` override for that column) found two real bugs. First, the "مستبدلة" (replaced) option was a no-op: a non-replaced row satisfied none of the early-return branches and fell through to a trailing `return true`, so selecting "مستبدلة" showed every row, not just replaced ones. Second, when the v123.3 "معلق" status (a submitted "لا يوجد صورة" no-image answer — real work, but not a completed inspection) was introduced, it was wired into `StatusBadge`'s rendering and into the Results tab's own filter, but never became a selectable option on the queue's filter, and the "مكتملة" branch matched any submitted answer regardless of the no-image case — so filtering to "مكتملة" silently mixed in معلق rows too.

**What changed:**
1. Extracted `buildAnswerStatusFilter` out of `XrayReferrals.tsx` into a new sibling module, `XrayReferrals/answerStatusFilter.ts` (same rationale as the existing `caseFilter.ts` split: a load-bearing predicate that should be unit-testable without rendering the page, and keeping it inline would also trip `react-refresh/only-export-components` once exported). Rewrote it to be exhaustive over the four states `StatusBadge`/`getReferralPreviewValue` can actually render — مستبدلة / مكتملة / معلق / قيد الانتظار — with no catch-all fallback: a non-replaced row now explicitly rejects the "replaced" filter, and a submitted answer is routed to either "submitted" or the new "on_hold" value based on `isNoImageSubmission(answer, template)`.
2. Added `template: TemplateSchema | null` as a second parameter (needed to detect the no-image case) and threaded the queue's already-available `activeTpl` through at the call site in `XrayReferrals.tsx`, including it in the `useMemo` deps.
3. Added a `{ value: "on_hold", label: L.status_on_hold }` option to the "answerStatus" column's `statusOptions` in `subComponents.tsx`'s `buildXrayColumns`, between "submitted" and "pending" — matching the order already used by `XrayInspectionResults.tsx`'s equivalent filter.
4. New `XrayReferrals/answerStatusFilter.test.ts`: 10 unit tests locking in both regressions (replaced-row rejection when not replaced, submitted-vs-on-hold split with and without a template, pending fallback) plus the pass-through behavior for other columns/filter kinds.

export function buildAnswerStatusFilter(
  answersMap: Map<string, ItemAnswer>,
  template: TemplateSchema | null
): (entry: DistributionEntry, colId: string, filter: AnyFilter) => boolean | null {
  return (entry, colId, filter) => {
    if (colId !== "answerStatus" || filter.kind !== "status") return null;
    const v = filter.value;
    if (!v || v === "all") return true;
    if (entry.status === "replaced") return v === "replaced";
    if (v === "replaced") return false;
    const answer = answersMap.get(`${entry.xrayImageId}::${entry.assignedTo}`);
    if (answer?.status === "submitted") {
      return isNoImageSubmission(answer, template) ? v === "on_hold" : v === "submitted";
    }
    return v === "pending";
  };
}
