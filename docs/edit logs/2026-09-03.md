## v131.13 — 2026-09-03 — Fix (executive-deck): stop fullscreen presentation slide from overflowing on zoom/resize

**Why:** The executive deck's single-slide fullscreen presentation mode
(`body.deck-fullscreen .slide.deck-slide-active`) set only `width` from a
`min(calc(100vw - 32px), calc((100dvh - 32px) * 297 / 167))` formula and left
`height` to whichever other CSS rule won the cascade for that property. Any
time the fullscreen window's effective CSS-px width dropped under 1152 —
which ordinary browser zoom (Ctrl +/-) does constantly, since zoom changes
`window.innerWidth` exactly like a resize — the higher-specificity
`.slide.v2{height:auto}` narrow-viewport rule took over `height`, so the
slide's real (uncompressed, budget-calibrated) content height came out well
over 630px while width kept shrinking toward the viewport. The result:
the slide overflowed top/bottom or right/left of the screen, or was clipped
under the fixed side nav, with no scroll to reach the clipped part (single-
slide fullscreen has `overflow:hidden`) — reproduced and confirmed headless
via Playwright by toggling `body.deck-fullscreen`/`.deck-slide-active` and
sweeping viewport sizes that stand in for zoom levels (100/120/150/80/90/
110%, cycling back to 100% to rule out any CSS-side accumulation). A second,
narrower case also overflowed above the 1152px breakpoint: a short-but-wide
window (e.g. 1300×600) where the fixed 630px height alone exceeded the
available vertical space, since width and height were being fit against two
independent constraints instead of one shared aspect ratio.

**What changed:** The fullscreen active-slide rule now pins the slide to its
real fixed 1120×630 design box (matching the row-budget math every other
slide layout in this deck is calibrated against) and uniformly scales that
whole box down (or up) via `transform:scale(var(--v2-fs-scale, 1))` so it
always fits both viewport axes without distortion or clipping — the same
proven pattern deck3's `--v3-scale` already uses, and for the same reason
CSS alone can't do it: `transform:scale()` needs a unitless `<number>`, and
dividing a length by a plain number stays a length in CSS (the declaration
is silently dropped). `--v2-fs-scale` is computed by a small new inline
script (`DECK_V2_FULLSCREEN_SCALE_SCRIPT`, deck2/index.ts) as
`min((innerWidth-32)/1120, (innerHeight-32)/630)`, re-run on `resize` and
`fullscreenchange`/`webkitfullscreenchange`. Deck2-only — deck3 already has
its own always-on scale script and is unaffected. Re-verified headless after
the fix across the same zoom sweep plus extra short/tall/huge viewports: no
overflow in any case, and results are identical across repeated 100% checks
(no drift). The non-fullscreen scroll layout (side nav show/hide, slide
reflow at ≤1152px) was re-checked and is unchanged. One existing test
(`deck2.test.ts`) asserted the old fullscreen-rule selector verbatim as a
substring and was updated to match the new selector; the golden byte-
identical snapshot and the deck2 CSS-content snapshot were regenerated to
reflect the intentional CSS/JS change (`npm run test:run -- -u` limited to
`deck2`, verified all 398 deck2 tests plus the full 4330-test suite pass).

## v131.10 — 2026-09-03 — Fix (distribution): guarantee a port-trapped employee's only reachable capacity instead of splitting it by raw need

**Why:** v131.9 (this same file, above) fixed each port re-apportioning independently by raw percentage, but weighting each port purely by an employee's *remaining stage-wide need* still had a gap: an employee eligible for only one small port, alongside colleagues who could also reach a much bigger port, had that small port split "fairly" by need even though the colleagues had 900 other rows to fall back on and the trapped employee had nowhere else to go. Verified counterexample (4 employees at 25% each of 1000 rows; a 900-row port reachable by a/b/c, a 100-row port reachable only by a/d): the v131.9 algorithm gave `a=307, b=322, c=321, d=50` — d stuck at 20% of target — when `300/300/300/100` was achievable and fair given d's actual reachable capacity.

**What changed:** Before apportioning each port, `calculateBulkAssignment` now splits each eligible employee's remaining need into a "forced" portion (need that exceeds their capacity across all NOT-YET-VISITED ports — i.e. this port is their last chance at some or all of it) and an "elastic" portion (the rest). Forced amounts are guaranteed outright (or, if forced demand exceeds the port's row count, scaled down proportionally to forced urgency); only the leftover rows are apportioned by elastic need. This stops the port an employee is trapped in from being shared "equally" with colleagues who have plenty of alternative capacity elsewhere. Also extracted the percentage→Hamilton-weight conversion (previously duplicated in two places) into a shared `allocWeight` helper.

## v131.9 — 2026-09-03 — Fix (distribution): keep per-employee sample totals equal when port restrictions are active

**Why:** With any employee port-restricted, `calculateBulkAssignment` partitioned a stage's rows by port and re-apportioned each port independently at 100% among only that port's eligible employees, using each employee's raw configured percentage as the weight. A restricted employee's excluded share on the ports they couldn't reach was never made up elsewhere, and employees who happened to share fewer ports with others were over-weighted on those ports — so with four employees configured at an equal 25% each, real totals drifted to reports like 1,800 / 2,000 / 2,500 / 1,400 instead of an equal split.

**What changed:** Before partitioning a restricted stage by port, `calculateBulkAssignment` now computes each employee's overall target for the WHOLE stage once (Hamilton apportionment of the stage's total row count by their configured percentage/exact value), then processes ports most-constrained-first (fewest eligible employees first) and apportions each port using each eligible employee's *remaining* stage-wide need as an exact-count weight, decrementing that shared pool as rows are actually assigned. This keeps every employee's final total anchored to their configured percentage regardless of how the stage happens to split across ports, while an employee with fewer allowed ports still draws a bigger share of the ports they can reach to make up the difference.
