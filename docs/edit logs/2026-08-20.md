## v104.1 — 2026-08-20 — Fix (distribution): matrix counts include already-assigned rows

**Why:** Owner report from a real month: after the sample was distributed, the
حصص الخبراء عبر المستويات matrix showed `0` under عادية, CertScan and الجديد for
every expert — and a `0` totals row — while the حالة التوزيع card directly above
it read `100٪ · 6,393 من 6,393 قيد الانتظار`. The distribution itself was
correct; the matrix was reporting nothing.

All three count columns were fed from `previewData`, the `calculateBulkAssignment`
dry run. That call is idempotent by design: it filters out every row that already
has a live distribution entry, so once a month is fully distributed it returns
zero events and the preview is legitimately empty. الجديد ("the new ones") is
supposed to read `0` there. عادية and CertScan are not — they are plain count
columns, and reading `0` for an expert who owns 1,598 rows is simply wrong.

**What changed:** عادية and CertScan now report what the expert actually holds:
rows already assigned to them in this sample (`distributionCurrent.entries`,
joined back to the sample rows for the CertScan/normal split) plus whatever the
pending run would add. الجديد is unchanged and stays preview-only, which is what
its label means. An entry in the `replaced` status is not counted — that row has
moved on to the expert who took it over, and that successor carries its own
entry, so counting it would bill one row to two people.

Column headers gained `title` hints (three new label keys) spelling out the
distinction, since "0 الجديد" on a fully distributed month is correct output that
still reads like a failure without them.

No change to which rows get assigned to whom: `calculateBulkAssignment` and
`handleRunBulkAssignment` are untouched.

## v104.0 — 2026-08-20 — Change (UI): implement the three-screen design handoff — in-page approval decisions with recorded undo, targeted notifications, fluid x-ray queue

**Why:** The `design_handoff_xqap_screens` package redesigns three screens — اعتماد الطلبات, مركز الإشعارات, and صور الأشعة المحالة — and two of them ask for behaviour the data layer could not express, so this is not a styling pass.

*Approvals* were to decide in place, with no confirmation dialog, and offer «تراجع» on the result toast — the handoff explicitly requiring undo to be a recorded reverse event rather than a deletion of the original decision. Nothing supported that: `effectiveDecision` is FIRST-wins, so appending a revocation would have changed nothing at all, and `approveReferral`'s replay guard would have treated the reversed reassignments as still applied.

*Notifications* were to be addressed to a group or to named people, previewed before publishing, and then edited / re-sent as a reminder / deleted with undo. `AppNotification` had no addressee at all — `computeAudienceUsers()` returned every active employee and supervisor, and that was the audience of every broadcast.

Two alternatives were rejected. Making undo a plain "delete the decision event" was rejected because the decision trail is the point of the approval flow — a reviewer who approves and immediately reverses must leave both facts on the record. Re-posting an edited notification as a NEW record was rejected because acknowledgements are keyed by notification id in per-employee ack files, so a new id silently asks everyone who already acknowledged to acknowledge again.

**What changed:**

**1. اعتماد الطلبات — decide in place, with a recorded undo.** `index.tsx` is now a queue + sticky detail pane on the handoff's `minmax(0, 0.9fr) minmax(0, 1.7fr)` grid: status chips, a request-kind segmented filter, a bulk bar, and SLA wait badges (≥5 days danger, ≥3 warning, otherwise success). `RequestQueue.tsx` and `RequestDetail.tsx` are new; `RequestCard.tsx`, `RequestList.tsx` and `ReviewModal.tsx` are deleted along with the confirm dialog itself — موافقة/رفض now write immediately and report on a toast that carries «تراجع».

The undo is real, and append-only. `DecisionEvent.status` gains `"reverted"`, plus `revokesDecisionAt` naming the decision it takes back (that decision's `reviewedAt`, in the same reviewer's file). `effectiveDecision` returns the earliest decision that has NOT been revoked — first-wins is preserved between competing reviewers, and a revoked decision simply stops counting while both events stay on the timeline. `undoDecision.ts` (new) reverses an approved referral by emitting counter-reassignments stamped `undo:{requestId}`, and `approveReferral`'s replay guard now asks "is this id's LAST reassignment for this request the forward transfer?" so an approve → undo → approve cycle re-emits the move instead of trusting reversed events.

Undo is deliberately NOT offered for two decisions: an approved replacement (the replacement row is already in the month's sample and the original retired) and an approved reopen (the answer is back in draft and may already be edited). The distribution fold has no legal transition back for either, so the toast states the reason instead of silently corrupting the month. Only the reviewer whose decision is authoritative may revoke it — a revocation from anyone else would name a decision in a file they do not own and revoke nothing.

**2. مركز الإشعارات — targeted publishing.** `views/NotificationManager.tsx` becomes `views/NotificationManager/` (composer, list, detail, presentation helpers). `AppNotification` gains `target` (`all` / `employees` / `supervisors` / `custom`), `audience[]` for the custom case, and `editedAt`. Targeting is enforced at every read: `isTargetedAt` / `audienceFor` are new, `getUnacceptedFor` takes the reader's role, and the recipient banner plus the sidebar unread badge pass it, so a notification addressed to supervisors no longer lands in front of every employee. Storage gains `updateNotificationMessage` (keeps id, `postedAt` and every acknowledgement; stamps `editedAt`), `deleteNotification`, and `restoreNotification` — the last restoring under the ORIGINAL id so a delete + undo is invisible to readers who had already acknowledged. «تذكير من لم يطّلع» posts a new `custom`-targeted notification to exactly the people still pending, rather than re-issuing the original to everyone. A `custom` post with an empty audience is rejected instead of being stored unreadable.

**3. صور الأشعة المحالة — a queue that scales with the window.** The inspection panel's fixed `470px` becomes `minmax(340px, 1.15fr) minmax(430px, 1fr)` with the search and selection bars spanning both columns, the table scrolling horizontally below `640px` instead of crushing its cells, and the panel sticky at `min-height: 560px; max-height: max(560px, calc(100vh - 240px))`. New previous/next sample chevrons move within the *filtered* rows and reset to phase one; because `InspectionPanel` is keyed on `xrayImageId`, a switch remounts and would destroy an unsaved draft, so a deliberate chevron click routes through a `ConfirmDialog` when a draft is dirty (a background refresh stays silent, unchanged). The select column now disables rows that `planReassignment` would reject, rather than offering a checkbox the planner drops. Per-column header filtering already existed in `DataTable`; it is restyled to the handoff's specification rather than rebuilt.

Column-level deviations, all deliberate: المستوى / المنفذ keep `DataTable`'s multiselect because its only single-select kind needs static options and ports are per-month; the visible column set stays today's `DEFAULT_VISIBLE`, since §3 contradicts itself (it says "same as `buildXrayColumns` + `DEFAULT_VISIBLE`" and then lists a different set).

**4. Supporting changes.** A new `decision-reverted` workspace action type and its Arabic label; `--c-announce-bg` / `--c-announce-fg` tokens so the notification surface carries no raw hex; ~90 new label keys across the three screens; and four extractions out of the `XrayReferrals` component body (`createRenderCell`, `createOpenReassignModal`, `computePersonalStats`, `sampleNavNeighbours`, `SampleNavDraftDialog`) to keep it inside the `max-lines-per-function` regression budget, which the redesign pushed from 1450 to 1569.

**Migration/rollback:** Both new on-disk shapes are additive and read-compatible in both directions.

`decisionEvents[].status` may now be `"reverted"`; older code reading such a file treats the revocation as an unrecognised decision and would take it as the request's outcome under first-wins — but only for a request whose decision has actually been taken back, and the `revokesDecisionAt` field it ignores is never destructive. Nothing is rewritten: the revoked decision stays byte-for-byte as written, B5 chain hash included, so downgrading loses the ability to *see* an undo, never the original decision.

`AppNotification.target` / `.audience` / `.editedAt` are optional. A notification written before this change has no `target` and is read as `"all"` — exactly its previous behaviour — and older code ignores the new fields, treating a targeted notification as a broadcast to everyone (over-delivery, never suppression).
```ts
export function revokedDecisionKeys(history: DecisionEvent[]): Set<string> {
  const revoked = new Set<string>();
  for (const event of history) {
    if (event.status !== "reverted" || !event.revokesDecisionAt) continue;
    revoked.add(decisionKey({ reviewedBy: event.reviewedBy, reviewedAt: event.revokesDecisionAt }));
  }
  return revoked;
}

export function effectiveDecision(history: DecisionEvent[]): DecisionOutcomeEvent | undefined {
  const revoked = revokedDecisionKeys(history);
  return history.find(
    (event): event is DecisionOutcomeEvent =>
      event.status !== "reverted" && !revoked.has(decisionKey(event))
  );
}
```
