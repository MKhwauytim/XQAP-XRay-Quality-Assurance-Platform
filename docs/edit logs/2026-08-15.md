## v86.0 — 2026-08-15 — Fix (storage): never materialize a whole file as one string, so a large month save cannot hit V8's string limit

**Why:** Found by running **real customer data** through the pipeline end to end, not by reading code. `bi.raw.json` comes out at **573,236,797 bytes**, decoding to **455,755,299 UTF-16 code units** against V8's maximum of **536,870,888** — 85% of a hard ceiling, on data a customer has today.

Past that ceiling `file.text()` throws `RangeError: Invalid string length`, which propagated out of `safeWriteJson`, out of `saveMonthRun`'s `Promise.all`, to the outer catch — so the **entire month save aborted**: no `population.final.json`, no `processing.summary.json`, no `population.aggregate.json`, no `month.manifest.json`, and a multi-hundred-MB orphaned `.tmp` left on disk. At ~2,300 bytes per BI row that is roughly **235k BI rows** from where this customer already is: one busier month, or one where BI covers inbound as well as outbound. This is a browser app, so it is a genuine Chrome limit, not a Node artifact.

v80.5 noted this as a known pre-existing limit ("a payload beyond V8's max string length would fail there today regardless"). That understated it — `safeWriteJson`'s promotion path already carried an explicit `isStringLengthError` catch, so the ceiling was known to be reachable *inside the recovery path*. It is now demonstrably reachable on the main path.

**The bug was bigger than the report.** Two whole-file-as-one-string reads sat on the streamed path, not one:
1. `readVerifiedStreamedFile` → `readText` → `file.text()` — staged verification, committed re-verification, and the `.tmp` promotion re-read.
2. **`safeWriteJson`'s pre-write read of the existing file**, which runs on *every* write to obtain the previous revision and the `.bak` snapshot. Fixing only (1) would have moved the ceiling to "the **second** save of a big month" rather than removing it. The `.bak` rollback read and `readEnvelopeRevision` had the same problem.

**What changed:**

*Chunked reading.* New `openFile` (same NotFound/NotReadable retry ladder as `readText`, stopping at the `File`) and `streamFileChunks`, walking `Blob.slice()` byte windows of 4 MB through a **single streaming `TextDecoder` (`{stream: true}`)`**. Byte-aligned slices *do* split multi-byte UTF-8 characters; the streaming decoder carries the partial sequence across the boundary, so emitted chunks concatenate to exactly what `file.text()` returned. **The hash domain therefore did not change** — `fileHash` stays `createSimpleHasher` over text, `fileLength` stays UTF-16 code units, identical to what `streamToFile` computes on the way out. No `contentHash` migration and no compatibility break. Hashing raw bytes was considered and rejected for exactly this reason: `contentHash` is `simpleHash(JSON.stringify(data))` in the text domain and is re-verified by `verifyContentHash` on read.

*Verification stays byte-exact.* `readVerifiedStreamedFile` becomes `verifyStreamedFile`, folding the same rolling hash over the read-back windows and comparing length **and** whole-file hash. No length-only check, no sampling, no weakening at any size.

*Commit streams file-to-file.* `writeVerifiedTextStreamed(text)` becomes `copyFileStreamed(source, target)`, streaming window-by-window out of the staged `.tmp` instead of accepting one verified string. Still exactly one serialization pass — v80.5's serialization-counter test is unchanged and still passes.

*Oversized existing files.* `readTextTolerant` classifies the pre-read as `missing | text | oversized`, catching the string-length `RangeError` via the existing `isStringLengthError`. For `oversized`, `readOversizedEnvelopeMetadata` recovers the envelope header from a bounded 64 KB **tail** window — the streamed writer emits `metadata` last — yielding the revision to continue from and a "worth snapshotting" signal. `.bak` snapshot and rollback fall back to `copyFileStreamed`; `readEnvelopeRevision` is oversize-tolerant too. This is deliberately weaker validation for a file that *cannot* be parsed, documented in-code, and it never accepts unverified bytes as the result of a write.

*Orphaned `.tmp` fixed.* Staging is wrapped so a mid-stream failure (quota, permission, share disappearing) removes the partial `.tmp` before rethrowing, in both `safeWriteJson` and `safeWriteJsonText`. The deliberate "keep `.tmp` as the survivor" path after a *failed commit* is unchanged, and promotion-copy failure is still caught so it ends in `staged copy kept as …`.

The whole ladder is preserved: `.bak` first → stage → verify → commit → re-verify → rollback/promote; `NotReadableError` retry now also applies per read window, re-opening the handle and refusing a size-changed replacement; `retryMissing` semantics untouched; the small-file path unchanged except that it now also snapshots an oversized predecessor. `createWritable` guards are intact — `copyFileStreamed` goes through `streamToFile`. **No change to `fileSystemAccess.ts` was needed.**

**The new ceiling:**
- **Writes: unbounded** by string length. Peak memory is one 4 MB read window plus one 64 KB write chunk.
- **Reads: unchanged, still bounded.** `safeReadJson` returns a parsed value, so it needs the whole file as one string for `JSON.parse` — the same ~536,870,888 code units. That is a property of `JSON.parse`, not of this module; removing it means not reading whole months at all (the paged/port-partitioned phases C/D of `LARGE_POPULATION_PERFORMANCE_PROPOSAL_2026-07-22.md`, still unapproved). So the app can now **write and keep** an over-ceiling `bi.raw.json` — raw import data, not read on the normal path — without losing the manifest; an over-ceiling file that must be *parsed* still cannot be loaded.
- Related, unchanged: `archiveExistingRaw` uses `safeReadJson` + `safeWriteJsonText`, so above the ceiling raw archiving silently stops working. Already best-effort (`try/catch` → `logError`).

**Proof above the old ceiling.** A real >512 MB file is not allocatable in this environment (the memory-directory double stores content as a JS string and could not hold one), so a **test seam** is used — precedent: `__setStreamingForcedSizeLimitForTests`. `__setMaxStringLengthForTests(n)` makes `readText` throw the same `RangeError` V8 would for any file over `n`. Identical production code path, smaller number: ~11.6 MB files of dense Arabic spanning **three read windows** with multi-byte characters straddling the boundaries, cap set to 1 MB. Four tests:
1. The write succeeds where it previously threw — and the impossibility is asserted directly: `safeReadJson` on the very file just written **does** reject with `RangeError`, while the committed bytes are a complete, correct envelope (identical `JSON.stringify(data)`, revision 1) and the `.tmp` is cleaned up.
2. **Re-save** of an already-oversized file: revision continues to 2 with `.bak` holding the previous revision — the pre-read fix.
3. Byte-exactness: one Arabic character swapped for another of the **same byte length**, ~5M chars in (a later window), so length is unchanged and only the hash can catch it. The write rejects with `Safe-write staging failed`, the live file is never created, the rejected `.tmp` is removed.
4. Mid-stream `QuotaExceededError` after three flushes leaves **no** orphaned `.tmp` and no live file.

Regression-checked against the old behaviour: restoring the old `file.text()` verification makes tests 1–3 fail with `RangeError: Invalid string length … bi.raw.json.tmp` propagating out of `safeWriteJson` — exactly the production symptom; removing the staging cleanup makes test 4 fail on the leftover `.tmp`.

**`saveMonthRun` resilience — deliberately NOT taken on.** The specific failure that turned a big-file problem into a total-loss problem is fixed at source: the `RangeError` can no longer occur. The remaining ways that `Promise.all` rejects — quota, permission, a share going away — are cases where aborting the save is defensible. Making it partial would invent new semantics: a month folder with `month.manifest.json` present and `status: "processed-saved"` but `bi.raw.json` missing or truncated, and a `SaveMonthRunResult` that is neither honestly `ok: true` nor usefully `ok: false`. That is a data-model and audit decision — what a month folder *means*, and what Archive and the integrity scan should make of a partial one — and it belongs to the owner, not to a storage-layer bugfix. The contained shape if wanted: `Promise.allSettled` for the first group, continue through `population.final.json` → summary/aggregate → manifest, and return `ok: false` naming the files that failed, so nothing is silently lost *and* the user is still told the save failed.

**Migration/rollback:** No on-disk format change and no migration. Files written by this version are byte-identical to what the previous version would have produced for any payload it could handle; the hash domain is unchanged, so an older client verifies them normally. Rollback re-imposes the old ceiling but reads everything written here. The only asymmetry is intended: this version can write and re-save files an older one would `RangeError` on.

## v85.0 — 2026-08-15 — Refactor (distribution): move the fold checkpoint to a sidecar, digest the event set, and shrink the log to its stamp

**Why:** Two files in the distribution layer carried payload that did not belong in them, and both were on hot paths.

1. The fold checkpoint was a **field** of `DistributionCurrentData`, so it was serialized into `distribution.current.json` — the largest, most widely-read file in a month (archive tiles, the backup XLSX export, every oversight load read it whole).
2. `eventSetId` was a **concatenation of every event id** — ~172 KB at 4,000 events, in *both* that file and the log, re-read and re-written constantly.
3. `distribution.log.json` still carried the full `events` array even though current clients durably write `distribution.events/{eventId}.json`. Every append rewrote the whole projection — ~980 KB at 4,000 events, growing without bound.

**What changed:**

*Checkpoint sidecar.* `distribution.checkpoint.json` in `2-samples/{month}/1-main`. `saveDistributionCurrent` strips the field and writes the sidecar; the load path reads it, falling back to a legacy inline checkpoint. Splitting one file into two creates a failure mode that did not exist — they can now disagree — so `DistributionFoldCheckpoint` gained an `eventSetId` binding it to the cache it was written with, and the resume path **refuses** any sidecar whose digest does not match. Verified by mutation: with that check removed, the new test yields **0 entries instead of 3** — precisely the silent event loss the split could have introduced.

*Commutative digest.* `distributionEventSetIdFromIds` hashes each id with the existing `createSimpleHasher` (djb2, no new dependency) and combines them with XOR **and** 32-bit modular addition, plus the count: `d1:{count}:{xor}:{sum}`. Commutative, so order does not affect set identity — which is the property actually wanted — and the caller-side `sort()` the old format required is gone. The `d1:` prefix guarantees an old concatenated id can never compare equal to a digest, so the format change reads as "stale cache", costs one refold, and self-heals. Documented tradeoff: this is no longer collision-*impossible*; the one call site that gates the cache also compares `logRevision`, so a stale cache would need a revision match **and** a digest collision.

*Log shrunk to its stamp.* Appends write a body-less projection. `revision`/`_writeToken`, `readDistributionLogStamp` and the casLoop write token are untouched — that stamp is both the cross-machine commit point and, since v84.0, the mirror-staleness authority. The CAS loop also lost a redundant read: `readProjectedEventIds` re-read the file `loadDistributionLog` had just read; both now come from one load.

**Measured, 4,000-event month:**

| File | Before | After |
|---|---|---|
| `distribution.current.json` | 2,769,042 B | 2,421,533 B (**−12.5%**) |
| `distribution.log.json` | 979,805 B | **340 B** (−99.97%) |
| `distribution.checkpoint.json` | — | 175,677 B |
| pair total | 3,748,847 B | 2,597,550 B (**−31%**) |

The write side matters more than the totals: every append used to rewrite ~980 KB and grow without bound; it is now a constant ~340 B.

**Four things the task description got wrong about the real code:**

1. **The log body could not be dropped unconditionally.** A workspace predating `distribution.events/` can hold events *only* in the projection, and nothing migrates data here. Appends now keep the **residual** — projection events whose ids are not in the immutable set. On a modern workspace that is `[]` on the first append; on a legacy one those events are carried forward verbatim, indefinitely. A failed event-directory scan yields an empty immutable set and therefore keeps the whole body: "I could not look" must never read as "it is durable". Tested both directions.
2. **`appendDistributionEvents` must still return a full log.** `useDistributionActions.refreshDistribution` derives the entire month from `result.log` and persists it, so returning a body-less log would have written a zeroed snapshot and **wiped every employee mirror**. The CAS loop still does the full read and returns the complete merged list; only what is *written* shrank.
3. **The log body was the event ORDERING base — undocumented anywhere.** A bulk distribution stamps one shared `eventAt` across the batch, and the projection's stored array was what preserved batch order; the immutable-store merge tie-broke by `eventId`. Dropping the body would have reordered every bulk assignment by random UUID — the order an employee's queue is displayed in. This was caught by a test in a file the agent was not permitted to edit, which is what forced the correct fix instead of an edited assertion: the merge now sorts by `eventAt` only, stably, over inputs that are already deterministic (name-sorted files, append-ordered segment lines), so ties resolve to true append order. New regression test, mutation-verified.
4. **`backupStorage`'s XLSX `distribution-log` dataset read the raw file** and would silently have exported zero event rows for every modern workspace. It now reads through `loadDistributionLog` (projection + segments + legacy per-event files).

**Backup/restore classification — the dangerous part.** `distribution.checkpoint.json` is classified `skip-derived` in `restoreActionFor` (dropped at collection, never restored, never reported) **and** added to `invalidateDistributionCaches`'s delete list alongside its `.bak`/`.tmp`, with the legacy `distribution.current.json` names kept since old caches still carry the checkpoint inline. A restore that resumed from a stale checkpoint whose byte offsets point into rewritten segments would **silently lose events**. Two new tests, both mutation-verified to fail when their line is reverted: a restore merging new events into a segment deletes the live sidecar; and a backed-up sidecar is never written into the live workspace, not even when the workspace has none.

**Migration/rollback:** Forward-compatible in both directions without a migration step. The sidecar is new and derived — deletable at any time, regenerated on the next save; an older client ignores it and falls back to the inline checkpoint it still understands. The digest format change is self-healing: a mismatched id reads as a stale cache and triggers one refold. The shrunken log keeps its stamp, so an older client still reads `revision`/`_writeToken` correctly; it would see fewer inline events, but every modern workspace has them durably in `distribution.events/`, and legacy-only events are deliberately retained in the residual precisely so a rollback does not lose them.

**Golden master: zero diffs.** `distributionDerivation.golden.test.ts` pins `distributionDerivation.ts`, which was not touched — all of this sits in the storage layer above the fold. Unmodified in `git status`, passes.

**Remaining large object in this area, out of scope:** the sidecar still carries `knownEventIds` (~176 KB at 4,000 events), needed to id-diff a legacy full-body projection.

## v84.0 — 2026-08-15 — Change (employee workspace): read the per-employee mirror first instead of the workspace-wide sample and derivation

**Why:** An employee opened their own work by loading `sample.master.json` **plus** the workspace-wide derived distribution — tens of MB to render one person's few hundred rows — while their own purpose-built ~340 KB file sat next to it, used only as a `??` fallback. The expensive path was primary. v82.0 made that file trustworthy (empty files on drop-to-zero, frozen quota, refreshed after replacement); this makes it the one that is read.

**What changed — three parts, in dependency order.**

**1. The mirror refresh is now synchronous where it must be.** `saveDistributionCurrent` inside `loadOrDeriveDistributionCurrent` was fire-and-forget on both the checkpoint-resume and full-refold paths, so after a reopen / approval / replacement the mirror was only *eventually* correct — fatal for a read path that trusts it. The rationale was checked before changing: both comments justify it purely on **cost** (an 18.8 MB `distribution.current.json` pre-B5), not on re-entrancy or lock safety. All four callers of `refreshDistributionCacheAfterWrite` have already completed their `appendDistributionEvents` casLoop before calling it, and `saveDistributionCurrent` is a leaf that never re-enters. So awaiting is safe — and that cost is what a *write* flow can afford and a *read* cannot.

New `awaitCachePersist?: boolean` (default `false`), threaded to both save sites. It changes only **when** the call resolves, never what is written, and **only `refreshDistributionCacheAfterWrite` opts in** — every read caller keeps the non-blocking behaviour. `sampleMirrorDropToZero.test.ts` tightens from a 50×5 ms poll to a single immediate assertion; flipping the flag back off fails 1 of the 4 flows (the other three settle incidentally on an in-memory FS where the write completes in the same microtask drain — on a real share they would not).

**2. `2-employees/_index.json`** — `{ username, sourceLogRevision }` keyed by **file name**, so it resolves sanitize collisions exactly as the files do and preserves `readExistingMirrors`'s deliberate file-name keying. One read replaces N full mirror parses (a read-log test proves one index read replaces six parses). Dual-read is enforced two ways:
- *Coverage check* — the directory listing (already needed) validates the index. Any listed mirror missing from it, or any entry naming a vanished file, ⇒ ignore the index and read the mirrors.
- *`pendingRevision`* — written non-null **before** the first mirror write, cleared **after** the last. A crash mid-projection can leave a mirror at a revision the index never recorded, so readers take `max(recorded, pendingRevision)`. Over-stating only makes the guard *skip* a write, recoverable at the next higher revision; under-stating would let an older derivation clobber a newer mirror, which must never happen.

The index write is best-effort — a failure is logged and swallowed, because it is a pure accelerator.

**3. The employee read path is inverted.** `loadData` is three phases. Phase 1 issues the small per-user reads in parallel (referral log, replacement log, ad-hoc entries, mirror, `readDistributionLogStamp`, own answers). Phase 2: if `mirror.sourceLogRevision >= stamp.revision` **and** the mirror carries a `quota`, that is the **entire** read — `sample.master.json` and the workspace-wide derivation are never touched. A stale or quota-less mirror is painted immediately, then phase 3 re-derives underneath and commits again.

**`canSeeAll` is unchanged** — oversight passes `null` for mirror and stamp, skips phase 2, and still reads `distribution.current.json`, because reading N mirrors is N round trips for the same data. A test pins that an oversight user ignores a perfectly current mirror that exists for them.

**Where the design did not match the code — the replacement dialog.** `openReplacementDialog` passes `allEntries` to `getReplacementCandidatesIndexed`, which builds its **exclusion set** from it. On the fast path `allEntries` holds only this employee's rows, so the dialog would have offered candidates another employee already owns. The mirror cannot answer this by construction — it is one person's view. Fix: the fast path sets `sampleMaster` to `null` (which also stops a stale one surviving a month switch), and a new `ensureReplacementContext()` resolves the sample master and the every-employee entry set **on demand**, only when the dialog opens. A test proves the dialog receives both drawn rows and both employees' entries while the queue itself showed only one.

**Boot splash left deliberately alone.** The source list and its registration point are unchanged, and the resulting imprecision is documented instead: `referrals_sample_master` / `referrals_distribution` report loaded on the fast path, where the mirror supplies both. Moving registration after the first await is precisely the effect-ordering shape that regressed five times in v59.190–197, so it was not touched.

Two safety details: the intermediate paint sets a local `painted` flag so a phase-3 failure logs and returns rather than replacing a rendered queue with an error state; and `commit` never touches selection or panel state, so no refresh path can close an open inspection form or drop an unsaved draft.

**Golden master: zero existing assertions changed.** `_index.json` deliberately does not end in `.samples.json`, so `listEmployeeFiles` — and `answerStorage`'s own `.answers.json` scan of the same folder — never see it. All 13 prior pins pass untouched. Six assertions were **added**: the committed index shape; a skipped file keeping its *higher* revision; a sanitize collision yielding one entry; dual-read (an index that both lies and disagrees with the listing is ignored, mirrors win, index rewritten); `pendingRevision` blocking an older derivation but not a newer one; and a **SURPRISE** pin — a *consistent* index is trusted even when it lies. That last one is the honest trust boundary of a listing-validated accelerator: it can only be wrong if something other than `syncSampleMirrors` wrote it, and the fallout is a stale mirror, never resurrected entries.

**Migration/rollback:** Additive only. `_index.json` is a new derived file in an existing folder; it is regenerated by the next projection and can be deleted at any time with no loss — readers fall back to the mirrors. An older client ignores it entirely (it does not match the `.samples.json` scan). Rolling back this change leaves the file orphaned and harmless. No existing file changes shape.

**Residual gap, documented not closed:** if a concurrent writer already persisted a cache at this exact log revision, the inner derive returns it without re-writing, so `refreshDistributionCacheAfterWrite` can resolve while that writer's own mirror write is still in flight. Cross-machine write/write ordering needs a backend — the same limitation recorded across this plan.

## v83.1 — 2026-08-15 — Fix (sync): parallelize the sized listing and stop size-only change detection missing same-length writes

**Why:** Three defects in the 45 s sync tick, on a medium (shared UNC/SMB, ~30 users) where round-trip *depth* is the cost.

1. The sized listing opened every file serially — one round trip after another, ~30 deep on the answers/approvals probe.
2. **Change detection compared file SIZE only**, so an edit preserving byte length was invisible. That is not hypothetical on a JSON envelope: `"revision":9` → `"revision":10`… any same-width field edit keeps the length, and another user's change would simply never be noticed.
3. Legacy subscribers ignored the per-family change set and reloaded wholesale.

**What changed:**

*(a)* `listDirectoryEntriesWithSize` issues its per-file opens through a bounded pool (`forEachBounded`, concurrency 8). Results land in slots indexed by listing position, so returned order and the vanished-entry log stay deterministic regardless of settle order. The **deliberate no-retry policy is preserved verbatim** — a failing tick fails fast and the next tick retries. `readSegmentTails` was deliberately left serial: it shares one retry budget across entries, and parallelising it would make budget consumption nondeterministic.

## v81.0 — 2026-08-15 — Refactor (workspace): cache resolved directory handles and key locks by full path

**Why:** Two independent costs in the same layer, both paid on every workspace read, and both invisible in a local test because they only hurt on a shared UNC/SMB volume where round trips dominate.

**What changed:**

*Directory-handle cache.* A per-root memo of resolved handles keyed on logical path, with resolution wrapped in the existing `dedupeInFlight` from `src/data/storage/inFlightReads.ts`. `getRoot`'s numbered-vs-legacy probe is memoized separately, so a legacy workspace stops paying a failed `1-population` probe on every call — though `create: true` still deliberately bypasses a cached *legacy* handle, preserving "always create the numbered root". *Lock-key registry.* `registerDirectoryPath`/`directoryPath`/`directoryResourceKey` live in `webLocks.ts` (the lock helper, not `safeWrite.ts`), backed by a `WeakMap`. Populated by `workspacePaths.ts` with the **logical** path — never the legacy folder name — and by `createMemoryDirectory` for test trees. An unregistered handle falls back to `dir.name`, i.e. exactly the old key. The registered path deliberately excludes any per-session workspace id: a too-coarse key only over-serializes, which is safe, whereas a key that differed between two references to the same folder would **under**-lock.

*Cache keyed on the root handle, not `workspaceScopeId(root)`.* `__clearInFlightForTests()` recycles scope-id strings, so a string key let one test's workspace answer for another's. A `WeakMap` plus a generation counter gives the un-iterable full purge.

## v80.5 — 2026-08-15 — Change (performance): commit streamed writes from the verified staged copy instead of serializing the payload twice

**Why:** The streamed write path staged the payload to `.tmp`, verified it byte-exactly, and then **serialized the whole payload a second time** to write the live file. On the large files this path exists for, that second full serialization is pure duplicated CPU — the exact bytes had already been produced and proven correct one step earlier.

**What changed:** `verifyStreamedFile` was split into `readVerifiedStreamedFile`, which reads the staged file back, checks length **and** whole-file hash, and returns the verified text instead of discarding it. A new `writeVerifiedTextStreamed` commits that already-verified string through the same `streamToFile` machinery, emitting the same 64 KB chunks so the writable sees an identical chunk pattern and per-chunk hashing. `safeWriteJson`'s streamed commit now writes those verified bytes rather than calling `streamEnvelopeToFile` again.

**A second, undocumented instance.** `safeWriteJsonText`'s streamed restore path had the same double serialization (it re-serialized `parsed` via `streamValueToFile`). Both are fixed.

**Verification got stronger, not weaker.** The commit previously verified against the *second* serialization's own info — self-consistent but circular. It now requires `liveInfo.fileHash/fileLength === stagedInfo.*` **and** a byte-exact read-back against `stagedInfo`, which additionally proves the committed file equals the staged copy. The promotion path also drops one redundant full-file read by reusing `readVerifiedStreamedFile` instead of verifying and then re-reading.

The whole ladder is preserved: `.bak` snapshot first, stage → verify → commit → re-verify, `createWritable` still guarded inside `streamToFile`/`writeText`, `NotReadableError` retry and `retryMissing` semantics untouched. The small-file path is unchanged.

**On the size of the win:** the plan claimed this "halves the CPU of every large write." That is optimistic. The streamed path is only entered *after* `wrap()` has already run `hashJsonValue` — itself a full serialization pass — and after a failed `JSON.stringify`. So a real large write went roughly three full passes (wrap-hash, stage, commit) to two: about a third off, plus one fewer full-file read on promotion. Recorded here rather than repeating the plan's figure.

**Not done, and why:** a true zero-copy pipe is unavailable. `FileHandleLike`'s writable is typed `write: (data: string) => Promise<void>` and `memoryDirectory` concatenates strings, so there is no `Blob`/stream primitive to hand over without changing `fileSystemAccess.ts`. Copying over the verified JS string is also what keeps multi-byte UTF-8 intact — a byte-offset `Blob.slice` approach would corrupt Arabic text mid-character.

**Pre-existing, unchanged:** staging verification still materializes the whole file as one string via `file.text()`, so a payload beyond V8's max string length would fail there today regardless. This change neither adds nor moves that limit.
