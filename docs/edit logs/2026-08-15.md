## v84.0 — 2026-08-15 — Change (employee workspace): read the per-employee mirror first instead of the workspace-wide sample and derivation

**Why:** An employee opened their own work by loading `sample.master.json` **plus** the workspace-wide derived distribution — tens of MB to render one person's few hundred rows — while their own purpose-built ~340 KB file sat next to it, used only as a `??` fallback. The expensive path was primary. v82.0 made that file trustworthy (empty files on drop-to-zero, frozen quota, refreshed after replacement); this makes it the one that is read.

**What changed — three parts, in dependency order.**

**1. The mirror refresh is now synchronous where it must be.** `saveDistributionCurrent` inside `loadOrDeriveDistributionCurrent` was fire-and-forget on both the checkpoint-resume and full-refold paths, so after a reopen / approval / replacement the mirror was only *eventually* correct — fatal for a read path that trusts it. The rationale was checked before changing: both comments justify it purely on **cost** (an 18.8 MB `distribution.current.json` pre-B5), not on re-entrancy or lock safety. All four callers of `refreshDistributionCacheAfterWrite` have already completed their `appendDistributionEvents` casLoop before calling it, and `saveDistributionCurrent` is a leaf that never re-enters. So awaiting is safe — and that cost is what a *write* flow can afford and a *read* cannot.

New `awaitCachePersist?: boolean` (default `false`), threaded to both save sites. It changes only **when** the call resolves, never what is written, and **only `refreshDistributionCacheAfterWrite` opts in** — every read caller keeps the non-blocking behaviour. `sampleMirrorDropToZero.test.ts` tightens from a 50×5 ms poll to a single immediate assertion; flipping the flag back off fails 1 of the 4 flows (the other three settle incidentally on an in-memory FS where the write completes in the same microtask drain — on a real share they would not).

**2. `2-employees/_index.json`** — `{ username, sourceLogRevision }` keyed by **file name**, so it resolves sanitize collisions exactly as the files do and preserves `readExistingMirrors`'s deliberate file-name keying. One read replaces N full mirror parses (a read-log test proves one index read replaces six parses). Dual-read is enforced two ways:
- *Coverage check* — the directory listing (already needed) validates the index. Any listed mirror missing from it, or any entry naming a vanished file, ⇒ ignore the index and read the mirrors.
- *`pendingRevision`* — written non-null **before** the first mirror write, cleared **after** the last. A crash mid-projection can leave a mirror at a revision the index never recorded, so readers take `max(recorded, pendingRevision)`. Over-stating only makes the guard *skip* a write, recoverable at the next higher revision; under-stating would let an older derivation clobber a newer mirror, which must never happen.

The index write is best-effort — a failure is logged and swallowed, because it is a pure accelerator.

**3. The employee read path is inverted.** `loadData` is three phases. Phase 1 issues the small per-user reads in parallel (referral log, replacement log, ad-hoc entries, mirror, `readDistributionLogStamp`, own answers). Phase 2: if `mirror.sourceLogRevision >= stamp.revision` **and** the mirror carries a `quota`, that is the **entire** read — `sample.master.json` and the workspace-wide derivation are never touched. A stale or quota-less mirror is painted immediately, then phase 3 re-derives underneath and commits again.

**`canSeeAll` is unchanged** — oversight passes `null` for mirror and stamp, skips phase 2, and still reads `distribution.current.json`, because reading N mirrors is N round trips for the same data. A test pins that an oversight user ignores a perfectly current mirror that exists for them.

**Where the design did not match the code — the replacement dialog.** `openReplacementDialog` passes `allEntries` to `getReplacementCandidatesIndexed`, which builds its **exclusion set** from it. On the fast path `allEntries` holds only this employee's rows, so the dialog would have offered candidates another employee already owns. The mirror cannot answer this by construction — it is one person's view. Fix: the fast path sets `sampleMaster` to `null` (which also stops a stale one surviving a month switch), and a new `ensureReplacementContext()` resolves the sample master and the every-employee entry set **on demand**, only when the dialog opens. A test proves the dialog receives both drawn rows and both employees' entries while the queue itself showed only one.

**Boot splash left deliberately alone.** The source list and its registration point are unchanged, and the resulting imprecision is documented instead: `referrals_sample_master` / `referrals_distribution` report loaded on the fast path, where the mirror supplies both. Moving registration after the first await is precisely the effect-ordering shape that regressed five times in v59.190–197, so it was not touched.

Two safety details: the intermediate paint sets a local `painted` flag so a phase-3 failure logs and returns rather than replacing a rendered queue with an error state; and `commit` never touches selection or panel state, so no refresh path can close an open inspection form or drop an unsaved draft.

**Golden master: zero existing assertions changed.** `_index.json` deliberately does not end in `.samples.json`, so `listEmployeeFiles` — and `answerStorage`'s own `.answers.json` scan of the same folder — never see it. All 13 prior pins pass untouched. Six assertions were **added**: the committed index shape; a skipped file keeping its *higher* revision; a sanitize collision yielding one entry; dual-read (an index that both lies and disagrees with the listing is ignored, mirrors win, index rewritten); `pendingRevision` blocking an older derivation but not a newer one; and a **SURPRISE** pin — a *consistent* index is trusted even when it lies. That last one is the honest trust boundary of a listing-validated accelerator: it can only be wrong if something other than `syncSampleMirrors` wrote it, and the fallout is a stale mirror, never resurrected entries.

**Migration/rollback:** Additive only. `_index.json` is a new derived file in an existing folder; it is regenerated by the next projection and can be deleted at any time with no loss — readers fall back to the mirrors. An older client ignores it entirely (it does not match the `.samples.json` scan). Rolling back this change leaves the file orphaned and harmless. No existing file changes shape.

**Residual gap, documented not closed:** if a concurrent writer already persisted a cache at this exact log revision, the inner derive returns it without re-writing, so `refreshDistributionCacheAfterWrite` can resolve while that writer's own mirror write is still in flight. Cross-machine write/write ordering needs a backend — the same limitation recorded across this plan.

## v83.1 — 2026-08-15 — Fix (sync): parallelize the sized listing and stop size-only change detection missing same-length writes

**Why:** Three defects in the 45 s sync tick, on a medium (shared UNC/SMB, ~30 users) where round-trip *depth* is the cost.

1. The sized listing opened every file serially — one round trip after another, ~30 deep on the answers/approvals probe.
2. **Change detection compared file SIZE only**, so an edit preserving byte length was invisible. That is not hypothetical on a JSON envelope: `"revision":9` → `"revision":10`… any same-width field edit keeps the length, and another user's change would simply never be noticed.
3. Legacy subscribers ignored the per-family change set and reloaded wholesale.

**What changed:**

*(a)* `listDirectoryEntriesWithSize` issues its per-file opens through a bounded pool (`forEachBounded`, concurrency 8). Results land in slots indexed by listing position, so returned order and the vanished-entry log stay deterministic regardless of settle order. The **deliberate no-retry policy is preserved verbatim** — a failing tick fails fast and the next tick retries. `readSegmentTails` was deliberately left serial: it shares one retry budget across entries, and parallelising it would make budget consumption nondeterministic.

*(b)* `SizedDirectoryEntry` gains `lastModified`; the signature is now `[name, size, lastModified]`.

*(c)* `useMonthLoad` moves from `subscribeToDataRefresh` to `subscribeToDataChange(["manifest", "distribution"])`.

**On (b) — why not read the envelope `revision`, as the plan asked.** Costed and rejected, for the two N-scaled families only (`answersSignature`, `approvalsSignature`; `manifest` and `notifications` already compare `readEnvelopeRevision`, and `distribution` compares `{revision, writeToken}`). `getFile()` yields a `File` **without transferring content**, so `size` and `lastModified` both fall out of the stat the probe already pays for. Reading `metadata.revision` means reading bytes — a second open/read per file, per tick, per client: at ~30 employees × ~30 users, roughly **900 extra round trips per 45 s cycle**, doubling the tick's dominant term on precisely the medium where round trips dominate. It would also have broken the "ONE operation per answers/decisions file, not two" budget test.

And `revision` buys nothing over `(size, lastModified)` here: they diverge only if two writes to one file land inside a single filesystem timestamp tick, and a `safeWriteJson` is several round trips long (stage → verify → commit → re-verify), so that window is not reachable. The residual gap (a share with 2 s mtime granularity, e.g. FAT) is documented in the code. The clock-skew objection that rules `lastModified` out elsewhere in this repo does **not** apply: the value is only ever compared against *the same file's* previous value on *the same client*, never across machines and never for ordering. That is called out in the doc comment so it is not "fixed" back.

**A premise in the plan was wrong:** envelope metadata is *not* always written last. `wrap()` emits `{metadata, data}` — metadata **first**; only the streamed writer for oversized payloads puts it last. So a prefix probe would in fact have worked for these small files. It was rejected on round-trip cost, not on layout.

**Honest accounting on (a): this is a latency win, not a count win.** Measured on a 30-employee / 3-supervisor month, warm tick: ops per unchanged tick stay at **45** (identical), while *sequential* round trips inside the answers/approvals probe drop **30 → 4** (`ceil(30/8)`). Every existing budget assertion is unchanged and still passes (`reads ≤ 9`, `opens === 4`, marginal cost `20`, no-month tick `1`). No budget number moved in either direction — concurrency cannot reduce a count.

**(c) is narrower than "reload everything" but broader than assumed.** `computeMonthLoadScope` gates `population`/`raw` to an oversight user on the process sub-tab — but it hardcodes `summary: true, sample: true, distribution: true` for **everyone**. So every legacy-subscriber tick re-read `month.manifest.json`, `processing.summary.json` and `sample.master.json` and re-ran `loadOrDeriveDistributionCurrent` — the expensive part even with `population: false` — none of which is touched by a notification, an answer submission, or a referral request. That is the actual win, and it lands on the ordinary personas, not just admins.

**Test-double bug fixed (`memoryDirectory.ts`).** `getFile()` built a fresh `File` per call, reporting `Date.now()` as `lastModified`, so an *untouched* file looked modified between two reads — the exact opposite of real behaviour, and it would have made the new signature untestable. Files now carry a monotonic mtime stamped at write time.

**Two gaps found and deliberately NOT silently closed:**
1. **No probe family covers `sample.master.json`.** Another user re-drawing an already-drawn month bumps neither the distribution stamp nor the manifest (`advanceMonthStatus` only writes on a rank increase), so before this change it was picked up only *incidentally*, when an unrelated family happened to change in the same tick. Closing it needs a `sample` family probe — one extra small read per tick, which would push the `reads ≤ 9` budget **up**. Reported rather than done, and flagged in a code comment at the subscription site.
2. Four legacy `subscribeToDataRefresh` subscribers remain (`XrayReferrals`, `XrayInspectionResults`, `NotificationManager`, `useApprovalData`, `NotificationBanner`), all in a tree owned by concurrent work. `NotificationBanner`/`NotificationManager` want `["notifications"]`; `useApprovalData` wants `["requests", "answers"]`.

## v83.0 — 2026-08-15 — Fix (sampling): resolve percentage stage rules to row counts, and stop phantom events inflating quotas

**Why:** Two pre-existing data-correctness bugs, both surfaced by the golden masters recorded in v80.6 and both corrupting real output today. Neither is performance work; they are fixed on their own merits.

**Bug 1 — percentage stage rules made the sample over-draw.** `rule.value` is method-dependent (`populationConfig.ts:86`): a percentage 0–100 under `method: "percentage"`, a row count under `"exact"`. `buildStagePlan` stored it verbatim in `plan.configuredValues`, and `redistributeStageShortfall` then compared that number against `availableCounts` — **rows** — and also used it as the absorber weight. So `percentage 25` over 12 available rows read as "13 rows short" and redistribution compensated for a shortfall that did not exist. Any month using percentage-method stage rules drew the wrong number of images.

**Bug 2 — phantom events inflated employee quotas.** `if (!row) continue` ran *before* `recordDroppedEvent`, so an event whose `xrayImageId` was absent from the sample rows landed in neither `droppedEventIds` nor `droppedImageIds`. `collectAssignmentFacts` filters only on `droppedEventIds`, so a phantom `assigned` event still raised `sampleCount` and therefore `dailyQuota`.

**What changed:**

*Bug 1.* Extracted `configuredRowCount(rule, available)` — the exact expression `configuredTarget` already used, i.e. a percentage resolved against the stage's own available row count, which is the denominator the surrounding code has always intended (`Math.round((value/100) * available)`). `configuredTarget` now delegates to it, behaviour identical; `configuredValues` is filled from it, so the shortfall comparison and the absorber weights are both in row units.

*Bug 2.* `FoldResult` gains a **separate** `absentRowEventIds`. `droppedEventIds`/`droppedImageIds` keep their exact prior meaning and contents — overloading them was rejected because they feed quota output, so widening them would have changed that output as a side effect of an observability fix. Absent-row events are aggregated once per call into `logError("distribution:fold-absent-row", …)`; the aggregate is suppressed when the existing `distribution:fold-no-rows` log already covers an empty row set, so one problem is not reported twice. Quota derivation now accepts `ReadonlySet | { droppedEventIds, absentRowEventIds }` — a `FoldResult` is structurally assignable — and excludes both.

**`SAMPLING_ALGORITHM_VERSION` bumped `"1.0"` → `"1.1"`.** Required: `drawSample` now returns a different set for the same seed and config, which is precisely the condition CLAUDE.md reserves the bump for. A 1.0 stage draw that used any percentage rule is **not replayable** under 1.1, and the docblock says so.

## v82.0 — 2026-08-15 — Fix (distribution): make the per-employee sample mirror a correct projection and refresh it after replacement

**Why:** An employee is meant to open their own work by reading one small per-employee file. That file existed but could not be trusted, for three separate reasons — so the expensive workspace-wide read stayed the primary path. Fixing the trust problem is the precondition for ever inverting that read.

1. **Bug F20 — the replacement flow never refreshed anything.** `executeReplacement` appended its events and returned. The other three write flows (`reopenAnswer:117`, `approveReferral:142`, `adhocImportAssignment:222`) all call `refreshDistributionCacheAfterWrite`; this one did not. So the flow that actually moves a row between employees left the derived cache **and every per-employee mirror** stale until the next 45 s tick.
2. **Bug F8 — a mirror could never recover.** `entriesByEmployee` was built only from `current.entries`, so an employee reassigned down to zero entries was never visited, their file never rewritten, and the `existingRevision >= sourceLogRevision` guard then blocked correction permanently. They kept seeing work they no longer owned.
3. **The mirror was not self-sufficient** — it carried no quota, so a reader still had to load the derived file anyway, which defeats the point.

**What changed:**

*F20.* `executeReplacement` now calls `refreshDistributionCacheAfterWrite` with `sampleResult.data.rows` — the sample master read back by `appendSampleRow`, so the freshest row set at that point, already including the appended replacement row.

*F8.* New `readExistingMirrors()` lists `2-employees/*.samples.json` and keys them by **file name**, not username — the monotonic guard is inherently per-file, and two usernames can sanitize to the same name. The write set is the union of on-disk mirrors and current assignees, so an employee who dropped to zero gets an explicit empty-entries file. The file is **emptied, never deleted**, keeping the mirror a stable read target. A directory-listing failure degrades to the old behaviour and reports via `logError` rather than failing the whole sync.

*Fan-out.* The unbounded `Promise.all` is replaced by the existing `mapWithConcurrency` (`src/data/storage/concurrency.ts`) at budget 8, for both the existing-mirror reads and the writes.

*Quota.* Optional `quota: { dailyQuota, daysRemainingAtAssignment, sampleCount }` copied from `current.quotas[username]`. The key is **omitted entirely** when there is no quota entry, so absent-`quota` mirrors keep working and readers fall back to the derived file — dual-read preserved.

*`main.samples.json` is no longer written.* Verified by grep across `src/` that nothing reads it: the only hits were the write site itself, its own revision guard, the golden test, a doc comment, and an unrelated `.samples.json` line. Nothing in `backup/`, `integrity/`, `powerbiExport/`, or any UI. The constant, the `MainSamplesFile` type and the now-unused `getSampleMainDir` import are gone, and `syncSampleMirrors` no longer touches `1-main/` at all (`saveDistributionCurrent` already creates that directory).

**Contract test, proven non-vacuous.** `sampleMirrorDropToZero.test.ts` drives all four write flows (distribute/assign, reopen, referral approval, replacement) and asserts an employee reassigned to zero ends with a zero-entry — not missing, not deleted — mirror. With the F8 union loop and the F20 refresh temporarily removed, **all four fail**; restored, all four pass. It is a real guard, not a restatement.

Only distribute/assign awaits the mirror write. So the guarantee through reopen, approval and replacement is **eventual, not synchronous** — the contract test polls (bounded, 50×5 ms) rather than asserting once. Before the employee read path is inverted onto the mirror, this needs handling: a view refreshing immediately after one of those flows can still read the pre-refresh mirror for a tick.

## v81.0 — 2026-08-15 — Refactor (workspace): cache resolved directory handles and key locks by full path

**Why:** Two independent costs in the same layer, both paid on every workspace read, and both invisible in a local test because they only hurt on a shared UNC/SMB volume where round trips dominate.

1. **Every read re-walked its directory chain.** Opening `2-samples/{month}/1-main/sample.master.json` re-resolved `2-samples`, then `{month}`, then `1-main` — 3–7 round trips per read, repeated for every sibling. The three sample sub-directories each re-walked `2-samples/{month}` independently.
2. **Every lock keyed on the leaf folder name.** `withResourceLock(\`${dir.name}/${fileName}\`)` produced the identical key `1-main/sample.master.json` for **every month**, so unrelated months serialized against one another for no reason.

**What changed:**

*Directory-handle cache.* A per-root memo of resolved handles keyed on logical path, with resolution wrapped in the existing `dedupeInFlight` from `src/data/storage/inFlightReads.ts`. `getRoot`'s numbered-vs-legacy probe is memoized separately, so a legacy workspace stops paying a failed `1-population` probe on every call — though `create: true` still deliberately bypasses a cached *legacy* handle, preserving "always create the numbered root". A new shared `getSampleSubDir` means sibling sub-directories cost one open instead of three walks.

*Lock-key registry.* `registerDirectoryPath`/`directoryPath`/`directoryResourceKey` live in `webLocks.ts` (the lock helper, not `safeWrite.ts`), backed by a `WeakMap`. Populated by `workspacePaths.ts` with the **logical** path — never the legacy folder name — and by `createMemoryDirectory` for test trees. An unregistered handle falls back to `dir.name`, i.e. exactly the old key. The registered path deliberately excludes any per-session workspace id: a too-coarse key only over-serializes, which is safe, whereas a key that differed between two references to the same folder would **under**-lock.

*Cache keyed on the root handle, not `workspaceScopeId(root)`.* `__clearInFlightForTests()` recycles scope-id strings, so a string key let one test's workspace answer for another's. A `WeakMap` plus a generation counter gives the un-iterable full purge.

**Invalidation** is the part that had to be right, since a stale handle reading a deleted-and-recreated directory is a correctness bug, not a slow path:
- `bumpWorkspaceEpoch` — month-scoped entries carry the epoch and are dropped lazily at lookup, so `inFlightReads.ts` needed no edit.
- Manual refresh — subscribes to `subscribeToDataRefresh` and purges on `"manual"` only (`window`-guarded, so worker/node contexts are unaffected).
- `NotFoundError` opening a child through a cached parent — the stale subtree is dropped and resolution retried once from a fresh chain.

**Known residual risk, deliberately not closed here.** The `NotFoundError` recovery is narrower than "any NotFound through a cached handle": it only fires where `workspacePaths` itself opens a child. A *file* read through a cached leaf directory whose folder was deleted externally still surfaces as "file missing" in `safeReadJson` and does **not** purge the cache. `invalidateWorkspaceDirCache(root)` is exported for whoever wires that in. Worth a follow-up before this is trusted against a workspace being reorganised underneath a running client.

**Also deliberately conservative:** epoch-based invalidation means every month *write* re-resolves that month's directories on the next read, even though directory topology cannot change because a file's contents did. Kept because correctness beats the remaining churn; a topology-aware epoch would remove it.

**Migration/rollback:** No data-format or on-disk change — this is resolution and locking only, both process-local. Rollback is a straight revert; nothing persists that a previous version could not read. Lock keys becoming *finer* cannot deadlock: the previous coarse key was a superset, so any pair that formerly serialized either still serializes or was independent all along.

**Budget tests updated, in the tightening direction.** Three exact-count assertions in `workspaceSync.test.tsx` moved because this change reduces what they measure: shared-parent opens **9 → 4**, the no-month cadence tick **2 ops → 1**, and `distinct.size` from `opens.length - 1` (one directory opened twice) to `opens.length` (none opened twice) — a stricter assertion than before. The marginal-cost test needed a second warm-up run: `runSync` bumps the workspace epoch at the end of a broadcasting run, invalidating month-scoped handles, so one warm-up left the cache unsettled and folded a re-resolution into the delta.

**Instrument correction:** the plan called for `getReadLog`, which only logs `getFile()` and therefore cannot see directory round trips at all. The assertions use `getOperationLog`/`trackOperations` from the same module, which logs `getDirectoryHandle`.

## v80.5 — 2026-08-15 — Change (performance): commit streamed writes from the verified staged copy instead of serializing the payload twice

**Why:** The streamed write path staged the payload to `.tmp`, verified it byte-exactly, and then **serialized the whole payload a second time** to write the live file. On the large files this path exists for, that second full serialization is pure duplicated CPU — the exact bytes had already been produced and proven correct one step earlier.

**What changed:** `verifyStreamedFile` was split into `readVerifiedStreamedFile`, which reads the staged file back, checks length **and** whole-file hash, and returns the verified text instead of discarding it. A new `writeVerifiedTextStreamed` commits that already-verified string through the same `streamToFile` machinery, emitting the same 64 KB chunks so the writable sees an identical chunk pattern and per-chunk hashing. `safeWriteJson`'s streamed commit now writes those verified bytes rather than calling `streamEnvelopeToFile` again.

**A second, undocumented instance.** `safeWriteJsonText`'s streamed restore path had the same double serialization (it re-serialized `parsed` via `streamValueToFile`). Both are fixed.

**Verification got stronger, not weaker.** The commit previously verified against the *second* serialization's own info — self-consistent but circular. It now requires `liveInfo.fileHash/fileLength === stagedInfo.*` **and** a byte-exact read-back against `stagedInfo`, which additionally proves the committed file equals the staged copy. The promotion path also drops one redundant full-file read by reusing `readVerifiedStreamedFile` instead of verifying and then re-reading.

The whole ladder is preserved: `.bak` snapshot first, stage → verify → commit → re-verify, `createWritable` still guarded inside `streamToFile`/`writeText`, `NotReadableError` retry and `retryMissing` semantics untouched. The small-file path is unchanged.

**On the size of the win:** the plan claimed this "halves the CPU of every large write." That is optimistic. The streamed path is only entered *after* `wrap()` has already run `hashJsonValue` — itself a full serialization pass — and after a failed `JSON.stringify`. So a real large write went roughly three full passes (wrap-hash, stage, commit) to two: about a third off, plus one fewer full-file read on promotion. Recorded here rather than repeating the plan's figure.

**Not done, and why:** a true zero-copy pipe is unavailable. `FileHandleLike`'s writable is typed `write: (data: string) => Promise<void>` and `memoryDirectory` concatenates strings, so there is no `Blob`/stream primitive to hand over without changing `fileSystemAccess.ts`. Copying over the verified JS string is also what keeps multi-byte UTF-8 intact — a byte-offset `Blob.slice` approach would corrupt Arabic text mid-character.

**Pre-existing, unchanged:** staging verification still materializes the whole file as one string via `file.text()`, so a payload beyond V8's max string length would fail there today regardless. This change neither adds nor moves that limit.
