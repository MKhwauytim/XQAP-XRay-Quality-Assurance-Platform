## v72.0 — 2026-08-13 — Remove: in-app سجل الإصدارات (ChangeLog) tab and its edit-log build aggregation

**Why:** The owner asked for the in-app version-history viewer to be removed entirely. The tab
was the only consumer of a build-time pipeline that read every file in `docs/edit logs/`,
concatenated them into a `virtual:edit-log` module, and inlined the result into the shipped
single-file bundle. That made the release artifact grow with the documentation archive rather
than with the product, and it forced a truncation plugin plus a separate injected define
(`__EDIT_LOG_TOTAL_VERSIONS__`) to exist purely to keep one on-screen statistic honest about the
history the bundle had just discarded. Removing the tab but keeping the plugin was rejected:
with no consumer, the plugin, its virtual-module type declaration, its define, and its test file
would all have been dead weight that the next reader has to re-derive a purpose for. The
edit-log protocol itself is untouched — `docs/edit logs/`, `scripts/editlog.mjs`, and
`npm run check:release` all keep working exactly as before. Only the in-app viewer and the
build-time aggregation that fed it are gone.

**What changed:** The whole `src/components/Sidebar/Tabs/ChangeLog/` directory was deleted
(tab entry point, lazy `TabView`, stylesheet, and component test), which also removes it from
`tabRegistry.ts`'s `import.meta.glob` discovery without any registry edit. Its catalog entry and
its five permission-matrix default rows were removed from `tabCatalog.ts` and `userManagement.ts`
together, since `tabCatalog.test.ts` enforces that the catalog and the registry agree and would
otherwise fail on a catalog entry with no registered tab. Three tests that asserted on the tab
list or on the admin-only ceiling set were updated rather than deleted: `tabCatalog.test.ts` and
`permissionMatrixEffect.test.ts` drop `change-log` from their admin-only expectations, and
`PermissionSections.test.tsx` now proves the same "no clickable control for an admin-only page"
behaviour against `adhoc-import` instead.

On the build side, `src/build/editLogTruncatePlugin.ts` and its test were deleted and the plugin
was unwired from both `vite.config.ts` and `vitest.config.ts`, including the
`countVersionHeadings(readDailyEditLogs())` call and the `__EDIT_LOG_TOTAL_VERSIONS__` define in
each. The matching `virtual:edit-log` module declaration and `__EDIT_LOG_TOTAL_VERSIONS__` global
declaration were removed from `src/vite-env.d.ts`; `__APP_VERSION__` stays, because it is still
injected from `package.json` and still read by Settings' About panel. `eslint.config.js` loses
both its ChangeLog lazy-boundary ignore path and the restricted-import rule that guarded that
boundary. `scripts/check-hex-literals.mjs` loses the `ChangeLog.css` baseline row, which would
otherwise have failed the check with `MISSING FILE`.

Settings' About panel pointed users at the tab that no longer exists, so its note line was
removed and the panel subtitle narrowed from "إصدار التطبيق الحالي وسجل التغييرات" to
"إصدار التطبيق الحالي". The now-unused `.settings-about-note` rule was dropped from

## v71.1 — 2026-08-13 — Fix (permissions): matrix controls an admin could toggle but that could never take effect

**Why:** Owner: "some permissions even as admin I can't give to roles." Two separate mechanisms
were making the User Management matrices lie about what they could do.

1. **Code ceilings outrank the matrix.** `TAB_ROLE_CEILINGS` / `SUB_TAB_ROLE_CEILINGS` in
   `tabCatalog.ts` cap what any matrix row can grant (`usePermissions.canAccessTab` checks the
   ceiling first). A cell outside its tab's ceiling was still rendered as three clickable
   buttons — the admin sets it, it saves to disk, and the role still cannot open the page.
2. **The feature cascade inherits that.** A feature is refused whenever its parent page is not
   accessible, so every feature on a ceiling-restricted page was a dead toggle too — and the UI
   labelled some of them with the *recoverable* hint "يتطلب تفعيل صلاحية الصفحة أولاً", which
   tells the admin to do something that cannot work. (The old check only recognised a
   strictly-admin-only ceiling, so `settings`' guest+admin ceiling was mislabelled this way.)

Audited the rest of the path and found it clean, so nothing was changed there:
`normalizeUserManagementState`'s `knownTabIds` filter drops nothing (every rendered row comes
from `MANAGED_TABS`); the `TabView → persistState → syncUserManagementToDisk → applyDiskUsers`
round-trip is lossless; every feature id in the catalogue has a real consumer.

The fix follows one rule: **a control an admin can toggle must actually do something, and a
restriction that is deliberate must not be presented as a toggle.** Where a ceiling had no
product justification it was widened; where it is deliberate the cell now says so instead of
pretending to be settable. Hiding the rows entirely was rejected — an admin auditing "who can
reach the archive?" needs to see the restricted state, not an absence.

**What changed:**

1. **`reports`, `reports/reports`, `archive` opened to `employee`** (`REPORT_ROLES` removed from
   `tabCatalog.ts`; those three now use `ALL_ROLES`). Nothing in the product requires reports or
   archive to be closed to employees, and the shipped matrix defaults still ship all three as
   `none` — this restores the *admin's ability to grant*, it does not grant anything. The
   knock-on effect is that `export-reports`, `report-designer.edit` and the three `archive.*`
   features become grantable to employees as well. `reports/kpi` and `reports/report-designer`
   keep their own narrower supervisor+manager+admin ceiling (hard-asserted in two test files as
   a deliberate B1 decision); `user-management*`, `change-log`, `adhoc-import` stay admin-only
   and `settings` stays guest+admin.
2. **One authority for "ceiling + matrix".** New `isTabRestrictedForRole(role, tabId)` and
   `canRoleAccessTab(...)` in `userManagement.ts`, now used by `usePermissions.canAccessTab`,
   `usePermissions.can`, `getMutationCapability`, and the matrix UI. Previously the hook and the
   UI each re-derived the rule from `roleCeilingFor` in slightly different ways, which is how
   the settings mislabel survived. What the matrix paints as restricted is now, by construction,
   exactly what the runtime refuses.
3. **`can()` and `getMutationCapability` now check the ceiling too.** Before, only navigation
   did. A permission row outside the ceiling — impossible to create in the UI, but reachable via
   a hand-edited `users.permissions.json` or a file written before a ceiling narrowed — could
   still authorize a mutation on a page the role can never open.
4. **The matrices explain themselves.** A ceiling-restricted cell renders the notice
   «مقيّد بالنظام — غير متاح لهذا الدور» in place of the toggle group, in both the page and
   feature matrices. A sub-tab cell whose *parent page* is currently `لا وصول` is disabled with
   «يتطلب تفعيل صلاحية الصفحة الأم أولاً» — that one is recoverable, so it stays a toggle rather
   than becoming a notice. Both matrix descriptions now name the two states. `FeatureSubGroup`
   also gained the previously-mistyped `"adhoc-import"` group.

**Migration/rollback:** No data-format change — `users.permissions.json` is untouched by this
entry. Widening a ceiling is backward-compatible: existing files keep whatever rows they have,
and rows for the newly-opened combinations simply start working. Rollback is a plain revert; any
employee×reports/archive grant made in the meantime becomes inert again (the row stays on disk,
the ceiling refuses it), which is the pre-v71.1 behaviour.

## v71.0 — 2026-08-13 — Add (auth): default passwords, admin username sign-in, and an admin-only passcode editor

**Why:** Owner request, four parts: every user should ship with the password `123`; `admin` /
`admin` should work from the ordinary sign-in form; Settings should be able to turn that
username sign-in on and off (leaving the hidden shortcut as the only way in when off); and the
admin password should be editable inside the app, by admins only.

Parts 3 and 4 are what forced a design decision, because the bootstrap admin passcode was a
**compile-time constant** (`BOOTSTRAP_ADMIN_PASSWORD_HASH` in `authConfig.ts`) — rotating it
meant editing source and rebuilding, which is not "edit it in the app". Two storage options
were considered:

- **`localStorage`** (what the label overrides do). Rejected: the passcode would be trapped in
  one browser profile on one machine, so an admin who changed it would find the *default* still
  in force on the next PC — the failure mode is silently keeping a guessable passcode alive.
- **`3-user-data/users.permissions.json`** (chosen). It is already the durable, CAS-protected,
  multi-writer home for users/roles/permissions and their Argon2id hashes, already read on
  workspace mount before login, and already carried into backups. An optional `adminAccount`
  block rides that existing path with no new file, no new lock, and no new sync timing.

**Security note (deliberate, recorded):** `admin`/`admin` and `123` are guess-in-one-attempt
credentials, and the bundled admin hash is offline-crackable by anyone holding the build. This
is an accepted owner decision for a client-only app whose security model is already advisory
(`docs/architecture/SECURITY_MODEL.md` §1), not an oversight — that doc's §2 now states the
defaults explicitly and says to change them before the app touches real data.

**What changed:**

1. **Default passwords are `123`.** `DEFAULT_USER_PASSWORD_HASH` in `userManagement.ts` is a
   fresh Argon2id hash of `123`, so all six seeded users (`createDefaultManagedUsers`) sign in
   with it. Existing users on disk are untouched — this is the seed, not a migration.
2. **Default admin passcode is `admin`.** `BOOTSTRAP_ADMIN_PASSWORD_HASH` re-generated for
   `admin`, and it is now only the *fallback*: `resolveAdminPasswordHash()` prefers the
   workspace's own `adminAccount.passwordHash` whenever one has been set.
3. **`admin` signs in from the normal form.** `loginAsEmployee` checks the reserved username
   **before** the managed-user lookup, so `admin` always resolves to the bootstrap superuser
   rather than to a same-named managed user, and verifies against the resolved admin hash. A
   wrong passcode there counts toward the same 3-attempt / 30-second lockout as any other
   failure (the duplicated attempt-counting in the two existing failure branches was folded
   into one `registerFailedAttempt()`). The sign-in form also stays rendered when a workspace
   has zero active users but admin-username sign-in is on — otherwise an empty workspace had no
   way in except the shortcut.
4. **New workspace-backed `adminAccount` state.** `UserManagementState` gains
   `adminAccount: { passwordHash, allowUsernameLogin, updatedAt, updatedBy }`, with
   `readAdminAccount()` / `resolveAdminPasswordHash()` / `updateAdminAccount()` accessors.
   `normalizeUserManagementState` fills it from defaults when absent, and its input type
   (`UserManagementStateInput`) makes the field optional on the way in so every existing caller
   still compiles. It round-trips through `syncUserManagementToDisk` / `applyDiskUsers`, and
   Archive's "import users & labels" restore now carries it too — omitting it there would have
   silently reset a custom passcode to the default on every backup restore.
5. **New Settings section `حساب المدير`** (`AdminAccountSection.tsx`): the on/off switch for
   admin-username sign-in, and the passcode editor (new + confirm, minimum 3 characters,
   hashed with `createPasswordHash` before it ever leaves the component). It is gated on
   `readRealSession()` — the **real** session, not the effective one — so an admin previewing
   another role cannot reach it from inside that preview, a demo/viewer session cannot (it is
   read-only), and no non-admin role sees it at all. With no workspace connected it says the
   change applied to this session only rather than implying it was saved.

**Migration/rollback:** `adminAccount` is an **optional, additive** field on
`UsersPermissionsData`. Older workspaces have no such block and read back as the shipped
defaults (`passwordHash: null` → bundled constant, `allowUsernameLogin: true`); older builds
reading a newer file ignore the unknown key. So the format change is forward- and
backward-compatible in both directions and needs no migration step. Rollback is a plain revert:
a workspace written by this version keeps a stale `adminAccount` block that the reverted code
ignores, falling back to the compile-time passcode.

## v70.10 — 2026-08-13 — Fix (population/sampling): guard foreign sub-tab events, thread stage mappings into replacement appends, and report true Excel row numbers

**Why:** Three independent defects surfaced by a full-codebase audit, each confirmed against the code and
each previously uncovered by the suite:

1. `Sidebar.tsx` dispatches the generic `pop-set-subtab` event on `window` for *every* tab's sub-tab clicks,
   and `App.tsx`'s tab-mount LRU keeps up to 3 tabs mounted (hidden, not unmounted). Population's listener
   therefore stayed live while another tab was active and accepted foreign ids: clicking Reports' `kpi`
   sub-tab set Population's `activeSubTab` to `"kpi"`, a value outside its own `SubTab` union. The render
   then hides Browse *and* returns `null` for Process simultaneously, so the tab goes blank. Its three
   sibling tabs (EmployeeWorkspace, Reports, UserManagement) all already guard against a known set;
   Population was the only one that did not.
2. `appendSampleRow` classified a replacement row with `getStageKey(row.stage)` and no mappings, silently
   falling back to `DEFAULT_STAGE_MAPPINGS` — while the draw path and `getReplacementCandidates` both thread
   the workspace's configured aliases. In a workspace using custom stage aliases the replacement row hit the
   `if (stageKey === "unknown") return allocations;` guard and was dropped from `stageAllocations`. The row
   still landed in `rows[]` and distributed and answered normally, so nothing failed loudly, but
   `actualDrawn` / `certScanDrawn` / `nonCertScanDrawn` permanently under-counted by one per replacement —
   and those fields feed `sampleReport.ts`, `executiveKpiProfiles.ts` and the executive deck.
3. `worksheetToSourceRows` passed `blankrows: false` to `sheet_to_json`, which drops fully blank rows before
   the mapping runs, then derived `sourceRowNumber` as `index + 1` over that compacted array. Every interior
   blank row shifted the reported number of everything below it. That number is user-facing: it is rendered
   as «رقم الصف المصدر» in the dropped-rows diagnostic, i.e. the pointer a user follows back into their
   spreadsheet to fix an invalid or duplicate X-ray ID. Blank spacer rows are common in hand-maintained
   agency exports, so users were being sent to the wrong line — or a blank one.

**What changed:**

- **Population sub-tab guard** — added `KNOWN_POPULATION_SUB_TABS` and a membership check in the
  `pop-set-subtab` handler, mirroring the pattern already proven in the three sibling tabs. The legacy event
  is deliberately left in place; migrating to `sidebar-subtab-changed` is a separate behavioural change
  (both `Sidebar.tsx` and `WorkspaceGate.tsx` still fire the legacy event).
- **Stage mappings threading** — `appendSampleRow` and `incrementStageAllocations` take an optional
  `stageMappings`; `executeReplacement` accepts and forwards it. `XrayReferrals.tsx` passes the mappings it
  already holds in state. `approveReferral.ts` resolves them via `loadPopulationConfig`, best-effort: a
  config-load failure falls back to `undefined` (today's behaviour) rather than failing an otherwise valid
  approval. Omitting the parameter preserves current behaviour at every other call site.

  anything is dropped. The existing `isNonEmptyRow` filter still discards the now-visible blank rows, after
  the index has been captured, so header derivation, `validColumnIndexes` and the double filter all behave
  identically. Clean sheets produce byte-identical output.

Deliberately **not** changed: `incrementStageAllocations`'s new-entry branch still labels the bucket from
`row.stage`, and no `SAMPLING_ALGORITHM_VERSION` bump — this fixes a derived counter on future writes only,
invalidating no historical draw.
