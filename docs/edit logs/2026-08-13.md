## v80.4 — 2026-08-13 — Change (performance): resolve the replacement row through the query worker instead of parsing the population on the main thread

**Why:** Confirming a sample replacement needs the **full** population row — the candidate list only carries the slim replacement-index projection — so the handler read `population.final.json` end to end and kept exactly one row. On a large month that `JSON.parse` is seconds of blocked main thread, on the click an employee makes most often. It is the freeze users actually report.

**What changed:** The query worker gains a `rowById` request and a matching `row` response, and a new `findPopulationRowById` resolves one row through it, so the parse happens off the main thread. The disk read itself is unchanged; only the parse moved.

`rowById` is deliberately **not** expressed as a `query` with a search param. `runPopulationQuery` runs the whole search → filter → sort → paginate pipeline and returns a page plus aggregates the caller discards, and — the real problem — its search matches *display* values across every column, so an id appearing inside another row's text would come back as a false positive. A test pins that case.

**Not a hook.** `usePopulationBrowseWorker` owns a long-lived worker plus a three-slot staleness guard tuned for Browse's interleaved query streams; this caller wants one answer, once. Reusing it would mean lifting lane machinery into a place with no lanes, and putting Browse's hard-won ordering logic at risk for no gain. `findPopulationRowById` owns a worker for one lookup and terminates it — a test asserts the terminate, since a leak would strand a full parsed population per confirm.

**Parity trap avoided.** The replaced accessor, `loadMonthPopulationFinal`, does **not** run rows through `appendMonthInfo`, unlike its siblings in the same file. Passing `monthFolder` to the worker's `load` — the obvious thing to do — would have added `_monthFolder`/`_month`/`_year` to a row that then gets written into `sample.master`. **Scope.** Only the employee-facing confirm is rerouted. `approveReferral.ts` still reads directly and now says why: routing it through a worker would pull Vite's `?worker&inline` specifier into the data layer's dependency graph, forcing a worker mock into every suite that merely imports the module — real test churn for a supervisor-only path far colder than the employee's click. Adding a response variant broke `usePopulationBrowseWorker`, which narrowed the union to `error` by elimination — caught by `tsc`, not by a test. It now discards `row` replies explicitly rather than mistaking one for a failure.

## v80.3 — 2026-08-13 — Fix (browse): collect the XLSX export in one query instead of once per page

**Why:** `runPopulationQuery` is stateless by design — every call re-runs search → filter → **sort** → slice over the whole dataset. Browse's XLSX export collected its rows by walking pages through that function with `maxPages = Infinity`, so exporting a 400k-row month re-sorted the entire month once per 100 rows: roughly 4,000 full sorts and ~1.6e9 row visits to produce one file.

**What changed:** `PopulationQueryParams` gains an optional `pageSize` (defaults to `DATA_PAGE_SIZE`, so every existing caller is bit-for-bit unaffected). `collectMatchingRows` now detects the unbounded case and issues a single query for the whole matching set. The bounded filter-preview path keeps paging on purpose — it wants an early exit after a few pages, not the full set. The worker needed no change: it forwards `request.params` to `runPopulationQuery` verbatim, so the new field propagates for free.

**Guarded a real trap:** the natural sentinel, `pageSize: Infinity`, silently returns an **empty** result. `pageSlice` computes `(page - 1) * pageSize`, and `0 * Infinity` is `NaN`, which `Array.slice` coerces to `0` for both bounds — so the export would have produced a well-formed file containing no rows. `Number.MAX_SAFE_INTEGER` takes the same "one page holds everything" branch without the trap, and a test pins the `Infinity` behaviour so the sentinel is not "simplified" back later.

Because `runPopulationQuery` feeds the export it is deterministic by contract, so a golden master was recorded **first** — full ordered output for a fixed input covering duplicate sort keys, an empty value, and numeric-vs-locale comparison. Two of the four pinned orderings did not match what the code was assumed to do (`"—"` sorts first ascending; the index tiebreak stays ascending under `desc`), which is precisely why the master records observed behaviour rather than intended behaviour. It is unchanged by this edit.

## v80.1 — 2026-08-13 — Fix (performance): defer hidden Browse reloads and route hand-rolled yields to the scheduler

**Why:** Two independent sources of wasted main-thread work on the Population tab.

Browse is deliberately kept mounted-but-hidden after its first visit so that switching away and back does not re-load the dataset. But `BrowseDataView`'s load effect is keyed on `refreshKey`, and every distribution mutation bumps `monthRefreshKey` — so a Manual Review session, which is a long run of mutations performed entirely on the *process* sub-tab, re-read the whole month roughly once per click for a view that was off screen the entire time. The worker absorbs the parse, but the main thread still reads and structured-clones a multi-hundred-MB payload on each one.

Separately, five production modules each defined their own `const yieldToMain = () => new Promise((resolve) => setTimeout(resolve, 0))` instead of importing the shared helper. `setTimeout(…, 0)` is subject to the HTML spec's 4 ms clamp; the shared `yieldToMain` prefers `scheduler.postTask({priority: "user-visible"})` on Chromium — which this app already requires for the File System Access API — and only falls back to the timer when `postTask` is absent.

Rejected for the Browse case: unmounting the view when inactive. That would discard the loaded dataset and force a re-read on every visit, which is precisely the cost the mounted-but-hidden design exists to avoid.

**What changed:** Added `useDeferredWhileHidden(value, isVisible)` — holds a value steady while a view is hidden and catches up the moment it becomes visible. Browse's `refreshKey` now flows through it, so mutations while hidden no longer trigger a load, and the reload happens once, at the point the user actually looks. Nothing is skipped and Browse cannot render stale data. Implemented as a render-phase state adjustment (the same idiom this file already uses for `visitedSubTabs`) rather than an effect, so no frame is rendered with the stale value.

The five hand-rolled yields now import the shared `yieldToMain`. The local definitions are deleted, not shadowed. Test files that use `setTimeout(resolve, 0)` to flush microtasks are deliberately untouched — those are awaiting the event loop, not yielding for responsiveness.

## v80.0 — 2026-08-13 — Refactor (storage): size-gate envelope hashing, byte-exact write verification, compact-by-default JSON

**Why:** Reading one month's population blocked the main thread for tens of seconds, and most of that time was not spent parsing. `validateEnvelope` ended with `contentHash === hashJsonValue(data)`, and `hashJsonValue` re-serializes the entire payload to hash it. It ran inside `parseValidJson`, so it fired on **every** parse with no size threshold. Measured on a representative row shape: the hash costs **7.1x the JSON.parse of the same payload** — the integrity check was several times more expensive than reading the file it checked. Every caller of `loadMonthPopulationFinal` paid it: replacement confirm, referral approval, reports, KPI tiles, Power BI export.

Two related defects sat in the same layer. Read-back verification was *inverted by size*: files over 512 KB got a byte-exact comparison, while files under it — the small, frequently-rewritten, most-contended ones — got only "does it parse", which a **concurrent writer's** valid envelope also passes, so a peer's file could be accepted as our own. And those same small files were pretty-printed at 2-space indentation, measured at 1.35x inflation on every byte written, read and sent over the share.

Rejected: deleting the content hash outright. It is still written, still checked for small payloads, and still available as an explicit `verifyContentHash` call for integrity scanning — the defect was that it ran unconditionally on the read path, not that it exists.

**What changed:** `validateEnvelope` is split into `validateEnvelopeStructure` (O(1) — schema version, revision shape, metadata presence) and `verifyContentHash` (O(payload)). `validateEnvelope` is retained as the composition of both, so its existing contract and tests are unchanged. `parseValidJson` now always validates structure and verifies the content hash only at or below `HASH_VERIFY_SIZE_LIMIT` (512 KB).

Read-back verification is now byte-exact at every size — `staged === serialized` rather than `parseValidJson(...) !== null` — which is both strictly stronger than the check it replaces and cheaper (no parse, no re-hash). `VERIFY_SIZE_LIMIT` is gone; there is no longer a size at which verification weakens. Pretty-printing is now gated at `PRETTY_PRINT_SIZE_LIMIT` (64 KB) instead of 512 KB.

What is still caught after this change: corruption that breaks JSON syntax (by `JSON.parse`), a structurally invalid envelope, and — for small files — a content-hash mismatch. All three still fall back to `.bak` exactly as before. Large payloads instead rely on the write path's byte-exact read-back, which is a stronger guarantee than re-hashing.

**Migration/rollback:** No schema change; `ENVELOPE_SCHEMA_VERSION` is unchanged and every file written before this edit reads back unchanged. The only on-disk difference is that files between 64 KB and 512 KB are now written compact instead of indented — still valid JSON, still the same parsed value, and existing indented files are read without conversion. Rollback is a straight revert: restoring the old `parseValidJson` re-enables unconditional hashing, and restoring `VERIFY_SIZE_LIMIT` re-enables the size-split verification. No data migration in either direction.

## v79.0 — 2026-08-13 — Refactor (distribution): bounded segment rotation for the event log

**Why:**

Each writer session owns one NDJSON segment in
`2-samples/{month}/1-main/distribution.events/` and **rewrote that entire file on
every append**. The File System Access `Like`-handle contract exposes no
positional write, so adding lines means read-modify-write of the whole session's
events. Both the bytes pushed over the wire per append and the amount of content
exposed to one failed write therefore grew linearly with session length — on the
UNC/SMB share this app is deployed to, that is the dominant write cost, and it
already produced a production failure (the transient-`NotFoundError` bug fixed in
v75.0: the longer the segment, the wider the window in which a rewrite could be
seen as missing).

Measured on a 900-event session appended in 180 batches of 5 (memory-directory
harness, instrumented at the writable stream): **23,357,305 bytes written, an
average of 129,763 bytes per append**, for a final segment of only ~232 KB. The
cost is quadratic in session length and unbounded.

Rejected alternatives:

- *Genuinely append-only writes.* There is no primitive for them on a
  user-picked directory. `createWritable({ keepExistingData: true })` is
  implemented in Chromium by copying the existing file into a swap file first, so
  a "positional append" pays the same O(file size) cost on the share while being
  harder to verify. True append exists only through
  `FileSystemSyncAccessHandle`, which is OPFS-only and cannot address the
  workspace folder at all. **The open segment therefore remains
  read-modify-write; what this change buys is that it is now bounded.**
- *One file per event* (the pre-v75 layout, still read — see below). It makes
  each write O(1) but multiplies the per-fold directory enumeration and read
  fan-out by the event count, which is the cost v75.0 removed deliberately.
- *Compaction / merging sealed segments.* Rewriting history on a shared,
  multi-writer, backend-free store has no safe point at which every reader's
  byte offsets can be invalidated together. Segments are append-only forever.

**What changed:**

*The chain.* A writer session's segments are now
`{deviceId}-{sessionId}.ndjson` (sequence 0), then `-1`, `-2`, … Only the
highest is ever opened for writing. Once the writer moves past a segment, that
segment is **sealed**: never rewritten, never renamed, never deleted. A reader
consequently only ever tails one growing file per writer session.

**Sequence 0 is deliberately the historical unsuffixed name.** A pre-rotation
writer's `{deviceId}-{sessionId}.ndjson` is then not a legacy special case
anywhere — it is simply a chain whose first segment never rotated, so it keeps
being read *and appended to* by the new code with no migration, no rename, and no
format flag. This is the house additive/read-both pattern (`workspacePaths.ts`
legacy roots; the legacy one-file-per-event `*.json` family in
`distributionStorage.ts`), and it is what keeps a mixed deployment — some
machines on an older build, some on this one — writing into the same directory
without either side noticing.

*Thresholds: 128 KiB (`MAX_OPEN_SEGMENT_BYTES`) or 2,000 lines
(`MAX_OPEN_SEGMENT_LINES`).* The trade-off runs in both directions and 128 KiB is
where the two curves cross:

- **Write side.** One append costs `fixed round trips + payload`. Chromium's
  swap-file write cycle (open, write, close, atomic rename) plus this module's
  post-close `verifySegmentSize` open is on the order of 20–40 ms of fixed
  latency on the share. 128 KiB at even a pessimistic 10 MB/s is ~13 ms — already
  a minority of the per-append cost. Halving the cap to 64 KiB would save only a
  few ms per append while doubling the file count: clear diminishing returns.
- **Read side.** Every extra segment costs a `getFile()` round trip per fold
  (`readSegmentTails` opens each matched name), paid by every client on every
  fold, forever. At ~258 bytes per event line (measured on a realistic event
  carrying an Arabic `notes` field), 128 KiB holds ~500 events, so a 9,000-event
  month gains ~18 files. Raising the cap to 256 KiB would halve that, but would
  double both the worst-case single append and the content sitting inside one
  crash-exposed rewrite.

The line cap is a second, cheap bound for the shape the byte cap cannot see. It
only binds when the average line is under ~65 bytes, which no current
`DistributionEvent` approaches; it is belt-and-braces against a future, much
smaller event shape making a segment expensive to *parse* rather than expensive
to *transfer*. It is not expected to fire today, and is documented as such.

*Crash safety.* Sealing is not an operation. There is no seal marker, no rename,
and no second file touched during a rotation, so there is no mid-rotation state
to be caught in. A rotation is exactly **one write of a new name**: it either
landed (the events are durable in `seq+1`) or it did not (the append reports
failure to its caller), and the previous segment is untouched either way. Two
writers cannot end up on the same `seq` — `deviceId`+`sessionId` is unique per
running app instance and a crashed process never resumes its own session id — and
within a session the resource lock now covers the writer **chain** rather than
one file name, so the rotation decision and the write it implies are a single
critical section. Locking per file name would have let two concurrent appends
both read a full segment, both decide to rotate, and race on `seq+1`.

Two further rules make resumption non-destructive:

- **Every append re-reads the file it is about to write**, including the one
  immediately after a rotation. So a segment left behind by a crashed run, or
  temporarily hidden from a stale SMB directory listing, keeps its lines instead
  of being overwritten. The rotation-target read is normally an immediate miss
  (an unwritten segment is not in `writtenSegmentsThisSession`, so its
  `NotFoundError` is taken at face value with no retry ladder), costing one round
  trip once per 128 KiB.
- **A segment found already at or over the cap on startup is rotated away from,
  not grown.** This falls out of the same predicate rather than being a separate
  branch: `existingBytes + addedBytes` already exceeds the cap, so the resuming
  writer's first append goes to `seq+1`.

*Sequence discovery.* A writer that has lost its in-memory position (first append
of a session, a workspace switch, a module reload) finds its own highest sequence
by listing the directory once and parsing **only names matching its own
`{deviceId}-{sessionId}` prefix**. This is writer-side introspection and is
confined to `parseOwnSegmentSeq`, which returns `null` for anything it does not
positively recognize (another writer's file, a stray name, leading zeros, out of
range) — so an unexpected shape can only make this writer start a fresh chain,
never claim someone else's file. A listing failure resolves to 0 rather than
throwing, because the read-before-write rule above makes the worst case
"appended to an already-full segment", never a lost line. The in-memory position
is recorded only for a segment a write actually landed in, so it can never point
ahead of what is on disk.

**The read path is untouched and must stay that way.** Every reader still
discovers segments through a pure `.ndjson` suffix glob (`readSegmentTails` →
`directoryScan`'s `entry.name.endsWith(suffix)`). No stricter filter was added —
narrowing it to a `-\d+` shape would make older writers' unsuffixed files
invisible and lose their events. Sealed segments are never renamed, because
`foldCheckpoint.segmentOffsets` and `readAppendOnlyDirectory`'s sibling
invalidation both key on the file *name*: a rename reads as "old name vanished,
new name at offset 0" and re-folds those events. An unknown name defaults to
offset 0 and is read in full, which is exactly how a reader holding a stale
offset for the previous segment picks up a newly-rotated one. Segment listing
order is lexicographic, so `-10` sorts before `-2` and `-1` sorts before the
unsuffixed name — all inert, because event order comes from a total
`(eventAt, eventId)` sort applied *after* concatenation.

```ts
    existing = await readExistingSegment(eventsDir, fileName, segmentMemoKey(writer.scopeId, fileName));
    existingBytes = utf8Length(existing);
  }

  await retryTransientWrite(/* full rewrite of `existing + addedText` */);
  writtenSegmentsThisSession.add(segmentMemoKey(writer.scopeId, fileName));
  openSegmentSeqByWriter.set(writerKey, seq);
  await verifySegmentSize(eventsDir, fileName, existingBytes + addedBytes);
});
```

**Migration/rollback:**

*There is no migration.* No existing file is moved, renamed, rewritten, or

may now be several, and the first of them keeps the exact name it always had.

*A workspace mid-flight* (some machines upgraded, some not, users mid-session)

- An **old writer** keeps appending to `{deviceId}-{sessionId}.ndjson`
  unboundedly. A new writer never touches another writer's chain, so nothing
  conflicts. That session simply does not get the bounded cost.
- A **new writer** resuming an old session's chain (same device, same session id
  — i.e. no page reload) sees the unsuffixed file as sequence 0, appends to it

- An **old reader** (a machine still on v78.0 or earlier) reads every `.ndjson`

  No change was needed there.

*Rollback* is reverting this commit and nothing else. Segments written as `-1`,

and must not be done.

## v78.0 — 2026-08-13 — Fix (backup): include distribution event segments in backup and restore

**Why:**

`backupStorage.ts` gated both its backup walk and its restore walk on
`entry.name.endsWith(".json")`. Distribution event segments are named
`{deviceId}-{sessionId}.ndjson`, and `"x.ndjson".endsWith(".json")` is **false** —
the character before `json` is `d`, not `.`. Every segment was therefore skipped
in both directions, silently and without any warning in the manifest.

The distribution event log is the append-only source of truth for all assignment
state. It has never been included in any backup. The consequence was worse than a
plain omission: `distribution.current.json` — the *derived* fold cache — is a
`.json` file and **was** captured, so a restore returned population and sample
data alongside a cache asserting an assignment state whose justifying events were
not restored with it.

A secondary defect surfaced while testing this: an event segment that could not be
read during the copy walk was silently dropped and the backup still reported
success with a clean manifest, because `readTextFile` resolves an unreadable file
to `null` and the walk treated `null` as "skip". For a last-write-wins JSON file
that tolerance is correct and deliberate (safeWriteJson's `.tmp` files appear and
disappear constantly on a live workspace). For an append-only segment it produces
a backup that is missing events while claiming to be whole.

**What changed:**

*One predicate for both walks.* `isSnapshotPayloadFile()` is now the single gate
used by `collectJsonFileEntries` (backup) and `collectJsonRestoreEntries`
(restore), so the two can no longer drift into capturing a family that cannot be
put back. It matches `.json` or `.ndjson` by **suffix equality**, not substring:
a substring test would have "fixed" the bug while also sweeping in `.json.bak`,
`.json.tmp` and `.ndjson.bak` — safeWrite's rollback and staging siblings, whose
restoration over a good file is exactly the corruption the safe-write layer
exists to prevent. Nothing is matched beyond the `.ndjson` suffix itself, so the
approved bounded-segment-rotation change (one session spanning
`{deviceId}-{sessionId}-{seq}.ndjson`) needs no further work here; N segments per
session are handled naturally by both walks and are covered by tests.

Before:

```ts
if (entry.kind !== "file" || !entry.name.endsWith(".json")) continue;
```

After:

```ts
if (entry.kind !== "file" || !isSnapshotPayloadFile(entry.name)) continue;
```

*Restore semantics — merge, not replace.* A backup snapshot is not uniformly
last-write-wins, and three distribution file families now carry their own
restore action (`RestoreAction`):

- **`merge-events` — `*.ndjson` segments.** Segments are append-only and immutable
  per writer session, so the backup's copy and the live copy are both prefixes of
  the same truth and **either may hold events the other lacks**: the backup carries
  events truncated or lost since it was taken (the disaster a restore exists to
  undo), the live file carries everything appended after the backup ran.
  Replace-file destroys the newer events; skip-if-present fails to repair the
  older ones. Only a union can lose neither, so the two sides are merged by
  `eventId` through the existing `mergeDistributionEvents` primitive
  (`distributionEventStore.ts`) rather than a reinvented dedupe. The live side is
  passed first, which keeps the live file's own line order as the base and appends
  only ids the live file lacks. When one id carries genuinely conflicting content
  on the two sides `mergeDistributionEvents` throws; that propagates and fails the
  restore, which is correct — two different events minted under one id is an
  integrity contradiction, not something to silently pick a winner for. A segment
  whose merge adds nothing is not rewritten at all, so a no-op restore stays a
  genuine no-op down to the byte.

- **`skip-derived` — `distribution.current.json`.** Never restored. It embeds a
  `foldCheckpoint.segmentOffsets` map of per-segment **byte offsets** meaning
  "already folded up to here". A merge above can grow a segment and shift where
  its lines sit, which would leave those offsets pointing into the middle of a
  line — the incremental reader would then either mis-parse or skip real events
  while holding a cache that claims to be current. `invalidateDistributionCaches`
  additionally deletes the **live** cache (and its `.bak`/`.tmp`) in every
  directory whose segments the restore actually rewrote. This is what satisfies
  "the cache must never be newer than the events backing it": the only state in
  which that is guaranteed is no cache at all, at the cost of one full re-derive
  on the next month load. Invalidation is keyed to segments that really changed,
  so a restore that adds no events does not cost every month a re-derive.

- **`restore-if-absent` — `distribution.log.json`.** The legacy full-event
  compatibility projection is CAS-protected and monotonically revisioned. Writing
  the backup's older revision over a newer live one both rolls the revision
  backwards and drops events. Every event it holds is also durable in the event
  segments / per-event `.json` files, which *are* restored, so leaving a live
  projection alone loses nothing — while still restoring it into a workspace that
  has none, which is the disaster-recovery case.

Everything else keeps the long-standing `replace` behavior.

*Unreadable segments are now fatal.* On both walks, a segment that is listed but
whose text cannot be read raises instead of being skipped. A segment is
append-only and never deleted, so it cannot legitimately vanish mid-walk, and
omitting one drops events that exist nowhere else in the snapshot. Failing loudly
turns a silently-incomplete backup into an obviously-failed one. Non-segment JSON
keeps its existing, deliberate tolerance for mid-walk churn.

*Restore refuses an unfinished backup.* `assertBackupComplete()` runs before any
mutation — before the pre-restore rollback backup, before the
`restore.inprogress.json` sentinel, before the walk — and requires both
`backup.manifest.json` (readable) and `backup.complete.json` (present). Both are
written only after the whole copy walk succeeds, so either one missing means the
backup stopped partway. This matters more under merge-events than it did under
replace: a truncated segment set would otherwise be folded into the live log as
if it were the full history.

*Archive status stops lying about distribution presence.* `loadArchiveStatus`
derived `hasDistribution` purely from `distribution.current.json`. Since that is a
rebuildable cache — and is now deliberately deleted by a restore that changed
segments — it can be absent while a complete event history exists. The check now
falls back to `hasDistributionEventFiles()`, a directory listing of
`distribution.events/` for any `.ndjson` or legacy per-event `.json`. It
short-circuits, so it is only paid for when the cache is already absent. Row
counts stay cache-derived (they would need a full fold) and read 0 until the month
is next loaded.

**Size:** measured on a realistic month (500k population rows, 9k sampled, ~19,350
events at a 244-byte average NDJSON line). Segments add **4.47 MB to an ~855 MB
backup: +0.52%.** They are nowhere near the bulk — `population.final.json`
(~448 MB) and `risk.raw.json` (~381 MB) are. Note that `distribution.log.json`,
the legacy projection carrying substantially the same events, was already being
backed up at ~4.73 MB, so excluding segments was never actually saving space.
No compression or cross-backup dedupe was implemented, and cross-backup dedupe was
**rejected on correctness grounds independent of size**: automatic backups are
pruned to `AUTO_BACKUP_RETENTION_COUNT`, so a segment "skipped because an older
backup already has it" becomes a dangling reference the moment that older backup
is pruned. Nothing is sampled, truncated, or dropped.

**Migration / rollback:**

*Migration:* none required. No on-disk format changes; no file is moved, renamed,
or deleted by the backup path. Existing workspaces are read unchanged. The first
backup taken after this lands is the first one that contains segments; every
earlier backup remains readable but restores without an event history exactly as
it does today.

*One deliberate breaking change:* backups created before the completion sentinel
existed (pre-2026-08-04) are no longer restorable through `restoreBackupSnapshot`,
because `assertBackupComplete` now requires `backup.complete.json`. Their `json/`
tree can still be copied back by hand. The trade is taken knowingly: the
alternative is accepting a snapshot that cannot be distinguished from a complete
one. If this proves disruptive, the narrowest revert is to drop the
`BACKUP_COMPLETE_FILE` clause in `assertBackupComplete` and keep the
`backup.manifest.json` clause, which is the strong long-standing signal
(`loadBackupHistory` already hides manifest-less backups from the restore picker).

*Rollback:* the change is confined to `backupStorage.ts` and is safe to revert
wholesale — reverting restores the previous `.json`-only behavior and no data
written under the new code becomes unreadable. Segments already copied into
backup folders simply stop being read. The one asymmetry to be aware of: a restore
performed under the new code may have deleted a `distribution.current.json` cache,
which the old code will transparently re-derive on next load.

*Out of scope, deliberately:* segment rotation itself is not implemented here (a
separate change owns it). Sampling, event folding, and report/export builders were
not touched — their snapshots are unchanged.

## v76.0 — 2026-08-13 — Fix (storage): tolerate entries that vanish between directory listing and open

**Why:** The UNC/SMB report had two distinct symptoms. v75.0 fixed the first (the
Arabic-wrapped "تمت إضافة البديل للعينة لكن فشل تسجيل الحدث" on the distribution write path).
The second — the *bare* English "A requested file or directory could not be found at the time
an operation was processed.", with no Arabic wrapper at all — came from somewhere else: the two
enumerate-then-open loops in `directoryScan.ts`. Both list a directory and then re-open each
matching entry by name, unguarded. On a shared folder an entry can be renamed, removed, or
simply not yet visible to this client in the gap between the two steps, and this client's
directory view can lag the server's. Chromium raises `NotFoundError`, which aborted the entire
enumeration and propagated as a raw DOMException.

`listDirectoryEntriesWithSize` (introduced with the stamp-gated sync tick) runs on every sync
tick across the answers and decisions families while other machines write concurrently.
`readSegmentTails` (introduced with the segment-based event store) runs on every distribution
read, reached from `distributionEventStore.readDistributionEventSegmentDelta` →
`distributionStorage.loadDistributionLog` — which `appendDistributionEvents` calls *inside* its
casLoop, so one throw there burned the whole retry budget and then surfaced as a failed append.

Rejected: wrapping both sites in a uniform maximum retry. These are hot read paths, and a
per-entry ladder multiplies worst-case latency by the entry count — on a workspace with many
employees that would turn one flaky share into a stalled sync tick every 45 s. Also rejected:
swallowing every error, which would hand callers a short listing indistinguishable from real
data when the actual cause is a permission or quota failure.

**What changed:** A shared `readListedEntry` helper in `directoryScan.ts` opens a listed entry
and resolves to `null` — never throws — when it has vanished. It reuses v75.0's
`transientFileErrors.ts` (`isNotFoundError`, `isNotReadableError`, `waitFor`, and a two-step
prefix of `TRANSIENT_WRITE_RETRY_DELAYS_MS` as `VANISHED_ENTRY_RETRY_DELAYS_MS`) rather than
introducing a parallel mechanism. Anything that is not a NotFound/NotReadable still propagates.

The retry policy differs per site, deliberately:

- `listDirectoryEntriesWithSize` — **no retries** (`budget: null`), skip and continue. Its output
  is a change-detection *signature*, not data: a skipped entry only makes this tick's signature
  differ from the last, which at worst reports the family as changed and costs one extra refresh.
  Both callers in `workspaceSync.ts` already degrade a failure to a neutral `""`. Paying a ladder
  per entry to avoid a benign extra refresh is the wrong trade on the app's hottest read loop.
- `readSegmentTails` — a **per-call** budget of 2 retry attempts shared across every segment
  (`SEGMENT_TAIL_VANISH_RETRY_BUDGET`), ~80 ms worst case regardless of how many segments are
  listed. A short retry is warranted here because the result feeds distribution event folding
  from inside an append's casLoop: folding without a segment that is merely invisible for a few
  milliseconds would let an append decide against state missing real events. A per-*entry* ladder
  was rejected for the same scaling reason as above — segment count grows with the number of
  machines using the workspace.

A skipped segment is recorded in `matchedNames` (it was in the listing) but gets **no**
`sizeByName` entry. Callers persist `sizeByName` as the next call's `knownOffsets`, so recording a
size for bytes that were never read would mark unread events as already consumed; omitting it

## v75.0 — 2026-08-13 — Fix (storage): treat NotFoundError as transient on the write/verify path so a completed write on a network share stops reporting as a failure

**Date:** 2026-08-13

**Why:**

A user working from a workspace on a UNC/SMB network share hit

> تمت إضافة البديل للعينة لكن فشل تسجيل الحدث — يُرجى المحاولة مرة أخرى: A requested file or directory could not be found at the time an operation was processed.

and, from other entry points, the same bare English sentence with no Arabic
wrapper at all. That sentence is Chromium's `NotFoundError` DOMException for
File System Access.

Nothing was actually missing. The whole write chain resolves its directories
with `{ create: true }` from root to leaf (`workspacePaths.ts`,
`distributionEventStore.ts`), so a genuinely absent directory was never the
cause. The real mechanism: on SMB the directory entry for a file is not always
visible to the next `getFileHandle()` after the writable stream's `close()` has
already returned successfully. The bytes are on the server; only the client's
view of the directory is stale.

`appendDistributionEventSegment`'s post-`close()` size verification re-opened
the segment file with `{ create: false }`, unguarded. On a lagging share that
threw `NotFoundError` *after the events had been durably written*.
`distributionStorage.appendDistributionEvents` caught it and returned
`{ ok: false, error: error.message }`, and `replacement.ts` interpolated that
message verbatim into an Arabic sentence — producing the exact report above: the
sample row written, the event append written, and the user told it had failed.

`safeWrite.ts` had the same shape at a lower level. It already retried
`NotReadableError` but classified `NotFoundError` as "file absent" everywhere,
including in the read-backs that verify a file it had just written and closed.

The second, compounding problem is presentational: several `result.ok === false`
branches put `result.error` straight on screen. That field is Arabic domain text
in the normal case but a raw English DOMException string when a thrown error was
passed through, so English leaked into an Arabic RTL UI. And
`XrayReferrals.handleReplace` had only a `finally`, no `catch` — a throw from
`executeReplacement` (its month-lock gate and directory resolution both sit
outside `appendDistributionEvents`' inner try) became an unhandled rejection
with no user feedback whatsoever.

**What changed:**

1. **A new module draws the line explicitly.** `transientFileErrors.ts` states
   the rule the codebase was missing: *"absent on read" and "transient on write"
   are different conditions that arrive as the same DOMException.* It owns the
   predicates (`isNotFoundError`, `isNotReadableError`, `isTransientWriteError`),
   the retry ladder (`TRANSIENT_WRITE_RETRY_DELAYS_MS = [20, 60, 150, 400]` — 4
   retries, ~630 ms worst case), the idempotent-write retry wrapper
   (`retryTransientWrite`), and the failure-path classifier described in (5).

2. **`safeWrite.ts` retries NotFoundError on the write/verify path only.**
   `writeText` is wrapped in `retryTransientWrite` (it re-opens the handle and
   rewrites whole content, so a retry is idempotent by construction). Every
   post-write verification read-back — staged `.tmp` verify, committed verify,
   the promotion re-reads, and `verifyStreamedFile` — opts in via a new
   `readText(dir, name, { retryMissing: true })`; `safeReadJson` gained the same
   opt-in for callers that read back their own write.

   **The read path is deliberately untouched.** `retryMissing` defaults to
   `false`, and the module header explains why: absence is the normal, correct
   answer for a first write, for an optional file, and for `safeReadJson`'s
   `.bak`/`.tmp` fallback probes. Retrying those by default would put ~630 ms of
   dead wait behind every absent-file read in the app.

3. **The post-close verification in `distributionEventStore.ts` is guarded.**
   `verifySegmentSize` retries both a missing directory entry and a short
   reported size on the shared ladder before calling the write failed; the
   segment write itself goes through `retryTransientWrite`. The pre-append
   re-read (`readExistingSegment`) also retries — but only for a segment this
   session has already written, tracked in `writtenSegmentsThisSession`. Before
   that first append, absence is the expected answer and must resolve
   immediately. That memo gates retrying only, never the final answer: it is
   keyed by file name (a directory handle has no stable identity to key on) and
   so can go stale when the user mounts a different workspace mid-session, so an
   exhausted retry still falls back to `""` exactly as before, with a log entry.
   The legacy one-file-per-event writer (`writeImmutableDistributionEvent`) gets
   the same treatment through `safeReadJson(…, { retryMissing: true })`.

4. **`handleReplace` has an error boundary.** The `try`/`finally` became
   `try`/`catch`/`finally`: a `MonthClosedError` shows the month-closed label,
   anything else logs to `errorLogger` under `xrayReferrals:handleReplace` and
   shows `msg_unexpected_write_error` in both the dialog and the status bar.

5. **Raw English DOMException text no longer reaches the Arabic UI.** New
   `writeErrorText.ts` exposes `userFacingErrorText` (for `result.error`
   strings) and `thrownErrorText` (for caught values). Both pass genuine Arabic
   domain text through untouched and replace anything without Arabic in it with
   `msg_unexpected_write_error`, logging the raw detail. The test is the text
   itself rather than a list of known DOMException wordings, which vary by
   browser, version and locale. Routed through it: the five `result.error` sites
   in `useDistributionActions.ts`, the six in `XrayReferrals.tsx` (plus its three
   `error.message` catch blocks), both in `ReferralApproval/index.tsx`,
   `reopenAnswer.ts`'s bare `eventResult.error`, and — importantly — the
   interpolated detail inside `replacement.ts`'s Arabic wrapper, which has to be
   mapped at the source because at the caller the whole string already looks
   Arabic. No new label keys were needed.

6. **Diagnosability.** When a `NotFoundError` survives every retry,
   `logExhaustedNotFound` records the file, the attempt count, and a
   `classifyNotFound` verdict that separates the two causes the raw exception
   cannot: `directory-writable` (share flake — retrying the action is the right
   advice) versus `directory-unreachable` (the workspace folder was moved,
   renamed or re-created since `WorkspaceProvider` restored the root handle from
   IndexedDB, so every write will keep failing until the user re-picks it). The
   probe creates and removes a throwaway entry with `{ create: true }`, the only
   call that distinguishes the two, and runs only after retries are exhausted.
   **Automatic handle recovery / re-picking is deliberately out of scope** — this
   change only makes the logs say which cause it was.

7. **Fault-injection harness.** `memoryDirectory.ts` gained an opt-in
   `SimulatedFault` plan (`{ operation, name | nameSuffix, create, errorName,
   times }`) plus `setSimulatedFaults` / `clearSimulatedFaults`, and an opt-in
   operation log (`trackOperations` / `getOperationLog`). `times` is what makes a
   lagging share reproducible: fail the first N matching calls, then behave
   normally. The operation log is what makes the read-path guarantee testable at
   all — nothing in the returned value distinguishes "absent" from "absent after
   four retries", only latency does, so the test asserts the attempt count.

   Both are defaulted off, so the ~160 existing test files that build a memory
   directory are unaffected.

**Migration / rollback:** No on-disk format, schema or API change. Every write

## v74.0 — 2026-08-13 — Add (settings): admin-configurable workspace sync interval

**Why:** The automatic sync cadence was the hard-coded constant `SYNC_TICK_INTERVAL_MS = 45_000`,
introduced with the single-sync-path refactor in v73.0. Forty-five seconds is a reasonable default,
but it is the wrong number for every workspace at once: a small department on a fast local folder
would rather see a colleague's referral decision in fifteen seconds, while a large department whose
workspace lives on a slow network share pays five directory-touching probes per client per tick and
would rather that happened a few times an hour. Only the people running the department know which of
those they are, so the owner asked for the cadence to become an admin-set value.

Two shapes were rejected before the one that shipped. A `localStorage` setting was rejected outright
by the owner: the point is that the admin sets it once and every employee on every machine inherits
it, and a browser-scoped value has to be re-applied per machine and per browser profile. A second
polling timer watching the settings file was rejected because it reintroduces exactly what v73.0
removed — a second, uncoordinated refresh mechanism with its own cadence and its own failure modes.
The cadence now rides along on the sync run that already exists.

**What changed:**

*Storage.* A new module, `src/data/workspace/syncSettings.ts`, owns a workspace-wide settings file at
`5-system/workspace-settings.json`, resolved through `getSystemRoot()` in `workspacePaths.ts` (no
folder name is hard-coded). No existing `5-system/` file was a sensible host:
`5-system/backups/auto-backup-settings.json` is backup-policy state living inside the backups folder,
`5-system/user-presets/` is per-user, and `3-user-data/users.permissions.json` is the identity and
permission matrix — rewritten wholesale by `syncUserManagementToDisk`, so folding an unrelated scalar
into it would put the sync cadence at the mercy of every permission save. The new file sits directly
under the system root, following the precedent of `restore.inprogress.json`, and is named generically
so a future workspace-wide scalar can join it rather than spawning another file. Writes go through
`casLoop` under a `:rmw` resource lock and are verified by revision + `_writeToken` read-back,
matching `notificationStorage.ts`. Unlike `saveAutoBackupSettings` — which documents a CAS exemption
for its single-scalar whole-object overwrite — this write merges into whatever is already in the
file, precisely because the file is designed to accumulate further settings; the moment a second
field exists, a blind overwrite would drop a concurrent admin's change to the other field.

*Bounds.* Minimum 15s, maximum 30min, clamped on both write and read-back; the read is never trusted,
because this is plain JSON on a shared folder that anyone can hand-edit. The floor is 15s because
every automatic run does a permission re-sync plus a five-part probe (distribution stamp,
notifications revision, two directory listings, the month manifest), each client pays it
independently, and below roughly fifteen seconds those probes begin overlapping their own cost on a
network share while buying no freshness a human can perceive against the 45s default. The ceiling is
30min because past half an hour the automatic path stops being a sync mechanism in any useful sense
— a revoked permission or a supervisor's decision could sit unseen for most of a working session and
the manual refresh button becomes the only real path; 30min is the largest value that still
guarantees a couple of automatic runs per shift. Non-finite, non-numeric and absent values fall back
to the 45s default rather than being clamped, since there is no number there to clamp; negatives and
out-of-range numbers clamp to the nearest bound. Nothing is ever rejected outright on read — a
malformed settings file must not be able to stop the app from syncing.

*Live re-arm, with no new timer.* `workspaceSync.ts` gained a module-level effective cadence, a
subscriber set, and `refreshSyncIntervalFromDisk()`. `performSync` calls it on every run — one small
JSON read next to the probe reads the run already performs — so an admin's change reaches every other
client within at most one interval. The read is deliberately not gated on a month being selected: the
cadence is workspace-wide, and a client sitting with no month selected still has to pick up a change.
`SyncTick.tsx` subscribes to the cadence and carries it in `intervalMs`, which is a dependency of the
timer effect, so a change clears the in-flight interval and reinstalls it at the new value
immediately rather than waiting for the old cadence to elapse one more time. It also does a single
on-mount read (a one-shot, not a poll) so a client loading into a workspace with a five-minute
cadence does not spend its first tick at 45s. `SYNC_TICK_INTERVAL_MS` remains exported, now aliasing
`DEFAULT_SYNC_INTERVAL_MS`, so nothing downstream had to change.

*UI.* A new admin-only `SyncIntervalSection` in the Settings tab, placed next to `AdminAccountSection`
and built the same way: gated on the REAL session (`readRealSession`), so an admin previewing another
role cannot change a workspace-wide setting from inside that preview, with the same collapsible card,
the same save/feedback pattern, and the same stylesheet — reused rather than cloned, since a second
copy of those rules would only drift. On top of the session gate, the persistent action goes through
the centralized `canMutate` capability at both boundaries: the input and save button are disabled
when it denies, and `handleSave` re-checks before touching disk, so a stale render can never be the
thing that authorizes a write. The section shows the effective cadence the sync path is actually
using — seeded from `getSyncIntervalMs()`, refreshed on mount, and kept live by
`subscribeToSyncInterval`, so another admin's change updates this panel too. The draft input is held
as `string | null`, where null means "mirror the effective value"; once the admin types it stops
following disk entirely, so a sync run landing mid-edit cannot overwrite a half-typed number. Every
string is a new `DEFAULT_LABELS` key (`settings_sync_*`); no Arabic is inlined. Validation is whole
seconds within the bounds, with an Arabic error naming the range — `isSyncIntervalInRange` alone would
accept 20.5s, since 20500ms is a legal integer millisecond count, so the component additionally
requires an integer number of seconds.

*Permissions.* A new `settings.syncInterval` feature on the `settings` tab, defaulting to false for
every non-admin role, because the cadence is workspace-wide and one careless change affects every
client on the shared folder. Two existing tests that enumerate the settings-tab feature set were
updated to include it.

The manual refresh button is untouched and deliberately unaffected: it still calls
`runSync({ manual: true })`, still probes, and still broadcasts unconditionally whatever the
configured cadence is. A regression test asserts exactly that at the 30-minute ceiling.

**Migration/rollback:** No migration is required and none is possible to get wrong. The settings file
is created on first save; until then — and on every workspace that never gets one —

`5-system/workspace-settings.json` is inert and can be deleted or left in place. Reverting mid-flight
is safe at any point because no other subsystem reads the file.

## v73.0 — 2026-08-13 — Refactor (sync): single sync path for the 45s tick and the manual refresh button

**Why:** The app had grown three overlapping refresh mechanisms that shared no code. `SyncTick.tsx` ran a
45s change-set probe and broadcast only the families it found changed. `AuthGate.tsx` ran a *second*,
independent 45s interval that called `refreshPermissions()` and broadcast nothing. The AdminToolbar refresh
button called `refreshPermissions()` and then broadcast a blind `"manual"` refresh with no probe at all,
which meant a manual press could not update the probe baseline and could not report what had actually
changed. Three timers-and-handlers with three separate in-flight guards (two of them absent) is one bug away
from a manual click and a tick probing concurrently and racing on the shared `previousProbes` map. The owner
asked for one sync function with two triggers. Rejected: keeping the permissions interval separate on the
grounds that permissions are not one of §4.2's data families — true, but it does not justify a second timer,
because the single run can simply always re-sync permissions and only conditionally probe. Also rejected: a
module-level registration singleton holding the "current" workspace/month/permissions callback, which would
have created a second month-selection authority able to drift from `useGlobalMonth()` after a month switch.

**What changed:** New module `src/data/workspace/workspaceSync.ts` owns the one sync path:
`runSync({ manual, directoryHandle, monthFolderName, refreshPermissions })`. It re-syncs permissions, probes
the selected month (skipped when no month is selected), and broadcasts. The probe helpers, the `Probe` type,
the `previousProbes` baseline map, `SYNC_TICK_INTERVAL_MS` and `FOCUS_COALESCE_WINDOW_MS` all moved here out
of `SyncTick.tsx`; `runSyncTick` is gone, replaced by `runSync`. Arguments are passed explicitly rather than
registered, so both callers derive them from the same hooks and no second month authority exists.

Automatic and manual differ in exactly one way. An automatic run is delta-only: it broadcasts
`{ source: "periodic", changed }` and, on an empty change set, broadcasts nothing at all (§4.2's
"unchanged ⇒ zero invalidation" invariant is preserved). A manual run still probes — so the baseline stays
correct and the reported change set is accurate — but always broadcasts `"manual"`, so `directoryScan.ts`'s
full cache purge and `queryRefreshBridge.ts`'s full query invalidation still fire even when the probe found
nothing. A manual run now also bumps the workspace epoch unconditionally; previously the toolbar bumped it
never, which left the session-scoped derive memo free to answer a "hard refresh" from cache.

Concurrency is one module-level guard shared by both triggers. An automatic run arriving while another run is
open is dropped and reports `ran: false` (the next tick catches up, as before). A manual run waits for the
open run to settle and then performs its own forced pass, so a click can never be absorbed into someone
else's delta-only run, and two probes can never interleave on `previousProbes`. The `document.hidden` skip
and the visibilitychange coalescing stay on the automatic path only; the coalescing window is now measured
against the last run of *either* trigger, so a manual press suppresses an immediately following focus run.

The baseline hazard is handled explicitly and documented in the module header: the first probe for a
(workspace, month) establishes its baseline silently and reports an empty change set, and a manual run can be
that first probe. That is safe only because the manual path broadcasts unconditionally — subscribers are told
to discard everything regardless — so a silently-established baseline can never hide state. Three tests pin
this down, including one that has a manual and an automatic run race on the same pending delta.

`SyncTick.tsx` is now only the timer. It gained an `enabled` prop (AuthGate passes `session.mode !== "demo"`,
the gating the deleted AuthGate interval used to do itself) and now installs the interval as soon as the
workspace is ready, month or no month — permission propagation must not depend on a month being selected.
AuthGate's `AUTO_REFRESH_INTERVAL_MS` effect and its `refreshPermissions` destructure are deleted.
`AdminToolbar.tsx` keeps its exact UX (spinner, disabled while running, green `is-success` for 2000 ms, red
`is-failed`, re-entry guard) and now derives that state from `runSync`'s `ok`.

Test coverage is written against the hazards this area has historically shipped: manual broadcasts on an
empty change set, automatic does not; the shared in-flight guard under automatic+manual and manual+manual
overlap; manual runs while `document.hidden`; the first-probe baseline surviving a manual run; both paths
invoking `refreshPermissions`; and the toolbar's running/success/failed/idle transitions. Stale comments
claiming a 3- or 5-minute cadence were corrected in `AdminToolbar.tsx`, `directoryScan.ts` (both sites),
`useMonthLoad.ts`, `NotificationBanner.tsx`, `queryClient.ts`, `dataRefreshSignal.ts` and `CLAUDE.md`.

## v71.1 — 2026-08-13 — Fix (permissions): matrix controls an admin could toggle but that could never take effect

were making the User Management matrices lie about what they could do.

   `tabCatalog.ts` cap what any matrix row can grant (`usePermissions.canAccessTab` checks the
   ceiling first). A cell outside its tab's ceiling was still rendered as three clickable
   buttons — the admin sets it, it saves to disk, and the role still cannot open the page.
2. **The feature cascade inherits that.** A feature is refused whenever its parent page is not

## v71.0 — 2026-08-13 — Add (auth): default passwords, admin username sign-in, and an admin-only passcode editor

**Why:** Owner request, four parts: every user should ship with the password `123`; `admin` /
`admin` should work from the ordinary sign-in form; Settings should be able to turn that
username sign-in on and off (leaving the hidden shortcut as the only way in when off); and the

Parts 3 and 4 are what forced a design decision, because the bootstrap admin passcode was a
**compile-time constant** (`BOOTSTRAP_ADMIN_PASSWORD_HASH` in `authConfig.ts`) — rotating it
meant editing source and rebuilding, which is not "edit it in the app". Two storage options
were considered:

- **`localStorage`** (what the label overrides do). Rejected: the passcode would be trapped in
  one browser profile on one machine, so an admin who changed it would find the *default* still
  in force on the next PC — the failure mode is silently keeping a guessable passcode alive.

  block rides that existing path with no new file, no new lock, and no new sync timing.

**Security note (deliberate, recorded):** `admin`/`admin` and `123` are guess-in-one-attempt
credentials, and the bundled admin hash is offline-crackable by anyone holding the build. This
is an accepted owner decision for a client-only app whose security model is already advisory
(`docs/architecture/SECURITY_MODEL.md` §1), not an oversight — that doc's §2 now states the
defaults explicitly and says to change them before the app touches real data.

**What changed:**

1. **Default passwords are `123`.** `DEFAULT_USER_PASSWORD_HASH` in `userManagement.ts` is a
   fresh Argon2id hash of `123`, so all six seeded users (`createDefaultManagedUsers`) sign in
   with it. Existing users on disk are untouched — this is the seed, not a migration.
2. **Default admin passcode is `admin`.** `BOOTSTRAP_ADMIN_PASSWORD_HASH` re-generated for
   `admin`, and it is now only the *fallback*: `resolveAdminPasswordHash()` prefers the
   workspace's own `adminAccount.passwordHash` whenever one has been set.
3. **`admin` signs in from the normal form.** `loginAsEmployee` checks the reserved username
   **before** the managed-user lookup, so `admin` always resolves to the bootstrap superuser
   rather than to a same-named managed user, and verifies against the resolved admin hash. A
   wrong passcode there counts toward the same 3-attempt / 30-second lockout as any other
   failure (the duplicated attempt-counting in the two existing failure branches was folded
   into one `registerFailedAttempt()`). The sign-in form also stays rendered when a workspace
   has zero active users but admin-username sign-in is on — otherwise an empty workspace had no
   way in except the shortcut.
4. **New workspace-backed `adminAccount` state.** `UserManagementState` gains
   `adminAccount: { passwordHash, allowUsernameLogin, updatedAt, updatedBy }`, with
   `readAdminAccount()` / `resolveAdminPasswordHash()` / `updateAdminAccount()` accessors.
   `normalizeUserManagementState` fills it from defaults when absent, and its input type

   change applied to this session only rather than implying it was saved.

**Migration/rollback:** `adminAccount` is an **optional, additive** field on
`UsersPermissionsData`. Older workspaces have no such block and read back as the shipped
defaults (`passwordHash: null` → bundled constant, `allowUsernameLogin: true`); older builds

backward-compatible in both directions and needs no migration step. Rollback is a plain revert:
a workspace written by this version keeps a stale `adminAccount` block that the reverted code
ignores, falling back to the compile-time passcode.

## v70.10 — 2026-08-13 — Fix (population/sampling): guard foreign sub-tab events, thread stage mappings into replacement appends, and report true Excel row numbers

**Why:** Three independent defects surfaced by a full-codebase audit, each confirmed against the code and
each previously uncovered by the suite:

1. `Sidebar.tsx` dispatches the generic `pop-set-subtab` event on `window` for *every* tab's sub-tab clicks,
   and `App.tsx`'s tab-mount LRU keeps up to 3 tabs mounted (hidden, not unmounted). Population's listener
   therefore stayed live while another tab was active and accepted foreign ids: clicking Reports' `kpi`
   sub-tab set Population's `activeSubTab` to `"kpi"`, a value outside its own `SubTab` union. The render
   then hides Browse *and* returns `null` for Process simultaneously, so the tab goes blank. Its three
   sibling tabs (EmployeeWorkspace, Reports, UserManagement) all already guard against a known set;
   Population was the only one that did not.
2. `appendSampleRow` classified a replacement row with `getStageKey(row.stage)` and no mappings, silently
   falling back to `DEFAULT_STAGE_MAPPINGS` — while the draw path and `getReplacementCandidates` both thread
   the workspace's configured aliases. In a workspace using custom stage aliases the replacement row hit the
   `if (stageKey === "unknown") return allocations;` guard and was dropped from `stageAllocations`. The row
   still landed in `rows[]` and distributed and answered normally, so nothing failed loudly, but
   `actualDrawn` / `certScanDrawn` / `nonCertScanDrawn` permanently under-counted by one per replacement —
   and those fields feed `sampleReport.ts`, `executiveKpiProfiles.ts` and the executive deck.
3. `worksheetToSourceRows` passed `blankrows: false` to `sheet_to_json`, which drops fully blank rows before
   the mapping runs, then derived `sourceRowNumber` as `index + 1` over that compacted array. Every interior
   blank row shifted the reported number of everything below it. That number is user-facing: it is rendered
   as «رقم الصف المصدر» in the dropped-rows diagnostic, i.e. the pointer a user follows back into their
   spreadsheet to fix an invalid or duplicate X-ray ID. Blank spacer rows are common in hand-maintained
   agency exports, so users were being sent to the wrong line — or a blank one.

**What changed:**

- **Population sub-tab guard** — added `KNOWN_POPULATION_SUB_TABS` and a membership check in the
  `pop-set-subtab` handler, mirroring the pattern already proven in the three sibling tabs. The legacy event
  is deliberately left in place; migrating to `sidebar-subtab-changed` is a separate behavioural change
  (both `Sidebar.tsx` and `WorkspaceGate.tsx` still fire the legacy event).
- **Stage mappings threading** — `appendSampleRow` and `incrementStageAllocations` take an optional
  `stageMappings`; `executeReplacement` accepts and forwards it. `XrayReferrals.tsx` passes the mappings it
  already holds in state. `approveReferral.ts` resolves them via `loadPopulationConfig`, best-effort: a
  config-load failure falls back to `undefined` (today's behaviour) rather than failing an otherwise valid
  approval. Omitting the parameter preserves current behaviour at every other call site.
- **True Excel row numbers** — `blankrows: true`, so array position tracks the worksheet row before
  anything is dropped. The existing `isNonEmptyRow` filter still discards the now-visible blank rows, after
  the index has been captured, so header derivation, `validColumnIndexes` and the double filter all behave
  identically. Clean sheets produce byte-identical output.

Deliberately **not** changed: `incrementStageAllocations`'s new-entry branch still labels the bucket from
`row.stage`, and no `SAMPLING_ALGORITHM_VERSION` bump — this fixes a derived counter on future writes only,
invalidating no historical draw.
