## v147.0 — 2026-09-29 — Fix (storage): sealed answer segments are no longer opened on every read, and one that grows is never missed

(final; supersedes the one above)

**Why:** `readSegmentTails` opened every listed segment on every read, so cost grew with the month's segment count. Skipping sealed segments is only safe if a sealed segment cannot grow, but a stable answer chain can be appended below its head (second tab with a stale memo, a thrown or lagging discovery listing).
**What changed:** (1) reader: skip `getFile()` for a name with a known offset that an earlier read confirmed sealed (higher-seq chain sibling listed), carrying its offset forward; chains are anchored on their seq-0 root. (2) writer: a stable writer never appends below the head of its chain as a successful listing (`listedSegmentNames`, from the answers read cache) showed it. (3) backstop: confirmations expire after 60 s and are dropped when the probe reports `answers` changed, on manual refresh, and after a backup restore that merged `answers.events` (which also clears the answers read cache).
**Before:**
```ts
reads[index] = await readListedEntry(dir, entry, ...); // every listed segment, every read
```
**After:**
```ts
if (skipped.has(entry.name)) return; // confirmed sealed + known offset + higher sibling listed + confirmation fresh
```
Migration / rollback: no on-disk format change (confirmations are in memory only); revert the commits to roll back.

## Hardening commit ("Fix (storage): a pre-lock listing hint never makes a segment's absence trusted")
The `listedSegmentNames` hint now raises only `seq` and `highestReliableSeq`; `listedHighestSeq` (which licenses trusting a NotFound as absent) still comes only from an in-lock successful listing.
