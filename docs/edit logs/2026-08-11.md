## v68.0 — 2026-08-11 — Fix (branding): rasterize PWA manifest icons to PNG, Chrome rejects SVG manifest icons

**Why:** The three PWA manifest icons were declared as `image/svg+xml` data URIs, composed at runtime by `composeIconUri`. On a properly served `http://localhost:5173` origin, Chrome DevTools -> Application -> Manifest reported every one of them as `failed to load` and flagged the missing square-icon requirement — Chrome's manifest icon pipeline does not accept SVG, only raster formats. An earlier verification pass that used `new Image()` in page context to confirm the SVGs "load" was a false pass: that only proves the page renderer can draw an SVG, never that Chrome's separate manifest icon decoder accepts it.

**What changed:** `icon192`, `icon512`, and `icon512Maskable` in `src/branding/appIcons.ts` are now committed PNG data URIs (rasterized via a browser `<canvas>` from the same navy-tile + shield composition `composeIconUri` used to build at runtime, then color-quantized to 12 levels per RGB channel to keep the bundle under budget — see the module comment for the full regeneration recipe) instead of runtime-composed SVG. `composeIconUri` and the `shieldRaw` import for the full-detail mark were removed as dead code once nothing composes them at runtime anymore; `composeIconUri` is kept only for `faviconSvg`, which stays SVG since `<link rel="icon">` in `index.html` is a normal HTML favicon (not a manifest icon) and every browser renders SVG there fine. `src/branding/appManifest.ts`'s `AppManifestIcon.type` and all three `icons[]` entries changed from `"image/svg+xml"` to `"image/png"`. `src/branding/appManifest.test.ts`'s icon assertions were rewritten to check the `data:image/png;base64,` prefix, `type === "image/png"`, and — critically — decode each committed PNG's real pixel width/height from its IHDR chunk and assert it matches the declared `sizes`, replacing an SVG-markup-decoding check that would not have caught a mis-sized raster icon.

**Migration/rollback:** No stored data format changed — this is client-bundle-only. Rollback is a plain revert of the three touched files; no on-disk workspace data is affected.

## v67.2 — 2026-08-11 — Fix (branding): skip PWA manifest injection on file:// origin

**Why:** Chrome DevTools on a double-clicked `dist/index.html` (`file://` origin) reported "Page is not served from a secure origin" plus three icon-load failures for the PWA manifest. PWA installation is impossible from `file://` (Chrome requires HTTPS/localhost), and each `file:` URL is its own unique opaque origin, so the manifest's `data:` icons can never load there either — the identical icons load fine on a served origin. Injecting the manifest on `file://` therefore produced only console noise and misleading DevTools warnings, never a working install prompt.

**What changed:** `registerAppManifest()` now returns before building/injecting the manifest when `isFileOrigin()` (the existing shared helper from `src/data/workspace/originDetection.ts`) reports a `file://` origin. Behavior on any served origin is unchanged. Also fixed a stale doc comment above the function that claimed the browser "ignores the manifest entirely" on `file://` — it no longer does since we skip injection ourselves. Updated `docs/product/HOSTING_FOR_INSTALL.md` to state plainly that installation can never be offered on `file://` and that the app deliberately doesn't inject the manifest link there.

```ts
export function registerAppManifest(): void {
  try {
    // Installation requires a secure origin (HTTPS or localhost); `file://`
    // is never one, so Chrome refuses to install regardless of what we
    // inject. Worse, each `file:` URL is its own unique opaque origin, so
    // the manifest's `data:` URI icons can never be fetched from it even for
    // display purposes. Injecting the manifest here would produce nothing
    // but console noise and misleading DevTools warnings ("Page is not
    // served from a secure origin", icon load failures) with no possible
    // benefit — so skip it outright rather than let the browser discover
    // that on its own.
    if (isFileOrigin()) {
      return;
    }
    const manifest = buildAppManifest(window.location);
```
