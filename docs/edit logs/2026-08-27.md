## v126.2 — 2026-08-27 — Fix (executive-report/deck3): correct horizontal centering that a prior fix (v125.4) got wrong

**Why:** Owner reported (with a screenshot) that at normal 100% browser
zoom, in the plain scrolling view (not fullscreen), the deck was "out of
the screen" — clipped on one edge with a horizontal scrollbar. v125.4 had
already replaced an earlier `margin:0 auto` with `right:50%;margin-right:
-960px`, verified centered at the time via `getBoundingClientRect` at
several viewport widths. The owner's real window (1357px wide) reproduced
it; a console snippet run on their live page nailed the cause precisely:
`slideLeft:-407, slideRight:667` (should have spanned roughly `[16,1090]`
for their measured `viewerClientWidth:1342`) — the slide was ~420px off,
not a rounding error.

Root cause: `.slide.v3` is `position:relative` in a `dir="rtl"` document.
CSS box-model resolution for a normal-flow block (this governs
`position:relative` boxes too, independent of any `top/right/bottom/left`
offset) treats `width` + `margin-left` + `margin-right` as "over-constrained"
whenever all three are definite (non-`auto`) values — and the moment
`margin-right` gets an explicit value, the *unset* `margin-left` still
counts as a definite `0`, not `auto`. Per spec, an RTL containing block
resolves this by keeping the specified `margin-right` and silently
recomputing `margin-left` to whatever satisfies the box-model equation —
here, `containerWidth - 1920 - marginRight`, not the `0` the CSS visually
implies. That recomputed static position is what the `right:50%` relative
offset then shifts *from* — two mechanisms stacking in a way that doesn't
resolve to true centering, at a magnitude that depends on `direction`,
window width, and how the two interact, which is exactly why it can look
correct at some viewport sizes (including the ones tested for v125.4) and
badly wrong at others. `margin:0 auto` (the pre-v125.4 attempt) most likely
tripped a related variant of the same class of box-model interaction, not
a genuinely different bug.

**What changed:** Replaced the CSS-only centering trick with a measured
pixel correction. `DECK_V3_SCALE_SCRIPT` (`index.ts`) now also sets a new
`--v3-tx` custom property: after applying the computed `--v3-scale`, it
reads the slide's actual rendered `getBoundingClientRect().left` (whatever
the browser's box-model resolution produced, correct or not) and the
viewer's target content-left position, and sets `--v3-tx` to the exact
pixel delta between them. `.slide.v3` centers via
`transform:translateX(var(--v3-tx,0px)) scale(var(--v3-scale))` with
`transform-origin:top left` and plain `margin:0` — `transform` is a
paint-time-only operation with no box-model/direction ambiguity, so this
is correct regardless of *why* the browser placed the static box where it
did. Fullscreen mode is untouched — it already centers via its own
`.deck-viewer-v3` flexbox layout (`align-items:center;justify-content:
center`), which doesn't have this failure mode; its override rule now just
drops `translateX` entirely (previously reset a `right:auto` that no
longer exists on the base rule either).

## v126.1 — 2026-08-27 — Fix (executive-report/deck3): preserve background colors when printing/exporting to PDF

**Why:** Owner reported "when exporting the report it loses its colors and
shapes." deck3's print stylesheet (`@media print` in `theme.ts`) never set
`print-color-adjust`, and Chromium strips background colors/images on print
by default to save ink — so every colored element (navy cover/divider
backgrounds, gold/blue/green tone bars, panel tints, bar-chart fills,
dashed reference lines drawn via `border-color`) printed as plain white,
leaving only text. `deck2/theme.ts` already works around this, but only on
a hand-picked list of elements (`.v2-bar-cell`, `.v2-prop-seg`, cover
mesh, etc.) — deck3's from-scratch rebuild never carried that forward at
all, so nothing was covered.

**What changed:** Added one blanket rule to deck3's `@media print` block —
`*{-webkit-print-color-adjust:exact!important;print-color-adjust:exact!important;color-adjust:exact!important;}`
— instead of deck2's per-element approach, since deck3 has many more
colored surfaces (chart bars, tone chips, tinted panels) than deck2's
narrow list and a blanket rule can't miss one.

## v126.0 — 2026-08-27 — Add (xray-referrals): معلقة export/correction re-import/bulk-reopen

**Why:** In صور الأشعة المحالة, an item goes «معلقة» (on-hold/pending) when a
reviewer submits «هل يوجد صورة» = «لا» — `isNoImageSubmission` in
`answers/noImageAnswer.ts`, a UI-derived label, not a stored status
(`ItemAnswerStatus` is only `"draft" | "submitted"`). The template makes
every other answer field optional the moment that happens, so there is
nothing wrong with the ANSWER for these items — the reviewer correctly
reported "no image" and stopped. Investigation of `PreparedPopulationRow`
and the default template confirmed the "missing/wrong information" the
owner described is the underlying POPULATION row's identifying/logistics
data (port, dates, declaration/chassis numbers, movement type) — what the
reviewer actually needed to locate the physical x-ray. That is the design
decision this whole feature is built on: corrections target population
fields, not answer fields. The template-field-routing escape hatch the task
brief allowed for was not needed once that was confirmed, since a معلقة
item's answer has nothing else worth correcting by construction.

A second, code-level finding drove most of the write-side design: a
population-field edit alone is invisible to the reviewer, because
`foldDistributionEvents` (`distribution/distributionDerivation.ts`) embeds
`toEmployeeMirrorRowStub(row)` from **`sample.master.json`** at fold time,
not from `population.final.json` — so `distribution.current.json` and every
employee mirror keep serving the OLD row forever unless `sample.master.json`
is patched too. Worse, the distribution cache's own staleness check
(`sampleRowsFingerprint`, v4) is an id-set/order fingerprint (djb2 of the
joined `xrayImageId`s), not a content hash — so a same-id-set field edit
passes the cache-validity check and the fold is silently skipped. Fixed by
explicitly invalidating (deleting) the cache after a sample-row patch
(`invalidateDistributionCacheForFieldEdit`) rather than teaching the
fingerprint about content.

## v125.4 — 2026-08-27 — Fix (executive-report/deck3): center the 1920px slide canvas correctly under RTL when it overflows the viewer

**Why:** Owner reported deck3 "opens correctly but looks visually wrong"
compared to the design handoff. Comparing a live render (via the dev
preview fixture) against the handoff's own `.dc.html` side by side in the
browser pane showed every slide badly mispositioned — titles clipped, whole
sections pushed off the left edge. Measuring `getBoundingClientRect()` in
the page traced it to `.slide.v3{ width:1920px; margin:0 auto; }`: the
handoff's 1920×1080 canvas is wider than the on-screen viewer on nearly
every real display once the sidebar and padding are subtracted, and CSS's
auto-margin resolution for an over-wide box in a `dir="rtl"` document is not
symmetric — Chrome resolved `margin-left`/`margin-right` to `-953px`/`0px`
(confirmed with a scratch `<div>` in the live page), not the `-476.5px`
split even split naive centering assumes, so the whole box (and the scaled
transform anchored to its own now-off-center midpoint) rendered shoved off
the left edge. This reproduces on any viewport narrower than ~2172px
(1920 canvas + 236px sidebar + 32px padding), i.e. effectively always —
plausibly the single cause of the reported mismatch, since it breaks every
slide identically. Verified the fix by re-rendering and measuring the same
box: with `right:50%; margin-right:-960px` its left/right edges landed
exactly on the viewer's content-box edges (`testLeft`/`testRight` matched
`wrapLeft`/`wrapRight` to sub-pixel precision) in both the normal stacked
view and after re-deriving the equivalent fullscreen-mode override.

Spot-checked ~10 other slides (cover, contents, glossary, risk levels, KPI
band, section divider, port-distribution table, per-port bar chart,
grouped bar chart) against the handoff side by side after the fix; colors,
type sizes, table classes, and the pure-CSS bar-chart construction already
matched the handoff exactly (theme.ts/slideKit.ts/chartKit.ts were already a
careful pixel-level rebuild — see the 2026-08-26 entries) — no other
concrete mismatch was found.

**What changed:** `.slide.v3`'s horizontal centering no longer uses
`margin:0 auto` (over-constrained + direction-dependent, breaks whenever the
1920px canvas doesn't fit). It now uses the RTL-correct equivalent of the
classic "wider than viewport" centering trick: `right:50%;
margin-right:-960px` on the `position:relative` box. The fullscreen-mode
override (`body.deck-fullscreen .slide.v3.deck-slide-active`), which relies
on its own flex-centering parent, now explicitly resets `right:auto` so the
base rule's offset doesn't double up with that flex centering.
