## v126.10 — 2026-08-27 — Fix: close PII-leak vector, stuck-import-button regression, and writeText close-vs-abort correctness from independent validation

**Why:** An independent adversarial validator (a fresh agent with no
involvement in implementing v126.9's fixes, tasked specifically with trying
to disprove each one) reviewed the four fixes above and found two of them
incomplete or newly regressive, plus researched a real correctness question
the writeText fix had left unresolved:
1. The demo debug PII fix (v126.9) stripped `username`/`role`/`stack` but
   its own docblock's claim that no other field "carries free text that
   names a person" was false — `message` (and, defensively, `context`/
   `action`) can embed a full per-user filename (e.g. `"Safe-write staging
   failed for ahmad.ali.answers.json."`) via raw error messages thrown
   elsewhere in the storage layer (`answerStorage.ts`'s `onExhausted`,
   `safeWrite.ts`'s own thrown messages, `sampleMirrorStorage.ts`,
   `errorLogStorage.ts`) — so a real username could still leak through the
   export.
2. The v126.8 generation-token fix for the pending-corrections import
   worker introduced a real regression: a worker that throws at module
   load, or is silently killed/never responds, left `importState` stuck at
   `"parsing"` forever — the import button permanently disabled, no visible
   error, no recovery short of unmounting the component. There was no
   `worker.onerror` handler anywhere. Separately, the 20,000-row import cap
   added in v126.8 ran *after* the full sheet had already been parsed into
   per-row records (defeating its own "fail fast" purpose), and counted
   only non-blank rows, so a sheet padded with blank rows could dodge the
   cap while still forcing the full parse.
3. `writeText()`'s v126.9 fix (matching 3 sibling writers' `close()`-in-
   catch pattern) was questioned because `writeText`, unlike those
   siblings, also commits LIVE business files directly — and a throw from
   that code path propagates out of `safeWriteJson` with no rollback.
   Investigated empirically rather than assumed either way: `close()` on a
   stream whose `write()` has already thrown is, per the WHATWG Streams
   spec (confirmed against the runtime's own `WritableStream`), inert —
   `WritableStreamClose` short-circuits on an already-errored stream, so
   the v126.9 fix could not actually have committed a truncated file for a
   failure raised by `write()` itself. But `abort()` is still the correct
   call: that safety only holds for failures that leave the stream in that
   specific state, and this codebase already hit the general version of
   this bug once before (`compressedEnvelope.ts`, a head-only file getting
   committed) and fixed it with `abort()`.

**What changed:**
- `demoDebugReport.ts`: added `redactUserFilenames()`, matching
  `\S+\.(answers|samples|errors|activity|actions)(?:\.\d{4})?\.json` and
  replacing the identifying prefix with `[user]` while preserving which
  file type failed (e.g. `"Safe-write staging failed for
  ahmad.ali.answers.json."` → `"...for [user].answers.json."`). Applied to
  `message`, `context`, and `action` before they reach the report. Docblock
  rewritten to state the actual guarantee instead of the disproven one.
- `PendingCorrections.tsx`: added `worker.onerror` alongside the existing
  `onmessage`, wired to the same generation-token guard; on a worker-level
  error it nulls `workerRef.current` (a worker that just threw is not
  assumed reusable — the next selection builds a fresh instance), logs via
  `logError`, and transitions `importState` to the same `"error"` phase
  already used for worker-reported failures, so the button re-enables and
  the failure is visible instead of silent.
- `pendingCorrectionsImportWorker.ts`: moved the `MAX_IMPORT_ROWS` check to
  immediately after the header row is sliced off the array-of-arrays —
  before the per-row `Record<string,string>` construction loop — and
  switched the counted quantity from post-filter non-blank row count to the
  raw post-header row count, an O(1) read that also correctly rejects a
  blank-padded pathological sheet.
- `safeWrite.ts`: replaced `writeText`'s `close()`-in-catch with
  `discardWritable(writable, error)`, a new helper that probes for an
  `abort` method, calls it best-effort (never masking the original error),
  and — deliberately — does **not** fall back to `close()` when `abort` is
  absent, since committing is the one thing this path must not do. A new
  regression test seeds a good live file, makes only the live-commit
  `write()` throw, and asserts the commit algorithm never runs and the file
  is byte-identical afterward; reverting to `close()` makes that test fail
  by truncating the file to empty, proving the fix is load-bearing rather
  than cosmetic. The 3 sibling writers (`streamToFile`, `copyFileBytes`,
  `copyFileBytesVerified`) share the same `close()`-in-catch shape and were
  deliberately left untouched — their multi-statement try blocks make a
  still-writable-stream throw more plausible there too, but their targets
  are `.bak`/`.tmp`/backup destinations rather than live files, so the
  exposure is lower; flagged as a candidate follow-up, not fixed here.

## v126.8 — 2026-08-27 — Fix (ew/pending-corrections): worker request race, worker leak, bulk-reopen re-entrancy, import row cap

**Why:** A reliability audit of the معلقة (pending) corrections import/reopen
flow in `PendingCorrections.tsx` traced three races and a missing ceiling,
each confirmed independently twice: (1) the single lazily-created `Worker`'s
`onmessage` is reassigned on every file selection with no request id, so a
second file picked before the first's async parse (it yields at `await
file.arrayBuffer()`) landed could have its response arrive out of order and
get applied as if it were the newer selection's preview; (2) the worker was
never `.terminate()`'d — no cleanup effect existed at all — leaking a worker

## v126.2 — 2026-08-27 — Fix (executive-report/deck3): correct horizontal centering that a prior fix (v125.4) got wrong

**Why:** Owner reported (with a screenshot) that at normal 100% browser
zoom, in the plain scrolling view (not fullscreen), the deck was "out of
the screen" — clipped on one edge with a horizontal scrollbar. v125.4 had
already replaced an earlier `margin:0 auto` with `right:50%;margin-right:
-960px`, verified centered at the time via `getBoundingClientRect` at
several viewport widths. The owner's real window (1357px wide) reproduced
it; a console snippet run on their live page nailed the cause precisely:
`slideLeft:-407, slideRight:667` (should have spanned roughly `[16,1090]`
for their measured `viewerClientWidth:1342`) — the slide was ~420px off,
not a rounding error.

Root cause: `.slide.v3` is `position:relative` in a `dir="rtl"` document.
CSS box-model resolution for a normal-flow block (this governs
`position:relative` boxes too, independent of any `top/right/bottom/left`
offset) treats `width` + `margin-left` + `margin-right` as "over-constrained"
whenever all three are definite (non-`auto`) values — and the moment
`margin-right` gets an explicit value, the *unset* `margin-left` still
counts as a definite `0`, not `auto`. Per spec, an RTL containing block
resolves this by keeping the specified `margin-right` and silently
recomputing `margin-left` to whatever satisfies the box-model equation —
here, `containerWidth - 1920 - marginRight`, not the `0` the CSS visually
implies. That recomputed static position is what the `right:50%` relative
offset then shifts *from* — two mechanisms stacking in a way that doesn't
resolve to true centering, at a magnitude that depends on `direction`,
window width, and how the two interact, which is exactly why it can look
correct at some viewport sizes (including the ones tested for v125.4) and
badly wrong at others. `margin:0 auto` (the pre-v125.4 attempt) most likely
tripped a related variant of the same class of box-model interaction, not
a genuinely different bug.

**What changed:** Replaced the CSS-only centering trick with a measured
pixel correction. `DECK_V3_SCALE_SCRIPT` (`index.ts`) now also sets a new
`--v3-tx` custom property: after applying the computed `--v3-scale`, it
reads the slide's actual rendered `getBoundingClientRect().left` (whatever
the browser's box-model resolution produced, correct or not) and the
viewer's target content-left position, and sets `--v3-tx` to the exact
pixel delta between them. `.slide.v3` centers via
`transform:translateX(var(--v3-tx,0px)) scale(var(--v3-scale))` with
`transform-origin:top left` and plain `margin:0` — `transform` is a
paint-time-only operation with no box-model/direction ambiguity, so this
is correct regardless of *why* the browser placed the static box where it
did. Fullscreen mode is untouched — it already centers via its own
`.deck-viewer-v3` flexbox layout (`align-items:center;justify-content:
center`), which doesn't have this failure mode; its override rule now just
drops `translateX` entirely (previously reset a `right:auto` that no
longer exists on the base rule either).

## v125.4 — 2026-08-27 — Fix (executive-report/deck3): center the 1920px slide canvas correctly under RTL when it overflows the viewer

**Why:** Owner reported deck3 "opens correctly but looks visually wrong"
compared to the design handoff. Comparing a live render (via the dev
preview fixture) against the handoff's own `.dc.html` side by side in the
browser pane showed every slide badly mispositioned — titles clipped, whole
sections pushed off the left edge. Measuring `getBoundingClientRect()` in
the page traced it to `.slide.v3{ width:1920px; margin:0 auto; }`: the
handoff's 1920×1080 canvas is wider than the on-screen viewer on nearly
every real display once the sidebar and padding are subtracted, and CSS's
auto-margin resolution for an over-wide box in a `dir="rtl"` document is not
symmetric — Chrome resolved `margin-left`/`margin-right` to `-953px`/`0px`
(confirmed with a scratch `<div>` in the live page), not the `-476.5px`
split even split naive centering assumes, so the whole box (and the scaled
transform anchored to its own now-off-center midpoint) rendered shoved off
the left edge. This reproduces on any viewport narrower than ~2172px
(1920 canvas + 236px sidebar + 32px padding), i.e. effectively always —
plausibly the single cause of the reported mismatch, since it breaks every
slide identically. Verified the fix by re-rendering and measuring the same
box: with `right:50%; margin-right:-960px` its left/right edges landed
exactly on the viewer's content-box edges (`testLeft`/`testRight` matched
`wrapLeft`/`wrapRight` to sub-pixel precision) in both the normal stacked
view and after re-deriving the equivalent fullscreen-mode override.

Spot-checked ~10 other slides (cover, contents, glossary, risk levels, KPI
band, section divider, port-distribution table, per-port bar chart,
grouped bar chart) against the handoff side by side after the fix; colors,
type sizes, table classes, and the pure-CSS bar-chart construction already
matched the handoff exactly (theme.ts/slideKit.ts/chartKit.ts were already a
careful pixel-level rebuild — see the 2026-08-26 entries) — no other

**What changed:** `.slide.v3`'s horizontal centering no longer uses
