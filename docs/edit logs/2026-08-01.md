### Item 3 — `portAgreement.ts:177` determinism violation

`orderRows`'s final tiebreak used `a.name.localeCompare(b.name, "ar")`, which
can drift with the host's ICU data — contradicting the file's own header
(`:24-25`) promising byte-identical output for the same input. Its sibling
pages (`levelAccuracy.ts:164-166`, `workloadAccuracy.ts:106-109`) already use a
plain codepoint compare for exactly this reason. Replaced with the same
pattern. Only affects tie-order on a full tie (rankability + rate + comparable
count all equal) — never changes which rows appear.

**File:** `src/data/reporting/executive/deck2/section3/portAgreement.ts`

**Before:**
```ts
 * The final tiebreak is the port name, so the order is total and deterministic.
 */

  return [...rows].sort((a, b) => {
    ...
    if (a.l1l2Comparable !== b.l1l2Comparable) return b.l1l2Comparable - a.l1l2Comparable;
```

**After:**
```ts

 * `localeCompare`, whose collation result can drift with the host's ICU
 * data) — the same discipline `levelAccuracy.ts`/`workloadAccuracy.ts` already

```

### Item 2 — sufficiency-gating gap: a secondary rate gated on the wrong (larger) count

`workloadAccuracy.ts`, `levelAccuracy.ts`, `markingImpact.ts` and
`qualityImpact.ts` each compute a *secondary* rate (missed-suspicion rate /
suspicion-detection rate) alongside a primary rate (accuracy), but gated the
secondary rate's suppression on the PRIMARY rate's own (larger) denominator
instead of the secondary rate's OWN (usually much smaller) denominator —
`portAgreement.ts`/`sourceAgreement.ts` already gate every rate on its own
denominator and were used as the reference pattern. Concrete proof case
(named in the audit): `markingImpact.test.ts:271` was a PASSING test
asserting `85.7%` published for a detection rate whose real denominator is
`correctSusp(6) + missedSusp(1) = 7` — `band(7)` is `"insufficient"`
(threshold table: 1-9 insufficient, 10-19 limited, 20+ sufficient), not
rankable, while the gate actually used was the arm's own total (20 images),
which clears the cut.

Fix: each of the 4 files now computes an own-denominator rankability flag
(`missedRankable` / `detectionRankable` / `missedRateRankable`) alongside the
existing primary-rate flag, and every render site (slot 0 table, Ledger table,
Ledger/slot-0 totals row, Briefing pooled figure, Grid matrix) for the
secondary rate now checks the new flag instead of the primary one. The primary
rate's own gating (accuracy against its own `evaluable`/`n` base) is
unchanged. Combined/pooled totals rows across multiple arms/ports now gate the
pooled secondary rate against the POOLED secondary denominator (its own band),
not the pooled primary denominator — matching the existing "pooling can clear
a cut neither arm alone does" discipline already documented for the primary
rate.

## v59.106 — 2026-08-01 — Add (workspace): generalize the refresh signal to all workspace data, not just permissions

Follow-up to v59.105: the user clarified the refresh button/auto-refresh should not be
permissions-only — the concrete complaint was that when one employee's sample gets reassigned to
another (a referral, replacement, or reopen decision), the receiving employee's already-open queue
doesn't pick it up without leaving and re-entering the tab, and they worried the same is true for
posted notifications.

Root cause (same shape as v59.105, different data): `XrayReferrals`, `XrayInspectionResults`,
`useApprovalData` (referral/replacement/reopen approvals), and `NotificationManager` each load their
own workspace data with a `loadData`/`reload` `useCallback` that only re-runs when its own deps

## v59.105 — 2026-08-01 — Fix (auth): permission/role edits never reached an already-open session; add manual + 5-minute auto refresh; fix default employee roster

Reported: editing a role's page/feature permissions (or a user's role) in the User Management tab
did not "take" for an employee who was already logged in elsewhere.

Root cause: the managed-user/permission matrix lives in a single in-memory module variable
(`runtimeUserManagementState` in `userManagement.ts`), hydrated from
`3-user-data/users.permissions.json` exactly once per browser tab — at workspace connect (page
load / directory reconnect). An admin's edit calls `writeUserManagementState`, which persists to
disk AND dispatches a same-window `xray-user-management-change` DOM event — but `window.dispatchEvent`
never crosses tabs/windows/machines, so only the *admin's own* tab ever reacted live (via the
existing `usePermissions`/`AuthGate` listeners, which already correctly force a clean re-login when
a role changes, or a live permission refresh when it doesn't). An employee's separately-open session
had no trigger to ever re-read the disk file again short of a full page reload. A pre-existing
`reloadWorkspace()` could re-sync it, but it also flips `status` to `"checking"`, which
`WorkspaceGate` renders as a full-screen spinner that unmounts the entire app — unusable for a
silent background refresh or a quick manual nudge mid-task.

Fix: added a new `refreshPermissions()` to the workspace context that re-reads *only*
`3-user-data/users.permissions.json` (via the already-cheap `loadWorkspaceFiles`, which per its own
comment only ever reads that one file) and re-syncs it into the in-memory state, without touching
`status`/`loadedFiles` — so it never triggers `WorkspaceGate`'s full-screen remount. Wired it to (1)
a new manual refresh button in `AdminToolbar` (visible to every non-demo session, not just admins,
so an admin can tell an affected employee to click it) and (2) a 5-minute interval in `AuthGate`
that starts when a real (non-demo) session becomes active against a ready workspace. Both paths
funnel through the existing `syncUsersFromDisk` → `writeUserManagementState` → change-event
machinery, so a role change still forces the existing "please log in again" flow, and a
page/feature-permission-only change live-updates the visible tabs without a forced logout.

Separately, `createDefaultManagedUsers()` (the seed roster used only for a brand-new/empty
workspace) had stale usernames and was missing a sixth real employee. Corrected the five existing
usernames to match the real roster and added the missing manager. This only affects a *fresh*
workspace's defaults, not an already-provisioned one — per the user's confirmation, no live
workspace needs a direct data edit here; the roster fix is defaults-only for now.
