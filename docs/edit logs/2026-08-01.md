## v59.120 — 2026-08-01 — Fix (ew/results): silence loadData's refresh reset so the quality-note editor survives the auto-refresh timer

Confirmed finding from the 2026-08-01 audit follow-up review (post `a18c3da6`, scoped to
changes since that commit) — same root cause as the `XrayReferrals.tsx` finding fixed
earlier today, applied to the results/quality-note view. `XrayInspectionResults.tsx`'s
`loadData` was invoked both on mount/month-change AND by `subscribeToDataRefresh` (the
5-minute background timer plus the manual toolbar refresh button), and unconditionally
ran `setExpandedRowKey(null)` + `setQualityNoteError(null)` (and `setLoadState("loading")`,
which unmounts the whole results `DataTable`) before its async work even started.
`QualityNoteEditor` keeps its draft in local `useState(row.answer?.qualityNote ?? "")`
with no autosave, so any background/manual refresh silently collapsed an open row and
destroyed whatever unsaved coaching note a supervisor was mid-typing.

Fix: gave `loadData` an optional `{ silent?: boolean }` param, mirroring the pattern
already used in `XrayReferrals.tsx`. The mount/month-change effect still calls
`loadData()` (silent defaults to false, so month changes and initial load behave exactly
as before). The `subscribeToDataRefresh` effect now calls `loadData({ silent: true })`,
which skips `setLoadState("loading")`/`setExpandedRowKey(null)`/`setQualityNoteError(null)`
and, on a caught error, logs via `logError` and leaves the current state alone instead of
flipping to the error view. Rows/audit logs are still re-fetched and swapped in place;
because `QualityNoteEditor` is keyed by `resultRowKey` (xrayImageId + assignedTo), the
same row's component instance — and its in-progress draft — survives the swap. Added a
regression test asserting the loading placeholder never appears and an unsaved draft
survives a `broadcastDataRefresh()` call while a row is expanded; verified it fails
without the fix (unconditional `setLoadState`/`setExpandedRowKey` reset) and passes with it.

## v59.116 — 2026-08-01 — Fix (user-management): UserManagementTab re-syncs with the shared runtime state instead of silently reverting a concurrent admin's disk change

Confirmed finding from the 2026-08-01 audit follow-up review (post `a18c3da6`, scoped to changes
since that commit). `UserManagementTab` seeded its local `state` once via
`useState(() => readUserManagementState())` and never subscribed to
`subscribeToUserManagementChanges` — unlike `App.tsx`, `usePermissions.ts`, `NotificationManager.tsx`,
and `WorkspaceGate.tsx`, which all do. `refreshPermissions()` (the manual toolbar button, and
AuthGate's 5-minute auto-refresh timer, both usable while this tab is open) updates only the shared
module-level `runtimeUserManagementState` via `applyDiskUsers` → `syncUsersFromDisk` →
`writeUserManagementState(..., true)` — it never touched this component's own `state`. So if a
different admin (same machine or another) had saved changes to `3-user-data/users.permissions.json`
in the meantime, this tab's `state` silently drifted stale relative to disk even though the toolbar
reported the refresh as a success. The next edit made here (`persistState`) spread that stale local
`state` and wrote it wholesale via `syncUserManagementToDisk` — which fully replaces
`data.users`/`data.permissions`/`data.featurePermissions` from the caller's snapshot rather than
merging against the freshly-read disk file (`userSync.ts:65-96` only carries over
`metadata.revision`/`createdAt` bookkeeping) — silently reverting the other admin's concurrent edit
with no conflict indication.

Fix: subscribe to `subscribeToUserManagementChanges` in `UserManagementTab` and reconcile local
`state` to `readUserManagementState()` on every change, mirroring the four other consumers listed
above. Draft-only local state (`identityEdits`, `resetPasswords`, the add-user `form`) lives outside
`UserManagementState` and is keyed by user id, so resyncing `state` here cannot discard an
in-progress, unsaved draft — it only keeps the base user/permission/feature-permission snapshot that
`persistState` spreads from up to date with whatever the runtime module last saw (its own writes
included, harmlessly idempotent).

## v59.115 — 2026-08-01 — Fix (employee-workspace): background data-refresh no longer discards an open, unsaved inspection-form draft

`XrayReferrals.tsx`'s `loadData()` unconditionally called `setLoadState("loading")` +
`setSelEntryId(null)` + `setSelectedIds(new Set())` at its very start. That was fine for a real
month/user change (the only caller until v59.106), but the `subscribeToDataRefresh(loadData)` effect
added in 684e2200 reuses the exact same function for the app-wide refresh signal — AuthGate's
5-minute auto-refresh timer (fires for every non-demo session, including plain employees, no role
check) and the manual toolbar refresh button anyone can click. `setLoadState("loading")` makes the
`{(loadState === "ready" || loadState === "idle") && (...)}` render gate go false, which unmounts the
entire detail-panel block regardless of `SampleDetailPanel`'s `key={entry.xrayImageId}` — and
`InspectionPanel` holds the employee's in-progress, unsaved answer draft only in local `useState`
(`index.tsx:47-54`, seeded from `savedAnswer` which is `null` until the employee actually submits).
So every 5-minute tick, or one click of the refresh button by anyone, silently threw away whatever
an employee had typed into an open inspection form but not yet saved — no warning, no recovery.

Fix: `loadData` now takes an optional `{ silent?: boolean }`. The mount/month-change effect calls it
with no options (unchanged: resets loading state + selection, exactly as before). The data-refresh
subscription now calls `loadData({ silent: true })`: a silent pass skips the loading-state flip and
the selection reset entirely, re-fetches in the background, and swaps `entries`/`allEntries`/
`sampleMaster`/`myQuota`/`answers` in place once it resolves — the open panel, its selected entry,
and the draft sitting in `InspectionPanel`'s local state are never touched. A silent pass that throws
is logged to the error ring buffer (`logError("xrayReferrals:loadData:silentRefresh", err)`) instead
of flipping `loadState` to `"error"`, so a transient background read hiccup can't force-close the
form either.

## v59.105 — 2026-08-01 — Fix (auth): permission/role edits never reached an already-open session; add manual + 5-minute auto refresh; fix default employee roster

Reported: editing a role's page/feature permissions (or a user's role) in the User Management tab
did not "take" for an employee who was already logged in elsewhere.

Root cause: the managed-user/permission matrix lives in a single in-memory module variable
(`runtimeUserManagementState` in `userManagement.ts`), hydrated from
`3-user-data/users.permissions.json` exactly once per browser tab — at workspace connect (page
load / directory reconnect). An admin's edit calls `writeUserManagementState`, which persists to
disk AND dispatches a same-window `xray-user-management-change` DOM event — but `window.dispatchEvent`
never crosses tabs/windows/machines, so only the *admin's own* tab ever reacted live (via the
existing `usePermissions`/`AuthGate` listeners, which already correctly force a clean re-login when
a role changes, or a live permission refresh when it doesn't). An employee's separately-open session
had no trigger to ever re-read the disk file again short of a full page reload. A pre-existing
`reloadWorkspace()` could re-sync it, but it also flips `status` to `"checking"`, which
`WorkspaceGate` renders as a full-screen spinner that unmounts the entire app — unusable for a
silent background refresh or a quick manual nudge mid-task.

Fix: added a new `refreshPermissions()` to the workspace context that re-reads *only*
`3-user-data/users.permissions.json` (via the already-cheap `loadWorkspaceFiles`, which per its own
comment only ever reads that one file) and re-syncs it into the in-memory state, without touching
`status`/`loadedFiles` — so it never triggers `WorkspaceGate`'s full-screen remount. Wired it to (1)
a new manual refresh button in `AdminToolbar` (visible to every non-demo session, not just admins,
so an admin can tell an affected employee to click it) and (2) a 5-minute interval in `AuthGate`
that starts when a real (non-demo) session becomes active against a ready workspace. Both paths
funnel through the existing `syncUsersFromDisk` → `writeUserManagementState` → change-event
machinery, so a role change still forces the existing "please log in again" flow, and a
page/feature-permission-only change live-updates the visible tabs without a forced logout.

Separately, `createDefaultManagedUsers()` (the seed roster used only for a brand-new/empty
workspace) had stale usernames and was missing a sixth real employee. Corrected the five existing
usernames to match the real roster and added the missing manager. This only affects a *fresh*
workspace's defaults, not an already-provisioned one — per the user's confirmation, no live
workspace needs a direct data edit here; the roster fix is defaults-only for now.
