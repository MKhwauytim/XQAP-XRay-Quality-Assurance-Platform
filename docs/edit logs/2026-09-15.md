# Edit Log — 2026-09-15

## v138.0 — 2026-09-15 — Fix (storage): bound the nested retry budget and stop the damaged-file trap behind the XQ-IO-036 failures

**Why:** An admin error-log export covering 2026-09-10..14 (25 entries, `Z:\` SMB share, ~4 concurrent `file://` clients) carried one failure family: `InvalidStateError` / **XQ-IO-036**, surfacing as `casLoop:exhausted(...)` for `answers:answer-save`, `answers:requestsFile`, `approvals:decisionEvent`, `distribution:events` and `feedback:threadsIndex`, plus `storage:bak-recovery` on five files. Users reported four things: an answer save taking ~4 minutes ("it wasn't this slow before"), a yellow damaged-file banner, طلب استبدال failing **always** rather than sometimes, feedback tickets taking forever, and a rising error count.

Four root causes were confirmed in code (each reproduced by a test that fails against the pre-fix tree):

1. **Nested retry budgets multiply.** `VERIFY_READBACK_RETRY_DELAYS_MS` is ~11.03 s and runs twice per `safeWriteJson`; `ANSWER_SAVE_MAX_RETRIES` is 14. 14 x 2 x 11.03 s is ~308 s — the four-minute save. Every layer's budget was individually defensible; nothing owned the product. `SNAPSHOT_STALE_RETRY_DELAYS_MS` already documents this exact principle ("an inner ladder multiplies against that ... Patience at the wrong layer makes contention worse, not better") and is deliberately capped at ~630 ms because of it; the 11 s ladder sits in the same nest, 17x longer.
2. **A damaged live file was an absorbing state.** `snapshotToBak` is gated on `hasCurrent`, so while the live file is unreadable the `.bak` is frozen; `rollbackFromBak` then restores that frozen `.bak` on a commit-verify mismatch, erasing the append and restoring the precondition. The CAS loop re-reads the same revision and fails identically, forever — which is why two employees' `*.requests.json` stayed in bak-recovery across the whole window.
3. **A durable append was reported as a failure.** `appendDistributionEvents` commits the immutable event files first, then updates `distribution.log.json` — a rebuildable compatibility projection. A projection CAS exhaustion returned `{ ok: false }`, so `executeReplacement` early-returned XQ-DIST-005 and skipped `refreshDistributionCacheAfterWrite`; on retry the fold saw the durable `assigned` event, classified the row `"taken"` and the dead row `"replaced"`, and the freshness guard rejected every retry instantly. The substitution had committed — the user was told it failed and then forbidden from redoing it. That is the deterministic استبدال failure.
4. **Feedback replies inherited the full default ladder** (10 x 200 ms with a delayed verify) nested over `safeWriteJson`'s own ladders.

**Rejected:** simply lowering the retry counts. It would have masked (2) and (3), which are correctness bugs that produce data loss and a permanently unretryable action, not slow ones. Retry tuning alone also cannot fix a deterministic failure. Also rejected: making the 11 s verify-readback ladder globally shorter — it is correct for a standalone month save, and only wrong when nested; a deadline is what distinguishes the two.

**What changed:**

- **New `src/data/storage/operationDeadline.ts`** — one wall-clock budget for one user action (`INTERACTIVE_WRITE_DEADLINE_MS` 30 s, `BULK_WRITE_DEADLINE_MS` 120 s). It never interrupts work in flight and never blocks a first attempt; it only answers "should I sleep and try *again*?", so the worst case is the deadline plus the one attempt already running. Omitting a deadline preserves the previous unbounded behaviour exactly, so call sites adopt it individually.
- **`casLoop`** takes an optional `deadline`: later attempts are gated on it and a spent budget stops the ladder instead of sleeping again and re-arming the same race.
- **`safeWrite.ts`** threads a `deadline` through `SafeWriteJsonOptions` into every read-back ladder (the not-found/verify-readback rungs and the NotReadable/stale-snapshot rungs, 5 sites). Delays are *truncated* to the remaining budget rather than refused, so ladder shape is preserved.
- **`safeWriteJson` rolls back only to a `.bak` it created in this write** (`hasCurrent &&`). When it did not snapshot, the `.bak` belongs to an older write and restoring it is not an undo — it discards the byte-verified `.tmp` and re-arms the trap. The promotion path that handles this correctly was already present and merely unreachable while a stale `.bak` existed; promoting also **repairs** the damaged live file, which is what clears the bak-recovery banner for every other reader.
- **`appendDistributionEvents` treats a failed projection write as a degraded success** (`projectionDegraded: true` on the `ok: true` branch, logged under `distribution:projection-degraded`), re-deriving the returned log from the durable events. A hard failure of the *durable* event write still reports `ok: false`. This lets `executeReplacement` reach its cache refresh, which rebuilds from the events that are already on disk.
- Interactive deadlines wired into the four `answerStorage` CAS sites, `feedback:threadReply`, and `distribution:events`.

**Not fixed here** (reported, out of scope): the error-log write amplification loop (a failed save emits many durable error entries, each rewriting a growing per-user file), the missing `sourceRequestId` idempotency key on the immediate-replace branch, and `readOptionalJson` discarding `recoveredFromBak` so a read-modify-write cannot tell it is building on a `.bak`-served base.

**Migration/rollback:** No on-disk format change; no migration required. `OperationDeadline` is additive and optional everywhere, and `projectionDegraded` is an optional field on an existing success shape, so a rollback is a plain revert with no data implications. Files already sitting in bak-recovery are healed opportunistically by the next successful write to them rather than by a migration pass.

## v137.2 — 2026-09-15 — Refactor (referrals): extract the column-preset writers and the queue shell to get back under the complexity budget

**Why:** `npm run check:complexity` fails on `main`: `Function 'XrayReferrals' has too many lines (1467). Maximum allowed is 1450`. Until now this was masked — GitHub Actions was blocked at the account level (billing), so every run on `main` died in 2-3 seconds before reaching the gate, and the overrun was noted-and-carried in the merge commits for #168 and #169. Actions is healthy again, so the gate now runs and blocks EVERY pull request, not just one.

`9a482a0` hit this same budget before and answered it by extracting a pure helper rather than raising the ceiling — but left only three lines of headroom, so the next few fixes (`7521a9b`, `b30aa6c`) put it straight back over. This follows that precedent and takes a larger bite.

**Rejected:** raising `max-lines-per-function`. It would retire the regression guard at exactly the moment it started doing its job on a component that has already crossed the line twice. Also rejected: extracting `loadData` (the largest block, 248 lines) — it registers boot sources, and CLAUDE.md records that area regressing five times in a row and requires it to be changed test-first and reviewed. Not something to move inside a PR whose purpose is unblocking CI.

**What changed:** Two extractions, both improvements in their own right rather than line-count shuffling.

- **New `XrayReferrals/columnPreset.ts`.** The preset object was built TWICE from the same four fields — in the split-resizer commit and in `onColConfigChange`, ~1000 lines apart — with the `visibleColumns` derivation (`baseColumns` minus `cfg.hidden`) duplicated verbatim. That is the shape CLAUDE.md's "no duplicate state — one place, one name, called everywhere" rule exists to prevent. `buildReferralColumnPreset` is now the single definition, with `persistReferralColumnPreset` and `persistReferralSplitRatio` as the two writers.
- **New `ReferralWorkspaceShell` in `subComponents.tsx`.** The stats strip, the two status notices and the table were inline in the render; they are purely presentational (every value is computed by the caller), so this is the cheapest part of that render to lift and the one that cannot change queue behaviour.

No behaviour change: the same fields are written to the same two stores, in the same order, under the same permission condition, and the shell renders the same elements with the same conditions.

**Result:** 1467 → 1447 lines; `check:complexity` passes.

**Residual risk — stated plainly:** 1447 leaves three lines of headroom, which is exactly the margin that let the budget be re-breached after `9a482a0`. It will very likely recur. The durable fix is a real decomposition of a 1400-line component, and that deserves its own change with its own tests — deliberately NOT smuggled into a PR whose job is to unblock CI. Every remaining candidate block I examined (the `tableEl` IIFE, the trailing dialog group, the column-config hooks) would have meant prop-drilling 20-30 values purely to move the count, which makes the code worse to satisfy a metric. One such hook was written and then backed out for that reason: threading `buildColumns`/`loadLocal`/`buildDefault`/`getVisible` in as callbacks would have added them to the memo dependency arrays, recomputing the column set on every render of a hot table.
