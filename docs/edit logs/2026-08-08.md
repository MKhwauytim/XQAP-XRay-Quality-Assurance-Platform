# Edit Log — 2026-08-08

## v66.0 — 2026-08-08 — Fix (adhoc): route answer + referral/replacement writes to the row's own store

**Why:** v65.0 made ad-hoc imported assignments *visible* to employees but left them **read-only**. Answers and referral/replacement requests still wrote to the globally-selected month, so acting on an ad-hoc row hit `handleReplace`'s fresh-read guard, failed to find the row in the selected month's distribution, and showed the generic "البيانات تغيّرت، حدّث الصفحة" error.

That failed safe — nothing was corrupted — but an employee could see an assignment and do nothing with it, which does not meet the owner's requirement (*"i want to assign ints samples to emploees"*).

**What changed:** routing is now derived from the **row**, not the selected month.

`adhocImportEmployeeView.ts` gains `isAdhocEntry()` and `monthFolderForEntry(entry, selectedMonthFolder)` — the rule lives next to the type that carries the routing key, rather than being re-derived at each call site. `XrayReferrals.tsx` gains a `folderForRow(xrayImageId)` resolver built on the existing `entriesById` map (O(1), no new scan), and four write paths were routed through it:

| Write | Was | Now |
|---|---|---|
| `upsertItemAnswer` | `selMonth` | `folderForRow(xrayImageId)` |
| `loadSampleMaster` + `loadOrDeriveDistributionCurrent` (the pre-write freshness guard) | `selMonth` | `folderForRow(entry.xrayImageId)` |
| `appendReplacementRequest` | `selMonth` | `folderForRow(entry.xrayImageId)` |
| `appendReferralRequest` | `selMonth` | `referralFolder` (see below) |

> **The double-assign guard is preserved, not weakened.** It still uses the authoritative `loadOrDeriveDistributionCurrent` (never the cached `...ForRead`) immediately before a write — it is simply pointed at the store the row actually lives in. Previously it was reading the *wrong* store, which is why it always reported staleness for ad-hoc rows.

**Mixed selections are refused, not silently split.** A referral request is **one record covering many rows**, and a selection can legitimately span the real month and an ad-hoc import since both render in the same table. Splitting it into two records would present to the supervisor as one action while a partial approval left half the rows in limbo. The mixed case now returns an explicit Arabic message asking the user to send each group separately. Refusing an ambiguous action beats guessing at the user's intent when the guess is unrecoverable.

**Both leak directions are pinned by test** (`adhocImportWriteRouting.test.ts`, 6 tests), because both are damaging and in opposite ways:
- an ad-hoc row written into the real month **contaminates a genuine audit trail** with rows from an unrelated population;
- a real row written into an ad-hoc store **silently disappears** from the month it belongs to.

Also pinned: two different imports never share a store; the ad-hoc namespace is structurally incompatible with a real `{month}-{MonthName}-{year}` folder, so collision is impossible rather than merely unlikely; and an entry with no ad-hoc marker falls back to the selected month — the conservative default, since a real row is the only thing that can lack the marker while still being actionable.

**Migration/rollback:** no data format changed and no existing file is read or written differently for a non-ad-hoc row. Rollback is a code revert; ad-hoc rows return to read-only.

**Verification:** all tier-3 gates green.
- `npm run lint` clean · `npm run typecheck` clean

- `check:complexity`, `check:hex-literals`, `check:vendor` clean
- `npm run build` succeeds · `check:bundle-size` **3468.8 kB / 1162.4 kB gzip** (budget 3.6 MB / 1.3 MB)

## v65.0 — 2026-08-08 — Fix (DataTable): flush filtered-rows to parent in layout effect; deck2 R4 slides; ad-hoc Excel import wired into employee views

**Why:** closing the last three open items — a real click-does-nothing race, deck2's missing R4 parity, and the ad-hoc import subsystem the owner deferred to last.

### 1. A real race: clicking a bulk action could silently do nothing

Two bulk-reassignment tests failed intermittently (~1 run in 3) with `Unable to find role="dialog"`. **Two hypotheses were investigated and refuted before the real cause was found**, which is worth recording because both were plausible:

- *Cross-file test pollution.* Ruled out — the file was flaky **in isolation** too (2, then 1, then 0 failures across three consecutive isolated runs).
- *A background silent refresh clearing the selection.* Refuted by reading the code: `loadData`'s `setSelectedIds(new Set())` calls are gated behind `if (!silent)`, so a silent refresh structurally cannot clear it.

**The actual cause:** `DataTable` reported its filtered rows to the parent through a **passive `useEffect`**, which fires one render tick *after* the rows commit to the DOM. So `filteredCount` / `selectableVisibleIds` lagged behind what was already visible on screen. A click landing in that window found a count of `0` — which both **disabled the button** and would have hit `openBulkReassignModal`'s `if (xrayImageIds.length === 0) return;` silent no-op.

**This was hitting real users, not just tests.** Anyone clicking a bulk action immediately after the table rendered got no modal, no error, no feedback — indistinguishable from a broken button. It is plausibly part of what the owner originally reported about bulk assignment.

**Fixed:** `useEffect` → `useLayoutEffect` in `DataTable`, so React flushes the parent's mirrored state synchronously before paint. Also made the three empty-selection early returns **non-silent** — a user click must never be a no-op without feedback.

> **A 5-second `asyncUtilTimeout` had already been configured and did not help.** That was the decisive evidence: the element never appeared rather than appearing late. Raising timeouts further, or weakening the assertions, would have produced a green suite while shipping the race.

Regression tests: one fires a refresh between selection and click (locking in the `if (!silent)` guard), one deliberately reproduces the original race by clicking without waiting for the filtered-count text. Isolated runs: **5/5 clean**, from 2/5 failing.

### 2. deck2 — R4 parity, and a deliberate refusal on R5

New `deck2/section4/`: coverage slides (per-stage and per-port, reusing `model.distributionCoverage`) and accountability slides (per-employee progress, replacements with reasons, reassignments, reusing `model.accountabilityProgress`). Both reuse the existing models verbatim — **no fourth accuracy fold was added**, since three disagreeing folds was a live bug fixed in v63.0.

Where per-port data exceeds the slide, it caps at top-8 by volume and folds the remainder into **one honest summed row** rather than truncating silently.

**R5 was deliberately NOT ported to decks.** A slide is a fixed 630px `overflow:hidden` box; the document's R5 lists up to ~2× the population's row count. There is no honest way to fit that without clipping or turning the deck into the document with slide chrome. The coverage/accountability slides are the deck-appropriate analogue — bounded by employee/bucket *count*, not row count. Documented in `section4/index.ts`.

**Golden-master diff was inspected before accepting `-u`:** every removed line was a page-foot denominator (`08 / 21` → `08 / 24`, numerator unchanged) from three inserted pages. Everything else was pure addition. **No existing figure or accuracy number changed.**

`sideRail()`'s static 4-tab list was deliberately left alone — it renders on every content slide, so a fifth tab would byte-diff dozens of unrelated characterization pins. Section 4 behaves like `cover`/`toc`/`closing`, which are also absent from that list.

### 3. W37 — ad-hoc Excel import, built and actually usable

> Owner: *"i have excel file with different population but i want to assign ints samples to emploees i CANT"* … *"this is advanced stuff leave it for last thing"*

New admin-only tab plus `src/data/adhocImport/`. Uploads an arbitrary workbook, maps it with the **existing** column config (`normalizeRiskRow` + `loadPopulationConfig().mappingTemplates[0]` — no duplicate mapping UI), validates required fields, flags duplicates, allows row exclusion in the existing virtualized `DataTable`, and assigns through the **unmodified** `buildAssignEvent` + `appendDistributionEvents`.

**Isolation from the real pipeline is structural, not conventional:** metadata under `5-system/adhoc-imports/`, rows under `2-samples/adhoc-{importId}/`. That synthetic folder name is regex-incompatible with a real `{month}-{MonthName}-{year}` folder, so it can never collide or appear in the month list. `xrayImageId` is namespaced `ADHOC-{importId}-{original}`, making collision with a real population id structurally impossible.

**Scope held deliberately:** no spreadsheet grid (Univer is multi-MB — disqualified on its face by the bundle budget), no SQL/Power Query/formula engine, **no new dependency**.

**The gap the implementing agent flagged rather than hid — and it was then closed.** Assignments were durable and correctly folded, but `EmployeeWorkspace` resolves `sampleRows` only from the selected month, so employees could not see them. A feature whose assignments are invisible to the assignee does not meet the requirement. New `adhocImportEmployeeView.ts` unions ad-hoc entries into both employee views, marked with an "استيراد يدوي" badge so an imported row is never mistaken for a sampled one — they belong to different populations and different audit stories.

**Cost is bounded:** only the small index is read unconditionally; per-import reads happen only for imports with `assignedRows > 0`. It rides the existing `loadData` (driven by the single 3-minute invalidation authority) — no second refetch trigger.

**Degradation is layered:** each per-import read is individually try/caught, the index read falls back to `[]`, and the caller wraps the whole call — so a corrupt ad-hoc store still leaves the employee's real month rendering.

**Documented boundary:** `useApprovalData` was not extended. Ad-hoc rows cannot currently produce referral/replacement/reopen requests (those write to the selected month). If an employee clicks replace on an ad-hoc row, the existing fresh-read guard correctly fails to find it and shows the pre-existing "البيانات تغيّرت" error rather than corrupting anything. Visibility was the scope; full write-path routing is a follow-up.

**Migration/rollback:** additive. New tab, new storage locations that cannot collide with existing ones, no change to any existing file format. `DataTable`'s effect timing change is behavioural but strictly corrective.

## v64.0 — 2026-08-08 — Add: CertScan match preview + fuzzy port alignment, shortfall reporting, R1/R4/R5 report completion

**Why:** closing the items previously listed as "blocked on the owner". On review, most were not actually blocked — they needed a decision made, or needed the *class* of failure prevented rather than one instance diagnosed.

### 1. CertScan matching — make a 30-vs-30,000 miss impossible to ship silently

**The owner's report:** *"it say there is only 30 certscan sample while if i do the process myself i get more than 30k"* — three orders of magnitude, which then cascaded into a 25% CertScan request drawing 20 and 10, simply because only ~30 CertScan rows existed to sample from.

**Root cause confirmed:** `matchCertScan` grouped CertScan entries by `normalizeCertScanPortName` with **zero fuzzy fallback**. A single port-name spelling divergence between the pasted table and the population silently zeroed that port's entire bucket.

The owner's actual paste is unavailable, so the exact divergence could not be reproduced. Rather than guess at it, the fix targets the failure *class*:

**A pre-commit match preview** (`certScanMatchPreview.ts` + `CertScanMatchPreviewPanel.tsx`), shown between the CertScan grid and the "معالجة المجتمع" button — **before** processing runs. It reports total devices parsed, candidate rows, expected matches and match rate, and a per-port table (population port → aligned paste port → match tier → counts). A warning fires automatically on a <5% match rate, on any port present on only one side, or on any looser-than-exact alignment. **The owner's problem would have been visible in seconds instead of after a full processing run.**

**A deterministic matching ladder** (`alignPortNames` / `buildCertScanPortIndex`): exact → normalized (alef/taa-marbuta/hamza forms, tatweel, Arabic-Indic digits, case-fold) → fuzzy (strips port-type descriptors منفذ/ميناء/جمرك/مطار/جاف, then punctuation). First-match-wins.

> **Nothing is ever silently fuzzy-matched.** Every non-exact alignment is surfaced through `looseTierAlignments` / `portBreakdown[].tier`. A silently-wrong port match would corrupt stratification, which is worse than a visible miss. `matchCertScan` and the preview consume the *same* index, so they cannot disagree about what will match.

**Verified against the real workbook.** Actual port names extracted from `Risk.xlsx` (130,198 rows): `ميناء جده الاسلامي` (70,002), `الربع الخالي` (59,936), `الوديعة`, `جديدة عرعر`, `الحديثة`, `الخفجي`, `الرقعي`, `الدره`, `جسر الملك فهد`, `حالة عمار`, `ميناء نيوم`. Realistic paste variants aligned as expected: hamza/taa-marbuta/alef-maksura spellings at `normalized`, a `منفذ`-prefixed variant at `fuzzy`, and a genuinely unrelated name stayed unmatched on both sides.

**Snippet generation was examined and left alone** — layered candidates plus length gates (digits ≥4, alnum ≥5) already give good recall, and no defect was found. Tightening it would only shrink matches further. Recorded as an observation, not changed on speculation.

### 2. CertScan shortfall — decided, then made visible

The owner was unsure whether a CertScan shortfall backfills from NonCertScan. It does not, and **deliberately still does not.**

> Silently substituting NonCertScan rows for missing CertScan rows would **misrepresent the stratum composition** of a sample feeding audit and statistical claims. A reviewer reading "25% CertScan" must be able to trust it. Under-filling is honest; silent substitution is not. But under-filling *invisibly* is also unacceptable — that is precisely how the owner got 20 and 10 with no explanation.

New `CertScanShortfall` records `{stageKey, stageLabel, portName, requestedCertScanQuota, actualCertScanDrawn, availableCertScanRows}` (`portName: null` = stage-wide). Surfaced **pre-draw** (estimated warning banner in Phase 3, alongside the existing floor-override warning), **post-draw** (`CertScanShortfallReport` naming each stratum with requested vs actual vs available and an explicit "not backfilled" explanation), and **on disk** in both `sampling.plan.json` and `sampling-proof.json` so the sample's real composition is self-describing to an auditor.

**The draw algorithm is untouched.** Golden-mastered drawn-row IDs before the change and asserted **byte-identical** after; `SAMPLING_ALGORITHM_VERSION` deliberately not bumped, since bumping it would wrongly mark historical draws non-replayable. The earlier hypothesis that CertScan was applied *additively* was refuted and was **not** "fixed". The legacy non-stage draw path structurally cannot produce a shortfall (its Hamilton split is bounded by pool size) — documented in code rather than given a fabricated detection path.

### 3. R1 / R4 / R5 — reports completed (document editions)

**R1:** new pages "قبل وبعد المعالجة — Risk" (original → valid/invalid ID → dedup → invalid-result-removed → final, plus CertScan split) and "— إثراء BI" (matched/unmatched + per-field fill summary), read verbatim from `ProcessingSummary` — which **no reporting file previously referenced at all**. The existing page becomes the merged view, matching the owner's page-1-separate / page-2-merged ask. When `processingSummary` is absent, page numbering is **byte-identical to before**, so older months render unchanged.

**R4:** implemented as a new **Part 6 "التغطية والمساءلة التشغيلية"** appended last — additive, so Parts 1–5 keep their numbering. It **reuses** R2's `computeDistributionModel` and R3's `computeManagementModel` verbatim rather than recomputing, which is what stops the folds diverging again.

**R5:** per-employee row listings (image id, port, stage/level, decision level, answer, date), chunked with `yieldToMain`. The sample document's artificial 60-row cap is removed; the distribution document gained stage/level and both level-one/two answer columns.

**Not done:** the deck2 slide additions for R4/R5. Everything landed for the **document** editions; the decks were left alone rather than starting a speculative decomposition of `slides.ts` (3,759 lines).

### 4. A test-isolation bug that was corrupting unrelated suites

Two bulk-reassignment tests failed in the full suite while passing in isolation and in their own directory, with `unable to find role="dialog"`.

**Root cause:** `readOnlyMode` is a **module-global** boolean, and `monthLock.test.ts` set it `true` without resetting. Every test file running afterwards saw a read-only workspace, so every `canMutate`-gated control silently stopped rendering — surfacing as a dialog assertion failing in a completely unrelated file.

Fixed at both ends: `monthLock.test.ts` now resets in a `finally` (so a failing assertion cannot poison the suite either), and `XrayReferrals.test.tsx` establishes the state it needs instead of inheriting it.

> **A wrong turn worth recording.** The first attempt added blanket global resets for auth state and read-only mode to `test-setup.ts`. That *increased* failures from 1 to 3, by clobbering state some files intentionally carry across tests within a file. Aggressive global resets were the wrong instinct; the correct fix was making the offending file clean up after itself. The narrower global additions that did survive — clearing the Query cache and browser storage between tests — are kept.

**Migration/rollback:** additive. New preview and shortfall data are new optional fields; report changes are in-memory except the additive `certScanShortfalls` in two audit artifacts; no existing workspace file format changed. Rollback is a code revert.
