## v117.3 — 2026-08-24 — Add (error-log): batching sink that persists every logged error to the workspace

**Why:** Task 5 of the error-log subsystem plan. `logError` (Task 2) is synchronous and called from hot paths across the app, so it cannot itself touch disk — a per-error write would multiply SMB round trips, the exact contention `actionLog.ts`'s per-actor split exists to avoid. This task is the bridge: an in-memory batching queue that flushes to `appendUserErrors` (Task 4) on a size threshold, a timer, or tab teardown, plus the headless component that installs it once a real (non-demo) session has a ready workspace.

**What changed:** Added `src/data/errorLog/errorLogSink.ts`: `installWorkspaceErrorSink({ directoryHandle, username, ... })` registers an `enqueue` function as the `errorLogger` sink (via `registerErrorSink` from Task 2). Entries queue in memory; a flush is triggered at `batchSize` (default 25), on a `flushDelayMs` timer (default 5s), or via `flushErrorLogNow()`, and concurrent flush calls coalesce into one in-flight write. Past `maxPending` (default 200) the OLDEST entries are dropped and the drop count survives as one synthetic `errorlog:overflow` entry in the next flush. Entries whose `context` starts with `errorlog:` (Task 4's own internal-failure prefix) are dropped before enqueueing, so a failing disk cannot generate an unbounded queue of errors about failing to write errors — this closes the async half of the recursion loop that `errorLogger.ts`'s synchronous `suppressDepth` guard (Task 2) closes the sync half of. `isReadOnlyMode()` short-circuits a flush to a no-op. `visibilitychange`/`pagehide` listeners flush on tab teardown. ## v117.0 — 2026-08-24 — Add (error-log): per-user persisted error store under 5-system/system-errors/

**Why:** Task 4 of the error-log subsystem plan, and the task that defines the new on-disk format. Errors logged today live only in a 50-entry per-browser `localStorage` ring (`errorLogger.ts`) — they die with the browser profile and are invisible to anyone but the person who hit them. The owner requirement is a durable, fleet-wide, admin-exportable record. A single shared file was rejected on the same measured grounds `actionLog.ts` already documents for the audit trail (483 whole-file rewrites per employee per shift on the real SMB deployment, one bad writer's failure becoming every writer's failure) — worse here, because an error log writes exactly when the workspace is already misbehaving and a storm hits every client at once. Per-user files, modelled line-for-line on `actionLog.ts`, remove that contention entirely: two machines never target the same file.

**What changed:** Added `src/data/errorLog/errorLogTypes.ts` (`PersistedErrorEntry`, `UserErrorLogFile`, `ErrorLogArchiveFile` — deliberately with NO `previousArchiveHash` B5 hash chain; see the security-model note below) and `src/data/errorLog/errorLogStorage.ts`: `appendUserErrors(directoryHandle, username, batch)` writes a whole batch in one `casLoop`-protected read-modify-write per user (6 retries × 100 ms base delay, copied verbatim from `actionLog.ts`'s tuning), archiving the oldest overflow past a 2,000-entry live cap to a per-user per-year archive file BEFORE trimming — archive failure blocks the trim, so no entry is ever silently dropped. `readAllWorkspaceErrors`/`readWorkspaceErrorArchive` merge every per-user file (first-writer-wins by `id`, sorted ascending by `at`/`id`). Best-effort by contract: `appendUserErrors` never throws; its own internal failures are logged through `logError` under the `errorlog:` prefix, which the Task 5 sink is taught to never queue for a disk write, so a failing disk cannot generate an unbounded stream of errors about failing to write errors.

**Migration/rollback:** **Migration: none, and none is possible** — there is no prior on-disk error log to convert. A workspace that has never run this version simply has no `5-system/system-errors/` folder; it is created lazily on the first error any client persists. **Forward compatibility:** readers tolerate a missing optional field, so an older file stays readable after a later field is added to `errorLogTypes.ts`; never remove or repurpose a field. **Rollback:** revert the code. Files already written are orphaned, not corrupt — nothing else in the app reads or requires them, `checkWorkspaceStructure` does not list `system-errors` among required folders, and the folder can be left in place indefinitely or deleted by hand — the same "read forever, written never, deleted never, migrated never" doctrine `auditPaths.ts:15-18` applies to the legacy shared audit files, applied in reverse. **Backups need no change:** `backupStorage`'s generic `.json` walk from the workspace root already sweeps these files in, and `restoreActionFor` falls them through to `"replace"` — the same semantics applied to the per-user audit logs, with the same documented consequence that a restore rolls back one user's log rather than the fleet's. **Security posture:** unchanged and stated explicitly — this is plain, tamperable JSON on a shared folder like every other business file (`docs/architecture/SECURITY_MODEL.md`), and it deliberately carries no hash chain: that chain exists for the audit trail's governance-evidence property, and this is diagnostic telemetry about software, not evidence about people.

## v115.4 — 2026-08-24 — Add (error-log): page/action/code/user fields on ErrorEntry plus a persistence sink hook

**Why:** Task 2 of the error-log subsystem plan. The 56 existing call sites must keep working with zero signature changes, so the new page/action/code/user fields have to be filled in by `logError` itself (reading Task 1's ambient context) rather than by the callers. The persisted store (Task 4) cannot be imported directly from `errorLogger.ts` — `safeWrite.ts` already imports `logError`, so that edge would close a module cycle — so a `registerErrorSink` hook is added instead, to be installed by the persistence layer once a workspace exists.

**What changed:** `ErrorEntry` gained four optional fields (`page`, `action`, `errorCode`, `username`, `role`). `logError(context, error, meta?)` now reads `readErrorContext()` for page/username/role, defaults `action` to the (already-truncated) context string, and recovers `errorCode` either from an explicit `meta.errorCode` or by parsing the `[XQ-AREA-NNN]` suffix `logCodedError` appends. Added `registerErrorSink`/`__resetErrorSinkForTests`; `logError` hands the finished entry to the sink synchronously, guarded by a `suppressDepth` counter so a throwing sink (or a sink that itself logs) can never recurse into or escape back out to the original caller. `logCodedError` (`errorCodes.ts`) now passes `{ errorCode: code }` explicitly instead of relying only on the suffix parse. `storageRegistry.ts`'s `xray_error_log_v1` entry now documents that it is the local half of a two-tier log.

## v115.3 — 2026-08-24 — Add (error-log): ambient page/actor context for error attribution

**Why:** Task 1 of the persistent error-log subsystem plan (`docs/superpowers/plans/2026-08-24-error-log-subsystem-plan.md`). The 56 existing `logError` call sites cannot each be taught the current page and signed-in user without a large, mechanical, permanently load-bearing change to every one of them — most sit in the data layer, below React entirely.
