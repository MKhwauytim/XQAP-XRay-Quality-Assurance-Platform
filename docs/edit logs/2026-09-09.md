## v135.0 — 2026-09-09 — Refactor (storage): delete a managed JSON name as a unit so an orphaned .bak cannot answer reads forever

**Why:** A production error-log export ran the same row for over eighteen
hours, for every user including the admin, from 2026-09-08 17:33 through at
least 2026-09-09 12:14:

> `"tmpl-1787457917309-ngm1iq.json" in "6-templates" could not be read from its
> live copy and was served from tmpl-1787457917309-ngm1iq.json.bak instead. The
> live file is damaged and every reader is falling back until something rewrites
> it.`

The file was not damaged. It had been **deleted**, and the message was chasing
a torn write that never happened. v134.4 had already looked at this row, added
a read-path self-heal, found it broke `templateFileRecovery.ts`'s ability to
detect the damaged state at all, and reverted it — the right call on the fix,
but the diagnosis underneath it was wrong, so the row kept running.

`safeWriteJson` maintains THREE names for one logical file — the live name,
`{file}.bak`, `{file}.tmp` — and `safeReadJson` reads them as ONE: on a miss of
the live name it falls through to the siblings and reports the recovery. Every
delete site in this codebase removed only the live name. So a delete did not
delete the record; it left an orphan that answers every subsequent read, and
because nothing ever rewrites a file that is supposed to be gone, the condition
is permanent by construction. `deleteTemplate` reaches this through
`loadTemplateIncludingDeleted` → `resolveAnswerTemplates`, which runs at every
sign-in — hence "every user, every session, forever".

The convention was known: `deleteDesign` carried a comment explaining precisely
this hazard and cleaned up its own siblings by hand. That is exactly how a rule
that lives only in a comment fails — six sites, one of them right.

Rejected: a read-path self-heal that rewrites the live file from its sibling
(v134.4 already tried and reverted it, and it cannot distinguish a deletion
orphan from a torn write, so it would have "repaired" deleted records back into
existence); changing the `.bak`/`.tmp` probe order (does nothing for an orphan);
and a bespoke `scripts/check-remove-entry.mjs` (an ESLint rule rides `lint:ci`,
which already gates every PR).

**What changed:**
- `safeWrite.ts`: new `safeRemoveJson(dir, fileName)` — the one way to delete a
  managed name. Removes `{file}.tmp`, then `{file}.bak`, then the live name
  **last**, under the same `withResourceLock` key `safeWriteJson` uses. The
  order is part of the contract: an interrupted delete must never land in the
  live-absent/siblings-present state that IS this bug, so an interruption
  leaves the live file readable and the delete reporting failure. Each removal
  rides `retryTransientWrite`, because on the SMB share a `removeEntry` fails
  for pure timing reasons (`NoModificationAllowedError` from another machine or
  an AV scanner holding the entry open) and aborting there would produce the
  very orphan this prevents. `NotFoundError` is swallowed INSIDE the retry
  callback — absent is the success case for a remove, and letting it reach the
  ladder made every delete pay the full backoff plus a reachability probe for
  the `.tmp` that is normally absent (seven attempts for one file that was never
  there, caught by this change's own ordering test). All three names are
  attempted regardless of an individual failure; the result names what remains,
  so a partial delete is reported rather than silent.
- Migrated six hand-written delete sites: `templateStorage.deleteTemplate`,
  `reportDesignStorage.deleteDesign`, `adhocImportStorage.deleteAdhocImportRecord`,
  `replacementIndexStorage`'s empty-bucket removal,
  `distributionStorage.invalidateDistributionCacheForFieldEdit` (its six-name
  list collapses to two `safeRemoveJson` calls, so the sibling list can no
  longer drift from what `safeWriteJson` writes), and
  `actionHistory.pruneActionHistory`.
- `eslint.config.js`: `no-restricted-syntax` bans raw `removeEntry` calls under
  `src/`, with a narrow allowlist (the primitive itself, `memoryDirectory`, the
  probe cleanup in `transientFileErrors`, `backupStorage`'s whole-folder and
  restore-marker removals, the two recovery archivers whose siblings ARE their
  recovery source, `feedbackStorage`'s legacy `messages.json` archive-out, and
  tests). `lint:ci` runs `--max-warnings 0`, so a seventh hand-written delete
  fails the PR instead of shipping another orphan. **This is the guard that
  makes the fix permanent**; the rest is the cleanup.
- `safeReadJson` gains `siblingFallback` (default `true`, unchanged for every
  existing caller). `false` stops after the live probe and never calls
  `reportBakRecovery` — for a caller that has its own authoritative answer for
  "the live file is gone".
- `loadTemplateIncludingDeleted` now reads the live file strictly, then
  branches on WHY it failed. `missing` → tombstone (an orphaned sibling must
  not pre-empt it). `corrupt` → the full recovery ladder FIRST, then the
  tombstone: deleting a template does not reserve its id, so a re-created
  template whose live file later tears must resolve to its own snapshot and not
  to the superseded tombstone — otherwise employees' answers resolve against
  the wrong questions. Only with neither live file nor tombstone does the
  last-resort ladder run, where a reported recovery is a genuine one.
- `bakRecoveryReport.ts` gains `BakRecoveryLiveState`. A sibling answering for
  an ABSENT live file no longer asserts "the live file is damaged" — it says
  there is no live copy and the sibling may be a deletion orphan. That wording
  is what sent an admin hunting for corruption in a deleted file for eighteen
  hours. `fileSystemAccess.readJsonFile` passes the same distinction so both
  ladders stay in lockstep.
- `memoryDirectory.ts`: `removeEntry` now participates in the fault-injection
  and operation-log surface, which is what lets the tests assert removal ORDER
  and the transient-retry behaviour deterministically.

**Migration/rollback:** No on-disk format change and no migration — this
changes which files a delete removes, not the shape of any file, so the
post-launch migration policy does not apply. Existing workspaces are NOT
retro-cleaned by this change: an orphan already on the share (the production
`tmpl-1787457917309-ngm1iq.json.bak`) stays there. What changes for it is that
`loadTemplateIncludingDeleted`'s strict read makes it INERT — the tombstone
answers, so the row and the banner stop on deploy — and the log line for any
remaining orphan now says so honestly. Reverting the PR restores live-only
deletes (new orphans resume) but loses no data: the primitive only removes
files the tombstone already supersedes.

## v134.6 — 2026-09-09 — Fix (workspace): stop logging XQ-WS-015 for the expected 'prompt' cold-start state

**Why:** A production error-log export (2026-09-08 18:26, 2026-09-09 08:17)
carried two `workspace:restore-permission [XQ-WS-015]` rows —
"restore-on-mount: remembered handle's readwrite grant is not 'granted'" — one
at the start of each day's first session. Nothing was wrong. `queryPermission`
on a handle rehydrated from IndexedDB answers `"prompt"` on a cold start by
design: Chromium cannot upgrade that grant without a user gesture, and this app
is a `file://` static page, so the installed-app persistent-grant path does not
apply either. The restore path logged EVERY non-`granted` answer as a fault, so
a perfectly healthy sign-in wrote an error row.

That is not only noise. `"denied"` — a persisted browser BLOCK for the origin
(the user chose "Don't allow", a dismiss-embargo, a site-settings entry, or the
`FileSystemWriteBlockedForUrls` policy) — is a genuine dead end, because
`ensureDirectoryPermission` returns false *without prompting*: the reconnect
button the user is then shown can never succeed, it just yields XQ-WS-009 and
redraws the same card. Logging both states identically meant the real one was
indistinguishable from the expected one, and the two production rows cannot now
be attributed to either.

**What changed:**
- `WorkspaceProvider.tsx`: the `permission !== "granted"` branch splits by
  outcome. All four state setters (`setDirectoryHandle`,
  `setSelectedDirectoryName`, `setPendingReconnect(true)`,
  `setStatus("not_selected")`) are unchanged and unreordered — `WorkspaceGate`
  depends on that pair, and this file is in the effect-timing-sensitive area
  CLAUDE.md flags. Only the log call and the message differ: `"prompt"` (and
  any other non-`denied` value) is shown on screen via `formatUserError` and
  never logged, following the XQ-WS-002 precedent; `"denied"` is logged with
  the queried value in the `Error` message, so a row written after this change
  is attributable, and the on-screen message gains a hint naming the browser
  setting to clear.
- `labelsStore.ts`: new `wsgate_picker_denied_hint` — the Arabic sentence
  telling the user the browser has blocked folder access for this site, where
  to allow it (Site settings → File editing / `chrome://settings/content/filesystem`),
  and to reload afterwards.
- `errorCodes.ts`: comment on the XQ-WS-015 catalog entry recording which state
  is logged and which is only displayed. The `meaning` string and the context
  string are untouched, so the pinned-meaning and unused-catalog-entry tests
  stay green.
- `WorkspaceProvider.test.tsx`: two new cases, plus `clearErrors()` in
  `beforeEach` (the error ring is module memory — `test-setup.ts` resets
  `localStorage` only, so entries leaked between tests).

The reconnect button deliberately still renders on `"denied"`. Hiding it needs
a new `WorkspaceContext` field and a `WorkspaceGate` branch in the
provider/gate pair that regressed five times running (v59.190–v59.197), and
the on-screen hint already removes the "unexplained loop" that made the button
misleading.

Two follow-ups are deliberately NOT bundled: `XQ-WS-009`
(`WorkspaceProvider.tsx`'s reconnect path) logs a user-DISMISSED prompt as a
fault in the same way, and is its own decision; and hydrated XQ-WS-015 rows
already in a user's 50-entry ring do not age out on a healthy install, so an
admin should clear the error log in Settings once after deploying.

## v134.5 — 2026-09-09 — Add (answers): automatic 30s background retry for a save that never reached the shared folder

**Why:** v134.4 added an IndexedDB backup of saved answers, reconciled every
60s — but only mirrored an answer on a SUCCESSFUL save. A save that failed
outright (share unreachable, permission lost, exhausted `casLoop` retries)
was never mirrored at all, so there was nothing for the periodic
reconciliation to replay: the employee saw an error and had to notice and
retry manually, with no visible sign anything was still unsaved. The owner
asked for this to close automatically, on a 30s cycle, with a visible
indicator so nothing sits silently unsynced.

**What changed:**
- `answerLocalMirror.ts`: mirror records now carry `synced: boolean`.
  `mirrorAnswerLocally` (a confirmed save) sets it `true`; the new
  `markAnswerPendingLocally` (a save that failed to reach the shared folder)
  sets it `false`. New `countPendingAnswers(month, username)` counts the
  `false` ones for the UI indicator.
- `answerStorage.ts`: `performAnswerWrite`'s failure branch now calls
  `markAnswerPendingLocally` with the same in-memory candidate item the
  success branch already mirrors — so a failed save is queued, not dropped.
- `XrayInspectionResults.tsx`: the periodic local-mirror tick moved from 60s
  to 30s (still skipped for a supervisor's `canSeeAll` view), and now also
  refreshes a `pendingSyncCount` state after each reconciliation. A new
  `ew_answers_pending_sync` label renders a "{count} إجابة لم تصل بعد..."
  notice (reusing the existing `ew-msg-warn` style) whenever that count is
  above zero, using the same `ew-msg-warn` treatment as the existing
  draft-retained notice.
- `answerStorage.localMirror.test.ts` (new): verifies a permanently-failing
  save calls `markAnswerPendingLocally` (never `mirrorAnswerLocally`), a
  successful save does the reverse, and `reconcileAnswersWithLocalMirror`
  replays a pending mirrored item into the file and re-mirrors it confirmed.

## v134.4 — 2026-09-09 — Add (answers): local IndexedDB backup for saved answers, reconciled on load and every 60s; Fix (history): stop re-discovering the same name-too-long path limit on every save

**Why:** A production error-log export (2026-09-08/09) showed two recurring
problems. First, every answer save for a subset of employees logged TWO
durable errors (`safeWrite:writeText` + `actionHistory:record`,
`cause=name-too-long`): the per-record pre-change history snapshot
(`recordActionHistorySnapshot`, added 2026-09-03) mints a brand-new deepest
directory per `xrayImageId` on every save, so on a workspace already deep on
the network share it re-discovered the SAME permanent path-length limit on
every single save — paying `writeText`'s full retry ladder plus
`classifyNotFound`'s own round-trip probes (over a second of hidden latency)
each time, for a write that is best-effort and never gated the real save.
Second, the owner asked for saved answers to also be kept in the browser's
IndexedDB as a redundant backup, reconciled against the workspace file on
load and every 60 seconds, so a save that reaches the browser but not (yet,
or ever) the shared folder can be recovered later — explicitly additive-only
in both directions (an empty/reset IndexedDB must never be read as "the
answers were deleted", and a browser mirror missing something the file has
must never delete it from the file).

An earlier version of this change also added a generic "rewrite the live
file after a `.bak`/`.tmp` recovery" self-heal to `safeReadJson` for the
second, unrelated `storage:bak-recovery` corruption row in the same log
(a damaged template file stuck permanently serving from `.bak`). That was
reverted before landing: `templateFileRecovery.ts`/`TemplateRepairSection.tsx`
(shipped just before this, 2026-09-08) already cover exactly this condition,
deliberately as an ARCHIVE-then-explicit-admin-repair action rather than a
silent read-path rewrite (see that module's own doc comment: "never repair
silently on read... a repair nobody asked for, on data nobody has verified,
is worse than the outage") — a silent auto-heal broke that tool's ability to
detect the damaged state at all (confirmed by `DecisionRepairSection.test.tsx`
failing once the self-heal was added), so admins should use the existing
Template Repair panel in Settings for `tmpl-1787457917309-ngm1iq.json`.

**What changed:**
- `actionHistory.ts`: cache scope PREFIXES (every `scopeParts` entry except
  the trailing per-record id) that have already proven `XQ-IO-034`
  (name-too-long) this session, and skip the write entirely for any sibling
  under that prefix instead of re-probing at full cost. Logged once, not on
  every save.
- `answerLocalMirror.ts` (new): a small IndexedDB-backed backup of an
  employee's own saved answers (`mirrorAnswerLocally` / `loadMirroredAnswers`),
  registered in `storageRegistry.ts`. Never a source of truth; every failure
  degrades to a silent no-op.
- `answerStorage.ts`: mirrors the just-saved item into IndexedDB after every
  successful `upsertItemAnswer`/etc. append — built from the in-memory
  event/previous state already computed by the write, so it costs no extra
  disk read. Adds `reconcileAnswersWithLocalMirror`: replays any mirrored
  item the file lacks or has an older `lastSavedAt` for back into the file
  via the normal `upsertItemAnswer` path (never a raw overwrite), then
  re-mirrors the file's own items — additive-only on both sides.
- `XrayInspectionResults.tsx`: calls `reconcileAnswersWithLocalMirror` once
  when an employee's OWN results load (never for a supervisor's `canSeeAll`
  view of someone else's answers), and again on a 60s interval while that
  view stays open.
