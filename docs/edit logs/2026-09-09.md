## v137.0 — 2026-09-09 — Add (integrity): admin boot self-check that repairs damaged and orphaned workspace files and reports what it did

**Why:** Broken workspace files were only ever discovered when something
happened to read them, reported only to whoever was looking at the screen at
that moment, and repaired only if an admin knew to open a Settings panel nobody
had told them about. The 2026-09-08/09 production log is the proof:
`tmpl-1787457917309-ngm1iq.json` was served from an orphaned `.bak` for over
eighteen hours, across every user including the admin, with a banner that
recurred on every read and that nobody acted on. The tooling to fix it had
shipped the day before (`templateFileRecovery.ts`, v134.3) and went unused,
because nothing ever pointed anyone at it.

The owner asked (2026-09-09) for a boot sequence that checks the files, fixes
them, and shows the admin what was broken — with the fixing automated rather
than gated behind a click.

**What changed:**
- `storage/orphanSiblings.ts` (new): `findOrphanSiblings` lists `{file}.bak` /
  `{file}.tmp` entries whose live file is absent — listing-only, no file
  opened, so it is cheap enough to sweep several roots at boot.
  `archiveOrphanSibling` copies the bytes to `{name}.orphaned-{timestamp}` (a
  name no read ladder probes and the `.json` scanners ignore) and only then
  removes the sibling. Copy-before-remove is deliberate: a failure after the
  copy leaves the bytes twice, which is recoverable; the reverse order can lose
  them. v135.0's `safeRemoveJson` stops NEW orphans; this finds the ones
  already on disk in workspaces that ran the old code.
- `integrity/bootIntegrityScan.ts` (new): the orchestration. Repairs damaged
  template files via the existing `recoverTemplateFile`, sweeps `6-templates`,
  `3-user-data`, `4-reports` and `5-system` for orphaned siblings, and returns
  a report of findings grouped by outcome. Every check is individually wrapped:
  a failure becomes a `could-not-check` row, never an exception into the boot
  path. A root the workspace has never created is silently skipped — a
  workspace with no report designs has no `4-reports`, and that is not a fault.
- `components/IntegrityReportDialog/` (new): the popup. Two visually distinct
  groups, because they ask different things of the reader — "repaired" is a
  record of what changed under the admin, "needs review" is a to-do list. It
  renders nothing at all when the scan found nothing, so a healthy workspace
  does not greet an admin with a dialog on every sign-in. File names are
  `unicode-bidi: isolate` so Latin names cannot be reordered by the surrounding
  RTL Arabic.
- `App.tsx`: runs the scan for `admin` only, once per boot session, on the same
  session+workspace key the auto-backup already uses. Deliberately narrower
  than that auto-backup, which also runs for managers: this one WRITES REPAIRS
  to files nobody has opened yet, which is an admin's call to have made on
  their behalf. Demo mode is excluded — its workspace is in-memory and has
  nothing real to repair.
- `templates/templateFileRecovery.ts`: docblock updated. That module states
  "never repair silently on read — a repair nobody asked for, on data nobody
  has verified, is worse than the outage", and shipping an automatic repair
  without amending it would leave the code and its own stated doctrine in
  disagreement.
- `eslint.config.js`: `orphanSiblings.ts` added to the raw-`removeEntry`
  allowlist. It removes exactly ONE sibling after archiving its bytes;
  `safeRemoveJson` would take the live file and the other sibling with it,
  which is the opposite of the intent. The rule catching this on the first
  attempt is the guard working.

**Migration/rollback:** No on-disk format change and no migration. The scan is
additive and read-mostly; its only writes are repairs that archive the original
first, so reverting the PR leaves every workspace exactly as it found it —
orphans return to being orphans, and the archived copies remain. The doctrine
narrowing is scoped in code to `bootIntegrityScan.ts`: `safeReadJson` still
never rewrites anything, and the Settings repair panels still work as before.

**A deliberate reversal, recorded.** Automatic repair contradicts this repo's
existing "never repair unasked" rule. The reversal is bounded — one role, one
known moment rather than every read, and a report of every single thing
touched — and the objection the old rule raises is answered by that report plus
the archive, not ignored. Owner decision, 2026-09-09.

## v136.0 — 2026-09-09 — Refactor (history): derive answers and distribution pre-change history from the event logs instead of copying it

**Why:** The 2026-09-03 owner requirement is "before a mutation overwrites a
template, an answer, or an assignment, keep what it replaced, so it can be
inspected or put back." As built, every mutation wrote that copy to its own
file at
`5-system/history/{family}/{month}/{user}/{xrayImageId}/{36-char timestamp}.json`
— ~115 characters relative to the workspace root. On a workspace already
~146–166 characters deep on the UNC share that crosses Windows' 260-character
cap, so on the deployment in the 2026-09-08/09 error log the write failed on
EVERY answer save: ~50 failures in three hours, two durable rows each.

v135.1 made that failure free (a construction-time path budget) rather than
expensive. Free and absent is still absent — the feature the owner asked for
had never once worked there.

The deeper problem is that for two of the three families the copy was redundant
the day it was written. The pre-change state is already on disk, immutably and
permanently, in logs the app never prunes: `answers.events/*.ndjson`
(append-only) and `distribution.events/{eventId}.json` (immutable by contract).
Replaying either to the point before event N reconstructs exactly what the
snapshot held. So the writer was not merely failing — it was duplicating state
the app already had, which is what CLAUDE.md's one-place rule exists to
prevent, and the duplication is precisely what forced the per-record directory
that made the path too long.

`templates` is the genuine exception: a template save is a whole-file overwrite
with no event log behind it, so it keeps a real file.

**What changed:**
- `actionHistory.ts` rewritten as templates-only. The API narrows from
  `scopeParts: readonly string[]` to `recordId: string`, so nesting is no
  longer expressible by a caller. Layout goes from one-directory-per-record
  plus one-file-per-snapshot to ONE FILE per record,
  `5-system/history/templates/{templateId}.json`, holding
  `{ recordId, revision, _writeToken, snapshots[] }` capped at
  `ACTION_HISTORY_RETENTION_COUNT`. Pruning is an array slice — no directory
  listing, no per-file removal. Written under `casLoop` (two admins can edit
  one template), and an OBJECT rather than a bare array specifically so
  `revision`/`_writeToken` have somewhere to live: without a token to verify on
  read-back the losing writer's snapshot is silently dropped, the exact
  false-positive-revision case `casLoop.ts` exists to catch. Same document
  shape as `audit/actionLog.ts`.
- `actionHistoryReaders.ts` (new): `loadAnswerActionHistory` folds an item's own
  answer events, emitting the folded state before each event; a
  `migration-seed` event stays in the fold input but is not itself emitted as a
  change. `loadDistributionActionHistory` takes cumulative prefixes of a row's
  events, gated by `ADMIN_EDIT_DISTRIBUTION_EVENT_TYPES` — imported from
  `distributionStorage.ts` rather than restated, so the two cannot drift.
- `answerStorage.ts`: both `recordActionHistorySnapshot` calls removed, along
  with the `historyRecorded` flag that existed to keep the write out of the
  retry body. `readAllAnswerEventsForMonth` and `eventsForEmployee` are now
  exported, so the reader folds the same input the deleted writer folded.
- `distributionStorage.ts`: the snapshot block removed, and with it the extra
  `loadDistributionLog` read that existed only to feed it.
  `ADMIN_EDIT_DISTRIBUTION_EVENT_TYPES` is exported instead of deleted.
- `templateStorage.ts`: call site updated to `recordId`.

**Migration/rollback:** No migration, deliberately. The legacy
`5-system/history/` tree is left in place, read-only — the same treatment the
legacy `feedback/` and `Population/` roots already get, and the precedent
CLAUDE.md's post-launch policy sets for archived-not-deleted originals.
Consolidating it would mean re-reading thousands of small files over SMB, many
unopenable from a machine whose mount is deeper than the one that wrote them,
to produce a second copy the app never reads. On the affected share the tree is
nearly empty anyway — the writes failed. Reverting this change restores the old
writers; nothing on disk blocks that, because nothing on disk was moved.

## v135.1 — 2026-09-09 — Fix (history): decide the action-history path-length verdict before touching the share, not after a full retry ladder

**Why:** The single highest-volume row in the 2026-09-08/09 production error
log: two employees, ~50 failures in three hours, TWO durable rows on every
single answer save —

```
safeWrite:writeText      NotFoundError persisted after 5 attempts on
                         "10B2526081300153/2026-09-09T09-03-07-106Z-000023.json.tmp"
                         (cause=name-too-long)
answers:answer:answer-save  NotFoundError  actionHistory:record
```

`recordActionHistorySnapshot` writes to
`5-system/history/{family}/{month}/{user}/{xrayImageId}/{36-char timestamp}.json`
— about 115 characters relative to the workspace root, which on a workspace
already deep on the UNC share crosses Windows' 260-character cap. Every other
file the app wrote in the same sessions, all under 94 relative, succeeded
against the same root.

A path-length limit is knowable from the NAME. This code discovered it by
trying: `writeText`'s five-attempt ladder (~630 ms) plus `classifyNotFound`'s
own round-trip probes (a second more), on a write that is best-effort and never
gated the save it was documenting. Worse, the trailing scope part is a
per-record id, so nearly every save minted a never-before-seen directory — via
`create: true`, so it also left an empty `{xrayImageId}` folder behind — and
paid the whole cost again. v134.4's `knownUnwritableScopePrefixes` cache helps
only within one tab: it resets on every page load, and it can only cache AFTER
paying the full price once.

**What changed:**
- `actionHistory.ts`: new exported `HISTORY_MAX_RELATIVE_PATH_CHARS = 94` and
  `historyRelativePath(family, scopeParts, fileName)`. Before any handle is
  opened, the planned relative path plus Chromium's `.tmp.crswap` staging
  suffix is measured against the budget; over budget, the snapshot is skipped
  in memory. The share is not touched at all — no minted directory, no ladder,
  no probes. The skip is reported once per family per session under a new
  `XQ-IO-037`, with the measured length, the budget and the path FIRST in the
  message (the durable log truncates, and the measurement is the actionable
  part).
- 94 is not a guess: it is the longest relative path that deployment is *known*
  to accept, read off the same log that shows 115 failing in the same tree on
  the same day. The reasoning lives in the constant's doc comment so the next
  person changing the layout finds it.
- The snapshot file name is now minted ONCE and reused by the write.
  `snapshotFileName` advances the per-tab sequence counter that keeps
  same-millisecond snapshots ordered, so measuring and then writing would have
  burned a number per save.
- `errorCodes.ts` / `labelsStore.ts`: `XQ-IO-037` and its Arabic label, which
  says plainly that the ACTION succeeded and only its history entry did not,
  and names the remedy (move the workspace closer to the share root).

**Scope — deliberately not the full fix.** This is a guard, not a redesign. The
real remedy is for these paths to be short enough that no budget is needed, and
Fable's analysis argues the `answers` and `distribution` snapshots are
duplicate state to begin with (their "previous state" already lives immutably
in `answers.events/*.ndjson` and `distribution.events/{eventId}.json`), so the
writers should be replaced by readers that fold those logs, leaving a file only
for `templates`. That changes what is on disk, needs an admin-offered migration
under the post-launch policy, and turns on an owner question — does an
event-derived history satisfy the 2026-09-03 requirement? — so it is NOT in
this change. What ships here makes the failure free and honest instead of
expensive and repeated, and `historyRelativePath` gives that redesign one place
to be measured from. On the affected share the history feature stays
unavailable for `answers` either way; the difference is that it now costs
nothing and says so once.

## v135.0 — 2026-09-09 — Refactor (storage): delete a managed JSON name as a unit so an orphaned .bak cannot answer reads forever

**Why:** A production error-log export ran the same row for over eighteen
hours, for every user including the admin, from 2026-09-08 17:33 through at
least 2026-09-09 12:14:

> `"tmpl-1787457917309-ngm1iq.json" in "6-templates" could not be read from its
> live copy and was served from tmpl-1787457917309-ngm1iq.json.bak instead. The
> live file is damaged and every reader is falling back until something rewrites
> it.`

The file was not damaged. It had been **deleted**, and the message was chasing
a torn write that never happened. v134.4 had already looked at this row, added
a read-path self-heal, found it broke `templateFileRecovery.ts`'s ability to
detect the damaged state at all, and reverted it — the right call on the fix,
but the diagnosis underneath it was wrong, so the row kept running.

`safeWriteJson` maintains THREE names for one logical file — the live name,
`{file}.bak`, `{file}.tmp` — and `safeReadJson` reads them as ONE: on a miss of
the live name it falls through to the siblings and reports the recovery. Every
delete site in this codebase removed only the live name. So a delete did not
delete the record; it left an orphan that answers every subsequent read, and
because nothing ever rewrites a file that is supposed to be gone, the condition
is permanent by construction. `deleteTemplate` reaches this through
`loadTemplateIncludingDeleted` → `resolveAnswerTemplates`, which runs at every
sign-in — hence "every user, every session, forever".

The convention was known: `deleteDesign` carried a comment explaining precisely
this hazard and cleaned up its own siblings by hand. That is exactly how a rule
that lives only in a comment fails — six sites, one of them right.

Rejected: a read-path self-heal that rewrites the live file from its sibling
(v134.4 already tried and reverted it, and it cannot distinguish a deletion
orphan from a torn write, so it would have "repaired" deleted records back into
existence); changing the `.bak`/`.tmp` probe order (does nothing for an orphan);
and a bespoke `scripts/check-remove-entry.mjs` (an ESLint rule rides `lint:ci`,
which already gates every PR).

**What changed:**
- `safeWrite.ts`: new `safeRemoveJson(dir, fileName)` — the one way to delete a
  managed name. Removes `{file}.tmp`, then `{file}.bak`, then the live name
  **last**, under the same `withResourceLock` key `safeWriteJson` uses. The
  order is part of the contract: an interrupted delete must never land in the
  live-absent/siblings-present state that IS this bug, so an interruption
  leaves the live file readable and the delete reporting failure. Each removal
  rides `retryTransientWrite`, because on the SMB share a `removeEntry` fails
  for pure timing reasons (`NoModificationAllowedError` from another machine or
  an AV scanner holding the entry open) and aborting there would produce the
  very orphan this prevents. `NotFoundError` is swallowed INSIDE the retry
  callback — absent is the success case for a remove, and letting it reach the
  ladder made every delete pay the full backoff plus a reachability probe for
  the `.tmp` that is normally absent (seven attempts for one file that was never
  there, caught by this change's own ordering test). All three names are
  attempted regardless of an individual failure; the result names what remains,
  so a partial delete is reported rather than silent.
- Migrated six hand-written delete sites: `templateStorage.deleteTemplate`,
  `reportDesignStorage.deleteDesign`, `adhocImportStorage.deleteAdhocImportRecord`,
  `replacementIndexStorage`'s empty-bucket removal,
  `distributionStorage.invalidateDistributionCacheForFieldEdit` (its six-name
  list collapses to two `safeRemoveJson` calls, so the sibling list can no
  longer drift from what `safeWriteJson` writes), and
  `actionHistory.pruneActionHistory`.
- `eslint.config.js`: `no-restricted-syntax` bans raw `removeEntry` calls under
  `src/`, with a narrow allowlist (the primitive itself, `memoryDirectory`, the
  probe cleanup in `transientFileErrors`, `backupStorage`'s whole-folder and
  restore-marker removals, the two recovery archivers whose siblings ARE their
  recovery source, `feedbackStorage`'s legacy `messages.json` archive-out, and
  tests). `lint:ci` runs `--max-warnings 0`, so a seventh hand-written delete
  fails the PR instead of shipping another orphan. **This is the guard that
  makes the fix permanent**; the rest is the cleanup.
- `safeReadJson` gains `siblingFallback` (default `true`, unchanged for every
  existing caller). `false` stops after the live probe and never calls
  `reportBakRecovery` — for a caller that has its own authoritative answer for
  "the live file is gone".
- `loadTemplateIncludingDeleted` now reads the live file strictly, then
  branches on WHY it failed. `missing` → tombstone (an orphaned sibling must
  not pre-empt it). `corrupt` → the full recovery ladder FIRST, then the
  tombstone: deleting a template does not reserve its id, so a re-created
  template whose live file later tears must resolve to its own snapshot and not
  to the superseded tombstone — otherwise employees' answers resolve against
  the wrong questions. Only with neither live file nor tombstone does the
  last-resort ladder run, where a reported recovery is a genuine one.
- `bakRecoveryReport.ts` gains `BakRecoveryLiveState`. A sibling answering for
  an ABSENT live file no longer asserts "the live file is damaged" — it says
  there is no live copy and the sibling may be a deletion orphan. That wording
  is what sent an admin hunting for corruption in a deleted file for eighteen
  hours. `fileSystemAccess.readJsonFile` passes the same distinction so both
  ladders stay in lockstep.
- `memoryDirectory.ts`: `removeEntry` now participates in the fault-injection
  and operation-log surface, which is what lets the tests assert removal ORDER
  and the transient-retry behaviour deterministically.

**Migration/rollback:** No on-disk format change and no migration — this
changes which files a delete removes, not the shape of any file, so the
post-launch migration policy does not apply. Existing workspaces are NOT
retro-cleaned by this change: an orphan already on the share (the production
`tmpl-1787457917309-ngm1iq.json.bak`) stays there. What changes for it is that
`loadTemplateIncludingDeleted`'s strict read makes it INERT — the tombstone
answers, so the row and the banner stop on deploy — and the log line for any
remaining orphan now says so honestly. Reverting the PR restores live-only
deletes (new orphans resume) but loses no data: the primitive only removes
files the tombstone already supersedes.

## v134.4 — 2026-09-09 — Add (answers): local IndexedDB backup for saved answers, reconciled on load and every 60s; Fix (history): stop re-discovering the same name-too-long path limit on every save

**Why:** A production error-log export (2026-09-08/09) showed two recurring
problems. First, every answer save for a subset of employees logged TWO
durable errors (`safeWrite:writeText` + `actionHistory:record`,
`cause=name-too-long`): the per-record pre-change history snapshot
(`recordActionHistorySnapshot`, added 2026-09-03) mints a brand-new deepest
directory per `xrayImageId` on every save, so on a workspace already deep on
the network share it re-discovered the SAME permanent path-length limit on
every single save — paying `writeText`'s full retry ladder plus
`classifyNotFound`'s own round-trip probes (over a second of hidden latency)
each time, for a write that is best-effort and never gated the real save.
Second, the owner asked for saved answers to also be kept in the browser's
IndexedDB as a redundant backup, reconciled against the workspace file on
load and every 60 seconds, so a save that reaches the browser but not (yet,
or ever) the shared folder can be recovered later — explicitly additive-only
in both directions (an empty/reset IndexedDB must never be read as "the
answers were deleted", and a browser mirror missing something the file has
must never delete it from the file).

An earlier version of this change also added a generic "rewrite the live
file after a `.bak`/`.tmp` recovery" self-heal to `safeReadJson` for the
second, unrelated `storage:bak-recovery` corruption row in the same log
(a damaged template file stuck permanently serving from `.bak`). That was
reverted before landing: `templateFileRecovery.ts`/`TemplateRepairSection.tsx`
(shipped just before this, 2026-09-08) already cover exactly this condition,
deliberately as an ARCHIVE-then-explicit-admin-repair action rather than a
silent read-path rewrite (see that module's own doc comment: "never repair
silently on read... a repair nobody asked for, on data nobody has verified,
is worse than the outage") — a silent auto-heal broke that tool's ability to
detect the damaged state at all (confirmed by `DecisionRepairSection.test.tsx`
failing once the self-heal was added), so admins should use the existing
Template Repair panel in Settings for `tmpl-1787457917309-ngm1iq.json`.

**What changed:**
- `actionHistory.ts`: cache scope PREFIXES (every `scopeParts` entry except
  the trailing per-record id) that have already proven `XQ-IO-034`
  (name-too-long) this session, and skip the write entirely for any sibling
  under that prefix instead of re-probing at full cost. Logged once, not on

- `answerLocalMirror.ts` (new): a small IndexedDB-backed backup of an

  when an employee's OWN results load (never for a supervisor's `canSeeAll`
