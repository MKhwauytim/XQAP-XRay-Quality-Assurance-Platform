## v130.0 — 2026-08-30 — Fix (backup): scope distribution cache invalidation to actual distribution-segment restores

**Why:** This is **Stage 3** of the answer-save append-only rewrite
(`docs/architecture/ANSWER_SAVE_DELTA_PROPOSAL_2026-08-27.md`, revision 4) —
the design doc's own closing validation stage, per §12: "full whole-repo
gate, a real before/after latency measurement..., and independent
adversarial validation of the diff before it ships." Stages 0 (v127.0), 1
(v128.0), and 2 (v129.0) were each independently reviewed as they landed,
but none of those reviews looked at the three stages together as one
integrated system — this stage is that pass, against the actual merged
`main`, not a branch. It found one real bug that only shows up from the
interaction between two consumers of the same generic module, plus one
benchmark-comment inaccuracy, and added an end-to-end integration test no
single stage's own test suite was positioned to write.

**What changed:** `distribution.events/` and `answers.events/` are
siblings under the same `2-samples/{month}/1-main/` directory
(`getSampleMainDir`). Round 3's §8a fix correctly generalized the backup
restore walk's cache-directory *capture* (`collectJsonRestoreEntries`) to
match any `*.events/`-suffixed directory, not just distribution's literal
name — but the two functions that actually consume that capture,
`invalidateDistributionCaches` and `republishRestoredDistributionStamps`,
are DISTRIBUTION-only side effects (delete
`distribution.current.json`/`distribution.checkpoint.json`, re-mint
`distribution.log.json`'s write token) and were never re-scoped to match.
Because both event directories share one `cacheDir`, a restore that
changed ONLY answer segments still added that shared directory to the
invalidation set — silently deleting distribution's rebuildable derived
cache and broadcasting a "distribution changed" signal to every client,
even though distribution was completely untouched. Not data loss (both
artifacts are rebuildable by design), but a real, confirmed
false-positive/wasted-refold bug, and exactly the class of cross-consumer
interaction a stage-by-stage review cannot see. Fixed by threading
`eventsDirName` through `restoreJsonTree`'s per-entry results and filtering
`cacheDirs` to only entries whose `eventsDirName` is specifically
`DISTRIBUTION_EVENTS_DIR` before calling either distribution-only function.
Answers needs no equivalent here: Stage 2 keeps no persisted checkpoint to
invalidate, and cross-tab freshness already comes from the read-only
bounded segment-size signature §6 wired into the sync tick.

Also fixed: `bench-answer-save-latency.mjs`'s summary line claimed the
wired path's growth was "expected: ~flat," which describes the *primitive*
append's disk cost, not the wired path's real, expected, bounded-by-one-
employee-history fold cost — a future reader could misread normal fold
growth as a regression. Reworded to say what's actually growing and why
it's fine.

Added: `answerFullWorkflow.integration.test.ts`, driving `upsertItemAnswer
→ reopenItemAnswer → upsertItemAnswer (correction) → setItemQualityNote →
upsertItemAnswer` against `createMemoryDirectory()` and checking the
folded state at every step, including a final COLD read (cache explicitly
reset) confirming the fold is a pure function of disk bytes — the kind of
whole-workflow test only the fully-wired system (all three stages) can
exercise.

Specifically probed and found sound, with no bug: `appendOnlyEventLog.ts`'s
module-level writer-memo state (confirmed the only state in the file,
correctly namespaced by `consumerNamespace` for every entry, not just the
ones the design doc named); cross-tab reopen visibility (a save's `previous`
computation always freshly folds from an uncached directory listing, so a
supervisor's reopen in another tab/machine is picked up on the very next
save regardless of any UI-level staleness); single-tab save/read
consistency (the optimistic UI patch after a save is cosmetic only — the
write path itself never trusts it, always folding fresh from disk).

**Migration/rollback:** None — this is a bug fix within the already-shipped
Stage 2 restore path, not a data-format or schema change. Reverting this
one commit restores the pre-fix (over-broad) invalidation behavior; no
disk-format implications either way.

## v129.0 — 2026-08-30 — Feature (answers): Stage 2 -- wire answer saves to the append-only event log

**Why:** Stage 2 of the answer-save append-only rewrite
(`docs/architecture/ANSWER_SAVE_DELTA_PROPOSAL_2026-08-27.md`, revision 4).
Stages 0 (v127.0) and 1 (v128.0) built the generic event-log mechanics and
the answers-specific fold logic with zero production callers. This stage
wires the real save/reopen/quality-note paths to it, closing out the
original complaint this whole rewrite exists for: employee answer saves get
progressively slower over a month because `upsertItemAnswer` was a
whole-file read-modify-write-and-verify, cost scaling with the employee's
own answer count.

**What changed:** `upsertItemAnswer`, `upsertItemAnswerOnBehalf`,
`reopenItemAnswer`, and `setItemQualityNote` in `answerStorage.ts` now
append `AnswerEvent`s via `appendAnswerEventSegment` instead of rewriting
`{username}.answers.json`. The three request queues (reopen, replacement,
referral) moved to their own `{username}.requests.json` file (§7), so the
legacy `.answers.json` is genuinely frozen post-migration — read only, as
the migration-seed source. `loadEmployeeAnswers` merges item-state
(segments+fold, or a direct legacy passthrough pre-migration) with the
requests file; `loadAllEmployeeFiles` became an enumerate-then-fold fan-out
over the union of `.answers.json`/`.requests.json` stems and every
username named in `answers.events/`, with a `loadAllEmployeeRequestFiles`
fast path for the (majority of) call sites that only need request-queue
data — `referralStorage.loadRequestLogs` now uses it, so its read cost
drops rather than growing to a full item fold it never needed.
`backupStorage.ts`'s `collectJsonRestoreEntries` now captures any events
directory by suffix instead of matching the literal distribution name, and
`mergeEventSegment` dispatches to a real `AnswerEvent`-aware content
comparator (distribution keeps its own; anything unrecognized gets a
conservative whole-object deep-equal default) — closing a real
silent-data-loss path round 3 of the design review found: two
different-content answer events sharing an `eventId` (a legitimate case,
since `eventId` is deliberately stable across a retried append) were being
declared identical by distribution's field-subset comparator and one
silently dropped. `workspaceSync.ts` gained a read-only
`answersEventsSignature` bounded-listing probe (§6) so another user's save
shows up on the next sync tick with zero new writes. Real `XQ-ANS-001..006`
error codes replace Stage 1's borrowed `XQ-DIST-*` placeholders, with
`AnswerFoldError` gaining a `reason` discriminant so `answerStorage.ts`
classifies `XQ-ANS-005` vs `XQ-ANS-006` without matching on message text.

The two pre-existing bugs Stage 1 found are reproduced here too, not fixed:
a supervisor's `qualityNote` is still silently dropped by the assignee's
next ordinary save, and `reopenItemAnswer` still records no `valueHistory`
entry.

A real performance regression was found and fixed before this shipped, not
after: the first working version of this wiring had every single save read
and parse the WHOLE month's `answers.events/` directory — every employee's
segments, not just the saving employee's — because segment filenames carry
no username by design (§1's Gap 1c fix, so the freshness signal stays a
single bounded listing), so filtering to one employee requires reading
everyone's bytes first. Combined with feeding `readAnswerEventDelta` an
empty offsets map on every call, this meant every save re-read and
re-parsed every segment written by the whole team that month, from scratch
— a structurally different, likely worse, scaling problem than the one
this rewrite exists to fix, in an app with two prior production incidents
(XQ-IO-031, XQ-IO-032) specifically about the cost of opening many small
files over its SMB-backed workspace share. Fixed with an in-memory,
per-tab-session, non-persisted cache (`answerEventsCacheByRoot` in
`answerStorage.ts`) that feeds `readAnswerEventDelta` real byte offsets
after the first read, so repeat saves within a session are incremental.
Deliberately NOT a disk-persisted shared checkpoint file (unlike
distribution's own `distribution.checkpoint.json`): answer saves are the
highest-frequency write in the app, and a shared file bumped by every save
is the exact hotspot shape round 2 of this same design review already
rejected (the `XQ-IO-032` pattern). Invalidated only on a manual admin
refresh — the identical precedent `directoryScan.ts`'s own `appendOnlyCache`
already uses in production for distribution today, verified rather than
assumed. Measured: ~10x fewer segment-read operations across 15 sequential
saves in one session (60 reads/save cold and warm, before the fix; 60 once
then ~2/save after — the residual "2" is the write path's own pre-existing
read-modify-write append cost, unrelated to this fix, and scales only with
the saving employee's own segment).

Independently reviewed by two separate reviewers (implementer ≠ fixer ≠
validator throughout): the on-behalf refusal, the blank-author guard
(confirmed synchronous, before any I/O), the append-then-confirm protocol
under a genuinely concurrent same-tab write (a new test drives this via
`Promise.all`), the cache's behavior under `casLoop` retries, and both
reproduced pre-existing bugs were checked against the actual pre-diff code,
not just read. Two smaller deviations were confirmed necessary rather than
accidental: an empty `.answers.json` shell is written once at first
migration (required by `readContract.test.ts`'s P0-1 corruption test, which
needs the file to physically exist to corrupt), and a narrow legacy-file
compatibility overlay merges in items that exist ONLY via the still-legacy,
test/seed-only `saveEmployeeAnswers` path for an already-migrated employee
(required by `answerOnBehalf.test.ts`; confirmed it can never shadow a
folded/segment-authoritative item for the same `xrayImageId`).

**Migration/rollback:** Reverting resumes writing `.answers.json` directly
(per the design doc's §10); a subsequent roll-forward must not re-fold
segments written after the revert against a legacy file that has since
diverged. No schema migration runs automatically — an employee's first
post-Stage-2 write seeds a `migration-seed` event from their current legacy
file content (or an empty-hash marker if none exists) and freezes the
legacy file from that point on.

async function readAllAnswerEventsForMonth(
  directoryHandle: DirectoryHandleLike,
  monthFolderName: string
): Promise<AnswerEvent[]> {
  const mainDir = await getSampleMainDir(directoryHandle, monthFolderName, true);
  try {
    const cached = getAnswerEventsCacheEntry(directoryHandle, monthFolderName);
    const delta = await readAnswerEventDelta(mainDir, cached?.offsets ?? {});

}

## v128.0 — 2026-08-30 — Feature (answers): Stage 1 -- answers-specific append-only fold logic on the generic event log

**Why:** Stage 1 of the answer-save append-only rewrite
(`docs/architecture/ANSWER_SAVE_DELTA_PROPOSAL_2026-08-27.md`, revision 4).
Stage 0 (merged, v127.0) extracted the generic append-only storage
mechanics from `distributionEventStore.ts` with zero behavior change; this
stage builds the answers-specific event type and fold logic ON TOP of those
primitives, in full isolation — zero production call sites are wired yet,
so this stage changes no runtime behavior of the shipping app. Wiring is
Stage 2, separate follow-up work.

**What changed:** New `answerEventStore.ts`: the `AnswerEvent` type (with a
wider shape than the design doc's original `§3` sketch — `templateId`,
`templateVersion`, `lastSavedAt`, `submittedAt`, `reason` and
`legacyContentHash` were all needed to reconstruct a real `ItemAnswer`, and
are added as optional fields with fold-time fallbacks); `foldAnswerEvents`
and `foldSingleItem`, reproducing `answerStorage.ts`'s existing business
logic (upsert-by-id, the `valueHistory` cap that keeps entry 0 plus the most
recent 19, `history` append semantics, the status-based on-behalf refusal,
`sameUser`'s trim/lowercase normalization) as pure fold steps rather than
inventing new rules — verified faithful by an independent reviewer's live
differential test driving the real `answerStorage.ts` functions against
`createMemoryDirectory()` under a pinned clock and comparing outputs
directly, not just by code reading. Ordering is `(eventAt, eventId)`
primary, `authority` deciding ONLY a same-instant tie (an earlier design
round found making `authority` the primary key would have broken the
reopen-then-correct workflow, the app's core correction loop, by making
every supervisor reopen permanently outrank the employee's own fix it
exists to invite) — proven correct by a reviewer's counterfactual: patching
the comparator back to authority-primary and re-running the suite fails 5
tests by name, including the two regression tests written specifically for
this case. The `migration-seed` marker (§8) hard-fails a chain with events
but no marker, rather than silently returning empty state, per the P0-1
"unreadable never becomes empty" contract this module already guarantees
elsewhere.

Two real findings surfaced during this stage, both deliberately NOT fixed
here (reproduced faithfully instead, since fixing them would be an
undocumented behavior change riding on a storage migration): a supervisor's
`qualityNote` is silently erased by the assignee's next ordinary save today
(`XrayReferrals.tsx`'s save path builds a fresh `ItemAnswer` with no
`qualityNote`, and `upsertItemAnswer` replaces rather than merges) — worth
its own decision later; and `reopenItemAnswer` records no `valueHistory`
entry, unlike an ordinary save.

One correctness fix applied after independent validation, before this
landed: `buildAnswerFoldCheckpoint` was dropping `seeded` (whether a
`migration-seed` has been consumed for a chain) from the persisted
checkpoint shape. In-memory resume (the same session, same `AnswerFoldResult`
object) carried it fine, but a checkpoint reconstructed from DISK — the
whole point of a checkpoint, and what Stage 2's read path will do on every
cold load — would default `seeded` to false and hit the "no migration-seed
marker" hard-failure path on the very next incremental fold: a spurious
"this employee has no answers this month" false negative, one read after
the first checkpoint. Fixed by widening `AnswerFoldCheckpoint` with a
`seeded: boolean` field, populated by `buildAnswerFoldCheckpoint`. A new
regression test reconstructs a resume state using ONLY the fields a
persisted checkpoint actually carries (not the original in-memory result)
and confirms folding new events against it neither throws nor diverges
from a full replay.

**Migration/rollback:** None — this stage has no production callers
(confirmed by `grep -rn "answerEventStore" src/` returning only the module's
own two files). Nothing to roll back; deleting the two new files fully
reverts this stage.
