## v130.4 — 2026-08-30 — Fix (reporting): dead fullscreen selector in deck2 and a scale-script race on fullscreen exit in deck3

**Why:** A systematic re-check of the reported "fullscreen/zoom breaks the layout" bug (v130.3
above fixed the same class of bug in deck3, used by تقرير المجتمع) turned up two more real,
confirmed instances that v130.3 missed: (1) `deck2/theme.ts`'s fullscreen CSS had
`body.deck-fullscreen .srev-footer{display:none;}` — but no element anywhere in the DOM ever
carries class `srev-footer`; the real footer class (`sourceRevisionsFooterHtml`) is
`.source-revisions`. Confirmed via a real headless-Chromium load of the DEFAULT (deckEdition
v2) التقرير التنفيذي export with a populated `sourceRevisions` map: the footer stayed a
visible flex sibling of the active slide inside `.deck-viewer-v2`'s fullscreen flex-center,
pushing the slide flush against the right edge with its title clipped — this is very likely
what the user was actually seeing when they said the bug also applied to "the new التقرير
التنفيذي" (v130.3's PR description incorrectly asserted deck2 was unaffected — it wasn't
independently re-verified with real sourceRevisions data at the time). (2) Separately, the
user reported that toggling fullscreen ON and then back OFF broke the normal (non-fullscreen)
layout, with slide content overlapping the nav sidebar. Traced via a real headless-Chromium
session logging `--v3-scale`/viewer padding across the toggle: `DECK_V3_SCALE_SCRIPT`'s
`fullscreenchange` listener (registered in `<head>`, so attached first) and
`DECK_FULLSCREEN_SCRIPT`'s `fullscreenchange` listener (registered at the end of `<body>`, so
attached second) both fire on the same event; browsers run same-event listeners in attachment
order, so on EXIT the scale script's `fit()` measured `.deck-viewer-v3`'s padding/clientWidth
*before* the fullscreen script's listener had toggled `body.deck-fullscreen` off — reading the
still-fullscreen `padding:0` layout and computing a scale as if there were no nav sidebar to
reserve space for. Nothing re-triggered `fit()` afterward, so the wrong scale (and pixel
`--v3-tx` offset) stuck permanently until the next manual resize, overlapping the slide with
the nav rail exactly as reported.

**What changed:** `deck2/theme.ts`'s dead selector now targets `.source-revisions` (the class
that's actually emitted), matching the equivalent deck3 fix from v130.3. `deck3/index.ts`'s
`DECK_V3_SCALE_SCRIPT` now defers its `fullscreenchange`-triggered `fit()` call to the next
animation frame (`requestAnimationFrame`) instead of running it synchronously inline with the
listener — this reads the DOM only after every same-event listener (including the other
script's class toggle) has finished running, regardless of which `<script>` tag happened to
attach its listener first. The `resize` listener and the initial/DOMContentLoaded call are
untouched (no cross-script race there).

## v130.0 — 2026-08-30 — Fix (backup): scope distribution cache invalidation to actual distribution-segment restores

**Why:** This is **Stage 3** of the answer-save append-only rewrite
(`docs/architecture/ANSWER_SAVE_DELTA_PROPOSAL_2026-08-27.md`, revision 4) —
the design doc's own closing validation stage, per §12: "full whole-repo
gate, a real before/after latency measurement..., and independent
adversarial validation of the diff before it ships." Stages 0 (v127.0), 1
(v128.0), and 2 (v129.0) were each independently reviewed as they landed,
but none of those reviews looked at the three stages together as one
integrated system — this stage is that pass, against the actual merged
`main`, not a branch. It found one real bug that only shows up from the
interaction between two consumers of the same generic module, plus one
benchmark-comment inaccuracy, and added an end-to-end integration test no
single stage's own test suite was positioned to write.

**What changed:** `distribution.events/` and `answers.events/` are
siblings under the same `2-samples/{month}/1-main/` directory
(`getSampleMainDir`). Round 3's §8a fix correctly generalized the backup
restore walk's cache-directory *capture* (`collectJsonRestoreEntries`) to
match any `*.events/`-suffixed directory, not just distribution's literal
name — but the two functions that actually consume that capture,
`invalidateDistributionCaches` and `republishRestoredDistributionStamps`,
are DISTRIBUTION-only side effects (delete
`distribution.current.json`/`distribution.checkpoint.json`, re-mint
`distribution.log.json`'s write token) and were never re-scoped to match.
Because both event directories share one `cacheDir`, a restore that
changed ONLY answer segments still added that shared directory to the
invalidation set — silently deleting distribution's rebuildable derived
cache and broadcasting a "distribution changed" signal to every client,
even though distribution was completely untouched. Not data loss (both
artifacts are rebuildable by design), but a real, confirmed
false-positive/wasted-refold bug, and exactly the class of cross-consumer
interaction a stage-by-stage review cannot see. Fixed by threading
`eventsDirName` through `restoreJsonTree`'s per-entry results and filtering
`cacheDirs` to only entries whose `eventsDirName` is specifically
`DISTRIBUTION_EVENTS_DIR` before calling either distribution-only function.
Answers needs no equivalent here: Stage 2 keeps no persisted checkpoint to
invalidate, and cross-tab freshness already comes from the read-only
bounded segment-size signature §6 wired into the sync tick.

Also fixed: `bench-answer-save-latency.mjs`'s summary line claimed the
wired path's growth was "expected: ~flat," which describes the *primitive*
append's disk cost, not the wired path's real, expected, bounded-by-one-
employee-history fold cost — a future reader could misread normal fold
growth as a regression. Reworded to say what's actually growing and why
it's fine.

Added: `answerFullWorkflow.integration.test.ts`, driving `upsertItemAnswer
→ reopenItemAnswer → upsertItemAnswer (correction) → setItemQualityNote →
upsertItemAnswer` against `createMemoryDirectory()` and checking the
folded state at every step, including a final COLD read (cache explicitly
reset) confirming the fold is a pure function of disk bytes — the kind of
whole-workflow test only the fully-wired system (all three stages) can
exercise.

Specifically probed and found sound, with no bug: `appendOnlyEventLog.ts`'s
module-level writer-memo state (confirmed the only state in the file,
correctly namespaced by `consumerNamespace` for every entry, not just the
ones the design doc named); cross-tab reopen visibility (a save's `previous`
computation always freshly folds from an uncached directory listing, so a
supervisor's reopen in another tab/machine is picked up on the very next
save regardless of any UI-level staleness); single-tab save/read
consistency (the optimistic UI patch after a save is cosmetic only — the
write path itself never trusts it, always folding fresh from disk).

Stage 2 restore path, not a data-format or schema change. Reverting this
one commit restores the pre-fix (over-broad) invalidation behavior; no
