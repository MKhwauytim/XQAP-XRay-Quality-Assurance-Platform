# Edit Log — 2026-08-30

## v128.0 — 2026-08-30 — Feature (answers): Stage 1 -- answers-specific append-only fold logic on the generic event log

**Why:** Stage 1 of the answer-save append-only rewrite
(`docs/architecture/ANSWER_SAVE_DELTA_PROPOSAL_2026-08-27.md`, revision 4).
Stage 0 (merged, v127.0) extracted the generic append-only storage
mechanics from `distributionEventStore.ts` with zero behavior change; this
stage builds the answers-specific event type and fold logic ON TOP of those
primitives, in full isolation — zero production call sites are wired yet,
so this stage changes no runtime behavior of the shipping app. Wiring is
Stage 2, separate follow-up work.

**What changed:** New `answerEventStore.ts`: the `AnswerEvent` type (with a
wider shape than the design doc's original `§3` sketch — `templateId`,
`templateVersion`, `lastSavedAt`, `submittedAt`, `reason` and
`legacyContentHash` were all needed to reconstruct a real `ItemAnswer`, and
are added as optional fields with fold-time fallbacks); `foldAnswerEvents`
and `foldSingleItem`, reproducing `answerStorage.ts`'s existing business
logic (upsert-by-id, the `valueHistory` cap that keeps entry 0 plus the most
recent 19, `history` append semantics, the status-based on-behalf refusal,
`sameUser`'s trim/lowercase normalization) as pure fold steps rather than
inventing new rules — verified faithful by an independent reviewer's live
differential test driving the real `answerStorage.ts` functions against
`createMemoryDirectory()` under a pinned clock and comparing outputs
directly, not just by code reading. Ordering is `(eventAt, eventId)`
primary, `authority` deciding ONLY a same-instant tie (an earlier design
round found making `authority` the primary key would have broken the
reopen-then-correct workflow, the app's core correction loop, by making
every supervisor reopen permanently outrank the employee's own fix it
exists to invite) — proven correct by a reviewer's counterfactual: patching
the comparator back to authority-primary and re-running the suite fails 5
tests by name, including the two regression tests written specifically for
this case. The `migration-seed` marker (§8) hard-fails a chain with events
but no marker, rather than silently returning empty state, per the P0-1
"unreadable never becomes empty" contract this module already guarantees
elsewhere.

Two real findings surfaced during this stage, both deliberately NOT fixed
here (reproduced faithfully instead, since fixing them would be an
undocumented behavior change riding on a storage migration): a supervisor's
`qualityNote` is silently erased by the assignee's next ordinary save today
(`XrayReferrals.tsx`'s save path builds a fresh `ItemAnswer` with no
`qualityNote`, and `upsertItemAnswer` replaces rather than merges) — worth
its own decision later; and `reopenItemAnswer` records no `valueHistory`
entry, unlike an ordinary save.

One correctness fix applied after independent validation, before this
landed: `buildAnswerFoldCheckpoint` was dropping `seeded` (whether a
`migration-seed` has been consumed for a chain) from the persisted
checkpoint shape. In-memory resume (the same session, same `AnswerFoldResult`
object) carried it fine, but a checkpoint reconstructed from DISK — the
whole point of a checkpoint, and what Stage 2's read path will do on every
cold load — would default `seeded` to false and hit the "no migration-seed
marker" hard-failure path on the very next incremental fold: a spurious
"this employee has no answers this month" false negative, one read after
the first checkpoint. Fixed by widening `AnswerFoldCheckpoint` with a
`seeded: boolean` field, populated by `buildAnswerFoldCheckpoint`. A new
regression test reconstructs a resume state using ONLY the fields a
persisted checkpoint actually carries (not the original in-memory result)
and confirms folding new events against it neither throws nor diverges
from a full replay.

**Migration/rollback:** None — this stage has no production callers
(confirmed by `grep -rn "answerEventStore" src/` returning only the module's
own two files). Nothing to roll back; deleting the two new files fully
reverts this stage.

**Before (the bug the seeded-persistence fix closes — `buildAnswerFoldCheckpoint`):**
```ts
export type AnswerFoldCheckpoint = AppendOnlyFoldCheckpoint;

export function buildAnswerFoldCheckpoint(
  result: AnswerFoldResult,
  segmentOffsets: Record<string, number>
): AnswerFoldCheckpoint {
  return {
    segmentOffsets: { ...segmentOffsets },
    knownEventIds: [...result.foldedEventIds],
    deriveVersion: ANSWER_DERIVE_VERSION,
    eventSetId: result.eventSetId,
  };
}
```

**After:**
```ts
export type AnswerFoldCheckpoint = AppendOnlyFoldCheckpoint & { seeded: boolean };

export function buildAnswerFoldCheckpoint(
  result: AnswerFoldResult,
  segmentOffsets: Record<string, number>
): AnswerFoldCheckpoint {
  return {
    segmentOffsets: { ...segmentOffsets },
    knownEventIds: [...result.foldedEventIds],
    deriveVersion: ANSWER_DERIVE_VERSION,
    eventSetId: result.eventSetId,
    seeded: result.seeded,
  };
}
```
