## v131.8 — 2026-09-01 — Fix (user-management): guard against losing a newly-added or edited user to a page reload before its disk write lands

**Why:** Reported bug: an admin creates a new user (role `guest`), sees it appear in the User Management list, refreshes the page, and the user is gone — and can't sign in as it. Root cause: `UserManagementTab` (`TabView.tsx`) writes every add/edit/delete to the shared in-memory runtime state and shows a success toast immediately, but the matching disk write (`syncUserManagementToDisk` → `3-user-data/users.permissions.json`, the sole persistence for the managed roster — see CLAUDE.md's "Two persistence layers") is fire-and-forget (`void saveUsersToDisk(next)`), with no completion guarantee and no guard against navigating away. A page reload discards the entire runtime module state (it's a plain in-memory JS variable) and, on reconnect, rebuilds it purely from whatever last actually landed on disk. If the admin reloads before that write lands, the new user never existed as far as disk is concerned — permanently, since disk is the only persistence layer for managed users. This is not guest-specific; it can drop any add/edit/delete on this page, but is most visible on "add a user" because that's the action most likely to be immediately followed by a confidence-checking refresh.

**What changed:** `UserManagementTab` now tracks how many `saveUsersToDisk()` calls have not yet resolved (`pendingDiskSaveCountRef`) and mirrors that into reactive state (`hasPendingDiskSave`), then wires it into the app's existing `useUnsavedWork` hook (the same mechanism built for the InspectionPanel draft-loss incident: `useUnloadGuard` prompts the browser's native "leave site?" confirmation before a reload/close, and `unsavedWorkRegistry` pins the tab against the tab-mount LRU eviction) for as long as any disk write requested by this tab is still in flight. No change to the write path itself, the roster's on-disk shape, or any other behavior — this only closes the window in which a reload can silently discard a write that hasn't landed yet.

**Before:**

const savingToDiskRef = useRef(false);

// ...

  if (!directoryHandle) return Promise.resolve();
  return coalesceToLatest(savingToDiskRef, pendingStateRef, async (state) => {

**After:**
```ts
const savingToDiskRef = useRef(false);
const pendingStateRef = useRef<UserManagementState | null>(null);
const pendingDiskSaveCountRef = useRef(0);
const [hasPendingDiskSave, setHasPendingDiskSave] = useState(false);
// ...
const saveUsersToDisk = useCallback((next: UserManagementState): Promise<void> => {
  if (!directoryHandle) return Promise.resolve();
  pendingDiskSaveCountRef.current += 1;
  if (pendingDiskSaveCountRef.current === 1) setHasPendingDiskSave(true);
  return coalesceToLatest(savingToDiskRef, pendingStateRef, async (state) => {
    const actor = readSession()?.username ?? "admin";
    await syncUserManagementToDisk(directoryHandle, state, actor);
  }, next).finally(() => {
    pendingDiskSaveCountRef.current -= 1;
    if (pendingDiskSaveCountRef.current === 0) setHasPendingDiskSave(false);
  });
}, [directoryHandle]);

useUnsavedWork(TAB_ID, hasPendingDiskSave);
```

## v131.6 — 2026-09-01 — Fix (employee-workspace): stop the results screen's periodic refresh from re-reading the whole month on every tick

**Why:** The results screen (صور الأشعة - النتائج, `XrayInspectionResults`) unconditionally re-runs its full `loadData` — whole-month `sample.master.json`, distribution derivation, distribution log, referral/replacement logs, and (for a supervisor) every employee's answer file — on every app-wide data-refresh broadcast, including the periodic ~45s sync tick, regardless of whether anything relevant to this screen changed. `XrayReferrals` and `useApprovalData.ts` already moved to the family-scoped `subscribeToDataChange`; this screen was still on the blanket `subscribeToDataRefresh`, so an idle tab paid the full read cost every tick. A prior investigation found population is already correctly never loaded for employees, and population/sample/distribution files are already gzip-compressed above 2,000 rows (`storagePolicy.ts`) — this fix targets the one remaining unaddressed cost: needless periodic reloads. A prior attempt at also deferring the referral/replacement-log reads to first tab visit was dropped after finding it would reintroduce the exact "no refetch on view-mode toggle" regression an existing test already guards against, for files that are small to begin with.

**What changed:** `XrayInspectionResults`'s periodic-refresh subscription now uses `subscribeToDataChange(RESULTS_REFRESH_FAMILIES, …)` with `RESULTS_REFRESH_FAMILIES = ["requests", "distribution", "answers"]` (the same list `useApprovalData.ts`'s `DECISION_REFRESH_FAMILIES` already uses for the same data) instead of the blanket `subscribeToDataRefresh`. A periodic tick that changed only an unrelated family (notifications, feedback, manifest) now costs nothing; a manual toolbar refresh still always reloads (`subscribeToDataChange`'s unconditional "manual" semantics), and the initial mount / view-mode-toggle behavior is unchanged. No workspace file format changed — nothing here requires the admin-migration flow.

## v131.4 — 2026-09-01 — Add (changelog): سجل التحديثات tab — latest 10 updates, generated at build time from edit logs

**Why:** Owner request: a new top-level tab, «سجل التحديثات», showing the app's own latest 10 updates. The open design question was where that content comes from, since the app has no backend and no LLM at runtime to turn an edit-log entry into a plain-language summary the way a human (or an offline assistant session) can. Two options were on the table: (a) a hand-maintained Arabic list, kept current by whoever writes each day's edit-log entry, or (b) a script that mechanically extracts each entry's own heading (category + title) from `docs/edit logs/` at build time — always in sync, but showing the entry's original English/technical wording rather than a translated summary. The owner chose (b). Rejected: re-embedding the *entire* edit-log history into the bundle, which is exactly what the old "سجل الإصدارات" tab did before it was removed in v72.0 (2026-08-13) for bloating the single-file build; this stays small by keeping only the newest 10 entries.

**What changed:** Added `scripts/generate-changelog-data.mjs`, which reads every `docs/edit logs/*.md` file, parses each top-level `## vX.Y — YYYY-MM-DD — Category (scope): Title` heading, maps the CLAUDE.md category to one of four display buckets (Fix/Security → إصلاح, Add/Feature → ميزة جديدة, Change/Remove → تحسين, Refactor → إعادة تصميم — Docs/Chore/Test/Merge/anything else is dropped as internal housekeeping), sorts by date then version descending, and writes the newest 10 as `src/data/changelog/latestUpdates.generated.ts`. Wired as a `pre*` hook on `dev`, `build`, `typecheck`, `test`, and `test:run` in `package.json` so the generated file can never silently go stale relative to the edit logs — it regenerates before every one of those commands, and the freshly generated copy is also committed so a plain `git clone` + open-in-browser (no npm install) still shows real, if slightly older, content. Added the new tab itself, `src/components/Sidebar/Tabs/Changelog/`: a read-only list of the 10 entries, each with a colored bucket badge (reusing the existing `.ui-badge` variants — no new colors), its date (formatted in Arabic), version tag, and title (kept LTR/English inline, since there is no translation path for it). Registered in `tabCatalog.ts` as `changelog` (group "system", `ALL_ROLES` ceiling, no explicit `createDefaultPermissions()` row — every non-admin role defaults to "none" via the existing fallback, same pattern as `population/adhoc-import`'s admin-only launch default: grantable, not granted). Added six `changelog_*` label keys to `labelsStore.ts` for the tab's own chrome (title/subtitle/bucket names/empty state); they fall through automatically into Settings' generated "أخرى" label group, so no change was needed there.

**Migration/rollback:** No on-disk workspace format changes — this tab reads nothing from the user's workspace folder, only from the repo's own `docs/edit logs/` at build time. Rollback is deleting the tab's catalog entry, its `src/` folder, `src/data/changelog/`, the generator script, and the five `pre*` package.json hooks.
