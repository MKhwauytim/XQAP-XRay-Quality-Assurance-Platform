## v99.6 — 2026-08-19 — Add (reporting): bridge entry day, محضر flag, and risk-engine value onto the report row

**Why:** Two upcoming report pages — a per-day accuracy trend and a risk-engine agreement
page — need three population-row fields that never made it onto `ExecutiveReportRow` or the
`DecisionRecord` fact table: the calendar day an image entered, whether its risk row carried
a محضر (seizure report) number, and the raw risk-engine targeting value. This task is scoped
to just carrying those three fields through the pipeline (population row → report row →
decision record); no page consumes them yet.

**What changed:**
1. New `entryDayOf(iso)` in `src/data/reporting/executive/model/entryDay.ts` extracts the
   day-of-month (1–31) from `PreparedPopulationRow.xrayEntryDate`. It deliberately does not
   parse dates — Phase 2's `normalizeDate` (`populationProcessor.ts`) already normalizes the
   field to ISO `YYYY-MM-DD`, so a second parser would be a second source of truth. What it
   does handle is `normalizeDate`'s documented fallback of returning unparseable input
   unchanged: anything that is not a well-formed ISO date with an in-range day (bad shape,
   non-ISO format, day `00` or `32`+) returns `null` rather than being guessed at, so the
   trend page can bucket it as غير مؤرخ.
2. `ExecutiveReportRow` gained three optional fields (`entryDay`, `hasReport`,
   `targetedByRiskEngine`), populated in `buildExecutiveReportRows` from `pop.xrayEntryDate`
   (via `entryDayOf`), `pop.reportNumber` (trimmed non-blank check), and
   `pop.targetedByRiskEngine` (carried through raw — the flag→verdict mapping belongs to the
   future risk-engine page, not this bridge).
3. `DecisionRecord` gained `entryDay` and `hasReport` (both optional), populated in
   `buildLevelRecord` from the corresponding report-row fields with null/false defaults.
4. All five new/changed fields are optional so the nine existing hand-built
   `ExecutiveReportRow` fixtures and the `DecisionRecord` literals in `reviewerKpis.test.ts`
   compile unchanged.

## v99.5 — 2026-08-19 — Add (reporting, dev): one-command static export of the executive deck, plus a section-4 fixture and a content/scope map for the rework

**Why:** The executive deck is about to be reworked, and there was no cheap way to look at the
finished thing. The only preview was `npm run dev` → `deck-preview.html`, which needs a dev
server running to read a report that is, by design, a self-contained static file. Worse, the
preview fixture passed `distribution: null`, so `model.distributionCoverage` and
`model.accountabilityProgress` were both null and the whole of section 4 rendered its empty
state — the preview could not show two of the deck's twenty-four pages at all.

**What changed:** Three things, all dev-side; no app or report code was touched.

1. `scripts/export-exec-report-static.mjs` (+ `npm run report:static`) renders the live deck to
   `dist-preview/executive-report.html`, a standalone file you can double-click. It runs the
   real TypeScript through Vite's SSR module loader (`createServer({ middlewareMode })` +
   `ssrLoadModule`) rather than a build or a bare node import — the deck pulls in `?inline`
   font assets that plain node cannot resolve, and this keeps the transforms identical to
   `npm run dev` without ever opening a port. `--variant-preview` embeds the style-variant
   arrows; a path argument writes elsewhere.
2. `src/dev/deckPreviewFixture.ts` gained `buildPreviewDistribution` — a deterministic
   synthetic distribution over the drawn sample (5 named reviewers, ~78% completed / 16%
   pending / replacements and replacement-requests, plus the matching `assigned` / `completed` /
   `reassigned` event history and replacement reasons), driven by the same seeded LCG as the
   rest of the fixture so the preview stays byte-stable across reloads. Section 4 now renders
   real coverage buckets, per-employee progress, replacement reasons, and a reassignment count.
3. `docs/product/EXECUTIVE_REPORT_CONTENT_MAP.md` documents the full chain from the raw risk/BI
   Excel upload to a submitted answer (17 stages, with the file each is stored in), the deck
   page by page with the model fields each page reads, and the scope brief for the rework
   (in/out of scope, the hard constraints, the open decisions).

`vite.static-preview.config.ts` is a three-line static server rooted at `dist-preview/` so the
exported file can be opened in a browser without `file://` restrictions; `.claude/launch.json`
gains a matching entry and `.gitignore` excludes `dist-preview/` (a regenerable artifact).

Two real defects surfaced while reading the rendered output and are recorded in the content map
rather than fixed here (the rework will touch both pages anyway): section 4's coverage page
groups by `e.row.stage`, which holds the raw Excel alias, so its by-level table reads
`FIRST_STAGE` / `SECOND_STAG` / `THIRD_STAGE` / `FORTH_STAG` instead of the canonical Arabic
labels every other page uses; and `sideRail` lists only four tabs, so section 4's pages print a
rail with no active tab.
