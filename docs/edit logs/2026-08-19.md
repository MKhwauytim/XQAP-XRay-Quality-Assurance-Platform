## v99.10 — 2026-08-19 — Fix (auth-admin, samples): ad-hoc-aware deletion footprint + block username rename that would orphan on-disk work

**Why:** Two admin-side guards that decide something irreversible were reading an incomplete picture of what a user owns on disk. (1) `getUserWorkspaceFootprint` — the pre-deletion safety check — walked only `listMonthFolders`, which enumerates `1-population/` and structurally cannot return an ad-hoc import's synthetic `2-samples/adhoc-{importId}/` store. Ad-hoc rows are assigned through the exact same event-log + mirror-sync path as a real month, so a user whose entire live workload came from ad-hoc imports reported an EMPTY footprint: User Management read that as "no active assignments, safe to delete" and deleting them orphaned every assignment and answer they owned. This is the fourth recurrence of the "month-folder walkers forget the ad-hoc store" class, which is why `adhocImportEmployeeView.ts` already exports `listAdhocSampleFolders`/`adhocMonthFolderName` and warns about exactly this in its docblock. (2) Every on-disk record keys on the raw username string — `{username}.answers.json`, `{username}.samples.json`, `assignedTo`/`answeredBy`/`eventBy` inside immutable distribution events, the per-user quota map, referral/replacement requests, approvals, notification acknowledgements — and nothing migrates them. The event log being append-only and immutable, nothing cheaply can. Renaming a user in the User Management tab was nevertheless a plain in-place field edit, so it silently orphaned all of that: the rows stayed assigned to a login that no longer exists, the employee's own view went empty, and the reports kept attributing the work to a name nobody can log in as.

**What changed:** `getUserWorkspaceFootprint` now scans real month folders AND ad-hoc stores, reusing `listAdhocSampleFolders` rather than re-deriving the folder names. Ad-hoc folders skip the `isMonthClosed` probe (they have no `month.manifest.json`, so the month lock is meaningless for them and would fail open anyway) and always count their pending work — the safe direction for a pre-deletion guard. Both the assignment and the answer halves of the footprint flow into the warning/blocking deletion UX unchanged. New `src/auth/usernameRenameGuard.ts` turns that same footprint into a rename decision: a username change is BLOCKED when the user has any activeAssignments or answerFileMonths, and fails CLOSED when the footprint cannot be established at all — no workspace mounted, or the scan itself throws (an unreadable mirror propagates by design; "I could not look" is not "there is nothing there"). Deletion and rename now share one definition of "has work on disk" instead of drifting apart. `handleSaveIdentity` became async and consults the guard only when the username actually changes; a rename with a genuinely empty footprint still succeeds. Reviewer correction, implemented: a rejected rename does NOT reject the display-name edit submitted through the same form — the display name is not a key for anything on disk, so discarding it would be a second, unrelated loss of the admin's work; it is saved, the draft is reset so the username input stops showing an edit that was not applied, and the Arabic explanation names the reason and what to do instead (three new label keys, no hard-coded strings).

## v99.8 — 2026-08-19 — Fix (population/distribution): tell an unreadable month from an empty one, and stop bulk assignment skipping unmapped stages in silence

**Why:** Two defects on the same theme — the app knows something the operator needs and says the opposite, or nothing at all. Both sit in the population pipeline, and both point the user at an action that is worse than doing nothing.

## v99.7 — 2026-08-19 — Fix (backup/sync/pages-ui): make a restore visible to the fleet, stop spurious refreshes from failed probe reads, and surface an interrupted restore

**Why:** Three defects that all share one shape — the app knows something important and never tells anyone.

1. **A completed restore was invisible to every other machine on the share.** `distribution.log.json` is classified `restore-if-absent` by `restoreActionFor`, deliberately: writing a backup's older revision over a newer live one would roll the revision backwards and drop events. But that file carries the *only* stamp the 45s sync probe compares for the `distribution` family (`readDistributionLogStamp` → `revision` + `_writeToken`). So a restore that merged real events back into `distribution.events/` moved durable assignment data while leaving the watched stamp frozen — and every other client kept serving its pre-restore snapshot indefinitely, until somebody happened to press the manual refresh button. Nothing on screen suggested a restore had happened at all.
2. **The probe could not see the event segments, and treated a failed read as an observation.** The segments are covered by the projection's CAS stamp only while the two move together; a restore breaks that (above), and so does an append whose segment write landed but whose projection write did not. Separately, every probe family degraded a *failed* read to a neutral placeholder (`revision: -1`, `""`) and then stored that placeholder as the new baseline — so the next healthy tick differed from it and broadcast a change nobody made. One transient SMB blip therefore cost every client a spurious refresh, and a refresh is not free: it has already been a real bug that one clobbers unsaved draft state.
3. **`restore.inprogress.json` was written and then ignored.** `restoreBackupSnapshot` writes the sentinel before its destructive walk and removes it only on success — deliberately leaving it behind when the walk throws, because that is the only evidence an interrupted restore leaves. No code anywhere read the file. A workspace left half-old and half-new looked exactly like a healthy one.

**What changed:**

- **`distributionStorage.ts` — new `refreshDistributionLogWriteToken(dir)`.** Re-mints `distribution.log.json`'s `_writeToken` under `casLoop` while leaving `revision`, `events` and everything else byte-for-byte as read. The revision is deliberately *not* bumped: it is the mirror-staleness authority (`sourceLogRevision`) and advances only on an event append. Only the token moves, which the probe compares just as strictly and nothing else treats as ordering. Never throws — a restore must not fail because a change-detection stamp could not be refreshed.
- **`backupStorage.ts` — `republishRestoredDistributionStamps`.** Called from `restoreJsonTree` with exactly the directories whose segments the restore actually *rewrote* — the same set `invalidateDistributionCaches` already receives — so an idempotent no-op restore still broadcasts nothing. Best-effort per directory, mirroring the cache-invalidation walk beside it.
- **`directoryScan.ts` — new `boundedSizeSignature(dir, suffix, maxStats)`.** One directory listing, no file *content* read, and at most `DEFAULT_SIZE_SIGNATURE_STAT_BUDGET` (64) `getFile()` size probes, taken from the **tail of the name-sorted listing** so the sampled set is stable tick to tick — a signature that reshuffled its own sample would report an untouched month as changed. **Why:** The department's biggest workspaces are large, old and on an SMB share — and on exactly those, the app could lose assignment data *and* be unable to take the backup that would have recovered it.

1. **The daily backup failed entirely on a big legacy workspace (STO-2).** `copyAllJsonFiles` moved every file as a decoded JavaScript **string** (`file.text()` → `writable.write(text)`). Real customer data is already at ~85 % of that ceiling (a 573 MB `bi.raw.json` decodes to ~456M code units), which is why `safeWriteJson`'s own write path was made streaming in the first place; the backup walk was the one place still holding a whole file as one string. 2. **No copy was ever verified (STO-5).** Nothing read a copy back. A share that dropped mid-flush, a disk that filled, an antivirus truncation — any of them left a short or damaged file inside a folder whose `backup.manifest.json` listed it as backed up and whose `backup.complete.json` sentinel certified the snapshot. The admin found out at restore time, which is the one moment the backup is supposed to be worth something.
3. **`users.permissions.json` had its revision counter reset by a read blip.** `syncUserManagementToDisk` reads the existing file inside its `casLoop` attempt and did `prevMeta = existing.ok ? … : null` — collapsing *every* failure reason into "there is no file yet".
