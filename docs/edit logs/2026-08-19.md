## v101.1 — 2026-08-19 — Add (population import, observability): duplicate-normalizing-header diagnostic and persisted error log

**Why:** Two owner-ruled deferred items from Batch 4 of the five-domain revision plan.

(1) `duplicate-normalized-headers`: `createHeaderLookup` in both `riskDataNormalizer.ts` and
`biDataNormalizer.ts` builds a `Map` keyed by normalized header, so when two *different* source
column headers normalize to the same key (e.g. one carries a stray diacritic or zero-width mark the
other doesn't), `Map.set`'s last-write-wins silently drops the first column's contribution to that
field with no trace anywhere. The owner's ruling: don't touch precedence (an existing workbook's
field could start reading a different column mid-history) — add a pure, additive detection-only
diagnostic instead, so the operator can at least see that two columns collapsed.

(2) `persist-error-log`: the in-memory error ring buffer (`errorLogger.ts`) died with the tab exactly
when a user says "it broke and I reloaded" — the one moment its contents matter most. The owner's
ruling: mirror it to `localStorage` (browser-local, not the workspace folder — sidesteps `safeWrite`
recursion, read-only-handle handling, and shared-disk retention policy entirely), governed by the
existing `storageRegistry.ts` convention.

**What changed:**

(1) Added `detectDuplicateNormalizedHeaders(headers: string[])` — a pure function — to both
normalizer files, using the same `normalizeHeader` the hot-path lookup itself uses. Each workbook's
per-sheet ingestion loop (`riskDataWorkbook.ts`, `biDataWorkbook.ts`) calls it exactly ONCE per sheet,
from `Object.keys(sourceRows[0].row)` — never per data row, so `normalizeRiskRow`/`normalizeBiRow`'s
hot path is untouched. A non-empty result is attached to that sheet's summary as
`duplicateHeaders?: DuplicateHeaderCollision[]` (new field on `RiskSheetSummary`/`BiSheetSummary`,
mirrored per-file the same way `ZeroXrayIdDiagnostic` already is). `PhaseOneUpload.tsx`'s
`RawFileSummaryCard` renders one warning `<p role="alert">` per collision, via a new label key
`phase_one_duplicate_headers_warning` in `labels.phaseOne.ts` (this screen's existing label-file
split), listing the normalized key and the colliding original headers. `createHeaderLookup`,
`getFirstAvailableValue`, and the last-write-wins precedence are byte-for-byte unchanged — proven by
a test that runs `normalizeRiskRow`/`normalizeBiRow` on a row with a real diacritic-noise collision
and asserts the resolved field equals the same row with only the winning header present.

(2) `errorLogger.ts`: `logError` now mirrors the ring to `localStorage["xray_error_log_v1"]` after
every push, with `context`/`message`/`stack` truncated to 100/500/500 chars. The mirror call is
wrapped in try/catch (quota/serialization failures are swallowed, never surfaced to the caller that
just reported a real error) plus a module-level `isPersisting` boolean so a persistence failure can
structurally never re-enter persistence. Module init hydrates the ring from the stored key if present
and parseable, tagging every restored entry `restored: true` so the UI (unchanged in this batch) could
later distinguish "logged this session" from "carried over from before a reload". `clearErrors` now
also removes the key. `typeof localStorage === "undefined"` (the default Node test environment) is
checked before every access, so the existing Node-env `errorLogger.test.ts` suite runs identically.
Registered `xray_error_log_v1` in `storageRegistry.ts` (purpose + loss consequence) per the existing
single-source-of-truth convention; `storageKeyCoverage.test.ts` continues to pass unmodified since the
key is referenced through a named constant, the same pattern every other registered key already uses.

## v101.0 — 2026-08-19 — Change (distribution): row-set fingerprint on the derived cache, DERIVE_VERSION 4

**Why:** Three deferred findings from the five-domain revision plan, all on the same primitive, ruled
and batched together so every workspace pays the cache invalidation **once** instead of three times.
The shared defect: `distribution.current.json` was validated on `logRevision` + `eventSetId` +
`deriveVersion`, and none of those three can see the ROW set a fold ran against. A replacement
appends a row to `sample.master.json` without appending an event, so all three fields stay identical
while the row set the fold must run against has changed — a cache derived from the pre-replacement
rows was served, and on the checkpoint-resume path extended, for a row set it was never derived from.
The same blindness sat in the session derive memo, whose key discriminated row sets by
`sampleRows.length` alone: a replacement swap (one row retired, one appended) keeps the count
identical, so two different row sets shared one memo entry for the rest of the workspace epoch.

Rejected: doing the three separately (three DERIVE_VERSION bumps, three full refolds per month per
workspace); and hashing content rather than ids (the fold only ever keys on `xrayImageId`, so a
content hash would invalidate caches on cosmetic row edits for no correctness gain).

**What changed:**
- **`sampleRowsFingerprint(rows)`** (new, `distributionLog.ts`) — djb2 over the rows' `xrayImageId`s
  joined with `|`, order-sensitive, prefixed with the row count (`2:c690b79`). Order-sensitive
  because the fold is not commutative and callers legitimately pass differently-ordered/filtered sets
  (`liveSampleRows` drops retired rows on purpose); count-prefixed so two different-length sets can
  never collide whatever the hash does. Streamed rather than materializing the join — it runs on
  every derive-memo lookup, and a 200k-row month would otherwise allocate a multi-megabyte string
  each time. A test pins it bit-identical to `hashSeedString(ids.join("|"))`.
- **Both derive paths stamp it** onto `DistributionCurrentData.sampleRowsFingerprint` (new optional
  field), full and incremental alike.
- **Every acceptance check requires it to match** the rows in hand: the fast path, the sidecar read,
  and checkpoint-resume. An absent field (any pre-v4 cache) never matches, so it reads as stale.
- **`DERIVE_VERSION` 3 → 4.** Validity semantics, not fold semantics: a v4 refold produces byte-identical
  ENTRIES to what v3 produced from the same events and rows, so no historical derivation is
  reinterpreted. The bump exists so the one-time invalidation is explicit and dated rather than a
  cache that is silently rejected forever.
- **The write path now stamps the full set** (`useDistributionActions.refreshDistribution`). It used
  to stamp `logRevision` only, so the reader rejected every cache it wrote and paid a full refold
  immediately after the most expensive write in the app. Now safe to make authoritative because
  acceptance is a four-field match, each field independent (any appended event moves `eventSetId`,
  any changed row set moves the fingerprint), and because this call site re-reads `sample.master.json`
  fresh on every call and already refuses to persist a zeroed derive while events exist.
  `eventSetId` is stamped **only when the log carries one** — a legacy log with no digest must leave
  the field absent rather than claim an identity nothing can re-verify. The long comment at that call
  site, which described the old contract and its (now-resolved) blockers, is rewritten.
- **The derive memo key** uses the fingerprint instead of `sampleRows.length`, which it strictly
  subsumes. In-memory only, session-scoped, no on-disk implication.

Deliberately left as-is: `loadOrDeriveDistributionCurrentForRead`'s in-flight dedupe key still
discriminates by `sampleRows.length`. Same defect class, outside this batch's ruling — noted for the
next pass rather than folded in silently.

**Migration/rollback:** No on-disk format migration and no rewrite of any stored file. Every existing
`distribution.current.json` and `distribution.checkpoint.json` — v3 or older, numbered or legacy
layout — is simply not accepted on the first load after upgrade and is refolded from the event files,
which remain the sole source of truth. **Cost: one full refold per month per workspace, once**,
bounded thereafter by the fresh cache and the derive memo; on the largest observed month that is the
same fold a DERIVE_VERSION bump has always paid (pinned by the v2 and v3 refold tests).
**Non-replayability:** a v3-stamped cache cannot be validated under v4 code and a v4-stamped cache
cannot be validated under v3 code — by design, in both directions. **Rollback:** revert
`DERIVE_VERSION` to 3 and the acceptance checks with it; v4 caches then fail the version check and
refold. No data is lost in either direction, because no event file is touched by any of this.

## v100.0 — 2026-08-19 — Add (templates): a customs-declaration phase in the default inspection template, and a multiselect field type to carry it

**Why:** The default inspection template asked the reviewer to judge the scan
(«ضمان جودة النتيجة») without ever asking what the shipment was *declared* to
be, so "the load does not match its declaration" had nowhere to be recorded and
never reached a report. A phase for reading the customs declaration now sits
between the image-quality check and the result judgement, so the reviewer knows
what they should be seeing before they judge what they saw.

Three shapes were rejected on the way:

- **Separate «هل يوجد اختلاف؟» and «نتيجة المطابقة» fields.** Two fields carry
  one judgement and can disagree with each other inside a single submitted
  answer. One verdict field, `هل الوارد مطابق للبيان الجمركي`, replaces both.
- **A commercial cargo vocabulary** (مواد غذائية / مواد صلبة / …). Those are
  tariff families, not X-ray signatures: canned food, sacked rice and frozen
  bulk share a category but nothing an operator can recognise in an image, and
  «مواد صلبة» would absorb most answers while distinguishing nothing. The
  categories are density/homogeneity/shape ones instead — and declared and
  observed deliberately draw from the SAME list, because two vocabularies would
  make the comparison, which is the entire point of the phase, meaningless.
- **`combobox` + free text for the multi-answer fields.** It needed no new
  field type, but a reviewer typing free text where several fixed options apply
  produces exactly the un-countable data this phase exists to replace.

**What changed:**

*Schema.* `TemplateFieldType` gains `"multiselect"`. Its answer is stored as the
selected options joined by `MULTISELECT_SEPARATOR` (`" | "`) in the existing
`FieldAnswer.value` string — NOT as an array. `FieldAnswer.value` is
`string | number | boolean | null` and is read by the report builders, the Power
BI CSV export and the per-item value-history snapshots; widening it to an array
would have to land in all of them at once, whereas a joined string leaves every
existing reader working and stays legible in a report cell. `serializeMultiValue`
is the only writer: it strips `|` out of option text so an option cannot forge a
boundary, and emits options in the template's declared order, so two employees
who pick the same set store a byte-identical string and group together when
counted. `toggleMultiValue` keeps a selection the template no longer offers
rather than silently dropping it.

*Conditions.* `evaluateCondition` now takes the source field, and on a
`multiselect` source reads `equals` as "this option is among those picked"
(`notEquals` as its negation). A plain string comparison against the joined value
would only ever match when exactly one option happened to be selected, so a
dependent field would vanish the moment the reviewer picked a second. An
unanswered multiselect still satisfies neither equality branch, unchanged.

*UI.* `InspectionPanel` renders a multiselect as a wrapping group of
`aria-pressed` toggle buttons — a native `<select multiple>` needs ctrl/cmd-click
to add a second option and drops the rest of the selection on a plain click,
which is the mistake this field exists to prevent. Required-ness counts a
multiselect as answered once one option is picked; the read-only view rejoins it
with an Arabic list separator. The Template Builder offers the new type, edits
its options through the existing options editor, strips `|` from option text as
it is entered, and treats a multiselect source like a dropdown when authoring a
condition against it.

*Default template.* Now three phases: `ضمان جودة الصورة` (unchanged) →

**Why:** Three ways the reporting surfaces were dishonest about what they knew. (1) Report Designer's autosave effect is scoped to `[doc]`, and that effect also runs on the FIRST commit — so merely OPENING a saved design scheduled a write-back of the untouched loaded document 800ms later. ## v99.7 — 2026-08-19 — Fix (backup/sync/pages-ui): make a restore visible to the fleet, stop spurious refreshes from failed probe reads, and surface an interrupted restore

**Why:** Three defects that all share one shape — the app knows something important and never tells anyone.

1. **A completed restore was invisible to every other machine on the share.** `distribution.log.json` is classified `restore-if-absent` by `restoreActionFor`, deliberately: writing a backup's older revision over a newer live one would roll the revision backwards and drop events. But that file carries the *only* stamp the 45s sync probe compares for the `distribution` family (`readDistributionLogStamp` → `revision` + `_writeToken`). So a restore that merged real events back into `distribution.events/` moved durable assignment data while leaving the watched stamp frozen — and every other client kept serving its pre-restore snapshot indefinitely, until somebody happened to press the manual refresh button. 2. **The probe could not see the event segments, and treated a failed read as an observation.** The segments are covered by the projection's CAS stamp only while the two move together; a restore breaks that (above), and so does an append whose segment write landed but whose projection write did not. Separately, every probe family degraded a *failed* read to a neutral placeholder (`revision: -1`, `""`) and then stored that placeholder as the new baseline — so the next healthy tick differed from it and broadcast a change nobody made. One transient SMB blip therefore cost every client a spurious refresh, and a refresh is not free: it has already been a real bug that one clobbers unsaved draft state.
3. **`restore.inprogress.json` was written and then ignored.** `restoreBackupSnapshot` writes the sentinel before its destructive walk and removes it only on success — deliberately leaving it behind when the walk throws, because that is the only evidence an interrupted restore leaves. ## v99.6 — 2026-08-19 — Fix (backup/storage/user-sync): byte-copy and verify every backup file, keep an unreadable identity file from resetting its revision, and add a legacy/mixed workspace fixture

**Why:** The department's biggest workspaces are large, old and on an SMB share — and on exactly those, the app could lose assignment data *and* be unable to take the backup that would have recovered it.

1. **The daily backup failed entirely on a big legacy workspace (STO-2).** `copyAllJsonFiles` moved every file as a decoded JavaScript **string** (`file.text()` → `writable.write(text)`). Past V8's max string length (~536,870,888 UTF-16 code units) that read throws `RangeError: Invalid string length`, and the throw propagated out of the concurrent walk, out of `copyAllJsonFiles`, into `createBackup`'s catch — so **one** oversized legacy `risk.raw.json` / `bi.raw.json` meant the whole workspace could never be backed up again. Real customer data is already at ~85 % of that ceiling (a 573 MB `bi.raw.json` decodes to ~456M code units), which is why `safeWriteJson`'s own write path was made streaming in the first place; the backup walk was the one place still holding a whole file as one string. The text round trip also forced a special case for compressed files, since decoding a gzip member as UTF-8 and re-encoding it is lossy.
2. **No copy was ever verified (STO-5).** Nothing read a copy back. A share that dropped mid-flush, a disk that filled, an antivirus truncation — any of them left a short or damaged file inside a folder whose `backup.manifest.json` listed it as backed up and whose `backup.complete.json` sentinel certified the snapshot. The admin found out at restore time, which is the one moment the backup is supposed to be worth something.
3. **`users.permissions.json` had its revision counter reset by a read blip.** `syncUserManagementToDisk` reads the existing file inside its `casLoop` attempt and did `prevMeta = existing.ok ? … : null` — collapsing *every* failure reason into "there is no file yet". A single transient `NotReadableError` (idle SMB session, antivirus lock) or a revoked grant therefore produced a write with `revision: 1`, `createdAt`/`createdBy` re-stamped to now/this admin, and the whole roster replaced by whatever this machine happened to hold. Measured on the unfixed source: a revision-**42** file with one manager came back as revision **1**, `createdBy: admin`, roster replaced. That is the identity file — users, roles, permissions, Argon2id hashes — and its `revision` + `_writeToken` pair is the *only* lost-update detector every other machine has.
4. **Nothing was ever tested against a legacy or mixed layout.** `workspacePaths.ts` resolves each root numbered-first with a permanent legacy fallback and there is no migration, so field workspaces stay unnumbered (`Population/`, `.system/`, `templates/`) or half-migrated forever — and every storage-level walk had only ever been exercised against a freshly-created numbered tree.

**What changed:**

- **`safeWrite.ts` — new `copyFileBytesVerified`.** Byte-windowed copy (no decode, no `JSON.parse`, no envelope assumption, so it is size- and format-agnostic) that then re-opens the **written copy** and compares its size and a two-accumulator byte digest against the **bytes this call actually read**. ## v99.5 — 2026-08-19 — Fix (storage/pages-ui/distribution): retry SMB lock contention, route ad-hoc quality notes, and never persist a fold that absorbed events

**Why:** Three defects that all end the same way on a large, busy SMB workspace — assignment data quietly disappears, or the recovery the user is offered cannot work.

1. `NoModificationAllowedError` was classified as terminal permission loss. On a shared Windows/SMB folder that name means the entry is **locked by another writer** — another tab, or another machine mid-write — which is a timing condition, not a revoked grant. `casLoop` aborted on the first one and told the user "فقد الوصول إلى مجلد العمل — أعد الاتصال بمساحة العمل", whose only remedy (re-pick the folder) is powerless against someone else's open handle; `isTransientWriteError` likewise refused to retry it, so `safeWriteJson` failed a write that a 20 ms retry would have completed. This is the mirror image of the doctrine this repo already enforces on the read side: "could not read" is not "does not exist", and "could not write right now" is not "the workspace is gone".
2. Quality-note **writes** for an ad-hoc row were routed to the globally-selected month's answer store, while the **reads** on the same screen were already routed per row to `2-samples/adhoc-{importId}/`. In the month's store no item matches the ad-hoc `xrayImageId`, so `setItemQualityNote` took its idempotent no-op branch: the UI reported success, nothing was written, and the note vanished on the next load. Third recurrence of the "month-folder walkers forget the ad-hoc store" class.
3. The headline one. `foldDistributionEvents` absorbs every event whose `xrayImageId` is not in the sample-row set it is handed. That is right for a genuine orphan and catastrophic for a row set that was stale or partially read: the assignments those events carry are simply not in the fold — and the fold is what gets written to `distribution.current.json` **and** its fold-checkpoint sidecar. Once written, every machine trusts the cache and the checkpoint is accepted forever, so one bad read of `sample.master.json` became the permanent, silent deletion of assignments from an audit month. The empty-row case was already gated (A6d) and the incremental resume path already refused to advance (`absorbedAbsentRows`); the FULL refold against a *partial* row set was the remaining hole, and it is the one Phase 4's own cache write steers readers onto — that cache carries no checkpoint and no `eventSetId`, so the next reader always takes the full path.

**What changed:**

- **`transientFileErrors.ts` / `casLoop.ts` (the classification points, not the call sites).** New `isLockContentionError`; `isTransientWriteError` now includes it, so `retryTransientWrite` rides the existing backoff ladder. `casLoop`'s `isPermissionLostError` no longer lists it, so it falls through to the retry loop. `NotAllowedError` / `SecurityError` remain terminal. New code **XQ-IO-035** (+ Arabic label `err_io_035_file_locked`) so an exhausted lock reports "in use by another device or window — try again shortly" instead of XQ-IO-032, whose text asserts the opposite ("وليس بسبب تعارض مع مستخدم آخر").
- **`XrayInspectionResults.tsx`.** The quality-note save now resolves its folder with the existing `monthFolderForEntry(row.entry, selectedMonth)` — the same per-row helper `XrayReferrals` and `useApprovalData` already use — instead of passing `selectedMonth` blind.
- **Absent-row persistence guard (`distributionDerivation.ts` → `distributionLog.ts` → `distributionStorage.ts`).** The fold now also reports `absentRowImageIds` (already computed for its own log line; purely additive — `entries` is untouched). `loadOrDeriveDistributionCurrent`'s full refold consults it: on absorption it re-reads `sample.master.json` fresh and, for every absorbed id the master holds and has **not** retired, re-folds against caller-rows ∪ those rows.
