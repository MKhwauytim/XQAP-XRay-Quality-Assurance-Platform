# Edit Log — 2026-08-19

## v100.0 — 2026-08-19 — Add (templates): a customs-declaration phase in the default inspection template, and a multiselect field type to carry it

**Why:** The default inspection template asked the reviewer to judge the scan
(«ضمان جودة النتيجة») without ever asking what the shipment was *declared* to
be, so "the load does not match its declaration" had nowhere to be recorded and
never reached a report. A phase for reading the customs declaration now sits
between the image-quality check and the result judgement, so the reviewer knows
what they should be seeing before they judge what they saw.

Three shapes were rejected on the way:

- **Separate «هل يوجد اختلاف؟» and «نتيجة المطابقة» fields.** Two fields carry
  one judgement and can disagree with each other inside a single submitted
  answer. One verdict field, `هل الوارد مطابق للبيان الجمركي`, replaces both.
- **A commercial cargo vocabulary** (مواد غذائية / مواد صلبة / …). Those are
  tariff families, not X-ray signatures: canned food, sacked rice and frozen
  bulk share a category but nothing an operator can recognise in an image, and
  «مواد صلبة» would absorb most answers while distinguishing nothing. The
  categories are density/homogeneity/shape ones instead — and declared and
  observed deliberately draw from the SAME list, because two vocabularies would
  make the comparison, which is the entire point of the phase, meaningless.
- **`combobox` + free text for the multi-answer fields.** It needed no new
  field type, but a reviewer typing free text where several fixed options apply
  produces exactly the un-countable data this phase exists to replace.

**What changed:**

*Schema.* `TemplateFieldType` gains `"multiselect"`. Its answer is stored as the
selected options joined by `MULTISELECT_SEPARATOR` (`" | "`) in the existing
`FieldAnswer.value` string — NOT as an array. `FieldAnswer.value` is
`string | number | boolean | null` and is read by the report builders, the Power
BI CSV export and the per-item value-history snapshots; widening it to an array
would have to land in all of them at once, whereas a joined string leaves every
existing reader working and stays legible in a report cell. `serializeMultiValue`
is the only writer: it strips `|` out of option text so an option cannot forge a
boundary, and emits options in the template's declared order, so two employees
who pick the same set store a byte-identical string and group together when
counted. `toggleMultiValue` keeps a selection the template no longer offers
rather than silently dropping it.

*Conditions.* `evaluateCondition` now takes the source field, and on a
`multiselect` source reads `equals` as "this option is among those picked"
(`notEquals` as its negation). A plain string comparison against the joined value
would only ever match when exactly one option happened to be selected, so a
dependent field would vanish the moment the reviewer picked a second. An
unanswered multiselect still satisfies neither equality branch, unchanged.

*UI.* `InspectionPanel` renders a multiselect as a wrapping group of
`aria-pressed` toggle buttons — a native `<select multiple>` needs ctrl/cmd-click
to add a second option and drops the rest of the selection on a plain click,
which is the mistake this field exists to prevent. Required-ness counts a
multiselect as answered once one option is picked; the read-only view rejoins it
with an Arabic list separator. The Template Builder offers the new type, edits
its options through the existing options editor, strips `|` from option text as
it is entered, and treats a multiselect source like a dropdown when authoring a
condition against it.

*Default template.* Now three phases: `ضمان جودة الصورة` (unchanged) →
`تحليل البيان الجمركي` (new) → `ضمان جودة النتيجة` (unchanged fields, moved from
phase 2 to phase 3). The new phase asks نوع البيان → طبيعة البضاعة المصرح بها →
طبيعة البضاعة الظاهرة بالأشعة → هل الوارد مطابق للبيان الجمركي →
أسباب عدم المطابقة → ملاحظات. Everything is gated on an image existing (with no
image there is nothing to compare a declaration against), and the reasons field
only on the verdict being «لا», so a matching declaration costs four answers, not
six. `buildDefaultInspectionTemplate` moved out of `TabView.tsx` into its own
module — it is data, not a component, and exporting it from the tab module
breaks react-refresh.

**Migration/rollback:** No migration, and none is possible: field ids are
generated fresh on every `buildDefaultInspectionTemplate` call, so a workspace
whose template already exists on disk keeps its two-phase structure and its
recorded answers keep resolving. **The new phase reaches NEW templates only** —
an existing workspace that wants it adds the fields through the Template Builder.
Answers written before this change are untouched and still parse: no existing
field is a multiselect, and `parseMultiValue` is only consulted for fields typed
as one. Rollback is a straight revert; a `multiselect` answer written in the
meantime survives it as its joined string under a field the older code renders as
whatever type the template then declares.

**Before:** — `src/data/templates/templateRuntime.ts`, equality against a single
stored value:

```ts
function evaluateCondition(
  condition: TemplateFieldCondition,
  value: TemplateAnswerValue | undefined
): boolean {
  ...
  const expected = condition.value;
  if (condition.operator === "equals") return String(value) === String(expected ?? "");
  if (condition.operator === "notEquals") return String(value) !== String(expected ?? "");
  return true;
}
```

**After:** — a multiselect source is a set, so equality is membership:

```ts
function evaluateCondition(
  condition: TemplateFieldCondition,
  value: TemplateAnswerValue | undefined,
  sourceField?: TemplateField
): boolean {
  ...
  const expected = condition.value;

  // On a multiselect source, `equals` asks "is this option among the ones
  // picked?" — comparing against the whole joined string instead would only
  // ever match when the employee happened to pick exactly one option, so a
  // dependent field would vanish the moment they picked a second.
  if (sourceField?.type === "multiselect") {
    const selected = parseMultiValue(value).includes(String(expected ?? "").trim());
    return condition.operator === "notEquals" ? !selected : selected;
  }

  if (condition.operator === "equals") return String(value) === String(expected ?? "");
  if (condition.operator === "notEquals") return String(value) !== String(expected ?? "");
  return true;
}
```
