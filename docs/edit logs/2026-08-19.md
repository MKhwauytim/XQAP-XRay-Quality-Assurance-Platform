## v99.6 — 2026-08-19 — Fix (backup/storage/user-sync): byte-copy and verify every backup file, keep an unreadable identity file from resetting its revision, and add a legacy/mixed workspace fixture

**Why:** The department's biggest workspaces are large, old and on an SMB share — and on exactly those, the app could lose assignment data *and* be unable to take the backup that would have recovered it.

1. **The daily backup failed entirely on a big legacy workspace (STO-2).** `copyAllJsonFiles` moved every file as a decoded JavaScript **string** (`file.text()` → `writable.write(text)`). Past V8's max string length (~536,870,888 UTF-16 code units) that read throws `RangeError: Invalid string length`, and the throw propagated out of the concurrent walk, out of `copyAllJsonFiles`, into `createBackup`'s catch — so **one** oversized legacy `risk.raw.json` / `bi.raw.json` meant the whole workspace could never be backed up again. Real customer data is already at ~85 % of that ceiling (a 573 MB `bi.raw.json` decodes to ~456M code units), which is why `safeWriteJson`'s own write path was made streaming in the first place; the backup walk was the one place still holding a whole file as one string. The text round trip also forced a special case for compressed files, since decoding a gzip member as UTF-8 and re-encoding it is lossy.
2. **No copy was ever verified (STO-5).** Nothing read a copy back. A share that dropped mid-flush, a disk that filled, an antivirus truncation — any of them left a short or damaged file inside a folder whose `backup.manifest.json` listed it as backed up and whose `backup.complete.json` sentinel certified the snapshot. The admin found out at restore time, which is the one moment the backup is supposed to be worth something.
3. **`users.permissions.json` had its revision counter reset by a read blip.** `syncUserManagementToDisk` reads the existing file inside its `casLoop` attempt and did `prevMeta = existing.ok ? … : null` — collapsing *every* failure reason into "there is no file yet". A single transient `NotReadableError` (idle SMB session, antivirus lock) or a revoked grant therefore produced a write with `revision: 1`, `createdAt`/`createdBy` re-stamped to now/this admin, and the whole roster replaced by whatever this machine happened to hold. Measured on the unfixed source: a revision-**42** file with one manager came back as revision **1**, `createdBy: admin`, roster replaced. That is the identity file — users, roles, permissions, Argon2id hashes — and its `revision` + `_writeToken` pair is the *only* lost-update detector every other machine has.
4. **Nothing was ever tested against a legacy or mixed layout.** `workspacePaths.ts` resolves each root numbered-first with a permanent legacy fallback and there is no migration, so field workspaces stay unnumbered (`Population/`, `.system/`, `templates/`) or half-migrated forever — and every storage-level walk had only ever been exercised against a freshly-created numbered tree.

**What changed:**

- **`safeWrite.ts` — new `copyFileBytesVerified`.** Byte-windowed copy (no decode, no `JSON.parse`, no envelope assumption, so it is size- and format-agnostic) that then re-opens the **written copy** and compares its size and a two-accumulator byte digest against the **bytes this call actually read**. Never against a re-stat or re-read of the live source: a source file is allowed to change under a running backup (another machine saving answers, a sync client), and comparing against it would turn that legitimate change into a phantom corruption report. Returns `copied` / `source_missing` / `verify_failed` rather than throwing, and rides `retryTransientWrite` exactly as `copyFileBytes` does.
- **`backupStorage.ts` — the copy walk is now byte-based, verified, and honest about what it holds.** A verification failure is retried once, then recorded as a **named** failure and the walk continues (one bad file must not cost the admin the other hundred); a file that vanished between the listing and the copy is still skipped and now noted; the pre-existing loud failures for a distribution **event segment** (append-only, cannot legitimately vanish) are preserved and extended to an unverifiable segment. `BackupManifest` gains `status: "complete" | "partial"`, `filesFailedVerification` and `filesSkippedMissing`; `BackupHistoryItem` gains `status` and `failedFilesCount`. All three manifest fields are **optional** — a manifest written before this change has none, and `loadBackupHistory` reads it as `complete`, which is truthful because that code aborted the whole backup on any failure.
- **`Archive/index.tsx` + two label keys.** A partial snapshot is announced as an error naming the files that could not be verified (`backup_partial_warning`), never with the success sentence, and is badged in the backup-history list (`backup_partial_badge`).
- **`userSync.ts` — a read failure is no longer an absence.** The CAS attempt now discriminates `readJsonFile`'s reason: `missing` / `invalid_json` still take the fresh-file seed path (nothing usable is on disk, and `readJsonFile` has already tried the `.bak`/`.tmp` ladder), while `read_failed` (transient) and `permission_denied` (terminal) abort the cycle **without writing** — the in-memory roster stays authoritative and the next tick retries. The abort travels through `casLoop`'s result channel rather than as a throw, so it does not burn the ten-attempt retry budget on a condition no retry inside that loop can fix.
- **`workspaceLayoutFixture.ts` (new, test-only).** Builds a `createMemoryDirectory` workspace in `numbered`, `legacy` or `mixed` layout — realistic month folders, the legacy unnumbered `raw/`/`processed/` children, the pre-`2-samples` flat sample master, and large **plain, non-envelope** payloads written through the raw handle (never `safeWriteJson`, which would wrap and possibly compress them). Its own baseline tests pin today's `workspacePaths` behaviour on all three, including "never create a numbered sibling next to an existing legacy root" and "the numbered root wins in a mixed workspace". Descriptive, not prescriptive: no production behaviour changed for it.

**Deliberately not done.** The **restore** walk still reads text (it needs parsed events to merge segments) — out of scope here and covered by its own semantics. A `partial` snapshot is still restorable: `assertBackupComplete` gates on the folder sentinel, and refusing a partial restore outright would take away a real recovery option; the admin now sees the verdict before choosing. Nothing in the sampling draw, the distribution fold, or any report/export builder was touched.

## v99.5 — 2026-08-19 — Fix (storage/pages-ui/distribution): retry SMB lock contention, route ad-hoc quality notes, and never persist a fold that absorbed events

**Why:** Three defects that all end the same way on a large, busy SMB workspace — assignment data quietly disappears, or the recovery the user is offered cannot work.

1. `NoModificationAllowedError` was classified as terminal permission loss. On a shared Windows/SMB folder that name means the entry is **locked by another writer** — another tab, or another machine mid-write — which is a timing condition, not a revoked grant. `casLoop` aborted on the first one and told the user "فقد الوصول إلى مجلد العمل — أعد الاتصال بمساحة العمل", whose only remedy (re-pick the folder) is powerless against someone else's open handle; `isTransientWriteError` likewise refused to retry it, so `safeWriteJson` failed a write that a 20 ms retry would have completed. This is the mirror image of the doctrine this repo already enforces on the read side: "could not read" is not "does not exist", and "could not write right now" is not "the workspace is gone".
2. Quality-note **writes** for an ad-hoc row were routed to the globally-selected month's answer store, while the **reads** on the same screen were already routed per row to `2-samples/adhoc-{importId}/`. In the month's store no item matches the ad-hoc `xrayImageId`, so `setItemQualityNote` took its idempotent no-op branch: the UI reported success, nothing was written, and the note vanished on the next load. Third recurrence of the "month-folder walkers forget the ad-hoc store" class.
3. The headline one. `foldDistributionEvents` absorbs every event whose `xrayImageId` is not in the sample-row set it is handed. That is right for a genuine orphan and catastrophic for a row set that was stale or partially read: the assignments those events carry are simply not in the fold — and the fold is what gets written to `distribution.current.json` **and** its fold-checkpoint sidecar. Once written, every machine trusts the cache and the checkpoint is accepted forever, so one bad read of `sample.master.json` became the permanent, silent deletion of assignments from an audit month. The empty-row case was already gated (A6d) and the incremental resume path already refused to advance (`absorbedAbsentRows`); the FULL refold against a *partial* row set was the remaining hole, and it is the one Phase 4's own cache write steers readers onto — that cache carries no checkpoint and no `eventSetId`, so the next reader always takes the full path.

**What changed:**

- **`transientFileErrors.ts` / `casLoop.ts` (the classification points, not the call sites).** New `isLockContentionError`; `isTransientWriteError` now includes it, so `retryTransientWrite` rides the existing backoff ladder. `casLoop`'s `isPermissionLostError` no longer lists it, so it falls through to the retry loop. `NotAllowedError` / `SecurityError` remain terminal. New code **XQ-IO-035** (+ Arabic label `err_io_035_file_locked`) so an exhausted lock reports "in use by another device or window — try again shortly" instead of XQ-IO-032, whose text asserts the opposite ("وليس بسبب تعارض مع مستخدم آخر").
- **`XrayInspectionResults.tsx`.** The quality-note save now resolves its folder with the existing `monthFolderForEntry(row.entry, selectedMonth)` — the same per-row helper `XrayReferrals` and `useApprovalData` already use — instead of passing `selectedMonth` blind.
- **Absent-row persistence guard (`distributionDerivation.ts` → `distributionLog.ts` → `distributionStorage.ts`).** The fold now also reports `absentRowImageIds` (already computed for its own log line; purely additive — `entries` is untouched). `loadOrDeriveDistributionCurrent`'s full refold consults it: on absorption it re-reads `sample.master.json` fresh and, for every absorbed id the master holds and has **not** retired, re-folds against caller-rows ∪ those rows. If that heals the absorption, the healed result is served and persisted; if the master cannot be read at all, or the absorption survives, the result is served **in memory only** — no cache, no checkpoint sidecar, no session derive memo. When the master agrees the row is gone (a true orphan, or a replacement-retired row a caller filtered out on purpose via `liveSampleRows`), behaviour is byte-identical to before.

**Deliberately not done — the fold's computed result is unchanged.** The guard decides only whether a result may be *persisted*; `foldDistributionEvents` and `deriveCurrentDistribution*` compute exactly what they computed before for a given `(events, sampleRows)`. The heal adds back only rows that are (a) referenced by an absorbed event, (b) present in the master and (c) not replacement-retired — the union, never the master wholesale — precisely so `runPowerBiExport` and the executive report data builder, which pass `liveSampleRows(sample)` on purpose, cannot have retired rows resurrected into their output.

**T-13 (`eventSetId` stamp on Phase 4's refresh) skipped, deliberately.** `useDistributionActions.refreshDistribution` writes its cache with `logRevision` and nothing else, so that cache is always rejected by the next reader. Stamping `eventSetId` there would make a previously-ignored cache authoritative for every existing workspace — a change to cache-validity semantics, at a call site that is *not* the one this guard sits on and that has no absent-row guard of its own. Left for its own reviewed change.
