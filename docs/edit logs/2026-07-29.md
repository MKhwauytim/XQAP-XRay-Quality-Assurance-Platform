## v59.101 — 2026-07-29 — Fix (ci): pin zatca-logo.svg to LF so CI (Linux) matches locally-captured golden snapshots

CI (PR #44) failed again after v59.99/v59.100 landed, this time at the test step (typecheck/lint
now clean): two `toMatchSnapshot()` golden fixtures — `executiveReport.test.ts`'s and
`deck2.test.ts`'s "P3-7 chunking safety" byte-identity pins — mismatched on a single embedded
`data:image/svg+xml` line, specifically `%0D%0A` (CRLF) in the "Expected" (committed) snapshot vs.
`%0A` (LF) in "Received" (CI's actual render).

Root cause: `src/branding/organization.ts` imports `src/branding/zatca-logo.svg` via Vite's `?raw`
loader, embedding the file's literal bytes — including line endings — into every generated report.
`.gitattributes` had no `eol` rule for `*.svg`, so this file's on-checkout line ending followed
each machine's own `core.autocrlf`: the git blob itself has always been LF (`git show HEAD:...`
confirms this), but this Windows dev machine's `core.autocrlf=true` silently checks it out as CRLF.
When the P3-7 golden snapshots were captured on this machine (v59.94-v59.98), the CRLF-converted
SVG got baked into the committed `.snap` files. CI checks out on Linux — no CRLF conversion — so
its render (correctly, per the actual repo content) produces LF, mismatching the CRLF the snapshot
had memorized. This predates v59.99/v59.100; it never surfaced earlier because CI's job aborts at
the first failing step, and typecheck (the v59.99 bug) always failed before the test step could run.

Fix: pinned `*.svg text eol=lf` in `.gitattributes` so every checkout gets LF regardless of local
`core.autocrlf` — deleted and re-checked-out `zatca-logo.svg` locally to force the new rule to
apply (content unchanged, confirmed via `git diff` — encoding only), then re-captured both golden
snapshots against the now-LF-normalized source. Re-ran the full suite with the other session's
unrelated pending username-rename files set aside (`git stash`/`pop`) to test in true isolation:
159/159 files, 1328/1328 tests pass; `typecheck` and `lint:ci` clean.

```ts
let deckBuildQueue: Promise<unknown> = Promise.resolve();

async function withDeckBuildLock<T>(callback: () => Promise<T>): Promise<T> {
  const previous = deckBuildQueue;
  let release!: () => void;
  const gate = new Promise<void>((resolve) => { release = resolve; });
  const next = previous.then(() => gate);
  deckBuildQueue = next;
  await previous.catch(() => undefined);
  try {
    return await callback();
  } finally {
    release();
    if (deckBuildQueue === next) deckBuildQueue = Promise.resolve();
  }
}
```

## v59.94 — 2026-07-29 — Fix (performance): chunk sample/distribution report builders with yieldToMain (P3-7)

Full-app-review finding P3-7: self-contained report/deck HTML builders ran fully synchronous
with no main-thread chunking, unlike the codebase's own `yieldToMain` idiom (previously used
only in Population-processing files: `populationProcessor.ts`, `biDataWorkbook.ts`,
`riskDataWorkbook.ts`). Confirmed builders were `executive/deck2/index.ts`, `executive/index.ts`,
`sampleReport.ts`, `distributionReport.ts`, and `management/managementDeck.ts` — all called
directly from Reports tab onClick handlers. Not urgent (no user-reported freezes; nice-to-have),
so this pass followed the mandatory determinism sequence literally: capture a byte-for-byte
golden snapshot of current output FIRST (`toMatchSnapshot()` added to `sampleReport.test.ts` /
`distributionReport.test.ts`, run and confirmed as the baseline), only THEN add
`await yieldToMain()` breaks, then re-ran the same snapshots and confirmed byte-identical output
(0 snapshot diffs) — proof the change altered only timing, never content.

**Scope — implemented for 2 of 5 builders**: `sampleReport.ts` and `distributionReport.ts` only.
Both are self-contained (~500 lines), have no module-level mutable state, and have clear
per-page/per-slide/per-chunk boundaries to yield at (mirrors the paginated-table chunking
`populationProcessor.ts` already does). **Deferred**, with rationale:
- `executive/deck2/index.ts` — carries genuine module-level mutable state
  (`setActiveStyleChoices` in `slideKit.ts`) with an explicitly documented "no cross-call
  interleaving" invariant; yielding mid-build would introduce a real reentrancy risk (a second
  concurrent build corrupting the first's style-choice reads) that needs a proper lock, out of
  scope for a nice-to-have perf pass.
- `executive/index.ts` (document) and `management/managementDeck.ts` — both drive off the shared
  `buildReportModel` (`executive/model/reportModel.ts`) and, for the document, the sprawling
  `executive/document/` part-module set (~1585 lines across many co-authored files) — a much
  larger, more diffuse surface than the two self-contained builders actually implemented, and
  touching the shared model would also brush up against the deferred deck2's dependency graph.

**Risk handled**: `openSampleReport`/`openSampleDeck`/`openDistributionDocument`/
`openDistributionDeck` all call `window.open()` via `htmlReport.ts`'s `openOrDownload`. Making
the builders `async` (yielding) and only THEN calling `openOrDownload` after the build resolves
would move `window.open()` out of the synchronous click-handler call stack, risking a
transient-activation timeout and a silently blocked popup. Fixed by splitting `openOrDownload`
into `openReportWindow()` (opens the blank tab synchronously) + `writeReportToWindow()` (writes
the built HTML in once ready) — `openOrDownload` itself is now just their composition, unchanged
behavior for every other (untouched) caller. Each of the 4 `openX` functions now: open the window
synchronously first → `await` the chunked build → write the result in.

## v59.76 — 2026-07-29 — Fix (data-table): keyboard path for DataTable's row-click/expand interaction

`DataTable`'s row-select/expand interaction (`onRowClick`) had no keyboard path — the `<tr>` had
`onClick` but no `tabIndex`, no `aria-selected`, and no `onKeyDown`, so mouse-only users could
select/expand a row but keyboard users could not, even though the row's cursor was already styled
as clickable. Confirmed the only 2 real consumers, `XrayReferrals.tsx` (row selects the expanded
referral entry) and `ReferralApproval/HistoryView.tsx` (row expands/collapses history detail), both
genuinely depend on row activation rather than using it decoratively. Fixed at the shared
`DataTable` level so both consumers inherit it: when `onRowClick` is provided, the row now gets
`tabIndex={0}` and `aria-selected` (kept `aria-selected` over `role="button"` since the surrounding
markup is a real `<table>`/`<tr>`/`<td>` structure — `role="button"` would strip that semantics from
screen readers), plus an `onKeyDown` that activates `onRowClick` on Enter or Space
(`preventDefault` on Space to stop page scroll). `XrayReferrals.tsx` already renders a row-select
checkbox inside one column whose `onClick` calls `stopPropagation()` to avoid toggling row
selection on a checkbox click; keyboard activation of that same checkbox (Space) fires a `keydown`
that still bubbles up to the row before the checkbox's own click-based guard applies, so the row's
new `onKeyDown` ignores any keydown whose `e.target !== e.currentTarget` — i.e. any keydown
originating from an interactive child rather than the row itself — so Space on the checkbox toggles
only the checkbox, never also activating `onRowClick`.

**File:** `src/components/DataTable/index.tsx`

**Before:**

**After:**
```tsx
                  <tr
                    className={`dt-tr${isExpanded ? " selected" : ""}${rowClassName ? ` ${rowClassName}` : ""}`}
                    onClick={() => onRowClick?.(row)}
                    {...(onRowClick
                      ? {
                          tabIndex: 0,
                          "aria-selected": isExpanded,
                          onKeyDown: (e: React.KeyboardEvent<HTMLTableRowElement>) => {
                            // Ignore keydowns bubbling up from interactive children (e.g. the
                            // row-select checkbox) — Space there toggles the checkbox, not the row.
                            if (e.target !== e.currentTarget) return;
```

## v59.75 — 2026-07-29 — Security (reporting): second-order DOM XSS in the executive/shared report viewers' TOC-building script

Both `executive/viewer.ts` and `shared/reportChrome.ts` embed an identical inline `VIEWER_JS`
`<script>` that builds the sidebar table-of-contents by reading each page's `data-title`
attribute off the live DOM (`p.dataset.title`) — which the browser HTML-entity-*decodes* back to
the raw title text — and then concatenating that decoded string straight into `a.innerHTML`. Since
`data-title` is written via `esc()` from Excel-derived, attacker-controllable port names
(`partAccountability.ts` → `document/shared.ts`'s `page()`), the innerHTML re-parse silently
undid the escaping: a malicious port name containing markup would execute as a real DOM XSS the
moment a privileged user opened the generated self-contained HTML report. This evaded the
static-string XSS corpus (`xssPayloads.ts`) because that corpus scans the generated HTML source,
not this runtime decode-then-innerHTML path. The safe idiom already existed one file over
(`executive/deck2/index.ts`'s `a.textContent = s.getAttribute('data-section-label')`); applied the
same pattern here: build the TOC entry with `document.createElement`/`textContent` instead of an
`innerHTML` string concat, so injected markup can only ever land as inert text.
