## v59.42 — 2026-07-25 — Fix (executive-deck/deck2): resolve saved style choices by family key so paginated slides survive page-count drift

Opus design-advisor review finding: an admin's saved per-slide variant choice
silently stops applying once a month's port count crosses a pagination
boundary. Paginated slide ids embed a page number (e.g.
`slide-port-population-1`, `slide-port-population-2`, ...); a choice was
always saved and looked up against the exact rendered id. If a later month's
data shifts how many pages a paginated section produces, the same logical
slide renders under a different id and `resolveVariantIndex` — which only
ever did an exact-id lookup — silently falls back to panel 0, discarding the
admin's choice with no error or warning.

Fixed by resolving choices through a normalized "family key" (the slide id
with its trailing `-<digits>` page-number suffix stripped) as a fallback tier
below the exact-id lookup: exact id match first (so per-page-id choices saved
before this fix keep working), then family key (a choice saved without a page
suffix now applies regardless of how many pages the section renders that
month), then the deck-wide default key `"*"`, then 0. `resolveVariantIndex`'s
public signature is unchanged; the new `familyKeyOf()`/`clampChoice()`
helpers are private to `slideKit.ts`.

`deck2/index.ts`'s in-browser `DECK_VARIANT_SCRIPT`'s `persist()` (the
function that reports an admin's live drag-through-the-switcher choice back
to the dev-tool endpoint and the in-app customizer's `postMessage` bridge)
previously reported the exact rendered slide id, which would have re-created
the same bug on the write path even after the read-path fix — the saved
choice would still be keyed to a page id that stops existing next month. It
now mirrors `familyKeyOf()` and reports the family key instead.

While transcribing that mirrored `familyKeyOf()` into the `DECK_VARIANT_SCRIPT`
template literal, caught and fixed a real correctness bug before it shipped:
`slideId.replace(/-\d+$/, '')` inside an untagged template literal is not the
same source text as the equivalent real regex literal in `slideKit.ts` —
inside a template literal (like a plain string), `\d` is not a recognized
escape sequence, so JS's cooked-value semantics silently drop the backslash,
producing `/-d+$/` at runtime (matching literal `d` characters, not digits).
Confirmed via a standalone Node repro before and after. Fixed with `\\d` so
the cooked runtime string is the intended `/-\d+$/`. (This also tripped
`no-useless-escape` in `npm run lint`, which is what surfaced it.)

Added 3 regression tests in `deck2.test.ts` (`-t "family-key"`): a family-key
fallback case (single-page render, choice saved under the bare family key,
panel 1 pre-selected), a backward-compatibility case (an exact per-page-id
choice still wins over a family-key choice for the same page), and a
non-paginated no-op case (`slide-cover`, family key equals the exact id).

## v59.29 — 2026-07-25 — Fix (executive-deck/deck2): stage×port totals row froze at a stale height on cold page loads

Owner report, with screenshots: مجتمع صور الفحص حسب المستوى والمنفذ and its
عيّنة sibling — the two stage×port grid pages — showed a large empty gap
between the last port row and الإجمالي on some of the four stage cards
(specifically the ones with fewer than `STAGE_CARD_TOP_N` (5) ports), i.e. the
totals-row-pinning fix from earlier today (`v2-fill-row` + `DECK_TABLE_FILL_SCRIPT`)
appeared to have regressed.

It had not regressed — reloading the same page in this browser session showed
the bug once, then not on the next reload, which is the signature of a load-order
race, not a logic bug. Root-caused live in the browser, not guessed:

1. `DECK_TABLE_FILL_SCRIPT` runs synchronously once, near the end of `<body>`.
   On a cold load, the embedded Arabic web font (a `data:` URI — no network
   fetch, but still real decode + reflow cost) can still be swapping in when
   that script's first pass measures each card's real rendered height. Rows
   measured against the fallback font are shorter than the same rows once the
   real font settles, and nothing re-measures afterward — the filler cell
   freezes at that stale, too-small height, and الإجمالي floats above the
   card's bottom edge by however many px the font swap added.
2. A first fix attempt — re-run `fillCards()` once `document.fonts.ready`
   resolves — was verified LIVE to be insufficient on its own: a fresh reload
   still showed a 23–67px gap even though `document.fonts.status` already read
   `"loaded"` by the time the callback fired. `document.fonts.ready` resolving
   is not the same event as the browser finishing the reflow the font swap
   triggers — there's a further gap between the two. Manually re-invoking
   `window.__deckFillCards()` immediately after, at the console, always
   corrected it to a 0px gap — confirming `fillCards()` itself was never wrong,
   only its timing.

Fix: stopped trusting any single "the page is ready" signal and instead
re-fire `fillCards()` on three independent, cheap checkpoints — `fonts.ready`
(an early attempt), the window `load` event (images/subresources settled), and
a double `requestAnimationFrame` after `load` (two full paint cycles, to clear
whatever reflow was still pending when `load` fired). Re-running `fillCards()`
when nothing has actually shifted is a no-op — the delta it computes is 0 — so
firing on all three costs nothing when the race doesn't occur.

Verified against genuinely cold loads (dev server stopped and restarted, not a
cached reload): 2 consecutive fresh navigations, both stage×port pages, all 4
stage cards each — 0px gap every time, where the same check had shown
`[0, 0, 0, 0]` on a warm cache but `[1, 23, 1, 67]` on the cold load that
exposed the bug.

## v59.27 — 2026-07-25 — Fix (executive-deck/deck2): pin every الإجمالي totals row flush to its card's bottom edge

Reported from the live deck preview: on the port tables (`نتائج جودة الصور في المنافذ` and every
sibling page built the same way) the الإجمالي row floated directly under the last data row instead
of sitting at the bottom of its card, leaving a large block of dead space beneath it — and, worse,
leaving the land and sea cards' totals rows on visibly different baselines whenever the two had
different port counts.

The file header for `portTable` already *claimed* this was handled ("The gap before الإجمالي is ONE
spacer row sized to the EXACT leftover pixels in the card's budget … the totals row always sits
flush against the bottom of the card, for any port count, in either tier"). No such spacer row
existed anywhere in the module — the described mechanism had been documented but never implemented,
or removed at some point without the comment following it.

Two things were established by measuring the rendered deck rather than reasoning from the row
budget, and both shaped the fix:

1. **The shortfall is not limited to short tables.** The first implementation gated the spacer on
   `rows.length < plan.rowsPerPage` — i.e. only pages whose chunk came up short of the planned row
   count. Measured live, the *longest* table on the quality page (8 rows, exactly the planned count)
   still left 139px unused: `BASE_ROWS_PER_PAGE` is a clipping ceiling derived from the *base* row
   height, while the `compact` tier that page renders in shrinks rows far below it. Gating on row
   count therefore missed the most common case. The spacer is now emitted for every non-empty table
   and simply measures to 0 when a table genuinely does fill its card.
2. **An absolute `card − header − table` subtraction is the wrong measurement.** It silently omits
   every box-model contributor that isn't one of those three rects — the card's own padding, the
   head's `margin-bottom`, border widths — and landed the stage-grid cards 41px off. Replaced with a
   self-correcting delta ("how far is tfoot's bottom from the card's inner bottom edge — add that to
   whatever the filler is already at"), which needs no model of the box, converges in one pass, and
   stays correct when re-run over an already-sized filler.

Verified in the live preview at the deck's design width: all 12 cards across the 6 affected slides
(port population, port sample, stage×port population, stage×port sample, port quality, port
accuracy) measure a 0px gap between the totals row and the card's inner bottom edge, in both row
tiers and both themes. At viewport widths where the table already overflows its card, the delta goes
negative and clamps to 0 — the pre-existing narrow-width clipping is neither fixed nor worsened by
this change.
