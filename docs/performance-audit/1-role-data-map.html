What each role loads, reads, and writes

No backend — every read and write below lands either in the browser (sessionStorage / localStorage) or as JSON files inside the user-picked workspace folder. Role controls what a session can reach; a single feature flag, view-all-entries, decides whether that reach is "my own records" or "every employee's."

Five roles, escalating clearance, read left→right below like a QC step-wedge: guest → employee → supervisor → manager → admin.

03 Where it actually lives

Two layers, never mixed: browser storage for the auth/UX layer, the workspace folder for every business record.

Browser — sessionStorage

xray_auth_session_v1
Login session. Survives reload, clears on tab/browser close, 7-day TTL guard.
xray_global_month_v1
App-wide selected month, resolved against the workspace's actual month folders on change.

Browser — localStorage

xray_custom_labels_v1
Admin label overrides, merged over DEFAULT_LABELS at module init — loads even before login.
xray_last_login_username_v1
Remembered username for the login form only.

In-memory only

userManagement runtime state
Users + tab/feature permissions. Rehydrated from disk every load — never persisted to a browser key itself.
error log ring buffer
Last 50 silent-catch entries, admin-visible in Settings, lost on reload.

Workspace folder — numbered roots

1-population/ … 2-samples/
Raw + processed population per month; sample master, distribution events, per-employee mirrors + answers, per-supervisor decisions.
3-user-data/ … 6-templates/
users.permissions.json · report designs · audit logs, notifications, backups, presets · inspection templates.

04 UNC / network-share cost

The File System Access API never tells the page whether a workspace folder is local or a UNC path — there's no handle.isRemote to check. What the app can control is how many separate round trips each operation makes, and that's exactly what got fixed this week after a production report of the workspace living on a network share.

Why it's structurally slow, not just unlucky: Chromium's own File System Access tracker (issue 40899722) measured 1,000 small file operations at 142s on a Windows network share vs. 3.4s local on macOS — roughly 40× slower. Every JSON file this app touches is exactly that kind of small-file operation, and safeWriteJson turns one logical write into 7 of them (.bak write, .tmp write, .tmp verify-read, live-file commit, live-file verify-read, pre-read, cleanup delete) — a deliberate crash-safety trade-off, not an oversight.

Population/month loadfull monolith on Process; paged worker on Browsegated by role capabilityPhase A + B shipped, Phase C not
createBackup / daily auto-backupevery JSON file in the whole workspace, unbounded by agemanual (admin only by default now) + daily auto-check for manager/admin regardlesspartial — 8-way parallel, scope still unbounded

Net effect: a workspace that's been running long enough to accumulate a lot of distribution.events/*.json files (one per assignment/replacement/reassignment/reopen — potentially 1,000+ in an active month) makes backup the single heaviest whole-workspace operation, and loadAllEmployeeFiles the heaviest thing supervisor/manager/admin trigger just by opening a tab. Both are already parallelized (8-way); neither is bounded in scope. The safe-write tax (item 1) is universal and untouched on purpose — it's what keeps a write from corrupting a file if the network drops mid-save, which matters more on an unreliable share, not less.

This isn't a hypothetical — docs/superpowers/specs/2026-08-03-distribution-performance-and-workflow-design.md (Part 4, §S–§V) was written from an actual "workspace folder is a UNC/network-share path, takes forever" production report, and ~20 commits have shipped against it. Two items remain deliberately deferred: relaxing safeWriteJson's verify cycle, and consolidating one-file-per-event distribution writes — both need their own risk review before touching.

05 Cross-cutting notes

One flag decides "mine" vs. "everyone's." FEATURE_DEFAULTS["view-all-entries"] is false for guest/employee, true for supervisor/manager/admin — every own-vs-all fork in the diagrams above traces back to this single flag.
All writes are staged. Every JSON read/write above routes through safeReadJson/safeWriteJson (temp-write → verify → commit, with a .bak kept). Files with more than one possible writer — users.permissions.json, notifications.json, designs.index.json, *.decisions.json, actions.log.json — add a CAS loop plus a Web Lock on top.
Notifications is two different UIs, not one gated tab. Employee/supervisor get the read-and-accept NotificationBanner in the app shell; manager/admin get the full NotificationManager sidebar tab (post + monitor). Both read the same notifications.json.
Settings' code ceiling is wider than its default grant. Guest is technically inside the tab's allowed-roles list, but the default permission matrix sets guest → none — it only becomes reachable if an admin grants it by hand.
The latest resync leans toward "deny by default, grant explicitly." population, reports, and archive all moved from view-by-default to none-by-default for the roles below admin/manager — guest lost its only default tab entirely, and supervisor's default footprint shrank to just its three employee-workspace sub-tabs. Every ceiling stayed the same; only the starting grant tightened. Read the tab matrix's † marks as "available on request," not "unavailable."
